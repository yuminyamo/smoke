# ログ・ファイル参照 skill の検討

- 検討日: 2026-10-03
- 状態: ログの添付と時刻の扱いは手順書に反映済み(proc-v013 テスト環境の定義、proc-v014 ログ収集と時刻)。ファイル参照は要求の整理まで(実現手段は別スレッドで検討する)
- 関連: 改訂履歴(`procedure/docs/000_overview.md` 23章・24章)、skill への要求(`docs/skill整備要求.md`)

---

## 1. 背景と目的

回帰テストの作成では、既存の DB 参照 skill(このワークスペースには置いていない)を、結果の確認と、操作方法を探索するときのシステム状態の確認に使っている。これと同じ目的で、サーバー上のログと、ファイルシステム上のファイルを参照する skill を加えることを検討した。

検討の発端となった理由は次の3つである。

1. **探索時に DB だけではシステム状態が分からないことがある。** 処理が行われれば DB は変化することが多いが、うまく動作していない場合や、処理しても DB が更新されない場合は、ログや特定のディレクトリのファイルを見ることで状態を把握できることがある。人間が操作するときも、このような確認をよく行う
2. **ログ・ファイルについての KB を蓄積したい。** 回帰テストの作成を通して DB の KB を蓄積しているのと同じく、ログやファイルの KB も蓄積し、後日、回帰テストの作成以外の用途にも使いたい
3. **健全性チェックの問い合わせの回答精度を上げたい。** 健全性チェックでアラートが上がって問い合わせるとき、DB の状態に加えてログやファイルの状況を入力できれば、回答の精度が上がり、解決する可能性が高くなる

## 2. 当初案の評価

当初案は「サーバー上のログ参照 skill」と「任意のファイル参照 skill」を加えるものだった。

**良い点**

- DB への `SELECT` を外部操作から切り出して安全規約で扱っている前例と同じ構造(読み取り専用の観測手段を増やす)であり、手順の思想と一貫している
- 「DB に何も残らない失敗」は実在し、ログやスプールのディレクトリにしか痕跡がない。現行の探索には、人間なら当然行う「ログを見る」が欠けていた
- 作業15(健全性の是正)の問い合わせの入力にログを足せることは、健全性シグナルの解決率に直結する

**問題点**

| 問題 | 内容 |
|---|---|
| 境界が消える | 「任意のファイル参照」は、実現手段が事実上サーバー OS へのシェルアクセスになり、手順が最も警戒している「PMSサーバOSへの操作」との境界が、AIの自制だけに依存する。読み取り専用は実行体の側で強制する必要がある |
| 秘密情報 | ログや設定ファイルには、パスワード・接続文字列・個人情報がそのまま載る。成果物と問い合わせの入力に秘密の値を書かない規約(lint `env_value_leak`)と衝突する |
| 検証手段への浸食 | ログが読めると、探索AIは「ログに ERROR が出ないこと」を判定に使い始める。ログは UI・DB より非決定的で(書式の変更・ローテーション・他プロセスの混入)、回帰テストの判定に使うと不安定なテストの原因になる。テストコードからログを読む実行体も必要になり、範囲が大きく広がる |
| コンテキストの消費 | ログは巨大であり、AIに生のログを検索させると探索のコンテキストと時間を大量に使う |
| 理由2は弱い | 「後日、別用途で使いたい」は現時点では仮説である。KB の構造を先回りで作り込むのは、「網羅的な事前ドキュメント整備を目指さない」という手順の思想と逆行する。KB は理由1・3の実需から自然に貯まる分で始める |

**提案した別のアプローチ**: ログ参照とファイル参照の2本の汎用ツールではなく、許可リスト・時間範囲・出力量の上限を実行体の側で強制する、読み取り専用の「診断スナップショットの収集」1本に寄せる。

## 3. 修正案と、その評価

当初案の評価を受けて、次の修正案が出された。

- **ログ**: 既存の製品のログ収集ツール(機密情報・個人情報をマスクする機能を持つ)を経由し、指定した時間のサーバーのログを集める skill を作る
  1. 回帰テストの skill は、健全性のアラートで問い合わせるときに、この skill で集めたログを問い合わせ skill に渡す。回帰テストを作るAIはログファイルを直接読まない
  2. 問い合わせ skill は、原因と、根拠になったログIDを含めて回答する。ログの解析でコンテキストを消費するおそれがあるため、問い合わせ skill は skill としての呼び出しのほかに、設定に応じて別プロセスで(コマンドで)呼び出せるようにする
  3. 回帰テストの skill は、回答で解決した場合、ログの KB に事象・原因・ログIDを記録する
  - 現時点では需要が分からないので、検証の判定にログは使わない
- **ファイル**: 任意のファイルではなく、結果の確認に必要な、特定のフォルダに出力されるファイルを参照する skill にする。例えばジョブログ収集機能には、保存期間を過ぎたジョブログを DB から CSV にエクスポートする機能があり、その検証にはエクスポートされた CSV を見る必要がある。skill には種別をあらかじめ定義しておき、「13:50〜13:55 に生成されたジョブログファイル」のように種別と作成時間帯を指定して、該当するファイルを返す。実現手段は別スレッドで検討する。コンテキストを消費するおそれがある場合は、コマンドでも呼び出せるようにする

**評価**: ログの側は「回帰テストを作るAIはログを読まず、問い合わせに渡すだけ」と線を引いたことで、当初の懸念(コンテキスト・秘密情報・検証手段への浸食)がほぼ解消した。一方、ファイル参照は性質が違う。CSV エクスポートの確認は**判定そのもの(検証手段)**であり、回帰テストの実行時にテストコードから呼べることが必須になる。「skill を1本足す」ではなく「検証手段を1つ増やす」変更として扱う必要がある。

## 4. 詰めた点と結論

### 4.1 ログ

| 論点 | 結論 |
|---|---|
| ステップの時刻 | 探索記録の各ステップに開始・終了時刻(`started_at`・`ended_at`)を、健全性シグナルに観測時刻(`observed_at`)を記録する。現行の記録は日付(`explored_at`)だけで、ログの時間範囲を決められなかったため |
| 時刻のずれ | 時刻合わせを行っても、操作の記録とサーバーのログの時刻は数秒ずれうる。ログを集める時間範囲の前後に **10秒** を足す。値は手順書に直書きせず `vocab.default.log_window_margin_sec` に置く |
| 時間範囲の終わり | ステップの終了時刻ではなく、**健全性シグナルを観測した時刻**とする。非同期処理は操作のあとにサーバー側で失敗することが多く、原因のログはステップの終了より後に出るため。範囲は「自データを作成・操作した最初のステップの `started_at` − 10秒」から「`observed_at` + 10秒」 |
| ログID | **PMS がログメッセージの種別ごとにあらかじめ割り当てた固定のID**(例: ジョブログの収集が失敗したときのメッセージは毎回同じID)。回帰テストの作成で採番するIDではない。環境・版をまたいで使える安定したキーになる |
| KB | 新カテゴリ **T12 ログID知見(`kb/log-ids/`)**。ログIDを主キーにし、1つのIDに複数の事象・原因を並べる(同じIDでも原因は1つとは限らない)。マニュアル・仕様書に原因と対策が載っているログもあるが、代表的な一例にとどまり情報量が少ないため、実測から蓄積する価値がある。文書の所在は T11 にポインタとして置く |
| ログIDの一覧 | ログ収集の実行体に「範囲内に出現したログIDと件数の一覧だけ」を返すモードを持たせる。本文を含まないので、秘密情報もコンテキストの心配もない。これにより、(1) 作業15の自己診断でログIDから KB T12 を引ける(過去に解決した事象なら問い合わせ0回で解消できる。理由2の KB の再利用が最初に効く場面)、(2) 回答が挙げたログIDが実際に出現しているかを機械的に確かめられる(存在しないIDを KB に入れない) |
| KB の出所 | `OBS`(回答に従って操作し、解消を観測した)。ただし原因は問い合わせの回答に由来するため、原因の確度は `中` とし、問い合わせの記録へのリンクを付ける |
| KB に記録する条件 | 解消したとき。操作の変更で解消した `resolved` と、環境の変更で解消した `env_changed` の両方 |
| 位置づけ | ログ収集 skill は**外部操作 skill として扱う**(KB T05 への登録・禁止操作リストとの照合が既存の仕組みに乗る) |
| ないとき | ログ収集 skill がなくても作業15は止めない。ログなしで問い合わせ、報告書に書く。外部操作需要リストには記録しない(ログは問い合わせの精度を上げる補助であり、なくても進められる) |
| 判定に使わない | ステップ1では、ログを判定(期待結果・検証手段・待機条件)に使わない |
| 問い合わせ skill の呼び出し | 「設定に応じて別プロセス」ではなく、**本体は常に CLI とし、skill は CLI を呼ぶ薄い入口にする**(1実装・2入口)。手順はもともと問い合わせ skill に CLI の同梱を求めており、設定による切り替えは分岐を増やすだけで得るものがない。CLI にしておけば、回帰テストからも、理由3の健全性チェックでの人間の問い合わせからも同じものを使える |

### 4.2 時刻合わせ

| 論点 | 結論 |
|---|---|
| 必要性 | ログの時間範囲を正しく取るため、ゴールデンイメージの復元のあとに、AI実行マシン・サーバー・複合機などの機器の時刻を合わせる。VM のチェックポイントから戻した直後は、VM の時計がチェックポイントを作った時刻のままのこともある |
| NTP ではなく都度合わせる | 複合機や関連サーバーは共有であり、NTP を安定して設定しておくことが難しい。毎回 hook で合わせる方が確実 |
| どこで行うか | 開始前シナリオ(`config/pre-stage-scenarios.json`)の `hooks.work10` と `hooks.work20` の両方に、復元エントリとして置く。ただし開始前シナリオは「回帰テストになったシナリオ」しか実行できず、時刻合わせは回帰テストではないため、**エントリの種類に「外部操作」を加えた**(`op` と `run`。KB T05 に登録した外部操作の実行体を実行する)。時刻合わせを Playwright のテストとしてコード化する案は、回帰テストセットに機能と関係のないテストが混ざり、一括実行のたびに共有機器の時計を触ることになるため採らなかった |
| 包括原則4 | 両方の hook の復元エントリの `restores` に書けば、その対象は復元範囲に入り、包括原則4に当たらない(定義どおり) |
| 包括原則3 | 包括原則4が外れても、共有の機器の時計を変えることは包括原則3(テスト環境の外に影響が及ぶおそれ)に当たる可能性があった。原因は「テスト環境」が定義されていなかったことにある。**テスト環境を「環境情報に人間の回答で接続先が登録された対象」と定義した**(proc-v013。テスト環境の対象を経由して外に作用する操作、例えばテスト環境のメールサーバからの外部宛メール送信は、引き続き包括原則3に当たる) |
| 合わせる先 | 各実行マシンの時計ではなく、**共通の時刻源1つ**に合わせる。共有の機器を、複数の実行が別々の時計に合わせ合うのを防ぐため |
| 記録 | 実行体は合わせる前と後のずれを JSON で返し、開始前シナリオの記録(`pre-stage-log.jsonl`)の `output` に残す。10秒の幅が足りているかを後から確かめられる |

### 4.3 ファイル参照

| 論点 | 結論 |
|---|---|
| 範囲 | 任意のファイルではなく、**あらかじめ定義した種別のファイルを、作成時間帯を指定して取得する**(例: 13:50〜13:55 に生成されたジョブログの CSV)。種別の定義は skill 側に人間が持つ |
| 位置づけ | 結果の確認(判定)に使う。したがって**回帰テストの実行時にテストコードから CLI で呼べることが必須**(外部操作 skill の条件1そのもの。「設定に応じて」ではない) |
| 実現手段 | 別スレッドで検討する。その際に持ち込む要求は `docs/skill整備要求.md` の「ファイル参照 skill」に整理した |
| 手順書 | **まだ変更していない。** 検証手段の語彙・非決定値カタログ・作業20の規約に手を入れる変更になるため、実現手段の検討と合わせて行う(下の「残る課題」) |

## 6. 反映していないもの・残る課題

- **ファイル参照の手順への取り込み**(別スレッドで実現手段を決めてから)。少なくとも次を決める必要がある
  - 検証手段の語彙(`vocab.verification` に「ファイル」を加えるか、「DB」に準ずる扱いとするか)と、原則 `両方` との関係
  - 自データの特定: 時間範囲は候補ファイルの絞り込みにだけ使い、判定はファイルの中の自データ(一意化した識別子)の行で行う。保存期間切れのエクスポートには他のデータの行も含まれ、並列実行・再実行では同じ時間範囲に別のエクスポートが混ざるため
  - 時刻の基準: 作成時間帯はサーバーの時刻で指定することになる。時刻合わせのずれと余裕幅の扱い
  - 非同期: エクスポートはすぐには出てこない。skill は「今あるものを1回返す」だけにし、待つのはテスト側の `waitUntil`(00 ■非同期完了の待機)に任せる
  - 作業02(非決定値カタログ)の観測対象にファイルの中身(出力時刻・ファイル名の連番など)を加える
  - 作業20と付録F(Playwright 規約)に、ファイル参照のラッパ(`tests/external/`)の規約を加える
  - 出力先が VM の外(共有のファイルサーバーなど)にある場合、ファイルが溜まり続ける。消す操作が要るなら、テスト環境・復元範囲として扱えるかを決める
  - 例のジョブログのエクスポートでは、ファイルを読むことより「保存期間切れのデータ」という前提状態を作ることの方が難所になりうる(保存期間の設定を変えるのか、日時を操作するのか。状態需要リスト・禁止操作の論点)
- **時刻合わせ skill と、ログ収集 skill・問い合わせ skill の拡張は未整備。** 整備までの間、時刻のずれは 10秒の幅で吸収し、ログ収集 skill がなければログなしで問い合わせる(手順はどちらの状態でも動く)
- **ステップの時刻の lint は、健全性シグナルのあるステップだけを検査する**(ログの時間範囲に要るのはそこだけのため)。全ステップの `started_at`・`ended_at` は §10 の DoD で求める
- **回答が挙げたログIDの確認と KB T12 への記録は、まだ lint で検査していない。** 数フロー回して記録の漏れが見られたら、検査を加える
- **理由3(回帰テスト以外の健全性チェックでの問い合わせ)は、手順書の範囲外。** 問い合わせ skill とログ収集 skill を CLI として整備すれば、人間や別の仕組みからも同じものを呼べる(`docs/skill整備要求.md`)
- 探索中に DB だけでは状態が分からない場面(理由1)で、ログを探索AIに読ませることはしていない。ログIDの一覧であれば探索中に見ても問題は小さいが、需要が見えてから検討する
