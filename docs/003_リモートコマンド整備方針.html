リモートコマンド整備方針

回帰テストのために、別のマシン(Hyper-V ホスト・PMS サーバー・印刷クライアントなど)でコマンドを実行する仕組みの整備方針です。新しいリモートコマンドを足すときは、この方針に揃えます。

第1部が方針(規範)、第2部が初心者向けの解説です。PowerShell のリモート処理や JEA を知らない方は、第2部から読んでください。AI は第1部だけを読みます。

第1部 整備方針

規範です。リモートコマンドを整備・拡張するときは、この部に従います。実装で詳細が変わったら、実装と同時にこの部を直します。

1. 目的と位置づけ

1.1 用途

リモートコマンドは、AI 実行環境から、テスト環境を構成する別のマシンでコマンドを実行するための仕組みである。用途は次の4つに分ける。

用途例ロールの重さ
環境情報の把握VM・チェックポイントの状態、サーバーの設定値の確認Read
テスト結果の把握ログ収集(SK-LOG)、ファイル参照(SK-FILE)、証跡の取得Read
テストの操作の一環で必要な外部コマンド印刷指示Change
テスト環境のセットアップゴールデンイメージの復元、時刻合わせ(SK-CLOCK)Change

1.2 JEA の位置づけ

JEA は、AI とテストコードが呼べる操作を、定義した関数に限るための「操作の枠」である。セキュリティの境界ではない。配置のために各マシンの管理者の資格情報が存在し、それを使えば JEA を通らずに何でもできるためである。テスト環境は検証用であり、この前提で管理を緩めてよい。ただし次の2点は守る。

  • skill とテストコードは、配置用(管理者)の資格情報を使わない。JEA のエンドポイント以外へ接続しない
  • 関数の引数を絞る原則(3章)を守る。JEA の枠が意味を持つのは、引数が絞られているときだけである

1.3 前提

  • AI 実行環境・Hyper-V ホスト・PMS サーバーVM・印刷クライアントPCは、それぞれ別のマシンとして設計する。同じマシンになる場合も、クライアント設定で接続先を同じにする(localhost など)だけで動くようにする
  • 対象のマシンはすべて Windows。リモート処理は Windows PowerShell 5.1 で動くこと(PowerShell 7 でも動いてよい)
  • ワークグループ(ドメイン非参加)を前提にする

2. 構成

要素規則
S-1 エンドポイント実行場所(マシン)ごとに1つ。名前はどのマシンでも PmsRemote。マシンごとの違いは、登録するロールで表す。機能ごとにエンドポイントを分けない
S-2 モジュール1つのパッケージ PmsRemote を全マシンに同じ版で置く。中身は機能(実行場所)ごとのファイルに分ける(Common.ps1・HyperV.ps1・Server.ps1・Client.ps1)。版はパッケージで1つ(PmsRemote.psd1 の ModuleVersion)。見せる関数はロールで決まるので、使わない関数が置かれていてもよい
S-3 ロールマシン × 重さで分ける。名前は <マシン種別><重さ>(HyperVRead・HyperVChange・ServerRead・ServerChange・ClientRead・ClientChange)。Read と Change の関数を同じロールに入れない
S-4 Read と ChangeRead = テスト対象(製品・データ・設定・機器・時計)の状態を変えない。作業用の一時ファイル(収集物など)の作成・削除は Read に含めてよい。Change = それ以外
S-5 共通の関数Get-PmsRemoteInfo(版・登録済みのロール・マシン名)、Read-PmsRemoteArtifact(成果物を分割して返す)、Remove-PmsRemoteArtifact(成果物を消す)は、すべてのロールに入れる
S-6 接続許可グループ各マシンのローカルグループ PmsRemoteRead(→ そのマシンの Read ロール)と PmsRemoteChange(→ Change ロール)。当面は AI 実行環境のアカウントを両方に入れてよい。分けてあるのは、後でグループの変更だけで絞れるようにするため
S-7 実行アカウント仮想アカウント。権限はエンドポイント単位で、登録したロールが必要とする権限の和にする(Hyper-V ロール → Hyper-V Administrators、Server・Client ロール → ローカル Administrators)。ロールを分けても実行時の権限は分かれない(S-3 の分離は「呼べる操作」の区別である)
S-8 排他同時に走ると壊れる Change の関数は、そのマシンのロック(state\<名前>.lock)を取り、取れなければ LOCKED を返す。マシンをまたいだ排他はしない(例: 復元中に PMS VM でログ収集が走ると、収集は途中で失敗する。それでよい)
S-9 記録エンドポイントの操作記録(トランスクリプト)を %ProgramData%\PmsRemote\Transcripts に残す。Change の関数は state\operations.log に開始・終了を1行ずつ残す。PMS VM の記録は復元で消える(許容する)

3. 関数の原則(防御の要)

JEA で見せた関数の中身は、制限なしに(管理者として)動く。何ができるかは、関数が受け取る引数で決まる。

規則内容
F-1 受け取ってよい引数列挙値(ValidateSet)、時刻(ISO 8601 の時差付き。ValidatePattern)、件数・番号(ValidateRange)、識別子(サーバーが採番したもの、またはクライアントが採番し ^[A-Za-z0-9_\-]{1,64}$ で検証したもの)
F-2 受け取ってはいけない引数パス・ファイル名・コマンド・スクリプト・正規表現・URL・接続文字列・任意の文字列。識別子からパスを組み立てるときは、固定のフォルダの直下に限る(F-1 のパターンにより .. や区切り文字は入らない)
F-3 対象の固定操作の対象(VM名・ツールのパス・引数の並び・出力先・マスクの指定など)は、リモート側の設定 %ProgramData%\PmsRemote\config.psd1 の機能ごとのセクションで固定する。クライアントからは変えられない
F-4 設定の原本リモート側の設定の原本は、リポジトリの remote/targets/<接続先名>/config.psd1 に置き、配置(5章)で送り込む。実行時に AI やクライアントから変える経路はない。原本の書き換えは、人間のレビューと skill の禁止事項で抑える
F-5 戻り値1つのオブジェクトを返す。少なくとも Success・ErrorCode・Message を持つ。想定内の失敗は例外にせず、Success=$false で返す
F-6 エラーの区分ErrorCode は英大文字とアンダースコア(例 TOOL_FAILED)。Message は "区分: 内容" の形にする。秘密の値を含めない
F-7 ファイルの受け渡しファイルの中身を戻り値に入れない。成果物(zip)として state\artifacts\<成果物ID>.zip に置き、成果物IDを返す。クライアントは Read-PmsRemoteArtifact -Id -Index で 4MB ずつ受け取り、Remove-PmsRemoteArtifact で消す。受け取られずに残った成果物は、保持時間(既定24時間)を過ぎたら次の作成時に消す。上限サイズは機能ごとの設定で決める
F-8 上限時間のかかる処理は、設定で上限時間を持ち、超えたら打ち切って区分付きで返す(例 TOOL_TIMEOUT)。時間範囲・件数の上限も設定で持つ
F-9 製品ツールの扱い製品のツールを呼ぶ関数では、ツールの正常終了とみなす終了コード(SuccessExitCodes)を設定で持つ。ツールの標準出力・標準エラーは成果物に入れず、リモート側の作業フォルダに残す(秘密の値を含むおそれがあるため)
F-10 命名関数名は <承認済みの動詞>-Pms<名詞>(例 Invoke-PmsLogCollect・Restore-PmsGoldenImage)

4. 通信と資格情報

規則内容
C-1 通信方式既定は HTTP(5985)+ NTLM。AI 実行環境の WinRM クライアント設定 TrustedHosts に、接続先を登録する(管理者で1回)。通信の中身は NTLM のセッションで暗号化される。HTTPS(5986)はクライアント設定で選べるようにしておくが、既定にしない
C-2 使わない方式PowerShell Direct(-VMName)は使わない。Hyper-V 上の VM にしか使えず、環境によって使えるかどうかが変わるため
C-3 資格情報参照名で引く。保存先は %APPDATA%\PmsRemote\cred\<参照名>.xml(Export-Clixml。DPAPI により、保存したユーザーと PC でしか復号できない)。保存は CLI の cred-set <参照名> で行う。参照名を指定しない接続先は、ログオン中のユーザーで接続する
C-4 通常用と配置用接続先ごとに、通常用(JEA の接続許可グループのメンバー)と配置用(そのマシンの管理者)の参照名を分ける。配置用を使うのは CLI の deploy と check-target だけである
C-5 接続先の一度きりの前提各接続先で、(1) WinRM が有効(Windows Server の既定)で、遅延なしの自動開始、(2) ファイアウォールで AI 実行環境から 5985 に接続できる、(3) 配置用の管理者アカウントがあり、パスワードが無期限、(4) ビルトインの Administrator 以外を使うなら LocalAccountTokenFilterPolicy=1(ローカルアカウントでの遠隔管理を許す)。PMS VM ではこれをゴールデンイメージに一度だけ入れる。check-target で確かめられる

5. 配置(共通インストーラ)

5.1 インストーラ remote/Install-PmsRemote.ps1

規則内容
D-1 共通全マシン共通の1本。-Role で登録するロールを選ぶ(例 -Role ServerRead,ServerChange)。新しい機能はロールを足すだけで、インストーラを機能ごとに作らない
D-2 処理の順序モジュール配置 → 設定作成 → グループ作成と ACL 付与 → (HTTPS を選んだときだけ)リスナー作成 → エンドポイント登録
D-3 冪等再実行で同じ状態になる。(1) 既存の設定は -Force なしでは上書きしない(差があれば警告する)。(2) 証明書は、同じ名前のものがあれば再利用し、毎回作らない。(3) エンドポイントは、構成(.pssc・ロール・版)が変わったときだけ登録し直す(登録し直すと WinRM が再起動するため)。(4) 版と構成が同じなら何もしない
D-4 機能ごとの準備ロールに固有の確認・準備(例 HyperV: 対象VMと同名チェックポイントがちょうど1つあること)は、機能のファイルに準備用の関数(Initialize-Pms<機能>)として置き、インストーラはそれを呼ぶだけにする
D-5 2通りの実行(a) 対象のマシンで管理者として直接実行する。(b) CLI の deploy が配置用の資格情報で管理者セッションを開き、モジュール・インストーラ・設定の原本を送り込んで実行する。中身は同じ
D-6 出力CLI と同じ約束事(6.2)で、最後の1行に JSON(実施した処理・版・登録したロール)を出す

5.2 ゴールデンイメージに焼き込まない

PMS VM のゴールデンイメージには、エンドポイントもモジュールも入れない。入れるのは C-5 の一度きりの前提だけである。エンドポイントは、復元のたびに自動で配置する(5.3)。モジュールを更新しても、チェックポイントを取り直す必要はない。

版が安定したら、配置済みの状態でチェックポイントを取り直してもよい。取り直すと、復元後の配置が「版が同じなので何もしない」になり、復元が数十秒速くなる。任意の最適化であり、必須ではない。取り直す場合は、復元 → 配置 → info で確認 → チェックポイント、の順で行う(作業中のデータを混ぜないため)。

5.3 復元後の配置

クライアント設定で restoredBy を持つ接続先は、CLI の restore が次の順で処理する。-SkipReadiness(回帰テストの一括実行)のときも配置は行う。

  1. hyperv-host の Restore-PmsGoldenImage(停止 → チェックポイント適用 → 起動 → ハートビート)
  2. 復元した接続先の WinRM が応答するまで待つ(上限は設定)
  3. その接続先に deploy(版と構成が同じなら何もしない)
  4. 起動確認(Web UI へのログイン。従来どおりテストコード側の起動確認テスト)
  5. 復元記録(マーカー)を追記

配置(2・3)に失敗しても、復元は成功として扱う(警告)。結果は出力の deploy(接続先ごとの status: deployed / skipped / failed と error_code)に残し、終了コードは変えない。その接続先のリモートコマンドは、配置されるまで ENDPOINT_NOT_FOUND や VERSION_MISMATCH で失敗する(ログ収集のように補助的な用途は、それでも作業を止めない)。

restoredBy は最初から書いておく(書き忘れて窓口が配置されないまま運用が続くのを防ぐため)。その接続先の一度きりの前提(C-5)が整うまでは、復元のたびに WinRM の応答を restore.winrmTimeoutSec(既定 30 秒)だけ待ってから、配置の警告が出る。前提には、WinRM を遅延なしの自動開始にすることを含める(遅延開始のままだと、準備が整っていても復元直後の待ち時間内に応答しないことがある)。

復元しない接続先(Hyper-V ホスト・印刷クライアント)は、人間が deploy を実行する。

5.4 版

  • 版は メジャー.マイナー.パッチ。パッチ = 関数の中身の修正。マイナー = 関数・ロール・設定キーの追加(後方互換)。メジャー = 引数・戻り値・設定キーの互換を壊す変更
  • CLI は、毎回の呼び出しの最初に Get-PmsRemoteInfo で版を確かめる。メジャーが一致し、かつ expectedVersion 以上なら続ける。そうでなければ VERSION_MISMATCH(終了コード2)で止め、deploy を促す
  • 関数・ロール・設定キーを足したら、マイナー版を上げ、expectedVersion も上げる

6. CLI と skill

6.1 構成

規則内容
W-1 CLI 本体tools/remote/pms-remote.ps1。接続・資格情報・版の確認・成果物の分割受け取り・出力の形式・終了コードの対応づけを一手に持つ。JEA を直接呼んでよいのはこれだけ
W-2 呼び方pms-remote.ps1 <サブコマンド> [-Target <接続先名>] [引数]。サブコマンドは小文字とハイフン(info・check-target・deploy・cred-set・restore・logs-collect・logs-ids など)。既定の接続先はサブコマンドごとに決めてよい(例 logs-collect は pms-vm)
W-3 skill の実行体外部操作 skill には実行体を同梱する。実行体は CLI 本体を固定のサブコマンドで呼ぶだけの薄い入口にする(例 collect-server-logs/scripts/collect-server-logs.ps1 → pms-remote.ps1 logs-collect)。引数と出力は入口でそのまま通す
W-4 テストコードPlaywright(Node)からは、tests/external/remote.ts のヘルパー経由で CLI 本体を子プロセスとして呼ぶ(execFileSync('powershell.exe', ['-NoProfile','-ExecutionPolicy','Bypass','-File', ...]))。テストコードから JEA を直接呼ばない
W-5 実行場所リポジトリのルートで実行する(クライアント設定を上位へ探索する。環境変数 PMS_REMOTE_CONFIG で上書きできる)

6.2 出力と終了コード(すべてのサブコマンド共通)

  • 標準出力の最後の1行に JSON を出す。キーは snake_case。非ASCII 文字は \uXXXX にエスケープする(呼び出し側のコードページに依存しないため)。進捗は標準エラーに出す
  • 共通のキー: success・command・target・error_code・message・started_at・completed_at・duration_sec。機能ごとのキーはこれに足す
終了コード意味例
0成功—
1実行の失敗(1回だけ再実行してよい)CONNECT_FAILED TOOL_FAILED TOOL_TIMEOUT TRANSFER_FAILED
2設定・資格情報・引数・実行環境の誤り(再実行しない)CONFIG_INVALID CREDENTIAL_INVALID INVALID_ARGUMENT VERSION_MISMATCH ROLE_NOT_AVAILABLE
3実行中(ロックが取れない)LOCKED
4成功したが、人間の確認が要る復元後、起動確認テストがまだない

区分を終了コードに対応づける表は CLI 本体が持つ。機能ごとに新しい区分を足したら、この表に足す(足さない区分は 1 になる)。

6.3 skill

  • リモートコマンドを AI が使う場合は、外部操作 skill として整備する(手順書 00 ■外部操作。KB T05 に登録してから使う)。.kiro/skills/ と .github/skills/ の両方に置く
  • SKILL.md には、いつ使うか(使わない場面を含む)、実行方法、出力の読み方(読むのは最後の1行の JSON だけ)、終了コードごとの対応、確立時の確認(info)、禁止事項を書く
  • 禁止事項には、少なくとも次を入れる: JEA・Invoke-Command・製品のツールを直接実行しない / 配置用の資格情報・deploy を使わない / remote/・tools/remote/・クライアント設定を書き換えない / 資格情報を探さない・書き出さない / 失敗を回避するために別の手段を編み出さない

第2部 初心者向けの解説

PowerShell のリモート処理や JEA を初めて知る人のための解説です。決まりごとは第1部にあり、この部は第1部を理解するための補助です。

1. この仕組みが解決すること

回帰テストを作る AI やテストコードは、AI 実行環境という1台の PC で動いています。ところが、テストに必要な操作の中には、別のマシンでしかできないものがあります。

  • PMS サーバーの中でしか動かない、製品のログ収集ツールを動かしたい
  • Hyper-V ホストで、PMS サーバーの VM をゴールデンイメージに戻したい
  • 将来は、印刷クライアントの PC から印刷を指示したい

このとき「別のマシンにログインして何でもできる」状態にすると、AI が誤って危険な操作をしてしまうおそれがあります。そこで、決めた操作だけを、決めた形でしか呼べない窓口を各マシンに作ります。その窓口を作る道具が、PowerShell のリモート処理と JEA です。

2. PowerShell リモート処理の基本

Windows には、ネットワーク越しに別のマシンで PowerShell のコマンドを実行する仕組みが標準で入っています。これを PowerShell リモート処理と呼びます。

  • WinRM(Windows Remote Management)は、要求を受け付ける Windows のサービスです。Windows Server では最初から動いていて、ポート 5985(HTTP)で待ち受けます
  • 手元からは Invoke-Command で「どのマシンで」「何を」実行するかを指定します。結果はデータ(オブジェクト)として戻ってきます
  • 接続するときは、相手のマシンのアカウントで認証します。ドメインに参加していない環境では NTLM という方式で認証し、通信の中身も暗号化されます。ただし、手元の PC に「このマシンには NTLM で接続してよい」と登録しておく必要があります(TrustedHosts)

3. JEA:決めた操作だけを呼べる窓口

3.1 素のリモート処理の問題

普通のリモート処理は、管理者として接続するとそのマシンで何でもできます。ファイルの削除も、サービスの停止も可能です。AI に管理者の資格情報を渡すと、手順を誤ったときに環境を壊すおそれがあります。

JEA(Just Enough Administration、「必要十分な管理」)は、この問題を解く Windows 標準の仕組みです。接続した人にはあらかじめ決めた関数しか見えず、その関数の中身だけが管理者の権限で動きます。

3.2 JEA の部品(役所の窓口にたとえると)

部品ファイル役割
エンドポイント(セッション構成).pssc窓口そのもの。名前(PmsRemote)、誰がどのロールを使えるか、どのアカウントで実行するか、操作記録を残す場所を決める。接続するときは名前で指定する(-ConfigurationName PmsRemote)
ロール(ロール機能).psrc手続きの一覧。見せる関数の名前を列挙する。この方針では、マシンごとに「読み取り(Read)」と「変更(Change)」の2つに分ける
モジュール.psm1 など関数の中身。この方針では全マシン共通の PmsRemote
仮想アカウント—接続のたびに自動で作られる一時的なアカウント。関数はこのアカウントの権限(管理者など)で動く。接続した人に管理者の資格情報を渡さずに済む
接続許可グループ—そのマシンのローカルグループ。メンバーだけが窓口に接続でき、グループごとに使えるロールが決まる

接続した人が使えるのは、窓口のメニューにある関数を「値をそのまま書いて」呼ぶことだけです(変数やスクリプトの構文は使えません)。CLI が関数を呼ぶときに値を文字列に埋め込んでいるのは、このためです。

4. なぜ「引数の設計」が防御の要なのか

JEA の関数の中身は、制限なしに管理者の権限で動きます。そのため、関数が何を受け取るかで、できることが決まります。

第1部の 3章(F-1・F-2)が「列挙値・時刻・件数・識別子だけを受け取り、パスやコマンドは受け取らない」と決めているのは、このためです。

5. この方針での全体像

モジュールは全マシン共通

関数の中身は1つのパッケージ PmsRemote にまとめ、全マシンに同じ版を置きます。どの関数が見えるかは、そのマシンに登録したロールで決まります。版が1つなので、「どのマシンが古いか」をすぐ確かめられます。

Read と Change を分ける

状態を変えない操作(Read)と変える操作(Change)を別のロールにします。今は同じアカウントで両方使いますが、後で「この利用者には読み取りだけ」と絞りたくなったときに、グループの変更だけで済みます。

呼ぶのは CLI 本体だけ

skill もテストコードも、JEA を直接呼ばずに pms-remote.ps1 を呼びます。接続の仕方・版の確認・出力の形式が1か所にまとまり、新しいコマンドを足しても使い方が揃います。

6. 1回のログ収集の流れ

ログのファイル(数十MB)は、関数の戻り値に直接入れずに「成果物」として一度サーバーに置き、4MB ずつ取りに行きます。これは第1部の F-7 の決まりで、ファイル参照や証跡の取得など、ファイルを扱う今後のコマンドでも同じ仕組みを使います。

7. 復元のたびに窓口を配置する仕組み

PMS サーバーVMは、作業のたびにゴールデンイメージ(チェックポイント)へ戻されます。戻すと、VM の中に後から入れたものはすべて消えます。窓口(エンドポイントとモジュール)も同じです。

窓口をゴールデンイメージに入れてしまう(焼き込む)方法もありますが、モジュールを直すたびにチェックポイントを取り直す手間がかかります。そこで復元のたびに、自動で窓口を配置し直す方式にしました。

配置には、そのマシンの管理者の資格情報を使います(JEA の窓口を作る作業そのものは、窓口の外で行うしかないため)。この資格情報は配置のときだけ使い、AI の skill からは使いません。第1部の 1.2 で「JEA はセキュリティの境界ではなく、AI の操作の枠」としているのは、この管理者の資格情報が存在するためです。

8. よくある質問

なぜ HTTPS ではなく HTTP なのですか?

HTTP でも、NTLM で接続すると通信の中身は暗号化されます。HTTPS にすると、マシンごとに証明書を作り、手元の PC に信頼させ、期限や名前を管理する手間が増えます。検証環境は隔離されたネットワークにあり、その手間に見合う利点が小さいため、HTTP を既定にしました。必要になれば設定で HTTPS に切り替えられます。

PowerShell Direct を使わないのはなぜですか?

PowerShell Direct は、Hyper-V ホストからその上の VM にネットワークなしで入れる便利な機能ですが、Hyper-V 上の VM にしか使えません。PMS サーバーが物理マシンや別の仮想基盤に変わると使えなくなるため、どこでも使えるネットワーク経由のリモート処理に揃えました。

ロールを Read と Change に分けると、実行する権限も分かれますか?

分かれません。関数を実行するアカウント(仮想アカウント)の権限は、窓口(エンドポイント)ごとに決まります。ロールで分かれるのは「誰がどの関数を呼べるか」です。今は同じアカウントで両方を使うので実質的な違いはありませんが、後で読み取りだけに絞りたくなったときに、グループの変更だけで済みます。

AI 実行環境と Hyper-V ホストが同じ PC でも動きますか?

動きます。クライアント設定で接続先を localhost にするだけです。別々のマシンになっても、接続先の名前を変えるだけで済むように設計しています。

新しいリモートコマンドを足したいときは?

第1部の 9章の手順に従います。関数の引数を「列挙値・時刻・件数・識別子」に絞ること、Read と Change を混ぜないこと、版を上げること、CLI 本体にサブコマンドを足すことがポイントです。

印刷の指示もこの仕組みでできますか?

窓口の仕組み自体は使えますが、JEA の仮想アカウントは画面のない別のセッションで動くため、ユーザーごとのプリンターや GUI アプリからの印刷はそのままでは動かないことが多いです。その場合は、窓口の関数から「特定のユーザーで動くタスク」を起動する形にします。整備の前に実機で確かめます。
