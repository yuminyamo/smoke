# 改訂指示 01 — 段1 共通の土台(作業10のフェーズA)

- 作成: 2026-10-07 / 前提の版: proc-v016 / この段で上げる版: 改訂時の版 + 1(proc-v017 の見込み)
- 先に `docs/94_改訂指示/00_共通の作法.md` を読むこと

## 0. この段でやること(要約)

1. **`pms act`** を作る。画面操作を1回ずつ実行し、そのたびに時刻・ロケータ・操作を記録ファイルに自動で書く
2. **タスクキューとカード**を作る。`pms next` が次のカードを出し、`pms submit` が AI の出力(JSON)を検査し、合格なら記録(setup-log)を書く。`pms status` が現在地を返す
3. カードは3種類: `setup.build`(状態を画面操作で作る)・`setup.code`(その状態の fixture・シナリオ部品のコードを書く)・`setup.reuse`(既存の fixture を流用し、成立を確かめる)
4. **setup-log は、すべてのエントリを pms が書く。** カードで `blocked` になった状態と、初期状態セットにない状態の、申し送り台帳・外部操作需要リストへの記録も pms が書く
5. 作業10のフェーズA(初期状態の準備)を、このカードで行うように手順書を改訂する。**この段では、カードは作業10と同じ会話の中で順に行う**(サブエージェントやスクリプト実行は段2・段3)

## 1. 変更の意図

**直す失敗**: 作業10を最後まで実施したのに、setup-log の `steps` と安定ロケータが抜けていた(`investigations/001_setup-log記録抜け.md`)。proc-v016 は「状態を1つ整備するたびに記録せよ」という規則と lint を足したが、**記録はまだ AI が書いている**。低価格のモデルは、長い会話の途中でこの義務を落とす。

**この段の考え方**(`00_共通の作法.md` 1章の P1・P5・P6):

- 操作の連番・時刻・ロケータは、`pms act` が操作のたびに記録する。**AI は記録を書かない。** AI が出すのは「成功した最短の操作は、記録の何番と何番か」という判断だけである
- setup-log の `built-by-ui` のエントリは、`pms submit` が検査に合格した提出から書く。記録にない操作(playwright-cli を直接呼んだ操作など)を含む提出は不合格になる
- 「どの状態を作るか」は、`pms` がシナリオの `requires` から機械的にカードにする。AI が選ばないので、一部の状態だけ作って先へ進む失敗が起きない
- カードは、そのカードに必要な規則と入力だけを載せた依頼文である。AI は 00・stages の全文を思い出さなくても、カードだけを見て正しく作業できる

**フェーズAの全部をカードと pms に移す理由**(段固有の人間の決定。改訂履歴の「人間の決定」に載せる):

> - 調査票001の結果を待たず、フェーズAで扱う状態はすべて、カードか pms の機械的な処理で扱う。既存 fixture の流用(`provided`)と、初期状態セットにない状態も含める

proc-v016 の改訂(改訂履歴26章)は、`provided` の書き方を調査票001の Q5 の結果待ちにしていた。しかし、どの原因であっても、AI に任せる部分が残れば低価格のモデルで抜けやばらつきが起きる余地が残る。一方で `provided` の記録は、流用元のエントリを写すだけで決まる(判断が要らない)。そこで、AI には「既存の fixture を実行し、成立したか」だけをカードで判断させ、記録は pms が流用元から写す。初期状態セットにない状態は判断そのものが要らないため、pms が記録する。

**この段で会話を分けない理由**: 道具(記録・キュー・検査)と実行形態(セッションの分け方)を同時に変えると、問題が起きたときにどちらが原因か分からなくなる。段1では道具だけを入れ、記録の抜けが 0 になることを先に確かめる。

### 3.2 `pms act` — 操作と記録の一体化

```
pms act --flow F-003 --card C-0001 open <URL|<env:キー>>
pms act --flow F-003 --card C-0001 snapshot
pms act --flow F-003 --card C-0001 --intent "<この操作の目的>" <操作> <ref> [値]
pms act --flow F-003 --card C-0001 --intent "<確かめること>" assert <ref> visible|hidden|text "<文言>"
pms act --flow F-003 --card C-0001 --intent "<目的>" ext --op <操作ID> -- <実行体の呼び出し...>
```

- `<操作>` は playwright-cli の画面操作のうち、作業10で使うもの(`click`・`dblclick`・`fill`・`type`・`select`・`check`・`uncheck`・`press`・`hover`・`goto`・`upload` など)。一覧は vocab に置く
- ブラウザのセッション名はフローIDにする(`playwright-cli -s=F-003`)。`open` は自動で閉じないようにする(`--idle-timeout=0`)
- **ロケータは操作の前に取る**: ref を受けたら、操作の前に `generate-locator <ref>` を実行する(操作のあとは画面が変わり ref が無効になることがある)
- **ロケータの区分**: 00 ■ロケータ規約の1〜5(`getByRole`・`getByLabel`・`getByPlaceholder`・`getByText`・`getByTestId`)なら `stable`、それ以外(`locator(...)` など CSS・構造)は `css` とする。さらに `run-code` で `count()` が 1 かを確かめ、`unique` に書く(規約の「一意に1要素へ解決されること」)
- **値**: `<env:キー>` を受けたら、`node tools/env/env.mjs get <キー> --reveal` で値を取り出して操作に使い、記録には `<env:キー>` と書く。**取り出した値は、playwright-cli の出力(入力した値がそのまま表示される)を含め、標準出力・記録のすべてで伏せる**
- **`assert`** は状態の成立の確認(established check)などに使う。ロケータを取り、条件を満たすかを確かめ、結果を記録する
- **`ext`** は外部操作の実行体を呼ぶ。操作ID・終了コード・時刻・標準出力の JSON(秘密情報は伏せる)を記録する。KB T05 への登録の確認は既存の lint `operation_registered` に任せる
- 操作に失敗しても記録は残す(`ok: false` と理由)
- **記録の1行**(act-log.jsonl)に最低限入れるもの: `seq`(フロー内の連番)・`card`・`action`・`ref`・`locator`・`locator_class`・`unique`・`value`(伏せた形)・`intent`・`code`(playwright-cli が出した Playwright のコード。値は伏せる)・`url_before`・`url_after`・`started_at`・`ended_at`(`vocab.timestamp_format`)・`ok`・`error`
- **標準出力**: JSON 1つ。操作の結果(`ok`・`seq`・`locator`・`locator_class`・`unique`・警告)に加えて、**毎回 `now`(現在のカードと、やること1行)と `next`(次に実行すべきコマンド)を付ける。** 会話が長くなったり要約されたりしても、AI が道具の出力から現在地を取り戻せるようにするためである(docs/004 7章の④)
- `css` や `unique: false` のときは、警告に「別の要素で操作し直すか、00 ■ロケータ規約の6(CSS の暫定使用と testid-requests への記録)に従う」と書く
- `snapshot` は、playwright-cli の snapshot をそのまま返し、末尾に `now`・`next` を付ける

### 3.3 タスクキューと `pms next` / `pms submit` / `pms status`

```
pms queue build --flow F-003 --phase A     フェーズAのカードを作る
pms next   --flow F-003                    次のカードの本文を出す。終わっていれば done、人間の判断が要れば STOP
pms submit --flow F-003 --card C-0001 --file work/_flows/F-003/out/C-0001.json
pms status --flow F-003 [--json]           現在のカード・残りの枚数・止まっている理由
```

**`queue build --phase A`**(カードを作る規則。AI に選ばせない):

1. そのフローの対象シナリオ(scenarios.md のうち、このフローで作ったもの)の `requires` を列挙して重複を除く。**`blocked` になりそうなシナリオの `requires` も除かない**(現行の §10 フェーズAの規定)
2. 状態ごとに次で振り分ける
   - 初期状態セット(`vocab.initial_state_set` と、状態需要リストの `採用` / `整備済`)にない → **カードにしない。** pms が setup-log に `classification: blocked`(理由 `初期状態外`)を書き、申し送り台帳に行を足す。パートBの記載ルール8と lint `requires_in_state_set` により通常は起きないため、`pms status` と報告書の材料に警告として残す
   - 過去のフローの setup-log に、同じ `state_id` の `built-by-ui`(または流用元を辿れる `provided`)で `verified: true` のエントリがあり、その `fixture` のファイルが存在する → `setup.reuse` のカードを1枚作る(流用元は最も新しいフローのエントリ)。ただし流用元のエントリに `steps` がない、または安定でないロケータがある(proc-v016 より前の記録など)ときは、写せる記録がないため `setup.build` を作って記録を取り直し、続く `setup.code` では既存の fixture・部品を同じ名前のまま直す
   - それ以外 → `setup.build` のカードを1枚作る
3. `setup.code` のカードは、同じ状態の `setup.build` が合格したときに作る
4. `setup.reuse` が `broken`(既存の fixture で状態が成立しない)で合格したら、同じ状態の `setup.build` を作り、続く `setup.code` で**既存の fixture・部品を同じ名前のまま作り直す**(ほかのテストがその名前で使っているため)。作り直したことを setup-log の `notes` と報告書の材料に残す

**`next`**:

- 出す順は作った順。出したカードの本文を `cards/` に保存し、状態を「出した」にして回数を数える
- **出したカードがまだ提出されていないまま `next` が呼ばれたら、同じカードをもう一度出す。** 本文の先頭に「前回は提出されなかった(n 回目)」と、そのカードで記録済みの操作の連番の一覧を添える
- 同じカードを `config/pms.json` の上限回数を超えて出すことになったら、出さずに STOP(人間の確認待ち)を返す
- 全部終わったら `done` を返す

**`submit`**: 4章の検査をすべて行う。合格なら記録を書き、カードを「合格」にする。不合格なら、理由(区分と、直し方1行)と次に実行すべきコマンドを返し、カードは「出した」のままにする。合否は毎回 `submit-log.jsonl` に書く(段2の計測に使う)。

**終了コード**: `next` は 0 = カードを出した / 0 = done(出力の JSON で区別)/ 3 = STOP。`submit` は 0 = 合格 / 1 = 不合格。どちらも 2 = 使い方・設定の誤り。

### 3.4 カードのテンプレートと規則の差し込み

- テンプレートは `procedure/cards/<種類>.md`、AI の出力のスキーマは `procedure/schemas/<種類>.out.json` に置く(手順書の一部として版の管理を受ける)
- テンプレートの構成は docs/94 §4 提案C の例に倣う: やること(1つだけ)/ 入力 / 規則 / 出力(JSON の形と、各欄の許される値)/ 合格した記入例 / 終わったら
- **規則は原本から差し込む。** 00・stages の規則の行に規則IDを付け(例 `**[R-LOC-1]**`)、テンプレートは `{{rule:R-LOC-1}}` で参照する。`pms next` がカードを作るときに、原本のその行を差し込む。**規則の文章をテンプレートに書き写さない**(同じことを2箇所に書かない)
  - この段で規則IDを付けるのは、2種類のカードが使う規則だけでよい(全体の分解は後の段)。IDの書式は `vocab.id_format` に足す
  - 保護ブロックの中の文に規則IDを付ける必要があるときは、保護ブロックを変えずに、ブロックごと差し込む仕組みにする(`00_共通の作法.md` 2.2)
- カードの入力のうち機械で埋められるもの(状態ID・定義・established check の案・状態需要リストの行・KB の該当ページのパス・現在の画面の URL)は pms が埋める

### 3.5 カード `setup.build`(状態を画面操作で作る)

**やること**: 状態を1つ、`pms act` による画面操作で作り、成立を `pms act assert` で確かめる。

**出力**(スキーマで縛る):

| 欄 | 内容 |
|---|---|
| `result` | `built` / `blocked` / `cannot_proceed` |
| `seqs` | 成功した最短の操作の連番を、順に並べた配列(`built` のとき必須) |
| `established_check_seq` | 成立を確かめた `assert` の連番(`built` のとき必須) |
| `fragile` | CSS の暫定ロケータを使った連番と理由の配列(00 ■ロケータ規約の6。なければ空) |
| `blocked` | `blocked` のときの理由(`vocab.reason_code`)・内容・参照(禁止ID・包括原則の番号など)。外部操作の手段がないときは、外部操作需要リストに書く項目(外部操作の業務語・操作対象・不足の区分)も入れる。pms はこれを見て台帳に書く |
| `notes` | 失敗した試行の要点(1〜2文。なければ null) |

### 3.6 カード `setup.reuse`(既存の fixture の流用)

**やること**: 既存の fixture を1回実行し、状態が成立する(established check が通る)かを確かめる(現行の §10 フェーズA「既存 fixture があれば実行し、established check が通ることを確認するのみ」)。再整備・再探索はしない。

- **カードの入力**(pms が埋める): 流用元のフローID・エントリ(`fixture`・`flow`・`steps`・`established_check`)、fixture を実行するコマンドの例(過去の `setup.code` の `runs` から取る)
- **出力**: `result`(`reused` / `broken` / `cannot_proceed`)・`runs`(実行したコマンド・終了コード・時刻。1回)・`notes`(`broken` のときは失敗のしかたを1〜2文)

### 3.7 カード `setup.code`(fixture とシナリオ部品のコード)

**やること**: 合格した `setup.build` の操作列を、00 ■シナリオ部品の規約・■ページオブジェクト規約に従ってシナリオ部品(`tests/flows/`)と fixture(`tests/fixtures/`)にし、現行の §10 フェーズAどおり2回実行して確かめる。ログイン状態(`S-ADMIN-LOGIN` / `S-USER-LOGIN`)を初めて整備したときは、起動確認テストも作る(現行の規定)。

- **カードの入力に、pms が記録から作ったコードの下書きを載せる**(act-log の `code` を連番の順に並べ、値を `<env:キー>` から環境情報の取り出しに置き換えたもの)。AI は下書きを規約に合う形に置き直す
- **出力**: `flow`(`<ファイル>#<関数>`)・`fixture`(`<ファイル>#<名前>`)・`runs`(2回の実行のコマンド・終了コード・時刻)・`cleanup`・`notes`

## 4. `pms submit` の検査

| 区分 | 検査 | 対象のカード |
|---|---|---|
| `schema` | 出力がスキーマを満たす(必須欄・列挙・文字数の上限) | 両方 |
| `seq_missing` | `seqs`・`established_check_seq` の連番が act-log にあり、このカードの記録で、`ok: true` で、順序が増えている | build |
| `unstable_locator` | `seqs` の各操作のロケータが `stable` かつ `unique`。`css` は `fragile` に挙げてあり、`work/_common/testid-requests.md` にそのセレクタがあるときだけ認める | build |
| `red_flag` | あいまいな語(「適宜」「など」「必要に応じて」「〜等」)、長すぎる・短すぎる欄、`blocked` なのに理由の参照がない、など(MAKER の red-flagging。docs/94 提案D) | 両方 |
| `code_mismatch` | `flow`・`fixture` のファイルと関数が存在し、setup-log の各 step のロケータ(文字列)が部品のコードに順に現れ、established check のロケータが fixture か部品に現れる | code |
| `runs` | `setup.code` は実行が2回あり、2回とも終了コード 0 のときだけ `verified: true` にする。`setup.reuse` は実行が1回あり、`reused` なら終了コード 0、`broken` なら 0 以外 | code・reuse |
| `reuse_source` | 流用元のエントリと fixture のファイルが今も存在する | reuse |
| `lint` | 書く予定の setup-log のエントリが、既存の lint `setup_steps_recorded`・`no_temp_locator`・`env_value_leak` を満たす | build |

**合格したら書くもの**:

- `setup.build`(`built`): setup-log に `built-by-ui` のエントリを書く。`steps` は `seqs` の記録から作る(`goto` は `detail`、`ext` は `operation_id`、それ以外は `locator`・`value`)。`established_check` は assert の記録から作る。**記録との対応を残す欄を付録Bに足す**(例: `act: { card: C-0001, seqs: [3,4,5,7] }`)。`flow`・`fixture` は空、`verified: false`
- `setup.build`(`blocked`): setup-log に `classification: blocked` と理由を書く。出力の `blocked` から、申し送り台帳に行を足し、外部操作の手段がないときは外部操作需要リストにも行を足す(同じ外部操作と操作対象の行があれば要求元を追記するだけ。00 ■外部操作の重複防止の規定どおり)。台帳の表の形は templates の書式に合わせ、ID は pms が採番する。**台帳への書き込みは段2でも使うため、共通の部品にする**
- `setup.reuse`(`reused`): setup-log に `classification: provided` のエントリを書く。`steps`・`flow`・`fixture`・`established_check` は流用元のエントリから**そのまま写し**、流用元を示す欄(例: `reused_from: { flow_id: F-001 }`)と、今回の実行の結果(`verified`)を書く
- `setup.reuse`(`broken`): setup-log にはまだ書かない(作り直しの `setup.build`・`setup.code` が合格したときに `built-by-ui` として書く)
- `setup.code`: setup-log の同じエントリの `flow`・`fixture`・`verified`・`cleanup` を埋める。状態需要リストの `採用` の状態なら、行の状態を `整備済` にし fixture の所在を書く(機械的な書き換え。表の形を崩さないこと)
