## 0. 目的と得たい効果

本構想の目的は、Web UIを持つPMS(Print Management System)商品のE2Eテストにおいて、以下の効果を得ることである。

- 機能追加時のテスト、不具合修正時の二次障害防止(デグレード検出)、OS・連携ソフトウェアのバージョンアップ時の動作検証にかかる**テスト工数の削減**
- 開発サイクルの早い段階での**不具合の早期検出による品質向上**
- E2Eテスト自動化を、社内の**品質点検の基盤**とすること

手段として生成AIを活用し、「テスト項目の策定(上流)」から「回帰テストの自動実行(下流)」までを一貫したパイプラインとして構築する。

## 1. 技術トレンド上の自動テストの段階定義と、現時点での推奨レベル

### 1.1 段階定義(自律テスト成熟度モデル)

業界では、自動運転のレベル分けになぞらえた「テスト自動化の自律度」の段階定義が定着しつつある。代表的なものに Katalon の Autonomous Software Testing Model (ASTM) があり、各社の整理もおおむね以下の6段階に収斂している。

| レベル | 呼称 | 概要 |
|---|---|---|
| Level 0 | 完全手動 | 人間がすべてのテストを設計・実行 |
| Level 1 | 自動化支援 | Selenium/Playwright等のスクリプト自動化。作成・保守は人間 |
| Level 2 | AI拡張 | self-healingロケータ、AIによるテストケース生成補助など、AIが人間を支援(AI-assisted testing) |
| Level 3 | インテリジェント自動化 | AIがテストの**生成・実行・保守・分析**を担い、人間はレビューとガバナンスに回る |
| Level 4 | 自律テスト | AIが最小限の人間監督でテストライフサイクル全体を駆動(差分検知→ギャップ特定→生成→実行→報告の閉ループ) |
| Level 5 | 完全自律 | AIが自らテスト戦略を適応・最適化。人間の介入なし |

「AIが指示されたテストを実行する」段階と、「AI自身がテスト項目を考え、意思決定して実行する」段階を区別する考え方は、業界では **Agentic Testing / Agentic QA / Autonomous Testing** と呼ばれる。

### 1.2 現時点で利用できる生成AIモデルを踏まえた推奨レベル

2026年時点の到達点は以下のように評価されている。

- Level 1〜3(self-healing、AIテスト生成、AIエージェントによる探索的操作)は、現行のLLM/マルチモーダルモデルと Playwright 系のエージェント基盤で**実用段階**にある。
- Level 4〜5は、ビジネスロジックの深い理解、エッジケース、テストオラクル(期待結果の正しさの判定基準)の限界から、学術レビューでも**依然として理論的段階**と評価されている。
- したがって、エンタープライズで最も投資対効果が出るのは **Level 3(+Level 4の部分導入)** であり、「人間をレビューとガバナンスに残した閉ループ(Human-in-the-Loop)」が2026年の推奨アーキテクチャである。

**推奨レベル:Level 3 を確立し、Level 4 の要素(差分検知トリガー、self-healing)を段階的に取り込む。**

## 2. 現時点で目指しているレベルと、具体的な実現イメージ

### 2.1 目指すレベル

**ASTM Level 3 相当。** AIがテスト項目の策定・探索的実行・回帰テストコード生成までを担い、人間は品質ガバナンスとレビューに専念する。ただしプロトタイプフェーズかつ人間工数が有限であることから、**レビューはパイプラインのブロッキングゲートにしない**(後述2.6)。回帰テストの実行自体はAIを使わず、決定的(deterministic)に実行する(コスト・再現性・実行速度の観点)。

### 2.2 オラクル原則: 現行バージョンの実挙動を正解とする

レガシー製品ではドキュメントの充足度が低く(後述)、「文書の正しさ」より「現行動作の合意」の方が現実的なオラクルになる。本構想では次を原則とする。

- **現行バージョンの実挙動を正解として凍結する。** マニュアル・仕様書はテスト手順を編み出すための情報源であり、正解の最終根拠ではない
- 実挙動と文書が食い違った場合、実挙動を正解として作業を継続し、**食い違いを不整合レポート(DISC)として記録する**。どちらが正しいかの判断はAIではなく人間が別活動で行う
- この方式で作った回帰テストは「基準バージョンから挙動が変わっていないこと」を機械的に証明する。二次障害(デグレード)防止という目的に直結する

### 2.3 段階構成: 3ステップで網を細かくしていく

全機能・全観点を一度に自動化しようとせず、**網の目を段階的に細かくする**3ステップ構成を採る。

| ステップ | 対象 | 目的 | 網の目 |
|---|---|---|---|
| **ステップ1**(現在) | E2E / シナリオ型(基本動作シナリオ)のみ | 全機能の基本動作が通ることの保証。致命的な破損の検出 | 粗い |
| ステップ2 | E2E / 単発型(独立検証項目)+ シナリオ型のバリエーション | E2Eの充実。基本動作から外れた検証の追加 | 中 |
| ステップ3 | E2E以外の手段(HTTP層・DB層への降下、メタモルフィック検証、異常注入等) | 機能特性に応じた効率的・網羅的な検証 | 細かい |

ステップ1で「単位時間あたり最大の機能が動作していること」を確認できるシナリオ型(利用者が実際に行う一連の作業をなぞる複数ステップのテスト)を先に整備し、細粒度の独立検証(単発型)はステップ2以降で安く作る。ステップ1はさらに、1機能内で完結する**単機能シナリオ**(3〜6ステップ)→機能をまたぐ**連結シナリオ**の順に進める。

**ステップ1で意図的に扱わなかった対象は「申し送り台帳」に統制語彙の理由コード付きで記録する。** 理由コード別の集計がそのままステップ2・3の投資計画になる(例: 「実操作で作れない前提状態」が多ければDB投入基盤への投資、「E2Eでは非効率」が多ければ下位層への降下)。粗い網は「管理された欠落」であり、説明可能である。

### 2.4 パイプラインの構成(ステップ1)

**フロー反復モデル**: 一度に全機能を扱わず、人間が指示した対象領域(1〜2機能程度)ごとに「シナリオ生成と探索 → 回帰テストコード生成」を1巡する。これを**フロー**と呼び、フローを繰り返して回帰テストセットを累積する。fixture・シナリオ部品・知見ベース・非決定値カタログはフロー横断で蓄積され、フローを重ねるほど流用が効いて1フローあたりのコストが下がる。

| 作業 | 内容 | 担当 | 位置づけ |
|---|---|---|---|
| 禁止操作リストの記入 | AIが**実行してはならない**操作を列挙する(2.4.1・3.4) | 人間 | 事前(以降は随時追記) |
| 手順改善 | 実行中に記録された手順の迷い・矛盾・逸脱などを集約し、手順書を差分で改訂して効果を判定する(2.8) | AI(実行AIとは別のセッション) | フロー開始時の条件付き(数フローごと)。停止しない |
| 知見蓄積 | 人間が指示した対象を調査し、知見ベース(KB)へ蓄積(2.7) | AI | 任意・随時 |
| 非決定値カタログ | 同一操作を反復実行し、値ごとの検証強度を実測で決定 | AI | 初回フロー前、以降は増分 |
| **シナリオ生成と探索** | シナリオ型の項目を生成し(全ステップに出典必須)、続けて playwright-cli と外部操作で操作手順を探索的に編み出して検証・記録する(操作列・安定ロケータ・実測待機時間) | AI | **フローの本線⑴** |
| レビュー(非ブロッキング) | シナリオ・判定・不整合(DISC)・不変条件違反の確認、as-is判断。後段と並行して実施 | **人間** | 並行 |
| **回帰テストコード生成** | 探索記録を忠実に決定的な Playwright 回帰テストコードへ変換し、項目IDとコードを機械的に突合 | AI | **フローの本線⑵** |
| 外部操作 skill の整備 | 必要と分かった外部操作の skill を、外部操作需要リストを見て優先度順に整備する(3.4) | 人間 | 随時。需要の発生とは切り離す |
| 再探索フロー | skill の整備後、その操作が無くて止まっていたシナリオを探索し直す | AI | 人間の指示時 |
| 状態カタログ案生成 | 探索記録を主入力に、実観測された状態をカタログ化(ステップ2の準備) | AI | 複数フロー完了後、人間の指示時 |

シナリオには操作手順を書かず検証意図と判定基準だけを書き、探索するAIが手順を編み出す構成は、研究分野の **Intent-Driven Testing(意図駆動テスト)** の方向性と一致する。

**段階間の受け渡しと停止点**: 各作業は人間向けの報告書とは別に、機械可読な段階間契約(status.yaml)を出力し、後段はそこから入力を機械的に取る。各作業の完了条件はチェックリスト(DoD)で定め、そのまま実行前検証(lint)の仕様になる。実行順序・分岐・停止点はワークフローのグラフ定義(pipeline.dot)に一元化している。**必須の停止点は3つだけ**である: シナリオ生成と探索の完了報告(コード生成の前)/ 要許可操作のエスカレーション / 状態カタログ検証のデータ変更。手順改善は停止点を増やさない。

**状態カタログを後置する理由**: ステップ1のシナリオが要求する前提状態は少数の「初期状態セット」(管理者ログイン済・一般ユーザーログイン済・デバイス登録済・初期環境)に収まるため事前整備は不要であり、仕様書・ソースから状態を推測列挙するより、実際にシナリオを流して観測された状態を起こす方が確度が高い。カタログはステップ2(単発型の項目生成)の語彙として使う。

#### 2.4.1 Web UI 以外の操作(外部操作)の扱い

印刷指示・機器パネル操作・AD やメールサーバへの操作など、Web UI 以外の手段で行う操作を**外部操作**と呼ぶ。外部操作は、人間が段階的に整備する **skill** を介してのみ行う。skill がまだない外部操作は**外部操作需要リスト**に積み、該当シナリオはいったん止めて(`blocked`)フローを先へ進める。skill を整備したら**再探索フロー**でそのシナリオへ戻る。詳しくは 3.4 で述べる。

### 2.5 回帰テストの信頼性を支える仕組み

回帰テストは flaky(不安定)になった瞬間に信頼を失う。ステップ1から次の機構を組み込む。

- **非決定値カタログ**: 実行のたびに変わる値(ジョブID、タイムスタンプ等)を実測で分類し、値ごとに検証強度(完全一致/関係式/パターン一致/存在のみ)を決める。金額・枚数のような「変わってはいけない値」の検出力を保ったまま安定性を確保する。テストが不安定だからと**テスト側で強度を勝手に下げることは禁止**し、カタログ見直し提案として人間に上げさせる
- **非同期待機の標準化**: 固定待機を全面禁止し、「目的の状態が成立した」を条件とするポーリング契約に統一。探索時の実測所要時間をタイムアウト値の根拠にし、実測値の推移は性能劣化の兆候検知にも使う
- **DB不変条件**: どのシナリオの後でも常に成立すべき条件(1ジョブ1課金、明細合計=総額、孤児レコードなし等)を機械的に検査する。全シナリオが同時に整合性テストになり、カバレッジが掛け算で増える。並列実行と干渉しないよう、シナリオ末尾では自シナリオのデータに限定した検査、スイート終端でDB全体の検査、の2段構えとする
- **実行環境と再実行耐性**: 回帰テストセットの実行開始前にゴールデンイメージ(VMスナップショット)を復元する。テスト項目間では復元しないため、各テストは作成データの一意化と自データにスコープした検証により、データが蓄積した環境・復元なしの再実行でも成立するように書く
- **安定ロケータ規約**: role/labelベースを優先し、取れない要素は `data-testid` の製品側追加を依頼する運用(製品はメンテナンス継続中であり反映可能)

### 2.6 レビュー方針:非ブロッキング・レビュー(Human-on-the-Loop)

人間の工数が有限であり、本活動がプロトタイプフェーズであることから、**人間のレビューをパイプラインのブロッキングゲートにしない**方針を採る。教科書的な Human-in-the-Loop(各段で人間の承認を待つ)ではなく、**Human-on-the-Loop**(人間は並行して監督し、必要な箇所に介入する)に近い運用である。

| 論点 | 方針 |
|---|---|
| 後段の参照可否 | AI成果物は未レビューでも後段のAI処理が参照してよい(レビュー待ちで停止しない) |
| レビュー状況の管理 | 全成果物にレビューヘッダ(`unreviewed` / `reviewed` / `needs-fix`)を持たせ、機械的に追跡可能にする |
| 状態管理 | 進捗軸(生成→探索→コード化)とレビュー軸を分離し、混ぜない |
| 問題発生時 | 後段で不調が起きたら前段のレビュー状況を参照し、未レビューであれば前段AI出力の誤りを原因候補として切り分ける |
| 工数配分 | AIが各報告書に「優先レビュー推奨リスト」を出し、限られた人間工数の投下先を示す |

これは「レビューを省く」のではなく「レビューを並行化し、重要な箇所に集中させる」設計である。承認待ちの直列化がパイプライン全体のスループットを律速する状態を避けつつ、後から誤りを追跡できる情報は残す。

**例外は2つのみ**である。成果物の品質レビューではなく「行為の許可」に当たるもの、すなわち**禁止操作リストで `要許可` とされた操作、および包括原則(表にない危険な操作へのセーフティネット)に触れる操作の実行**(実機・VM外の連携システムへの予期しない操作)と、**状態カタログ検証におけるデータ変更操作**(環境破壊のおそれ)は、人間の許可を必要とする。

加えて、探索で `failed` / `human-check` となった項目を「現状挙動が正解(as-is)」として回帰テストに凍結する判断は、AIに行わせない。これはゲートではなく、**不具合を回帰テストの正解として固定してしまわない**ための責任分界である(未判断の項目があってもコード生成は残りの項目で進む)。

### 2.7 知見蓄積フェーズと知見ベース(KB)

自動回帰テスト作成の各手順(項目生成・探索・コード生成)は、いずれも対象システムの理解を必要とする。何もしなければ、同じ調査(この画面はどこにあるか、この列は何を意味するか、この非同期処理は何秒かかるか)が手順ごとに繰り返される。これを避けるため、**任意・随時の知見蓄積フェーズ**を設ける。

- **起動は人間の指示による。** 人間は調査対象(操作または機能。例: 「複合機からジョブログを収集する操作」)を指示するだけでよい。**何を調べるべきかは、AIが後段の各手順から逆算する**(手順ごとに必要な知見カテゴリの対応表を指示書に用意)
- **調査手段**: 文献調査(マニュアル・仕様書の**転記はせず所在のみ**記録。例「ステータス一覧は仕様書5.2章」)、DB定義と**実際に蓄積されているデータ**の観測、Web画面操作、必要な場合は外部操作(印刷指示・機器パネル操作等。skill がある場合に限る。ない場合は外部操作需要リストへ記録する)
- **成果はKB(`kb/`)に蓄積**し、全手順が索引経由で参照し、作業中に判明した知見をその場で更新する。KBは自動回帰テスト以外の用途(調査・教育・仕様書補完・障害解析)でも生成AIと人間の双方が利用できる資産として設計する
- **「分からなかったこと」も成果物**として記録する。文書に記載がないと判明した主題の一覧は、そのまま仕様書補完のタスクリストになる(3.1の課題に直結)
- KBに無い事項を各手順が自分で調べること自体は禁止しない。ただし**発見ログ**への記録義務を負い、「KBがあるのに参照されなかった」再発見率が可視化される。再発見が多い領域が次の知見蓄積の対象になる

この仕組みは、ドキュメント充足度の低さ(マニュアル5割・仕様書6割・設計書2割)というレガシー特有の制約に対する、**網羅的な事前整備をせずに必要な知見だけを実測で埋めていく**アプローチである。知見の完成はパイプライン開始の前提条件ではない。

### 2.8 手順の自己改善

KB が「対象システムについての事実」を実行から学ぶ仕組みだとすれば、**手順の自己改善は「テストの作り方」そのものを実行から学ぶ仕組み**である。

- **その場で記録する**: 各作業のAIは、手順について迷った・矛盾を見つけた・実行できなかった・手順と違う方法で実施した出来事を、手順改善台帳に事実だけ記録する(手順改善シグナル)。後段の作業が前段の成果物の不足で困った場合は、前段の手順の問題として記録する。**AIは実行中に手順書を書き換えない**
- **別のAIがまとめて直す**: 数フローごとに、実行AIとは別のセッションのAI(作業40)がシグナルを集約し、多くは KB などの適切な置き場所へ回付したうえで、手順の問題だけを**差分で**改訂する。改訂案には「期待する変化・判定期間・撤回条件」を起票時に登録し、判定期限に定着か撤回かを決める
- **検証を弱める「改善」を防ぐ**: AIに手順を改善させると、検証を緩めて摩擦を減らす方向に進むおそれがある。テストが緑のまま不具合を通すため、誰も気づかない。これを防ぐため、改訂を**自律適用・人間採否・不可侵**の3区分に分け、オラクル原則・禁止操作・期待結果の書き換え禁止など安全と検出力の根幹を**保護ブロック**として固定し、効果の判定には効率とは別に**検出力ガード指標**を使う
- **最終的な決定権は人間**: 区分はAIが自律的に変えてよい範囲を決めるものであり、人間が明示的に指示した改訂は区分に関わらずAIが行う(拒否しない)

参考にした研究: ACE(Agentic Context Engineering)。実行・振り返り・統合の役割分担と、差分による更新を取り入れた。

## 3. 実現イメージの具体化に向けたチャレンジポイントと、整備・確立すべき重要な点

対象商品は市場供給約15年のレガシーソフトウェアであり、以下の現状を前提とする。

| 資産 | 現状(あるべき姿に対する充足度の体感値) |
|---|---|
| マニュアル | あり。ただし情報量は約5割 |
| 仕様書 | それなりにあり。約6割 |
| 設計情報 | 一貫してメンテナンスされたものはなし。約2割 |
| Web UIのPlaywright操作性 | 95%は操作可能。残りは実装修正不要で、解析や操作のコツを与えれば自動操作可能 |
| テスト範囲 | Web UI操作に加え、Web UI以外の操作(外部操作。機器での印刷実行と結果の取得等)が必要 |

### 3.1 チャレンジポイント①:ドキュメント充足度の低さ(AIの入力品質問題)

マニュアル5割・仕様書6割という充足度では、AIは不足分を推測で埋めるため、ハルシネーションによる誤った期待結果の混入リスクが高い。

**整備・確立すべき点(設計済み):**

- **トレーサビリティの強制**: 全テスト項目に出典を必須とし、出典のない項目は `推測(仕様未記載)` / `画面観察` と機械的にマークする規約。「AIの創作」がレビューで確実に捕捉できる
- **オラクル原則による吸収**: 文書が不足・矛盾する領域は、実挙動を as-is 正解とする判断を人間が行う(2.2)。食い違いはすべて DISC として採番・記録され、握りつぶせない
- **仕様の欠落を成果物に変える運用**: 「未確認事項」と DISC に集まった仕様未記載・矛盾、および知見蓄積フェーズが記録する「文書に記載なし」の一覧を、有識者ヒアリング→仕様書追記のサイクルに乗せる。テスト自動化の副産物としてドキュメントが漸進的に補完される
- **知見ベース(KB)による調査の一度きり化**(2.7): 調べた事実を索引付きで蓄積し、各手順が参照・更新する。同じ調査の繰り返しを排除するとともに、KB自体がAIの読める形の実質的なシステム説明資料になる

### 3.2 チャレンジポイント②:テストオラクル問題(期待結果の正しさ)

ドキュメントが不完全な環境では「何が正しい動作か」の判定基準自体が曖昧になる。LLM自律テスト研究でも最大の未解決課題(incomplete test oracles)として指摘されている。

**整備・確立すべき点(設計済み):**

- 期待結果は特定のUI文字列に依存せず**業務的な意味レベル**で記述する規約。UI変更への頑健性とレビュー時の妥当性判断のしやすさを両立する
- 判定は `passed` / `failed` に加え、AIが正否を断定できない場合の `human-check`、実行自体ができない場合の `blocked` を設け、無理な Pass/Fail 判定をさせない
- 全期待結果に検証手段(`画面` / `DB` / `両方`)を付与し、原則「画面で確認しDBで裏付ける」二重確認とする

### 3.3 チャレンジポイント③:前提状態の管理(長い業務フローとテスト間依存)

PMSのユースケースは「印刷ジョブ投入→機器での実行→実績記録→課金確定→レポート集計」のような機能をまたぐデータ連鎖を含み、テスト間の依存関係が複雑化しやすい。

**整備・確立すべき点(設計済み):**

- **テスト項目間の参照連鎖を禁止**する。前提状態は名前付きの「状態」として定義し、Playwright の fixtures / setup projects が充足する。項目間依存は連鎖故障と並列実行阻害の原因になるため採用しない
- ステップ1は少数の**初期状態セット**だけで進め、**状態カタログはステップ1の探索記録から後付けで生成する**(2.4)。推測列挙より実観測の方が確度が高く、15年もののレガシーに残る「死んだ enum 値」をカタログに混入させない
- 機能をまたぐ連鎖そのものの検証は連結シナリオとして、単機能シナリオで得た部品の再利用により段階的に構築する
- 実操作で作れない前提状態(過去日付データ、0件状態、大量データ)は申し送り台帳に記録し、DB投入によるデータセットアップ基盤(ステップ2以降)で解決する

### 3.4 チャレンジポイント④:Web UI以外の操作(外部操作)と検証

Playwrightで完結しない操作(印刷指示、機器パネル操作、AD・メールサーバ・PMSサーバOSへの操作等)と結果取得が検証範囲に含まれる。これらを**外部操作**と総称する。課題は3つある。操作の手段が揃うまでに時間がかかること、AIが勝手に手段を作ると検証されていない手段が回帰テストに入ること、実機やVM外のシステムへの誤操作は巻き戻らないことである。

**整備・確立すべき点(設計済み):**

- **外部操作は skill を介してのみ行う**: 外部操作の手段は、人間が整備する skill に限る。AIが自律的に行ってよいのは skill の使い方(引数・前提条件・完了判定)の確立までであり、skill のない操作を自作の手段で実行しない。どの skill があるかは skills の機構で管理し、別の一覧は持たない
- **skill には、コードから呼べる実行体の同梱を求める**: 回帰テストは実行時にAIを使わないため、AIが探索で使えるだけの skill では回帰テストにならない。CLI・スクリプトとして非対話で起動でき、成否を機械的に判定できることを条件とし、探索時と回帰テストコード生成の前に確認する
- **skill は需要に応じて段階的に整備する(外部操作需要リスト)**: skill の整備にはコストがかかるため、特に初期は必要な skill が揃っていない。AIは必要と分かった外部操作をその場で需要リストに積み(1つの外部操作につき1行。何件のシナリオを止めているか・代替手段の有無などの事実を記録)、該当シナリオは `blocked` にして先へ進む。**優先度付けと整備は人間が、需要の発生とは切り離して任意の時期に行う**
- **整備後は再探索フローで戻る**: skill を整備したら、人間が再探索フローを指示し、その操作が無くて止まっていたシナリオを探索し直して回帰テストに加える。これにより、段階的な整備がそのまま回帰テストの増加につながる
- **禁止操作リスト(ブラックリスト)+包括原則**: AIが実行してはならない操作を人間が列挙する。当初は許可された操作を列挙する語彙表(ホワイトリスト)方式だったが、人間が書き切るまでAIが動けず、対象システムが広がるほど記入コストが増えるため転換した。表にない操作でも、物理資源の大量消費・復旧困難・テスト環境外への影響・VM復元で戻らない変更のおそれがあれば実行前にエスカレーションする(迷ったら実行しない)。**リストは人間が守り、skill は人間が整備し、確立済みの操作の台帳(知見ベース)はAIが育てる**という役割分担である
- **確立した操作は台帳に登録してから使う**: skill を使って確立した外部操作は操作IDを付けて知見ベースに登録し、テストコードからは操作IDと1対1のラッパ経由で呼ぶ。座標値や機器固有の手順・実行体の引数はラッパと知見ベース側に持たせ、機器や skill の入れ替え時の変更範囲を局所化する
- 外部操作を含むテストはタグで分離し、同時実行できない操作対象(共有の実機等)を使うテストだけを直列実行する
- 結果の検証は画面とDB(SQL Server への SELECT)の両面で行う。課金の予測金額(PDL解析)・実績金額(ジョブログ)の内部処理検証や異常注入(クラッシュ・重複・順序逆転)は、Web UI操作では誘発できないため**ステップ3の下位層検証**(PDL解析のゴールデンコーパス回帰、機器シミュレータによる異常注入等)として計画する。ただし課金の基本シナリオがE2Eで押さえられていること自体に品質点検上の価値があるため、ステップ1(単機能シナリオ・連結シナリオ)でも基本経路は扱う

### 3.5 チャレンジポイント⑤:操作困難な5%への対処(ナレッジの形式知化)

Playwrightで素直に操作できない5%は、「解析や操作のコツ」を教えれば操作可能という現状がある。

**整備・確立すべき点(設計済み):**

- コツを属人的な暗黙知のままにせず、**AIエージェントが参照できる知見ベース(KB)** として整備する(2.7)。探索中に自力で見つけた攻略法もAIがその場で追記し、資産として蓄積する
- 安定ロケータ規約(role/labelベース優先)を定め、取れない要素は `data-testid` の製品側追加を依頼→反映→暫定ロケータ置換のサイクルで解消する。CSSセレクタは一時措置とし、`FRAGILE` マーク付きで追跡する

### 3.6 チャレンジポイント⑥:AI生成物の品質ガバナンス

**整備・確立すべき点(設計済み):**

- シナリオ生成と探索の完了報告で必ず停止し、成果物とレビュー状況が記録として残る構造。レビューは非ブロッキングだが(2.6)、**AIが優先レビュー推奨リストを出して人間工数の投下先を示す**責任を負う
- **段階間の受け渡しを機械可読にする**: 各作業は status.yaml(段階間契約)を出力し、後段は報告書の読解ではなくそこから入力を取る。完了条件(DoD)をチェックリストで定め、実行前検証(lint)でエラーがあれば次の作業を起動しない
- 項目ID⇔テストコードの**機械的な突合検証**(一意性・完全性・ステップ網羅)を回帰テストコード生成の必須手順とし、突合表を成果物として残す。スキップした項目も理由付きで表に残し、黙って落とさせない
- プロトタイピング原則: 完璧な手順を事前に編み出そうとしない。1フローの作業単位(1〜2機能)がすでに小さいため、作業の中にさらにパイロット段階は設けず、絞り込みが必要なら領域指示の側で絞る。**手順の欠陥は実行中に直さず手順改善シグナルとして記録し、手順の自己改善(2.8)で直す**
- **手順の改訂そのものを統制する**: AIによる手順の改訂は差分に限り、改訂の区分・保護ブロック・検出力ガード指標・判定基準の事前登録で、検証を弱める方向の改訂を防ぐ。手順書の版を記録し、どの版の手順でどのテストが作られたかを追えるようにする(生成したテストには生成元のフローと手順版を注釈として残す)
- 手順書の前提に関わる未確認事項は要確認事項台帳で一元管理し、回答が出たら手順書へ反映する

## 4. 将来に向けて:推奨レベル(Level 3確立+Level 4要素)へのギャップと課題

### 4.1 現構想と将来像のギャップ

現構想は「人間が起点となってパイプラインを回す」Level 3である。トレンド上の次の段階は、**変更の検知を起点にパイプラインが自動起動する閉ループ(Closed-Loop QA)** であり、Level 4の部分導入に相当する。

| 観点 | 現構想(Level 3) | 将来像(Level 4要素の導入) |
|---|---|---|
| 起動 | 人間がパイプラインを起動 | コード差分・仕様差分・UI差分の検知で自動起動 |
| カバレッジ | 人間が項目の網羅性を判断(申し送り台帳の集計が計画の入力) | AIが既存カバレッジと変更差分を突合し、不足テストを提案 |
| 保守 | テストコード破損時は人間+AIで修正 | self-healing(UI変化の検知とセレクタ自動修復、修正はPR形式で人間承認) |
| 失敗分析 | 人間がログ・スクリーンショットを分析 | AIによる一次切り分け(製品不具合/テスト不具合/環境要因)と根本原因分析の下書き |
| 手順の保守 | 作業40が実績から手順を差分で改訂し、効果を判定する(区分Aの自律適用は保護機構の実装後。区分B・Cは人間) | 実績を見て自律適用の範囲を段階的に広げる。検出力ガードと保護ブロックは維持する |

### 4.2 ギャップ解消に向けたチャレンジポイントと整備すべき点

**①差分検知の仕組み**: 閉ループの起点となる「何が変わったか」の検知基盤。設計情報が2割しかない現状では変更影響分析の精度が出ないため、**テスト資産自体を「生きた設計情報」として蓄積する**戦略が有効。シナリオ・探索記録・状態カタログ・DISC・トレーサビリティ、および知見ベース(KB)が実質的な仕様リポジトリになる。第3章の資産整備がそのままLevel 4への布石になる。

**②CI/CDへの組み込み**: 回帰テストをCIパイプラインに常設し、失敗時のアーティファクト(trace、スクリーンショット、動画)を自動収集する基盤。項目ID⇔コードの突合検証と lint をスクリプト化し、パイプラインの品質ゲートにする。回帰実行の失敗の切り分け結果(当面は人間)は手順改善台帳に1行で記録し、テスト起因のものを生成手順の改訂につなげる。

**③self-healingの導入と統制**: UI変更でテストが壊れた際、AIがセレクタや操作を修復する仕組み。「テストが壊れた」のか「製品が壊れた」のかの判別を誤ると不具合を隠蔽するため、**修復は必ず差分提案(PR)として人間承認を経る**。ここを無審査にしないことがLevel 4導入時の最重要ガバナンスポイント。回帰実行の失敗の切り分けをAIに任せる場合も同じで、「製品不具合ではない」と判断することの扱いを導入前に決める。

**④エージェントの観測可能性(Observability)**: エージェントの判断・行動をログとして記録し、「なぜこのテストを生成/修復/スキップしたか」を追跡できるようにする。現構想の探索記録・DISC・申し送り台帳・外部操作需要リスト・手順改善台帳・完了報告・status.yaml は、この要件を先取りした一級のテスト成果物である。

**⑤コスト・実行時間の管理**: 探索的実行やカバレッジ分析にLLMを使う頻度が上がるため、トークンコストと実行時間の予算管理を整備する。「回帰実行にはAIを使わない」という現構想の原則は、Level 4に進んでも維持すべきコスト統制の要である。実行時間は外部操作あり/なしで分けて計測しており、高速化投資(DB投入セットアップ、並列化)の判断材料になる。

**⑥手順の自律改善の範囲の拡大**: 手順改善の自律適用は、lint の保護機構(保護ブロックのハッシュ照合・区分の再計算)の実装後に解禁し、実績(定着率・ガード異常の有無)を見て人間採否の範囲の一部を自律適用へ移していく。安全と検出力の根幹(保護ブロック)と、人間の明示的な指示を最優先する原則は、自律度を上げても維持する。

### 4.3 段階的ロードマップ(まとめ)

1. **フェーズ1(現構想=Level 3の確立)**: ステップ1(シナリオ型・粗い網)のパイプラインをフロー単位で人間起点で回し、禁止操作リスト・非決定値カタログ・知見ベース(KB)・申し送り台帳・外部操作需要リスト・手順改善台帳を整備する。外部操作 skill は需要リストに基づいて段階的に整備し、再探索フローで回帰テストに取り込む。手順は実績から作業40で改善していく(当初は全改訂を人間が採否)。単機能シナリオ→連結シナリオと進め、全機能の基本動作を機械的に証明できる状態を作る
2. **フェーズ2(Level 3の定着と資産化)**: ステップ2(単発型・状態カタログ活用・DB投入フィクスチャ)へ拡張し、未確認事項・DISCの消化による仕様書補完を回す。回帰テストをCIに常設し、失敗の切り分けを手順の改善につなげる。lint の保護機構を実装し、手順改善の区分Aの自律適用を解禁する
3. **フェーズ3(ステップ3+Level 4要素の部分導入)**: 機能特性に応じた下位層検証(HTTP層、State-Diff、メタモルフィック、異常注入)を導入し、差分検知トリガー・self-healing(人間承認付き)・AI一次失敗分析で閉ループ化する。人間の役割を「項目レビュー」から「品質目標の定義とAI成果物の監督」へシフトさせる
