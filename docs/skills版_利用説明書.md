# skills版 利用説明書

PMS 回帰テスト作成の手順書を、GitHub Copilot と Kiro の skills として使えるようにした一式の説明書です。

- **第1部 使う人向け** — 回帰テストを作るメンバーが読む部分です。10分で読めます
- **第2部 管理者向け** — 導入・手順書の改訂・人の判断が必要な場面の対応をする人が読む部分です

手順版: `proc-v017`(2026-10-07)

---

# 第1部 使う人向け

## 1. 何ができるか

AIに対象の機能を伝えるだけで、次のことを手順書どおりに進めてもらえます。

1. その機能の基本動作のシナリオを作る
2. 実際の画面を操作して確かめ、記録する
3. その記録から、AIを使わずに毎回同じように動く回帰テスト(Playwright)を作る

手順書を読んだり、手順書をAIに渡したりする必要はありません。

## 2. 準備

- このリポジトリを取得します(skills はリポジトリに含まれています)
- VS Code の GitHub Copilot(エージェントモード)または Kiro で、リポジトリのルートを開きます
- 作業を始める前に、他のメンバーの変更を取り込みます(`git pull`)

## 3. 使い方

チャットで `/pms-regression` に続けて依頼を書きます。覚える言い方は次の3つだけです。

| したいこと | 書き方の例 |
|---|---|
| 新しく回帰テストを作る | `/pms-regression 印刷実行機能の回帰テストを作って` |
| 途中から続ける | `/pms-regression F-003 の続き` |
| 進み具合を知る | `/pms-regression いまどうなってる?` |

`/pms-regression` を付けなくても、依頼の内容からAIが自動で選ぶことがあります。確実に使うには付けてください。

### 対象の決め方

- **1回の依頼は1〜2機能まで**にします。大きすぎるとAIが分割を提案します
- 正常な基本操作だけが対象です。「異常系も」「全パターン」などを頼んでも、AIは確認のために止まります(異常系などは台帳に記録され、あとの段階で扱います)
- **シナリオを何から作るか**は、依頼の書き方で選べます。何も書かなければ、マニュアル・仕様書から作ります

  | 作り方 | 書き方の例 |
  |---|---|
  | マニュアル・仕様書から(既定) | `/pms-regression 印刷実行機能の回帰テストを作って` |
  | 既存のテストスクリプトをもとに | `/pms-regression 既存の手順書 docs/印刷_回帰テスト.xlsx をもとに、印刷実行機能の回帰テストを作って` |
  | 新しく実装した機能の仕様書から | `/pms-regression 新機能の一括印刷の仕様書 docs/一括印刷_機能仕様_v1.0.docx からテストを作って` |

  AIは選んだ作り方を最初に1行で伝えます。どの作り方でも、できあがるシナリオ・記録・テストコードの置き場所と書式は同じです。1本の流れの途中で作り方は変えられません(別の作り方で作り足すときは、新しく依頼します)。**新機能の仕様書から作るときは、先にその機能を検証環境(ゴールデンイメージ)に入れておいてください。** 入っていないと、AIはシナリオを作らずに止まります
- 以前に人が作ったテストスクリプト(手動テストの手順書、過去の自動テストなど)があれば、依頼に所在を添えてください(例: `/pms-regression 印刷実行機能の回帰テストを作って。既存の手順書 docs/印刷_回帰テスト.xlsx も参考にして`)。AIはマニュアル・仕様書と同じく**参考**として読みます。書かれた操作や結果をそのまま正解にはせず、実際の画面で確かめます。食い違いがあれば記録に残し、管理者が判断します

## 4. 1本の流れ

```
あなた: /pms-regression 〇〇機能の回帰テストを作って
  AI : シナリオを作る(フロー番号 F-xxx が付く)
  AI : 「シナリオができました。端末で node tools/pms/pms.mjs run --flow F-xxx を実行してください」 ← proc-v018 以降

あなた(端末): node tools/pms/pms.mjs run --flow F-xxx          ← 端末で進める(既定)
  進行役: 前提状態の準備と画面での確認を、カードごとに新しいAIのセッションで行い、報告書まで作る

 ※ チャットで進めるときは、端末の代わりに次のようにします(proc-v019 以降)
あなた: (チャットのエージェントを pms-runner に切り替えて)F-xxx を進めて
  AI : カードを1枚ずつ別のAI(サブエージェント)に行わせ、1枚ごとに1行で知らせる
  AI : 「終わりました。エージェントを元に戻して『F-xxx の続き』と伝えてください」

あなた: /pms-regression F-xxx の続き
  AI : 記録を検査して「終わりました。新しいチャットで『F-xxx の続き』と伝えてください」 ← ここで必ず止まる

(新しいチャットを開く)

 ※ 動作はしたが正常に終わっていないもの(例: ジョブがエラー)があったときだけ、先に次が入ります
あなた: /pms-regression F-xxx の続き
  AI : 問い合わせ用のエージェントに聞いて、正常に終わる操作をやり直す(作業15)
  AI : 「やり直しました(解消 n件、解消せず m件)。新しいチャットで『F-xxx の続き』と伝えてください」

(新しいチャットを開く)

あなた: /pms-regression F-xxx の続き
  AI : 記録から回帰テストを作り、実行して確かめる
  AI : 「回帰テストを n 件追加しました。フローは完了です」
```

- 途中で止まるのは正常です。シナリオ作成とコード生成の間では**必ず止まる**設計になっています
- 作業の始めに、検証環境をゴールデンイメージに戻し、設定されていれば機器なども決まった状態に戻します(開始前シナリオ)。設定がなければそのまま進みます
- 検証環境の情報(PMS の URL、アカウント、複合機の IP など)が登録されていなければ、作業の始めとシナリオを作ったあとに、AIが足りない値をまとめて聞いてきます(5. の「環境の情報を聞かれたら」)。**一度答えた値は保存され、次からは聞かれません**
- 正常に終わらなかったものを問い合わせても解決しなかったときは、記録だけを残してコード生成へ進みます(管理者の確認待ちになります)
- 2回目は**新しいチャット**で頼むのがおすすめです(1回目のやり取りに引きずられず、記録だけを元にテストを作らせるため)
- 途中で中断しても、`F-xxx の続き` で再開できます(進み具合はファイルに残っています)
- シナリオを作ったあとの前提状態の準備(ログイン済みにする・テスト用デバイスを登録する など)と、画面での確認(探索)は、進行役のプログラム(`tools/pms/pms.mjs`)が「カード」に分けて行います(前提状態の準備は proc-v017、探索は proc-v018 以降)。**端末で `node tools/pms/pms.mjs run --flow F-xxx` を実行すると、進行役がカードを1枚ずつ、新しいAIのセッション(Copilot CLI か Kiro CLI)に行わせます。** AIが途中で止まっても進行役が同じカードをやり直させ、提出されたかどうかは進行役が記録で確かめます。画面の操作・記録・報告書の数値はプログラムが作るので、AIが記録を書き忘れることはありません。終わったらチャットで「F-xxx の続き」と伝えます
- `pms run` は時間がかかります(1枚の上限は既定で15分)。途中で止めたいときは Ctrl+C で止め、もう一度 `pms run` を実行すれば続きから行います。進み具合は `node tools/pms/pms.mjs status --flow F-xxx` で見られます
- **進め方は2つから選べます**(proc-v019 以降)。ふだんは**端末で進める**(`pms run`。既定)を使います。人がそばにいなくても進み、AIの会話が長くならないためです。**チャットで進める**は、チャットのエージェントを `pms-runner` に切り替えて「F-xxx を進めて」と伝える方法です。次のときに使います
  - AIの動きを見ながら、おかしければその場で止めたいとき(初めての画面を探索するとき・カードの中身を作り込むとき)
  - 途中で人の判断(環境の情報が足りない・許可が要る操作など)が要りそうで、その場で答えたいとき
  - Copilot CLI・Kiro CLI を使えないとき
- エージェントの切り替え方: VS Code はチャットの **Agent のドロップダウン**で `pms-runner` を選びます。Kiro はチャットの入力欄の行にある**エージェントの選択**で `pms-runner` を選びます。終わったら元のエージェントに戻し、`/pms-regression F-xxx の続き` と伝えます(報告書と記録の検査はそこで行います)
- チャットで進めていて止まった(「続けますか」と聞かれた・返事が途中で終わった)ときは、`pms-runner` に「続けて」と伝えれば続きから進みます。進み具合はファイルにあるので、やり直しにはなりません。どちらの進め方でも、記録・検査・報告書は同じです
- IDE でサブエージェントを使えない(`pms-runner` が一覧に出ない・別のAIを呼べない)ときは、`/pms-regression F-xxx の続き。pms-runner を使えない` と伝えてください。チャットの中でカードを順に行います(時間がかかり、長い会話になります)
- コード生成の前とフローの完了の前に、AIが記録を自動で検査します(lint)。決まりを満たしていない箇所が見つかると、「作業10で直します」などと伝えたうえで、AIが自分で前の作業に戻って直します。止まらないので、そのままで構いません

## 5. 止まって「管理者の判断が必要」と言われたら

AIは止まった理由と、誰に何を頼めばよいかを伝えてきます。その内容とフロー番号を管理者に伝えてください。判断が出たら、`/pms-regression F-xxx の続き` に**誰が何と判断したか**を添えて伝えます。

例: `/pms-regression F-003 の続き。シミュレータ再起動は、ゆうさんが SC-PRT-02 に限って許可`

使い始めのころ(ログインの仕組みがまだテストコードにないうち)は、作業の開始時に検証環境をゴールデンイメージへ戻したあと、AIが「PMS の画面にログインできることを確かめてください」と言って止まります。管理者に確認してもらい、`/pms-regression F-001 の続き。ログイン確認済み(ゆうさん)` のように伝えてください。ログインの仕組みができたあとは、AIが自動で確かめるので止まりません。

記録の検査(lint)で、AIがやり直しても直らない問題が残ったときも止まります。伝えられた内容を管理者に伝えてください。

カードで、AIが同じカードを何度やっても合格しなかったとき、またはカードの範囲で判断できなかったときは、`pms run` が「カード C-xxxx は人間の確認待ちです: (理由)」と出して止まります(STOP。終了コード 3)。内容を管理者に伝えてください。そのカードを後回しにして残りを進めてよければ、**もう一度 `node tools/pms/pms.mjs run --flow F-xxx` を実行します**(残りのカードを続け、そのカードは報告書に載ります。探索のステップのカードなら、同じシナリオの後のステップも後回しになります)。管理者が原因を直してそのカードをやり直させるときは、`node tools/pms/pms.mjs reopen --flow F-xxx --card C-xxxx` を実行してから `pms run` を実行します。チャットの `pms-runner` で進めている場合は、`pms-runner` が同じ文を伝えて止まります。後回しでよければ `pms-runner` に「続けて」と伝えます(やり直させるときは、先に `reopen` を実行します)。`pms-runner` も使えずチャットの中でカードを行っている場合は、`/pms-regression F-xxx の続き。C-xxxx は後回しでよい(ゆうさん)` のように伝えます。

`pms run` が報告書を作ったあとの記録の検査(lint)で直すところが見つかったときも止まります(「lint 止まり」)。チャットで `F-xxx の続き` と伝えると、作業10が指摘を直します。

作業の始めの準備(開始前シナリオ。例: 機器のゴールデンイメージ復元)が失敗したときも、作業を始めずに止まります。伝えられた内容を管理者に伝え、直ったら `F-xxx の続き` に対応した人と内容を添えて伝えてください。

次のものは止まりません。完了時に件数が伝えられるだけなので、そのままで構いません。

- 管理者の確認待ちの項目(期待どおりか AI が判断できなかったもの)
- 外部操作(画面以外の操作)の準備待ちで保留したシナリオ
- 禁止操作リストに当たるため保留したステップ
- 手順の改善のための記録

### 環境の情報を聞かれたら

「検証環境の情報が足りません。次の値を教えてください」と止まったときは、聞かれた値を答えて `/pms-regression F-xxx の続き` と伝えます(例: `/pms-regression F-003 の続き。複合機Aの IP は 192.0.2.10、管理者アカウントは admin`)。管理者の判断は要りません。

- 答えた値は設定ファイル(`config/environments.json`)に保存され、次のフローからは聞かれません。**パスワードなどの秘密情報は各自の `config/environments.local.json` に保存され、git には入りません**
- パスワードをチャットに書きたくないときは、自分で保存してから「続き」と伝えても構いません: `node tools/env/env.mjs set <キー> -`(値を入力して Enter、Ctrl+D。Windows は Ctrl+Z → Enter)
- その環境にない機器(例: 複合機がない)を聞かれたら「この環境にはない」と答えてください。AIはその機器を使うステップを保留にして記録します
- URL や IP が変わったときは、`/pms-regression 複合機Aの IP が 192.0.2.20 に変わった` のように伝えれば保存し直します

### 禁止操作のため保留したものがあると言われたら

シナリオ作成が終わったとき、「禁止操作リストに当たるため保留したステップが n件あります」と伝えられることがあります。管理者が禁止操作リストを見直した場合でも、**そのまま `F-xxx の続き` と伝えるだけ**で構いません。コード生成の前に、リストが変わったかどうかをAIが自動で確かめ、変わっていれば保留したステップを先にやり直します(やり直しのあと、もう一度止まります)。リストを直したことをAIに伝える必要はありません。

## 6. してはいけないこと

- `procedure/` と、`.github/skills/pms-*`・`.kiro/skills/pms-*` のファイルを**編集しない**(手順書です。変更は管理者が行います)
- AIが作った成果物の先頭にある `review_status` を書き換えない(レビューした管理者が書き換えます)
- AIに「期待結果を直して」「比較を緩めて」と頼まない(不具合を見逃すテストになります。おかしいと思ったら管理者へ)
- コード生成(2回目)の途中で、AIに頼まれても画面を手で操作してデータを作らない(テストコードが作らないデータに頼ったテストは、環境を戻したあとに失敗します)
- `config/environments.local.json`(パスワードなどを保存した各自の設定)をコミットしない・他の人に渡さない(`config/.gitignore` で git に入らないようになっています)
- 前提状態の準備の途中で、`work/<機能>/exploration/setup-log.yaml`・`act-log.jsonl`・`work/_flows/F-xxx/queue.json` を手で直さない(進行役のプログラムが書く記録です)

## 7. 一式の構成

```

    00_common.md                  既定(全作業に適用)。lint の規則の一覧もここ
    vocab.yaml                    統制語彙。手順版 meta.procedure_version もここ
    pipeline.dot                  実行順序・分岐・停止点
    stages.md                     作業ごとの手順(§01〜§40)と付録A〜G
    methods/                      シナリオ策定方式(シナリオを何から作るか)。1方式1ファイル
    templates/                    記入用テンプレート 90〜95 の原本
    router/SKILL.md               入口 skill(pms-regression)の原稿。唯一の手書き skill

  tools/pre-stage/

    test/run-scenarios.test.mjs   そのテスト(node --test)
  config/
    pre-stage-scenarios.sample.json  開始前シナリオの設定例(使うときは pre-stage-scenarios.json にコピー)
    environments.sample.json      検証環境の情報の設定例(読まれない。実際の設定は tools/env/env.mjs が作る)
    .gitignore                    各自の設定 environments.local.json・pms.json を git に入れない
  tools/env/
    env.mjs                       検証環境の情報(接続先・アカウント)の読み書き(Node.js のみ)

  tools/checks/
    prohibited-ops.mjs            禁止操作リストの記入状態・版の取得と、コード生成前の照合(Node.js のみ)

  procedure/schemas/              カードの出力の形(JSON Schema)と stage10-context.json の形。正本の一部
  tools/pms/

    README.md                     進行役の仕様(データの形・検査・設定・AI の CLI の呼び出し)
    lib/ test/ test-support/      その部品とテスト(node --test。playwright-cli と AI の CLI は偽物に差し替える)
  config/pms.sample.json          進行役の設定例(使うときは pms.json にコピー。pms.json は git に入れない)
  tools/lint/
    lint.mjs                      lint のランナー。実装済みの規則を1コマンドで実行する(Node.js のみ)
    lib/ rules/                   ランナーの部品(YAML・Markdown の読み取り、規則の実装)
    test/lint.test.mjs            ランナーのテスト(node --test)
  tools/git-hooks/
    pre-commit                    コミットの前の lint(手順書と skills の一致)。有効にする手順は 8. の4
  work/_common/
    prohibited-operations.md      禁止操作リスト(未記入のものを初期配置。記入は管理者)
  .github/skills/pms-*/           生成物(Copilot 用)。直接編集しない
  .kiro/skills/pms-*/             生成物(Kiro 用)。直接編集しない
  .github/agents/pms-card-*       生成物(カードの種類ごとのエージェント。Copilot 用)。直接編集しない
```

生成される skill は8つです。

| skill | 中身 | 起動 |
|---|---|---|
| `pms-regression` | 入口。依頼とフローの記録から次の作業を決める | 使う人が起動 |
| `pms-01-kb` | §01 知見蓄積 | 入口から(管理者の指示時) |
| `pms-02-nd` | §02 非決定値カタログ抽出 | 入口から(カタログがないとき自動) |
| `pms-10-explore` | §10 シナリオ生成と探索(禁止操作の再判定を含む)。シナリオ策定方式の方式ファイルを同梱 | 入口から |
| `pms-15-health` | §15 健全性の是正(問い合わせと操作のやり直し) | 入口から(作業10で健全性シグナルが出たとき) |
| `pms-20-codegen` | §20 回帰テストコード生成 | 入口から |
| `pms-30-catalog` | §30 状態カタログ案生成 | 入口から(管理者の指示時) |
| `pms-40-improve` | §40 手順改善 | 管理者が別セッションで起動(Copilot では自動起動しない) |

作業ごとの skill の中身は、`SKILL.md`(stages.md の該当節と読み込み指示)と `references/`(00_common.md・vocab.yaml・参照付録・記入用テンプレート)です。これは、これまで手で組み立てていた「00_common.md + vocab.yaml + stages.md の該当節と参照付録」そのものです。`pms-10-explore` には、加えて `references/methods/` に全方式の方式ファイルが入ります(AIはフローの記録が指す1つだけを読みます)。`kb/00_索引.md` と flow.md は作業場所のデータなので同梱せず、skill の起動時に読ませます。

加えて、カードの種類ごとのエージェント(`pms-card-setup-build` など7つ)と、チャットで進めるときの入口のエージェント `pms-runner` を、Copilot 用(`.github/agents/`)と Kiro 用(`.kiro/agents/`)に生成します(正本はどちらも `procedure/cards/agents.yaml`)。カードのエージェントは、`pms run` がカードごとに起こすセッションと、`pms-runner` が呼ぶサブエージェントの両方で使い、本文はどれも「カードを読み、指示どおりに行い、提出する」という短い指示です。`pms-runner` の本文は「`pms next` を呼び、出たカードをカードのエージェントに渡し、また `pms next` を呼ぶ」という5行の手順だけで、呼べるのはカードのエージェントだけです。

## 9. 手順書を改訂する

手順書を変えるときは、**必ず正本(`procedure/`)を直して再生成します。** skills を直接直すと、次の生成で消え、`--check` でも検出されます。

1. 正本を直す(自分で直す、または新しいセッションで `/pms-40-improve` に箇所と内容を特定して指示する)
2. `procedure/vocab.yaml` の `meta.procedure_version` を1つ上げる(例 `proc-v005` → `proc-v006`)
3. `procedure/docs/000_overview.md` の改訂履歴に記録する(AIへの指示による改訂は、指示の原文を転記する)
4. 生成して検査する
   ```
   node tools/build-skills/build-skills.mjs
   node tools/build-skills/build-skills.mjs --check
   ```
   lint の規則を実装・変更したときは、あわせて `node tools/lint/lint.mjs --list`(00 の lint 表と実装が一致しているか)と `node --test tools/lint/test/lint.test.mjs` を実行します(検証環境の情報の実行体を変えたときは `node --test tools/env/test/env.test.mjs` も)
5. 正本と生成物を同じコミットに含め、版と同じ名前のタグを付ける
6. **配るのはフローの切れ目で。** 実行中のフローがあるときに取り込むと、1つのフローの途中で手順版が変わります。メンバーには「実行中のフローを完了してから取り込む」ように伝えます

生成スクリプトは次のときにエラーを出し、何も書き出しません。

- `stages.md` の本文が参照している付録・テンプレートが、その節の「参照付録」「参照テンプレート」の行にない
- 保護ブロックの目印が閉じていない・入れ子になっている、または生成物の保護ブロックが正本と一致しない
- skill名・説明の書式が skills の仕様(英小文字・数字・ハイフン、説明は1024文字以内)に合わない

skill を追加・改名するときは `procedure/skills.config.json` を直します。何を同梱するかは `stages.md` の各節の「参照付録」「参照テンプレート」の行が決めます。

CI やコミット前の検査に `node tools/build-skills/build-skills.mjs --check`(または lint のランナー全体)を入れておくと、生成物の手編集や再生成し忘れを防げます(lint `skills_in_sync`)。

**禁止操作リストは手順書ではありません。** 記入・書き換えに版の更新や再生成は不要で、いつ書き換えても構いません。書き換えると、禁止操作で保留していたステップがあるフローでは、次のコード生成の前に照合で検出され、作業10がそのステップを判定し直します。

## 10. lint を実行する

lint は、各作業の成果物(status.yaml・探索記録・セットアップ記録・台帳・KB)が手順書の決まりを満たしているかを機械的に確かめる検査です。**AIの「DoD を満たした」という自己申告に頼らず**、セットアップの抜けや blocked の記録の抜けを見つけるために使います。規則の一覧は 00_common.md ■lint の表で、実装済みの規則には「実装:」が書いてあります。

```
node tools/lint/lint.mjs --flow F-003 --stage 10    作業10の成果物を確かめる(作業15・コード生成に進む前)
node tools/lint/lint.mjs --flow F-003 --stage 15    作業15の成果物を確かめる(コード生成に進む前)
node tools/lint/lint.mjs --flow F-003 --stage 20    作業20の成果物を確かめる(フローの完了時)
node tools/lint/lint.mjs                            全フローの成果物をまとめて確かめる
node tools/lint/lint.mjs --list                     規則の一覧と実装状況
```

- 結果は規則ごとに `OK` / `NG` / `--`(未実行)で出ます。`NG` の下に、どのファイルの何が問題かが出ます
- **ERROR が1件でもあれば、次の作業に進めません**(00 ■lint)。作業10の成果物で ERROR が出たら、`/pms-regression F-003 の続き` の前に、指摘の内容をAIに伝えて作業10で直させてください(例: 「lint の requires_covered で S-DEVICE-REGISTERED が setup-log にないと言われた。作業10で整備して記録して」)
- 終了コードは 0 = ERROR なし / 1 = ERROR あり / 2 = lint を実行できない(引数の誤り、正本が読めない等)。スクリプトや CI から使うときは `--json` で結果を機械可読にできます
- `env_value_leak` は、パスワードなどの秘密情報の値が記録やテストコード、skills(`.github/skills/`・`.kiro/skills/`。proc-v020 以降)に書かれていないかを確かめます(各自の `config/environments.local.json` の値を探すので、その値を知っている各自の環境で意味を持ちます。指摘には値そのものは出しません)。`env_value_hardcoded`(WARNING)は、テストコードに URL などの接続先が直接書かれていないかを確かめます
- `env_restored`(復元の記録の検査)は PowerShell と skill `restore-golden-image` が必要です。どちらかがない環境では「未実行」と出ます(ERROR にはしません。ERROR として扱いたいときは `--strict`)

**lint はいつ実行されるか**(00 ■lint 実行の契機)。管理者が毎回手で実行する必要はありません。

| いつ | 誰が | 問題があったとき |
|---|---|---|
| 作業10・15・20の完了報告の前 | その作業のAI | AIが直して再実行する。直せないものは報告書 §6 に書く |
| 作業10のあと(作業15・コード生成の前) | 入口 skill(と作業20) | 先に進まず、作業10に戻って直す(止まらない) |
| 作業15のあと(コード生成の前) | 入口 skill(と作業20) | コード生成に進まず、作業15に戻って直す(止まらない) |
| フローの完了の前 | 入口 skill | フローを完了にせず、作業20に戻って直す(止まらない) |
| コミットの前 | pre-commit フック | コミットを止める(手順書と skills の一致だけを見る) |

- 前の作業に戻って直すのは、同じ場所で1回までです。**戻っても直らないときは止まり**、「記録の検査で、やり直しても直らない問題が残っています」と伝えられます(11. の表)
- 「手順書と skills が一致していない」と言われたら、正本から skills を再生成してコミットしてください(9. の4)
- 管理者が手で実行するのは、状況を確かめたいときと、止まった原因を調べるときです

## 11. 人の判断が必要な場面

## 12. 複数人で並行するときの注意(暫定の運用)

手順書は1人で順に進める前提で書かれています。並行する場合の決め事は `000_overview.md` §5 の未確定事項に残してあります。決まるまでは次の運用を勧めます。

- **フロー番号の重なり**: フローを始める前に `git pull` する。重なったら、後から取り込んだ側の番号を振り直してからフローを始める(入口 skill も開始前に一言確認します)
- **共有の台帳**(申し送り・外部操作の需要・手順の改善・KB 索引・非決定値カタログ): 行の追記だけにして、既存の行は書き換えない。マージで衝突したら両方の行を残す。連番が重なったら後から取り込んだ側を振り直す
- **テスト環境**: 探索は環境にデータを書き込むため、**1人1台の VM** を勧めます。同じ VM を使う場合は、同時に探索しない(特に非決定値カタログの観測中)
- **手順版の配布**: 作業40・手順の改訂は、全員の実行中のフローが完了している時期に行う。または配布日を決め、その日以降に始めるフローから新しい版を使う

## 13. 既知の制約

- skills の仕組みは Copilot・Kiro ともに比較的新しく、仕様が変わることがあります。動作確認(8. の13)は、ツールの更新後にも行ってください
- 依頼の内容による自動起動は確実ではありません。使う人には `/pms-regression` を付けるよう案内してください
- 作業 skill は `references/` のファイルを読む指示を持っていますが、実際に読むかはAIに依存します。8. の13で確かめてください
- lint は42規則のうち20規則を実装済みです(`node tools/lint/lint.mjs --list`)。`explore_act_linked`(探索の記録と操作の記録の一致)・`requires_covered`(セットアップの抜け)・`setup_steps_recorded`(セットアップの操作列とロケータの抜け)・`act_log_linked`(セットアップの記録と操作の記録の一致)・`phase_a_queue_complete`(前提状態の準備のカードの終わり)・`requires_in_state_set`(初期状態セットにない状態)・`blocked_recorded`(blocked の記録の抜け)・`health_recorded`(健全性シグナルの記録)・`env_value_leak`(秘密情報の書き込み)・`env_value_hardcoded`(接続先の直書き)・`status_yaml_valid`・`procedure_version_present`・`operation_registered`・`ext_demand_linked`・`verdict_enum`・`reason_code_enum`・`no_temp_locator` と、既存の `skills_in_sync`・`env_restored`・`prohibition_recheck` です。作業20の突合・生成コードの静的検査・保護ブロックの検査(`protected_unchanged`)などは未実装です
- pre-commit フックが検査するのは作業ツリーの内容です。正本を直して再生成したら、再生成した skills も同じコミットに含めてください。また、フックは各自が有効にする必要があります(8. の4)
- lint は、成果物の YAML を簡易的なパーサで読みます。アンカー・エイリアス・タグは使えません。読めないファイルは「成果物の読み取り」の ERROR として出ます
- 検証環境の情報の秘密情報(パスワードなど)は、各自のパソコンの `config/environments.local.json` に**平文で**保存されます。ファイルの扱いに注意してください。また、AIはログインなどのためにその値を読みます(記録には書きません)。リモートコマンドのクライアント設定 `config/remote-targets.json`(Hyper-V ホスト・PMS VM の接続先)は、検証環境の情報とは別のファイルです。こちらは資格情報を参照名で持ち、値は各自のパソコンに DPAPI で暗号化して保存します(`pms-remote.ps1 cred-set`)
- 進行役(`tools/pms/`)のカードで行うのは、proc-v018 では作業10のフェーズA(前提状態の準備)とパートC(探索と報告の所見)です。工程0・シナリオの作成(パートB)・作業01・02・15・20・30は、これまでどおりチャットの skill が行います(画面操作は playwright-cli を直接使います。proc-v020 で明記)。`pms run` が起こすセッションで playwright-cli の直接の呼び出し・秘密情報の取り出し・手順書への書き込みを禁止するパターンは、CLI の実物で効くかを確かめていません(`tools/pms/README.md` 13章)。効かなくても、記録を通らない操作を含む提出は不合格になります
- `pms run` はカードごとに新しいセッションを起こすので、カードの枚数だけ AI への依頼が増えます(探索はシナリオのステップごとに1枚)。課金の数え方によっては、チャットで行うより費用がかかることがあります
- `pms run` の lint で指摘が残ったとき(lint 止まり)、指摘を直すのはチャットの作業10です(直すカードはまだありません)
- チャットで進める(`pms-runner`)ときは、IDE の道具の設定で playwright-cli の直接の呼び出しを止められないことがあります(VS Code のエージェントの道具はコマンドごとに絞れません)。直接呼んだ操作は記録に残らないため、その操作を含む提出は不合格になり、AIがやり直します(記録が誤ることはありませんが、やり直しの分だけ時間がかかります)。フックは使っていません
- Kiro の IDE で Workflows を有効にしていると、`pms-runner` がサブエージェントの終わりを待たずに次のカードを取りに行き、同じカードが二重に出ることがあります(実物で確かめていません。`tools/pms/README.md` 14章)。`pms-runner` を使うあいだは Workflows を無効にしてください
- `pms-runner` は、サブエージェントが提出したかどうかを `pms next` で確かめるので、AIが「できました」と言っても提出がなければ同じカードを出し直します。出し直しの上限(既定 3 回)を超えると「人間の確認待ち」で止まります
- 進行役は playwright-cli の出力の形(ロケータ・結果・URL の出し方)を前提にしています。テストは偽物の playwright-cli で行っており、実物の版が変わると読み取れなくなることがあります(`tools/pms/README.md` 8章。多くは `config/pms.json` で直せます)
- proc-v009 以前の版で始めたフローは、status.yaml に `environment` がなくても lint は求めません。そのフローは旧版のとおり完了させてください
- proc-v004 より前の版で始めたフローは、禁止操作リストの照合ができません(照合スクリプトが「照合できない」を返します。lint のランナーはそのフローの照合を省きます)。そのフローは旧版のとおり完了させてください

## 14. よくある質問

**Q. `stages.md` の他の節をAIに読ませたい。**
読ませないでください。作業ごとに関心を分けるための設計です(00 ■AIへの渡し方)。必要な付録が足りなければ、その節の「参照付録」の行に加えて再生成します。

**Q. skill の中身を少し直したい。**
正本を直して再生成してください。生成物を直すと `--check` で失敗し、次の生成で消えます。

**Q. 外部操作用の skill(印刷指示など)も同じ skills ディレクトリに置いてよいか。**
置いて構いません。生成スクリプトは `skills.config.json` にある skill のディレクトリだけを作り直し、他の skill には触れません。

**Q. 手順版を上げ忘れた。**
版と中身の対応が崩れ、手順改善の効果を版に結び付けられなくなります。改訂のたびに必ず上げてください(撤回も新しい版として上げます)。

**Q. 禁止操作リストが空のままだと、AIが何でも実行してしまわないか。**
リストが未記入でも、包括原則(物理資源の大量消費・復旧に人手や長時間を要する操作・テスト環境の外への影響・ゴールデンイメージで戻らない対象への変更)に当たりそうな操作は、AIは実行せずに止まって許可を求めます。VM の直接操作や DB への書き込みも、リストとは別の規約で禁止されています。危険な操作が分かっていれば、早めに表へ書いてください。

**Q. 検証環境の URL や複合機の IP が変わった。別の検証環境を使いたい。**
`node tools/env/env.mjs set <キー> <新しい値>` で保存し直します(`/pms-regression` に「複合機Aの IP が 〇〇 に変わった」と伝えても保存します)。別の環境を使うときは、その環境ID で値を登録し、`node tools/env/env.mjs use <環境ID>` で既定を切り替えるか、環境変数 `PMS_ENV` で指定します。登録されている環境とキーは `node tools/env/env.mjs envs` と `list` で確かめられます(パスワードは伏せて表示されます)。

**Q. 既存のテストスクリプトからシナリオを作ってほしい。**
「〇〇をもとに作って」と頼むと、スクリプトを主な材料にする作り方(`legacy_script`)になります。「〇〇も参考にして」と添えるだけなら、マニュアル・仕様書から作りながらスクリプトを参考にします。どちらの場合も、スクリプトの操作や期待結果をそのまま写すことはせず、手順書の決まり(1機能・正常系・代表値)に沿ってシナリオを作り、実際の画面で確かめます。スクリプトにある異常系などは台帳に記録されます。

**Q. シナリオの作り方(方式)を増やしたい。**
`procedure/vocab.yaml` の `scenario_source` に方式IDを加え、同じ名前の方式ファイルを `procedure/methods/` に7つの見出し(入力資料〜方式固有のKB・DISC)で書き、入口 skill の原稿(`procedure/router/SKILL.md`)の方式の決め方にも加えます。版を上げて再生成してください(9.)。生成スクリプトが、語彙と方式ファイルの過不足や見出しの順を検査します。方式ファイルには「どの資料からどう候補を拾うか」だけを書き、シナリオの決まり(1機能・正常系・代表値など)は §10 パートBの共通の決まりに任せます(00 ■シナリオ策定方式)。

**Q. lint で ERROR が出たが、手順書の規則の方がおかしいと思う。**
lint の規則は 00_common.md ■lint の表と各作業の DoD が仕様です。規則を直すのは手順書の改訂にあたるので、正本を直して版を上げ(9.)、実装も合わせてください。lint の実装だけを直して規則とずらすと、`--list` の表示と実際の検査が食い違います。
