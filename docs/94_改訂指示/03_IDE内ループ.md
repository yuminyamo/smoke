# 改訂指示 03 — 段3 IDE 内のループ(B1・フックなし)

- 作成: 2026-10-07 / 前提: 段2(`02_スクリプト実行.md`)が反映済み / この段で上げる版: 段2 の版 + 1
- 先に `docs/94_改訂指示/00_共通の作法.md` を読むこと

## 0. この段でやること(要約)

1. VS Code + Copilot のチャットで、`pms run` と同じことを行えるようにする。**入口のエージェント**がカードを1枚ずつ**サブエージェント**(カードの種類ごとの custom agent)に渡し、終わるたびに `pms next` を呼ぶ
2. サブエージェントが提出せずに終わったら、次の `pms next` が同じカードを出し直す(段1の規則をそのまま使う)
3. 入口 skill の「pms run 待ち」の扱いに、チャットで進める選択肢を足す
4. **フックは使わない**(段4で必要と判断した場合だけ足す)

## 1. 変更の意図

主な実行形態は B2(`pms run`)である。この段で作る B1 は**副経路**で、次の場面のために残す(docs/94 §4 提案B「B1 が B2 より優れる点」)。

- カードのテンプレートを作り込むときや、初めての画面を探索するときに、AI の動きを見ながら止められる
- 途中の人間の判断(環境情報の不足・要許可操作など)に、チャットでその場で答えられる
- Copilot CLI を使えない人・環境でも、今の使い方(チャットで「F-003 の続き」)のまま進められる

**フックを使わずに正しさを保つ仕組み**(段1・段2で入っているもの。この段では使うだけ):

| 起きうること | 止める仕組み |
|---|---|
| サブエージェントが playwright-cli を直接呼ぶ | 記録に残らないため、その連番を含む提出は不合格(`seq_missing`) |
| サブエージェントが提出せずに終わる | 入口は結果を信じず、必ず `pms next` を呼ぶ。同じカードが出し直される。上限を超えたら STOP |
| 会話が長くなり現在地を見失う | `pms` の出力の `now`・`next` で現在地を取り戻す。カードごとにサブエージェントの会話は捨てられる |
| 入口エージェント自身が止まる(継続の確認など) | 利用者が「続けて」と伝えれば、`pms next` から再開する。キューはファイルにあるので失うものはない |

この段の計測(`pms stats` の実行形態 `b1` の数値)が、段4(フック)を入れるかどうかの判断材料になる。

## 3. 作るもの

### 3.1 入口のエージェント `pms-runner`

- `build-skills.mjs` が正本から生成する(Copilot は `.github/agents/pms-runner.agent.md`)。正本の置き場所は段2のエージェントの正本に合わせる
- 呼べるサブエージェントを、段2で生成したカードの種類ごとのエージェント(`pms-card-*`)だけに絞る(`agents`)
- 自分で使ってよい道具は、端末で `pms next`・`pms status` を実行することと、サブエージェントを呼ぶことだけにする
- **本文は、どのモデルでも守れる短さにする。** 次の内容だけを書く

```
あなたはカードを配る係である。カードの作業は自分でしない。
1. `node tools/pms/pms.mjs next --flow <フローID>` を実行する
2. done なら、`pms status` の要約を利用者に伝えて終わる
3. STOP なら、出力の文面をそのまま利用者に伝えて終わる
4. カードなら、カードの種類に対応するサブエージェント(pms-card-<種類>)に、カードの本文をそのまま渡す
5. サブエージェントの返事の内容にかかわらず、1 に戻る
```

- カードの種類とサブエージェントの対応は、`pms next` の出力に入れる(入口が対応表を覚えなくてよいように)
- サブエージェントの返事を利用者に長く伝えない(1カード1行まで)

### 3.2 サブエージェント(`pms-card-*`)

段2で生成したものを、そのまま VS Code の custom agent としても使えるかを確かめる。使えなければ、同じ正本から VS Code 用を生成する。

- サブエージェントとして呼ばれたときも、エージェントに指定したモデルで動くこと(VS Code のドキュメントでは、custom agent の `model` が使われる)
- B1 では、playwright-cli を道具の設定で使用禁止にできない場合がある。そのときは提出の検査(`seq_missing`)で止まることを前提にし、カードの本文に「画面操作は `pms act` で行う」が入っていることを確かめる
- サブエージェントの環境で `PMS_RUNNER` が設定されない場合、提出の記録の実行形態は `b1` になる(段2の既定)。計測が `b1` と `b2` で分かれることを確かめる

### 3.3 Kiro

- Kiro の IDE で、入口のエージェントからカードの種類ごとのサブエージェントを呼べるかを、公式ドキュメントで確かめる
- 呼べる → Copilot と同じ形で生成する
- 呼べない → Kiro の IDE では、入口のエージェントが同じ会話の中でカードを順に行う(段1の形)と書き、利用説明書の既知の制約に載せる

### 3.4 入口 skill(`procedure/router/SKILL.md`)

- 「pms run 待ち」の行を、次の2つから選べるように書き換える。**既定は端末の `pms run`**(主な経路)
  - 端末で `pms run`(B2)
  - チャットで進める(B1): エージェント `pms-runner` に切り替えて「F-003 を進めて」と伝える(切り替え方は、VS Code・Kiro の実際の操作に合わせて書く)
- 利用者への伝え方の文面を足す(2つの選び方を1〜2行で)
- これまで「CLI が使えない環境の代わり」として作業10が同じ会話でカードを行っていた規定(段2)は、`pms-runner` に置き換える。Kiro の IDE でサブエージェントを使えない場合だけ残す

## 4. 手順書の変更

- `stages.md` §10: パートC の実行のしかたに B1 を足す(B2 を既定とし、B1 を選んでよい場面を書く)。記録・検査・成果物は B1 と B2 で同じであることを書く
- `00_common.md` ■進行役と記録の道具(pms): 実行形態の表(B2 主・B1 副・それぞれが向く場面)と、フックなしで正しさを保つ仕組み(1章の表)を書く。フックは使わないこと、使う場合は段4の判断によることを書く
- `vocab.yaml`: 必要なら実行形態の値を確かめる(段2で `b1` / `b2` を足している)
- 利用説明書: 第1部(使う人向け)に「端末で進める(既定)」「チャットで進める」の2つの進め方、第2部(管理者向け)にエージェントの生成と配置、モデルの設定、Kiro の制約

### 変えないもの

- 保護ブロック・`pipeline.dot`
- カード・検査・記録の仕組み(段1・段2のまま)
- フック(`.github/hooks/` を作らない)

## 5. テスト

- `build-skills.mjs` が入口のエージェントとカードのエージェントを生成し、`skills_in_sync` がそれらを検査すること

- 入口のエージェントの本文が、3.1 の5行の手順と食い違っていないこと(生成物の見本との比較でよい)
