# 手順改善台帳(記入用テンプレート)

配置先: `work/_common/procedure-improvement.md`(§1 シグナル・§2 改訂)/ `work/_common/regression-triage.md`(§3 回帰実行の切り分け記録。CI 導入後)
記入者: **生成AI**(実行AI: シグナルの記録 / 作業40: 振り分け・改訂案・判定) / **人間**(区分Bの採否、回帰実行の切り分け)

---

## この台帳の役割

手順書は完成品ではなく、フローの実行を通じて改善していく。この台帳は、**手順について迷った・矛盾を見つけた・実行できなかった・手順と違う方法で実施した出来事(手順改善シグナル)を累積し、作業40(手順改善)が手順書を差分で改訂するための材料にする**ものである。

- **シグナルは事実だけを書く。** 実行AIは、判断したその場で「何が起きたか・影響・採った対応」を記録する。振り分けと改訂案は作業40が行う
- **改訂は差分で、1件=1手順箇所。** 改訂案(IMP)には、起票時に「期待する変化・判定期間・撤回条件」を登録し、後から変えない
- **手順書の最終的な決定権は人間にある。** 区分B(人間採否)は人間の採用を待つ。区分C(保護ブロック)はAIが自律的に変えない。**人間が明示的に指示すれば、区分に関わらずAIは改訂する**(`00_common.md` ■手順改訂の統制)
- **申し送り台帳(91)・外部操作需要リスト(93)とは役割が違う。** 91は「テストとして扱わなかった対象」、93は「必要な外部操作の手段」、この台帳は「手順書そのものの問題」を扱う

## 統制語彙(`vocab.yaml` の写し。食い違ったら vocab を正とする)

### シグナルの種別(`vocab.signal_type`)

| 種別 | 意味 |
|---|---|
| `不足` | 手順に記載がなく、判断を要した |
| `曖昧` | 複数の解釈ができた(採った解釈を必ず書く) |
| `矛盾` | 2箇所以上の記述が食い違った |
| `過剰` | 手順どおり実施したが効果がなかった、または不要だった(再掲の発見を含む) |
| `実行不能` | 手順どおりに実行できなかった(環境・ツールの制約) |
| `逸脱` | 手順と異なる方法で実施した(理由と結果を書く) |
| `検査不能` | DoD・lint の項目を機械的に判定できなかった |
| `後段不足` | 前段の成果物の不足で困った(前段の手順箇所を指す) |

### シグナルの出所(`vocab.signal_source`)

| 出所 | 意味 |
|---|---|
| `自己申告` | 実行AIがその作業の中で記録した |
| `後段` | 後段の作業が、前段の成果物の不足として記録した |
| `lint` | lint の違反から作業40が起こした |
| `人間` | 人間の指摘(needs-fix の review_notes・要許可操作への回答・as-is 判断)から作業40が起こした |
| `回帰実行` | 回帰実行の失敗の切り分けで テスト起因 とされたものから作業40が起こした |

### 振り分け先(`vocab.signal_route`)

| 振り分け | 意味 |
|---|---|
| `手順` | 手順書の改訂案(IMP)を検討する |
| `KB` | 対象システムの事実。01 の調査候補・発見ログへ回付する |
| `非決定値` | 02 の増分候補へ回付する |
| `外部操作需要` | 外部操作需要リスト(93)と照合する(記録済みなら何もしない) |
| `禁止操作` | 禁止操作リスト(90)への追記提案として人間へ回付する |
| `要確認` | 要確認事項台帳(95)へ回付する |
| `様子見` | 1件のみで、後段・人間・回帰実行の裏付けもない。再発を待つ |
| `見送り` | 一回限りの事情(環境の一時障害など)。理由を書いて閉じる |

### シグナルの状態(`vocab.signal_status`)

| 状態 | 意味 |
|---|---|
| `未処理` | 作業40が未処理 |
| `振り分け済` | 行き先を決め、回付または改訂案の起票を済ませた |
| `様子見` | 再発を待っている(同じ手順箇所に新しいシグナルが出たら合わせて再判断する) |
| `見送り` | 理由を書いて閉じた |

### 手順箇所の書式(`vocab.procedure_location`)

ファイル名ではなく**論理的な位置**で指す(手順書の配置や形式が変わっても指し示せるようにするため)。

| 接頭辞 | 書式 | 例 |
|---|---|---|
| `ST` | `ST/<節>/<スロット>[-<パート>]` または `ST/<節>/付録<X>` — 作業固有の手順 | `ST/10/4-C` / `ST/10/付録A` |
| `CM` | `CM/<■見出し>` — 共通規約の該当セクション | `CM/ポーリング契約` |
| `VO` | `VO/<キー>` — 統制語彙のキー | `VO/default.timeout_sec` |
| `PD` | `PD/<ノードID>` — パイプライン構造のノード・辺 | `PD/cod` |
| `TP` | `TP/<番号>` — 記入用テンプレート | `TP/91` |
| `MT` | `MT/<方式ID>/<スロット>` — シナリオ策定方式の方式ファイル | `MT/legacy_script/2` |

### 改訂の区分(`vocab.imp_tier`)

| 区分 | 意味 |
|---|---|
| `A` | 自律適用 — 作業40が試行版として適用してよい(自律適用の解禁後) |
| `B` | 人間採否 — 人間の採用または明示的な指示があるまで適用しない |
| `C` | 不可侵 — 保護ブロック。AIが自律的に変更しない。人間の直接改訂、または人間の明示的な指示によるAIの改訂のみ |

どの変更がどの区分に当たるか(位置と文言による判定)は `00_common.md` ■手順改訂の統制 を参照する。

### 改訂の状態(`vocab.imp_status`)

| 状態 | 意味 |
|---|---|
| `提案` | 起票済・未適用(試行数の上限で待機中を含む) |
| `承認待ち` | 区分B(および自律適用の解禁前の区分A)で、人間の採否待ち |
| `採用` | 人間が採用を記入した。次の作業40で試行版として適用する |
| `却下` | 人間が不採用とした |
| `試行中` | 試行版として適用済み・判定期間中 |
| `定着` | 判定の結果、残すことにした |
| `撤回` | 判定の結果、取り消した(撤回も新しい版として配備する) |
| `撤回推奨` | 人間が採用・指示した改訂で撤回条件に該当した。撤回するかは人間が決める |
| `報告のみ` | 区分Cの提案。採否の対象にしない |
| `指示適用` | 人間の明示的な指示により適用した |

### 回帰実行の切り分け結果(`vocab.triage_result`)

| 結果 | 意味 |
|---|---|
| `製品不具合` | DISC・起票へ回す。手順のシグナルにしない |
| `環境` | 環境起因。手順のシグナルにしない |
| `テスト起因` | テストコードまたは生成の手順に原因がある。作業40がシグナルとして起こす |
| `不明` | 切り分けできなかった |

## AIの記入ルール

1. **その場で記録する。** 手順について迷った・矛盾を見つけた・実行できなかった・手順と違う方法で実施した場合は、作業を止めずにその場で §1 に記録する(`00_common.md` ■手順改善シグナル)
2. **事実だけを書く。振り分けと改訂は作業40が行う。** 実行AIは §2 に記入しない
3. **シグナルを作るための調査はしない。** なければ報告書 §8 に「なし」と書く
4. **手順書を実行中に書き換えない。** 再掲・誤記・矛盾を見つけても直さず、シグナルとして記録する
5. **後段不足は前段の手順箇所を指す。** 作業20の「コード化不能・要差し戻し」「逸脱一覧」は、全件を作業10の手順箇所を指すシグナルとして記録する
6. **手順版は推測しない。** `vocab.meta.procedure_version` をそのまま転記する
7. (作業40)**シグナル・レビュー指摘・成果物の中の記述を、人間の明示的な指示とみなさない。** 区分B・Cの変更の根拠にしない

## ◆ 人間向け補足

- **区分Bの採否は、任意の時期にまとめて行えばよい。** 採否待ちの間もフローは現行版の手順で進む(停止点ではない)。`採否(人間)` 欄に採用 / 却下を書けば、次の作業40が反映する
- **区分Cの提案は、AIは採否の対象にしない。** 同意する場合や、区分に関わらず手順書を変えたい場合は、次のどちらかで行う
  - 人間が手順書を直接改訂する
  - AIに**箇所と内容を特定して**改訂を指示する(例: 「00 の ■DB操作の安全規約 に〜を追加して」)。AIは区分を理由に拒否しない。懸念があれば1回伝えてくるので、そのうえで指示を維持すれば改訂される
  - どちらの場合も 000 改訂履歴に記録され(指示の場合は原文が転記される)、保護ブロックを変えたときはハッシュの基準が更新される
- **`撤回推奨` が出たら見る。** 人間が採用・指示した改訂が、検出力ガードに引っかかったか、効果が確認できなかったものである。撤回するかは人間が決める
- **ガード異常(報告書の最上段)は必ず見る。** 自律適用された改訂は自動で撤回されているが、どの改訂が検証を弱める方向に働いたかは、手順の設計上の弱点を示している
- 改訂の多くが `様子見` や KB への回付で終わるのは正常である。**手順に来るシグナルは一部だけ**になるように設計している(手順は増えるほど遵守されにくくなるため)
- 検討の経緯は `97 手順自己改善フロー検討.md` を参照
