# フローの再実行手順(同じ機能の回帰テスト作成をやり直して、改善の効果を確かめる)

手順書の改善や KB の蓄積をしたあとに、**すでに回帰テストを作った機能で、作成をもう一度最初から行い、前回と比べる**ための手順である。

- 読む人: 回帰テスト作成を進めているメンバーと、手順の改善を確かめたい管理者
- 前回の成果物があると、作業10の資産棚卸し(T1)が前回の fixture・ページオブジェクトをそのまま流用するので、改善の効果を確かめられない。そこで前回の成果物を**消さずに退避**してから、新しいフローでやり直す
- 例は「ユーザー管理(F-001・機能コード USR)をやり直す」場合。フローIDと機能コードは読み替える

---

## 1. 全体の流れ

| # | すること | 章 |
|---|---|---|
| 1 | やり直してよい状態かを確かめる | 2 |
| 2 | 前回の成果物を退避する(`tools/flow-reset`) | 3 |
| 3 | 新しいセッションで、前回と同じ依頼をする | 4 |
| 4 | 前回と比べる | 5 |
| (必要なら) | 退避を取り消す | 6 |

---

## 2. やり直してよい状態かを確かめる

- やり直すフローが**完了(`done`)か中断(`suspended`)**であること。作業中のフロー(`open`・`in-progress(…)`)は退避できない
- 手順の改善(`procedure/`)・KB(`kb/`)の更新が、作業場所に取り込み済みであること(`git pull` など)
- 同じ機能コードを対象にした他のフロー(再探索フローを含む)があれば、それも一緒に退避する(`work/<機能コード>/` を共有しているため。ツールが止めて教える)

---

## 3. 前回の成果物を退避する

まず、何が退避されるかを確かめる(何も変わらない)。

```
node tools/flow-reset/flow-reset.mjs --flow F-001
```

表示を確かめたら、`--apply` を付けて実行する。

```
node tools/flow-reset/flow-reset.mjs --flow F-001 --apply
```

退避先は `work/.archive/<日時>-F-001/`。リポジトリ内のパスを保ったまま移すので、前回の成果物はそこで読める(lint・pms はドットで始まるディレクトリを読まないので、やり直しには影響しない)。

### 退避するもの・台帳から外すもの

| 対象 | 扱い | 理由 |
|---|---|---|
| `work/_flows/F-001/`(キュー・カード・提出の記録) | 退避 | 新しいフローの記録と混ざらないように |
| `work/USR/`(シナリオ・探索記録・作業20の報告) | 退避 | 作業10が前回のシナリオ・setup-log を流用しないように |
| `tests/specs/usr/`・`traceability/USR-matrix.md` | 退避 | 作業20が作り直す |
| `tests/` 全体・`playwright.config.ts` | **他のフローの成果物が残らないときだけ**退避 | 共有のテスト資産(ログインの fixture・ページオブジェクト・起動確認テスト)も前回の成果物。他の機能のフローが残るときは、そのテストが使うので残す |
| 申し送り台帳の行(発生元が F-001) | 外す | やり直しで同じ判断が出るかを確かめるため |
| 状態需要リスト・外部操作需要リストの行(要求元がすべて外した申し送り) | 外す | 同上。作業02など他の要求元がある行は残す |
| フロー台帳の F-001 の行 | **残し**、備考に退避先を書く | フローIDは指標(`work/_improve/metrics.md`)・KB・品質評価(`work/_assess/`)から参照されているため。やり直しは次の番号の新しいフローになる |

`--apply` は退避の前に、次の2つを退避先に保存する。

- `_ledgers-before/`: 編集前の台帳(フロー台帳・申し送り台帳・状態需要リスト・外部操作需要リスト)
- `_baseline/pms-stats-F-001.md`: 前回のカードの合格率と記録の充足率(`pms stats`。退避すると集計できなくなるので先に取る)

### 残すもの

KB(`kb/`)・発見ログ(`logs/`)・非決定値カタログ(作業02)・機能一覧・禁止操作リスト・手順改善台帳・品質評価(`_assess`)・手順改善(`_improve`)。これらは「改善の側」なので残す。`testid-requests.md` は行ごとの発生元が分からないので残す(やり直しで同じ依頼が追記されることがある)。

### 表示に「KB に残る参照」が出たら

KB の記述が、退避したファイル(例 `tests/pages/UserListPage.ts`)や外した ID(例 `SD-001`)を指している。KB は変えない。やり直しの探索では「参照先がない」ことになるが、KB の知見(操作のこつ)そのものは使える。前回の実装をそのまま写させないためにも、そのままでよい。

---

## 4. 新しいセッションで、前回と同じ依頼をする

1. **新しいチャットのセッション**を開く(前回の経緯を持ち込まないため)
2. 前回の依頼文を、退避先の `work/.archive/<日時>-F-001/work/_flows/F-001/flow.md` の「領域指示(人間の指示原文)」からそのまま写して、`/pms-regression` に伝える
3. 範囲の絞り込みなどを聞かれたら、同じ flow.md の「補足制約」に書かれた前回の答えと**同じ答え**をする(条件をそろえるため)
4. あとは通常のフローと同じ(作業10の完了で止まる → 「続けて」で作業20へ)

新しいフローは `F-002`(次の番号)・`flow_seq=subsequent` になる。前回と次の点が違う。

- 機能一覧(`feature-list.md`)の確定と、非決定値カタログの初期作成(作業02)は行わない(残してあるものを使う)
- ゴールデンイメージへの復元は、作業10・作業20の開始時にいつもどおり行われる(PMS のデータは前回の影響を受けない)

---

## 5. 前回と比べる

| 見るもの | 前回 | 今回 |
|---|---|---|
| カードの初回合格率・不合格の区分・記録の充足率 | `work/.archive/<日時>-F-001/_baseline/pms-stats-F-001.md` | `node tools/pms/pms.mjs stats --flow F-002` |
| 品質評価(作業35) | `work/_assess/QA-001/report.md` | 新しいセッションで `/pms-35-assess` を起動し「F-002 を評価して」 |
| 指標の推移(再発見率・lint ERR・flaky など) | `work/_improve/metrics.md` の F-001 の行 | 次の作業40で F-002 の行が足される |
| 報告書(手順改善シグナル・申し送りの件数など) | 退避先の `work/USR/exploration/report.md`・`work/USR/codegen/report.md` | `work/USR/` の同じファイル |

比べるときは、手順版が違うこと(前回は flow.md の `procedure_version`、今回は新しい flow.md)を併せて書いておく。

---

## 6. 退避を取り消す(やり直しを始める前だけ)

新しいフローを**まだ始めていない**ときだけ、元に戻せる。

1. 退避先の `work/`・`tests/`・`traceability/`・`playwright.config.ts` を、リポジトリの同じ場所へ戻す
2. `_ledgers-before/` の4つの台帳を元の場所(`work/_flows/00_フロー台帳.md`、ほかは `work/_common/`)へ上書きで戻す
3. 退避先のディレクトリを消す

新しいフローを始めたあとは、台帳に新しい行が足されているので上書きで戻さない。前回の成果物は退避先で読むだけにする。
