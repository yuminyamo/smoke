### AIへの渡し方(skills)

```
<作業>の実行時 = 00_common.md + vocab.yaml + stages.md の §<作業> と参照付録 + kb/00_索引.md
```

この組み立ては、**生成スクリプト(`tools/build-skills/build-skills.mjs`)が作業ごとの skill として行う。** 人間は組み立てず、入口 skill(`pms-regression`)に依頼を伝えるだけでよい。`kb/00_索引.md` と flow.md は作業場所の実データなので同梱せず、skill の起動時に読ませる。

| skill | 作業 | 起動 |
|---|---|---|
| `pms-regression` | 入口。依頼と flow.md・status.yaml から次の作業を決める | 利用者が使う |
| `pms-01-kb` / `pms-02-nd` / `pms-10-explore` / `pms-20-codegen` / `pms-30-catalog` | §01 / §02 / §10 / §20 / §30 | 入口 skill から |
| `pms-40-improve` | §40 | 管理者が別セッションで起動(Copilot では自動起動しない設定) |

統合したのは**保守の単位**であって、**実行時の投入単位ではない**。作業40は、これに加えて改訂対象の手順箇所を含む節を正本から読む。

**skills は生成物であり、直接編集しない。** 手順を変えるときは正本を直し、版を上げ、生成スクリプトで再生成して、正本と skills を同じコミットに含める。`--check` で生成物と正本の一致を検査できる(lint `skills_in_sync`)。

## 2. 3ステップ構成とフロー反復モデル

| ステップ | 対象 | 目的 | 網の目 | 状態 |
|---|---|---|---|---|
| **ステップ1** | E2E / シナリオ型のみ | 全機能の基本動作が通ることの保証 | 粗い | **現在の対象** |
| ステップ2 | E2E / 単発型 + シナリオ型(バリエーション) | E2Eの充実 | 中 | 未着手 |
| ステップ3 | E2E以外の手段 | 機能特性に応じた効率的・網羅的な検証 | 細かい | 未着手 |

ステップ1はさらに**単機能シナリオ**(3〜6ステップ、1機能内で完結。**現在の生成対象**)と**連結シナリオ**(制限なし。単機能シナリオの一巡後)に分かれる。種別の定義・旧称との対応は `vocab.yaml` の `test_type` / `scenario_length` に集約している。

### フロー反復モデル

ステップ1は一度に全機能を扱わず、**フロー**の反復で進める。

- **1フロー = 人間が指示した対象領域について、作業10 → 作業20 を1巡すること**
- 一度に全機能を扱わない理由: 機能が膨大であること、外部操作の skill が段階的にしか整備されないこと
- fixture・シナリオ部品・KB・非決定値カタログ・探索記録は**フロー横断で累積**し、2回目以降のフローは前回までの成果物を流用して処理コストと時間を節約する
- 進捗は `work/_flows/` でテキスト管理する。**中断・再開・別インスタンスへの引き継ぎは flow.md を読むだけで可能にする**
- **ステップ1の規則(シナリオ型のみ・正常系のみ・単機能粒度)は全フロー共通・不変。** 領域指示は範囲の指定であり、粒度規則の変更ではない
- **再探索フロー**: 外部操作の skill がなくて `blocked` になったシナリオは、人間が skill を整備したあと、再探索フローで探索し直す(下の2つ目の図)。skill の整備は需要の発生と切り離し、外部操作需要リスト(93)を見て任意の時期に行う
- **状態の追加**: 初期状態セットにない前提状態が要るシナリオ候補は、申し送り台帳(`初期状態外`)に記録すると同時に状態需要リスト(96)に提案される(フローは止まらない)。人間が採用すると、その状態は以後のフローで `requires` に使え、最初に使ったフローの作業10が fixture を実操作で整備する(下の4つ目の図)
- **禁止操作の再判定**: 禁止操作リストのために `blocked` になったステップは、人間がリストを書き換えると、次に作業20へ進む前の照合で検出され、同じフローの作業10(パートP)が判定し直す(下の3つ目の図)
- **1フローは1つの手順版で実行する。** 手順書の配備はフローの境界でのみ行う

```
人間: 領域指示 ──▶ [作業10 生成+探索] ─完了報告+status.yaml─▶ [作業20 コード生成] ─▶ 回帰テストセットへ追加
                        │                                          │
                        └── fixture・部品・KB・カタログを流用/蓄積 ──┘
                                    (フローを繰り返すほど流用率が上がる)
```

外部操作の skill がない場合の流れ:

```
[作業10] skill のない外部操作を検出 ─▶ 外部操作需要リスト(93)に記録 / 該当シナリオは blocked(フローは続行)
                                              │
                        [人間] 任意の時期に優先度を付けて skill を整備し、整備記録を記入
                                              │
                        [人間] 再探索フローを指示(需要IDを指定)
                                              ▼
[作業10 パートR] blocked シナリオを特定して探索し直す ─▶ [作業20] ─▶ 回帰テストセットへ追加
```

禁止操作リストのために blocked になった場合の流れ:

```
[作業10] 禁止操作で blocked(前提状態の整備と、blocked の手前までの記録は残す)
         status.yaml に 禁止操作リストの版(prohibited_ops.digest)と blocked_by_prohibition を記録 ─▶ 停止
                                              │
                        [人間] 禁止操作リストを見直す(AIに伝える必要はない)
                                              │
[作業20 の前] 照合スクリプト(tools/checks/prohibited-ops.mjs --compare)
         ├ 変わっていない ─▶ [作業20]
         └ 変わった ─▶ [作業10 パートP] 判定し直し、実行できるものを探索し直す ─▶ 停止 ─▶ [作業20]
```

初期状態セットにない前提状態が要る場合の流れ:

```
[作業10 パートB] 前提状態が初期状態セットにない ─▶ 申し送り台帳に 初期状態外(想定手段に SD-ID)
                                                    + 状態需要リスト(96)に提案(フローは続行。シナリオは作らない)
                                              │
                        [人間] 任意の時期に採否を記入(採用 / 不採用)
                                              │
                        [人間] 「SD-001 の状態を使うシナリオを作って」(通常フロー)
                                              ▼
[作業10 パートB] 要求元の申し送りをシナリオ候補として見直す ─▶ [フェーズA] fixture を実操作で整備(整備済)─▶ [作業20]
```

### 手順の自己改善

手順書そのものも、フローの実行結果から改善していく。**手順について迷った・矛盾を見つけた・実行できなかった・手順と違う方法で実施した出来事(手順改善シグナル)を全作業がその場で記録し、作業40(手順改善)が数フローごとに集約して、手順書を差分で改訂する。**

```
[01/02/10/20/30] シグナルを記録(後段不足・逸脱を含む) ─┐
[lint] 違反 / [人間] needs-fix・回答 / [回帰実行] テスト起因 ─┴─▶ 94 手順改善台帳
                                                                   │ lint が improvement_due を判定(当面は人間の指示)
                                                                   ▼
[作業40 別セッション] 集計 → 振り分け(多くは KB・93・95 等へ回付)→ 改訂案(差分・判定基準を事前登録)
          │                     ├ 区分A 自律適用 → 試行版を適用(版を上げる)
          │                     ├ 区分B 人間採否 → 台帳に積む(フローは現行版で進む)
          │                     └ 区分C 不可侵   → 報告のみ
          ▼
    判定期限で 定着 / 撤回 / 撤回推奨(検出力ガードに異常があれば自律適用分は即撤回)

[人間] 手順書の直接改訂、または箇所と内容を特定した指示 ──▶ 区分に関わらず改訂される(AIは拒否しない)
```

最大のリスクは「**検証を弱めることで摩擦を減らす**」方向の改善である(テストが緑のまま不具合を通す)。これを防ぐため、安全と検出力の根幹(オラクル原則・禁止操作・期待結果の書き換え禁止など13項目)を**保護ブロック**にしてハッシュで固定し、効果の判定には効率指標とは別に**検出力ガード指標**を置く(`00_common.md` ■手順改訂の統制)。

## 3. 実行順序

**実行順序・分岐・停止点は `pipeline.dot` を正とする。** 本書に表を持たない(二重管理を避けるため)。

概要だけ述べると、**本線は `10 → 20` の2作業だけ**である。`01`(知見蓄積)・`02`(非決定値カタログ)・`15`(健全性の是正)・`30`(状態カタログ)・`40`(手順改善)は本線に置かず、条件付き起動の枝とした。作業15は、作業10で健全性シグナルが出たときだけ作業10と20の間に入る(`pipeline.dot` 注記11)。解消しないことを理由には止まらず、解消しなかったものは記録を残して作業20へ進む(止まるのは、要許可操作・包括原則に当たる操作が必要になったときだけで、作業10と同じ停止点 `perm` を使う)。作業40はフローの開始時に置く(改訂をそのフローから効かせるため)。再探索フローも同じ本線を通り、作業10の中で手順(パートR)を切り替える(`pipeline.dot` 注記5)。入口 skill は、flow.md と status.yaml をこの辺の条件に当てはめて次の作業を選ぶ(注記4)。

描画: `dot -Tsvg pipeline.dot -o pipeline.svg`

**必須の停止点は3つだけである。**

| 停止点 | 理由 |
|---|---|
| 作業10の完了報告(作業20の前) | 成果物境界。AIの関心の混入を防ぐ |
| 要許可操作 / 包括原則へのエスカレーション | 行為の許可(人間の承認が必要な例外1) |
| 作業30フェーズ3のデータ変更 | 行為の許可(人間の承認が必要な例外2) |

DB不変条件の違反は自動リトライで処理せず、人間の判断へ回す(停止ではなく分岐)。**作業40は停止しない。** 手順改訂の区分Bの採否は台帳に積まれるだけで、停止点ではない。

このほか、**ログイン fixture がまだない初期に限り**、作業10・20の開始時の復元のあとで止まる。起動完了(Web UI へのログイン成功)を確かめる起動確認テストがまだないため、人間がログインを確かめる(00 ■回帰実行の環境前提)。行為の許可ではなく環境の前提の確認であり、ログイン fixture ができたあとは止まらない。

作業20の開始前の禁止操作リストの照合で再判定が必要と分かったときは、**止まらずに**作業10(パートP)へ戻る(`pipeline.dot` 注記9)。作業10はパートPのあと、通常どおり完了報告を出して止まる。

作業10・20の開始時(工程0)に、ゴールデンイメージの復元に続けて**開始前シナリオ**(機器のゴールデンイメージ復元など、設定されたテストシナリオ)を実行する(`pipeline.dot` 注記12・00 ■回帰実行の環境前提)。設定がなければ何もしない。失敗したら作業を始めずに止まり、管理者が直したら工程0からやり直す。

**lint の関所**が3つある(`pipeline.dot` 注記10・11・00 ■lint 実行の契機)。作業10のあと(作業15・20の前。照合のあと)に作業10の成果物を、作業15のあと(作業20の前)に作業10・15の成果物を、フロー完了の前に作業20の成果物を lint で検査し、ERROR があれば**止まらずに**その作業へ差し戻す。差し戻しは同じ関所で1回までで、差し戻しても直らないとき(と、手順書と skills が一致しないとき)だけ止まって人間に伝える。作業10・20は、関所の前に自分でも lint を実行して直す。

```
[作業10] … 完了前の lint(自分で直す)─▶ 停止
   └▶ [作業15・20の前] 照合 ─▶ lint(作業10の成果物)─┬ OK ─┬ 健全性シグナルなし ─▶ [作業20] … 完了前の lint(自分で直す)
                                                      │      └ あり ─▶ [作業15] … 完了前の lint ─▶ 停止
                                                      └ ERROR ─▶ [作業10 lint の指摘の修正](1回まで)
[作業15] ─▶ [作業20の前] 照合 ─▶ lint(作業10・15の成果物)─┬ OK ─▶ [作業20]
                                                          └ ERROR ─▶ [作業15 lint の指摘の修正](1回まで)
[作業20] ─▶ [フロー完了の前] lint(作業20の成果物)─┬ OK ─▶ フロー完了
                                                   └ ERROR ─▶ [作業20 lint の指摘の修正](1回まで)
[コミットの前] pre-commit フック ─▶ lint(skills_in_sync)
```

## 4. 進め方の推奨順序

1. **禁止操作リスト(90)を記入する** — 未記入のリストを `work/_common/prohibited-operations.md` に初期配置してある。**未記入のままでも始められる**(禁止操作なしとして扱い、包括原則だけが働く)。網羅は不要。明らかに危険な操作から書き始めてよい。途中で書き換えても、禁止操作で止まっていたステップは作業20の前の照合で自動的に判定し直される
2. **ゴールデンイメージの自動復元を導入する** — Hyper-V ホストの復元専用エンドポイント、外部操作 skill `restore-golden-image`、`config/golden-restore.json`、`tests/global-setup.ts`、`playwright.readiness.config.ts`。手順は復元の一式に付属の README
3. (任意)**検証環境の情報を登録する** — `node tools/env/env.mjs set <キー> <値> --env <環境ID>` で、PMS の URL・ログインするアカウント・DB の接続先などを登録する(基本キーは `vocab.env_base_keys`。例は `config/environments.sample.json`)。**登録しなくても始められる**(作業10の開始時とシナリオ生成のあとに、足りない値をAIがまとめて聞き、答えた値を保存する。一度答えた値は二度聞かれない)。パスワードなどの秘密情報は各自の `config/environments.local.json` に保存され、git に入らない
4. (任意)**知見蓄積(01)** — 最初に扱う領域の知見が乏しければ実施
5. **非決定値カタログの初期作成(02)** — 入口 skill は、カタログがなければ最初のフローの前に自動で実施する

## 34. 2026-10-08 改訂(DB への接続を `pms db` に集約)— 手順版 proc-v024

**人間の指示による改訂である。** `node tools/pms/pms.mjs run --flow F-001` が `explore.close` のカードで `STOP`(`cannot_proceed: DB不変条件の検査に必要な認証確認とSELECTを実行できなかったため。探索記録上、機器グループの説明変更手順はマニュアルに記載がない。`)になった。発生環境で調べたところ、カードの AI が DB の接続情報を確かめるために `node env.mjs get db.server` などを含むコマンドを実行し、`config/pms.json` の使用禁止 `shell(node tools/env/env.mjs get:*)` に当たって拒否されていた。人間の指示は、提案した案(`pms db` の新設とそれに合わせる改訂)で手順を直すこと。DB の認証は混合モード(Windows 認証と SQL Server 認証のどちらも使える)である。

**原因**: カードは DB を確かめるよう求めていたが、接続先とログインを知る手段がカードになかった。33.3 で「カードを行う AI は `env.mjs get` を使えないため」pms が「DB の接続」の行を作るとしたが、行に書いたのはサーバ証明書の扱いだけで、`db.server`・`db.name` の値も、ログインの方式も書かなかった。Copilot CLI の使用禁止のパターンは `--reveal` の有無を分けられないため、`get` 全体が止まっている(正本 `agents.yaml` の意図は `--reveal` だけの禁止)。また、DB のログインの方式(Windows 認証か SQL Server 認証か)が手順書と環境情報のどこにも決まっていなかった。SQL Server 認証ならパスワードが要り、[R-ENV-2] によりAIは取り出せない。理由の文の後半(マニュアルの記載)は同じカードの別の出力 `manual_gap`(R-EXP-18)の補足であり、止まった原因ではない。

| # | 修正 |
|---|---|
| 8.1 | **テスト種別を改名**: 種別B→シナリオ型、種別A→単発型、1-A→単機能シナリオ、1-B→連結シナリオ |
| 8.2 | **テスト種別の定義を新設**(旧版では括弧書きの言い換えしかなかった) |
| 8.3 | **機器操作語彙表(ホワイトリスト)を廃止し、禁止操作リスト(ブラックリスト)へ転換**。AIは操作手段を自律的に編み出してよく、禁止・要許可に該当する操作のみ実行しない。対象をAD・SMTP・PMSサーバOS等の連携システム全体に拡大。表にない操作は**包括原則**でエスカレーションする |

| 8.6 | 操作IDの表記を `DEV-OP-<連番>` から `OP-<対象略号>-<連番>` へ変更 |

**転換の理由(8.3)**: ホワイトリスト方式は、人間が語彙表を書き切るまでAIが動けず、対象システムが広がるほど記入コストが線形に増える。実際の制約は「してよい操作の列挙」ではなく「してはならない操作」の方が圧倒的に少ないため、ブラックリスト+包括原則の方が記入コストが小さく、AIの自律性も活かせる。一方で失われる「使える操作が一覧できる」機能を 8.5 の KB T05 登録義務で補う。**リストは人間が守り(禁止)、台帳はAIが育てる(確立済み操作)**という役割分担である。

## 3. 初期設計からの主な変更点(2026-08-30時点)

※作業番号は当時の構成(①〜④、05/10分離)の表記のまま残している。現行構成は1〜4章と9章を参照。

- **3.2 シナリオ型を主軸に、単発型はステップ2へ** — 単位時間あたり最大の機能が動作していることの確認には、1本で複数機能を通過するシナリオ型が構造的に有利
