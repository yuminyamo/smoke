## 1. 事象

作業10(シナリオ生成と探索)を最後まで実施したのに、setup-log(`work/<feature_code>/exploration/setup-log.yaml`)で安定ロケータの記録が抜けていた。作業20(回帰テストコード生成)を実行したAIが抜けに気づき、作業10に差し戻した。

発生時の状況(利用者の観察):

- 実行環境は GitHub Copilot(VS Code のエージェントモード)、モデルは gpt6-luna
- 作業10の途中で2回、「長く処理しているが、続けるか、止めて指示し直すか」という確認が割り込んだ。2回とも continue を選んだ
- 2回とも、continue を選んだ直後に、それまでの途中の処理の履歴が画面で見えなくなった。文脈の要約(コンパクション)が起きたように見えたが、実際に起きたかは確かめていない

## 2. 調査の目的

手順書の改訂方針を決めるために、次の2点を事実で確かめる。

- 何が、どの形で抜けていたか
- 作業10の DoD と lint が、なぜ抜けを止めなかったか

管理側が立てている仮説は、次の7つである(Q12 で選ぶ)。

| 記号 | 仮説 |
|---|---|
| H1 | フェーズA(初期状態の準備)に「その場で記録」の規定がなく、setup-log への記録をパートCのあとにまとめて行った |
| H2 | 付録B(setup-log の書式)に補足ルールがなく、`steps` と `locator` が必須だと読み取れなかった |
| H3 | DoD に setup-log の `steps` と `locator` の項目がなく、自己点検で気づけなかった |
| H4 | lint が `steps` と `locator` の有無を見ていないため、関所を通過した |
| H5 | fixture とシナリオ部品のコードにロケータを書いたことで、記録済みと扱われた |
| H6 | 作業10の途中(continue の前後)で文脈が要約され、ファイルに書く前のセットアップ時のロケータの情報が失われた |
| H7 | 既存資産の流用(`provided`)では `steps` を書かなくてよいと解釈された |

## 3. 調査するときの制約(必ず守る)

- **読むだけにする。** 成果物(`work/`・`tests/`・`kb/`・`traceability/`)、台帳、手順書を変更しない。抜けている記録を見つけても、補わない(補うのは差し戻しを受けた作業10の役目である)
- **環境の復元(skill `restore-golden-image`)、テストの実行、画面の操作、外部操作 skill の実行をしない**
- 実行してよいコマンドは、ファイルの閲覧と検索、`git log` / `git show` / `git diff`、lint(`node tools/lint/lint.mjs`)だけとする
- ワークスペースの外にあるファイル(Q11 の Copilot の会話の記録など)は、**利用者の許可を得てから**読む。許可がなければ読まず、その設問は「判別不能」を選ぶ
- **秘密情報の値(パスワードなど)を回答に書かない。** 値が必要な場面では `<env:キー>` と書く
- 差し戻しを受けて作業10を再実施した後なら、**差し戻し前の状態**を答える。git の履歴などで差し戻し前の状態が分からなければ「判別不能」を選ぶ
- 意図(「なぜそうしたか」)は、作業10を実行したAIの自己申告ではなく、成果物に残った痕跡から答える。痕跡がなければ「判別不能」を選ぶ
- 選択式の設問は `[ ]` を `[x]` に変える。自由記入は1行以内で書く。根拠として、ファイルのパスと行番号を1つ以上書く
