# レビューと運用の観点(人間向け)

旧指示書の「◆ 人間向け補足」を集約したもの。**このファイルはAIに渡さない。** 渡すのは `00_common.md` / `vocab.yaml` / `stages.md` の該当節 / `pipeline.dot` である。

改訂: 2026-09-23 / 版: v3(手順の自己改善: §40 手順改善・手順改善台帳(94)・手順書の改訂のしかたの観点を追加。前版 v2 は同日の外部操作 skill・外部操作需要リスト・再探索フロー)

## 全体

- `00_common.md` は各作業間の**受け渡し契約**を定めるものである。成果物がこの契約を満たしていれば、後続作業は画面やドキュメントを再解析せずに機械的に処理できる、という設計意図。
- ステップ1の設計思想は「粗い網を全機能に張る」こと。網羅性はステップ2・3で上げる。**レビューでは「足りない項目」を追加させるのではなく、申し送り台帳に入っているかを確認する**のが正しい観点。
- レビューは非ブロッキングだが、**後回しにしたレビューは消えない**。パイプラインが進むほど、前段の誤りが後段に伝播した状態で発見されるようになる。工数配分の目安として、AIが出す優先レビュー推奨リストから先に見ると、同じ時間で発見できる誤りが多くなる。
- `unreviewed` のまま先へ進めた成果物が増えると、後段の失敗時に「疑うべき候補」も増える。レビュー状況の一覧(各報告書に含まれる)を見て、未レビューが集中している領域を把握しておくと切り分けが速い。
- DB不変条件は全シナリオに掛かるため、条件を1つ足すだけでカバレッジが全シナリオ分増える。**最も費用対効果の高い投資箇所**であり、優先して育てる価値がある。
- 検証手段が `DB` 単独の箇所は、UIに機能が露出していないか、露出していても確認しづらいかのどちらか。前者は仕様上の情報であり、後者はステップ3での手段見直し候補になる。理由の1文がその判別材料になる。
- 申し送り台帳の理由コード別集計が、ステップ2・3の計画の入力そのものになる(`vocab.reason_code` の `next_investment`)。
- フロー台帳を見れば、どの領域がどこまで自動化済みかが一覧できる。**領域指示の粒度は「1〜2機能」または「1ユースケース」程度が扱いやすい。** 大きすぎる指示は1フローの所要が長くなり、中断・切り分けのコストが上がる。
- フローを重ねるほど資産流用率が上がり、1フローあたりのAI処理コストは下がっていく。報告書の「流用/新規」の区別は、この効果の実測材料になる。
- 各報告書の §8 には、そのフローで記録された**手順改善シグナル**のIDが並ぶ。`曖昧` と `逸脱` は、AIが手順をどう読んだか・どこで手順から外れたかの記録であり、手順の読み違いを早く見つける手がかりになる。**AIは実行中に手順書を直さない**ので、手順の不備はここに出てくる。

### フェーズ0を廃止したことについて

旧版には各作業に「フェーズ0(パイロット)= 1〜2件通して必ず停止して報告する」があった。これは**機能バッチ駆動だった旧構成**の産物である。全機能を一度に扱う前提では、広い横展開の前に機構を確かめる必要があった。

フロー駆動に移行したことで、1回の作業単位が「1〜2機能・機能あたりシナリオ1〜2本」まで小さくなり、**作業単位そのものがパイロットの性質(小さい・やり直しが安い)を持つようになった**。フェーズ0は入れ子のパイロットになっていたため廃止した。

フェーズ0相当の動作が必要な場合は、**領域指示の側で絞る**(「印刷実行だけ」「1シナリオだけ」)。手順側に段階を作らない。

フェーズ0に相乗りしていた2つは別建てで残してある。

1. **初回フロー(F-001)の機能一覧・機能コード確定** — パイロットではなく初期化処理。`context.flow_seq=first` の条件分岐として §10 A2 に置いた
2. **未経験の機構を含むフローで1本だけ先行させる判断** — フェーズではなく通常の判断。§10 A4 に1行として置いた(停止は不要)

副次的な効果として、`pipeline.dot` から判定ノードと人間ゲートが1つずつ消え、グラフが素直になった。**残る必須の停止点は3つだけである**: 作業10の完了報告(作業20の前)/ 要許可操作のエスカレーション / 作業30フェーズ3のデータ変更。作業40(手順改善)を追加しても、停止点は増えていない。

## §01 知見蓄積

- **指示のしかたは「操作」または「機能」の粒度でよい**(例: 「複合機からジョブログを収集する操作」「料金表の設定機能」)。調査項目を列挙する必要はない。何を調べるべきかの逆算(S1)がAI側の仕事であり、その一覧が報告書の冒頭に出るので、ずれていればそこで指摘すればよい。
- **本作業は任意である。** 実施しなくてもパイプラインは回る。ただし、作業10の探索で同じことを繰り返し調べている兆候(発見ログの `再発見` が多い)が出たら、その領域について01を実施すると効率が上がる。
- **「分からなかったこと」の報告が、この作業の隠れた主成果物である。** 文書に記載がない領域が明らかになれば、それは仕様書補完のタスクリストになる。
- 蓄積された知見は自動回帰テスト以外の用途(調査、教育、仕様書補完、障害解析)でも使える。そのため**AIが読みやすい形式**(索引経由・1ファイル200行以内)と**人間が読める記述**の両立を優先している。
- KBのレビューは非ブロッキングだが、**T03(DB)とT06(待機)は後段への影響が大きい**。工数を割くならここから。
- カテゴリ拡張をAIに許しているのは、KBの分類が「格納場所」でしかないため。申し送り台帳の理由コードのように集計が計画に直結する統制語彙とは扱いを分けている。
- 発見ログの `再発見` 率が下がらない場合、KBの分類・索引・参照規約のいずれかが機能していない。その場合は §01 自体の改訂が要る(作業40の効率指標にも再発見率が入っている)。

## §02 非決定値カタログ

- このカタログは一度作れば以降のすべての作業が参照する共通資産になる。**育てる資産として扱う。**
- レビューはブロッキングではないが、**カタログの誤りは全シナリオの検出力に波及する**ため、優先レビュー推奨の上位は早めに見る価値が高い。後段で flaky が多発した場合は、切り分けプロトコルに従いカタログの強度設定を原因候補に挙げること。
- **レビューの最重要観点は「`存在のみ` に落とされた値の中に、本当は検証すべきものが混ざっていないか」。** 強度を下げるほどテストは安定するが、同時に検出力を失う。安定性を理由に検出力を捨てていないかを見る。
- 「条件依存が疑われる値」は、そのまま不具合の芽である可能性がある。特に**表示順の不定、同時刻データの扱い、丸め処理**は、後で flaky テストの原因になる。ここで潰しておくと後段が楽になる。
- 日付依存の値(月初/月末、年度境界)は3回の観測では出てこない。カタログに載らない前提で、シナリオ設計側で意識する必要がある。
- 観測回数3回は費用対効果の判断であり、重要な値については人間の判断で増やしてよい。

## §10 シナリオ生成と探索

- **レビューはブロッキングではない。** 本成果物は `unreviewed` のまま作業20が参照する。レビューは作業20と並行してよい。
- 工数が限られる場合、**優先レビュー推奨の上位から見る**。特に課金・金額に関わる期待結果、根拠が `推測(仕様未記載)` の項目、`human-check`、DISC関連。
- まず **DB不変条件の違反**を見る。シナリオが `passed` でも不変条件が落ちていれば本物の不具合の可能性が高い。1ジョブ1課金の破れは特に重い。
- **「足りない項目」を追加させないこと。** ステップ1は粗い網で正しい。追加したくなった対象が申し送り台帳に入っているかを確認するのが正しい観点。**台帳の件数が多いことは失敗ではなく設計通り。**
- `failed` / `human-check` を as-is として凍結するかは**AIに判断させない**。as-is と判断した項目に `reviewed` を付ければ、次回の作業20実行時にコード化対象へ加わる。
- `human-check` と DISC が多い領域は、シナリオ定義側の誤りが原因のことがある。scenarios.md が `unreviewed` ならそちらを先に見る方が効率がよい。
- `assertion_hint` が「決定的な検証手段なし」のステップは、作業20へ進めてもアサーションが書けない。ハーネス整備か「人間確認要」区分の維持かをここで決める。**status.yaml の `assertion_gap_items` に列挙されている。**
- 非同期待機の実測値は版を追って見ると**性能劣化の兆候**になる。DB単独検証の一覧はステップ3の手段設計の入力になる。
- 「資産流用の実績」で流用率の推移を見る。**フローを重ねても流用が増えない場合、部品化・KB反映のどこかが機能していない。**
- **KB T05 に新規登録された操作は必ず目を通す。** skill の想定外の使い方(例: skill 経由で機器の管理画面の裏口や直接API呼び出しを行っている)で実現されていないか、**実行体の呼び出しだけで操作が完結しているか**(AIの対話的な介入に頼っていないか)の確認になる。問題があれば禁止操作リストへ追記するか、skill を改修する。
- `操作手段なし` で `blocked` になったシナリオは、外部操作需要リスト(93)に需要として積まれている。レビューで足すべきものではなく、skill の整備と再探索フローで拾うものである。
- AIが包括原則でエスカレーションしてきた操作のうち、恒久的に扱いを定めるべきものを禁止操作リストへ追記していく。**リストの充実は運用しながら進める前提であり、初回から網羅する必要はない。**
- 単機能シナリオが一巡したら、蓄積したシナリオ部品を材料に連結シナリオへ進む。

## §20 回帰テストコード生成

- **レビューの入口は突合表。** 作業10の全シナリオが行として存在し、コード化/スキップの理由が追えることを確認する。本作業のレビューもブロッキングではないが、**生成されたテストコードは以後の回帰実行の基準になる**ため、突合表の「スキップ理由」だけは早めに目を通す価値がある(黙って落ちた項目がないかの確認)。
- `failed` / `human-check` の項目は、人間が as-is 判断を下すまでコード化されない。これは意図的な設計で、**不具合を回帰テストの正解として凍結しない**ための切り分けである。判断がついた分は次回の作業20実行で拾われる。
- **flaky テストはステップ1の最大の敵である。** 回帰テストは信頼されなくなった瞬間に価値を失う。flaky を「たまに落ちるもの」として放置せず、非決定値カタログか待機契約のどちらかの問題として必ず解消する。**テスト側で強度を下げて黙らせるのは最悪の対処**であり、規約で明示的に禁止している。
- red のうち「作業10の記録との乖離」は、作業10実施後に環境や画面が変わった可能性がある。作業10の部分再実行を検討する。
- 実行時間の内訳は、ステップ2以降でどこに高速化投資をすべきかの直接の入力になる。外部操作が支配的なら外部操作の削減、または操作対象ごとの直列化(`@serial-<対象略号>`)の見直し、UI操作が支配的ならDB投入セットアップの導入、が候補になる。
- 突合表に「外部操作 skill の不備」によるスキップがあれば、次のどちらかで拾う。**skill が未配備**なら、報告書に挙がった skill名で探して配備し、作業20を再実行する。**実行体がない**なら、skill を改修して外部操作需要リストに整備記録を書き、再探索フローを指示する。
- 「コード化不能・要差し戻し」と「逸脱一覧」は、差し戻しとは別に、**作業10の手順の不足を示す後段シグナル**として手順改善台帳に残る。同じ不足が複数フローで出るなら、作業10の手順(多くは付録Aの書き方)を直す材料になる。
- 生成されたテストには、生成したフローと手順版の注釈(`generated-by`)が付く。CI で回帰テストが落ちたとき、どのフロー・どの版の手順で作られたテストかがすぐ分かる。
- CIへの常設に進む際は、**突合表の生成と lint をスクリプト化してパイプラインの品質ゲートにする**ことを推奨。`00_common.md` の lint 規則がその仕様になっている。
- ステップ1のコードが揃った時点で、**「全機能の基本動作が通ること」を機械的に証明できる状態**になる。これが社内品質点検上の主要な成果物になる。

## §30 状態カタログ案生成

**一発で完成させない。需要駆動で育てる。**

1. 本作業でステップ1の実績をもとに初版を作る
2. ステップ2の項目生成で「新規状態の提案」を回収する(需要側)
3. 提案をカタログに統合し、「検証担当項目」の `未採番` を実IDに置換する

**後工程へ渡す列の抜粋**:

- ステップ2の項目生成AI → 状態ID・状態名・内容・排他・検証担当項目のみ。**整備状況・構築の骨子は渡さない**(整備難易度を理由に項目設計が歪むのを防ぐため)
- ステップ2の探索AI → 全列。特に成立確認方法・構築の骨子・整備状況が起点になる

**レビューの着眼点**:

- **出所が「探索記録」の状態は信頼してよい。文書・ソースのみを出所とする状態を先に見る**
- 確度 `推測` `確認不能` を優先的に確認する
- 「複数の項目が使うか」で不要な状態を落とす。落とした理由をログに残させる
- 排他列の対称性(AとBが排他ならBにもAが書かれているか)
- `未整備(実操作不可)` の状態は、非UI手段での整備を手配するか、その状態を使う項目を諦めるかの判断が要る
- 「解除方法: 不可」の状態は並列実行で共有されるため、専用データ割り当ての対象にする

**ソースコードを渡す際の注意**: 全量より、ロール定義・ステータス enum・ルーティング・DBスキーマ(マイグレーション)の所在を先に示す方が精度が上がる。**15年もののレガシーでは死んだ enum 値が残る。** ソースだけで確度 `確認済` にさせず画面確認を必須にしているのはこのため。

## §40 手順改善

- **起動は、当面は人間の指示でよい。** 目安は3フローごと、または同じ手順箇所へのシグナルが2件たまったとき(lint `improvement_due` を実装すれば自動で判定される)。**実行AIとは別のセッション**で起動する。モデルは同じでよい
- **最初に報告書の最上段(ガード異常)を見る。** 自律適用された改訂でガード指標(期待結果の変更・`存在のみ` 比率・`両方` 比率・改訂直後の `blocked`/`passed` の急変など)に異常が出たものは自動で撤回されているが、**どの改訂が検証を弱める方向に働いたか**は手順の設計上の弱点を示している
- **承認待ち(区分B)の採否は、任意の時期にまとめて行えばよい。** 採否待ちの間もフローは現行版で進む。台帳の「採否(人間)」欄に採用 / 却下を書けば、次の作業40が反映する。見るときは「期待する変化」と「撤回条件」が具体的か(判定できる形か)を確認する
- **lint `protected_unchanged`・`imp_tier_valid` が実装されるまでは、区分Aも承認待ちに来る。** この期間に、AIの区分判定が妥当か(Aとしたものに義務・禁止の緩和が紛れていないか)を見ておくと、自律適用を解禁してよいかの判断材料になる
- **`撤回推奨` は人間が決める。** 人間が採用・指示した改訂で、ガード指標に引っかかったか効果が確認できなかったものである
- **区分C(報告のみ)の提案は、AIの「こうしたい」の記録として読む。** 同じ保護ブロックへの提案が繰り返し出る場合、保護ブロックの規約と現場の実態がずれている可能性がある。変えるかどうかは人間が判断する
- 振り分けの多くが `様子見` や KB への回付で終わるのは正常である。**手順に来るシグナルは一部だけ**になるよう設計している(手順は増えるほど遵守されにくくなるため)。逆に、手順行きが多すぎる場合は、個別の事例をルールにしようとしていないかを見る
- 手順書の行数が増え続けている場合は要注意。効果の確認できない追加は撤回される既定だが、判定期間中の追加が積み重なっていないかを `metrics.md` と改訂表で見る

### 手順書の改訂のしかた(人間)

手順書の最終的な決定権は人間にある。区分(A/B/C)は、**AIが自律的に変えてよい範囲**を決めるものであり、人間の改訂を制限しない。

- **直接改訂する**: 手順書を自分で書き換えてよい。保護ブロックを変えた場合は、基準ハッシュ(`lint/protected-baseline.yaml`)を更新し、000 の改訂履歴に記録する。版(`vocab.meta.procedure_version`)を上げ、git のタグを付ける
- **AIに指示して改訂させる**: **箇所と内容を特定して**指示する(例: 「00 の ■DB操作の安全規約 に〜を追記して」「§10 のパートB 記載ルール6を〜に変えて」)。AIは区分や保護ブロックであることを理由に拒否しない。検出力や安全を下げると考える場合は懸念を1回伝えてくるので、そのうえで指示を維持すれば改訂される。指示が曖昧だと、箇所と内容を確認してくる(拒否ではない)
- AIに指示した改訂は、指示の原文が 000 改訂履歴に転記され、手順改善台帳に `指示適用` として残る
- **レビューのコメント(`review_notes`)に書いただけでは、手順書は変わらない。** AIはレビューの指摘を「人間の指示」とはみなさず、手順改善シグナルとして扱う(区分B・Cの変更の根拠にしない)。手順書を変えたいときは、直接改訂するか、明示的に指示する
- 配備(実行AIが読む手順書の差し替え)は、実行中のフローがないときに行う

## 外部操作 skill の整備と再探索フロー

外部操作(Web UI 以外の手段で行う操作)は skill を介してのみ行う。**skill を整備するのは人間**であり、AIは必要と分かった外部操作を外部操作需要リスト(93)に積むだけである。

- **整備のタイミングは需要の発生と切り離してよい。** フローは skill がなくても止まらず、該当シナリオが `blocked` になるだけである。需要リストがある程度たまってから、まとめて見て優先度を付ければよい
- **どの skill から整備するかは、申し送り台帳ではなく需要リストで判断する。** 需要リストは外部操作単位に集約されており、要求元の件数(止めているシナリオの数)が見える。目安は、要求元が多い / 課金など影響の大きい機能が含まれる / 代替手段が `なし` / 操作対象がシミュレータ(VMで巻き戻るため運用しやすい)
- **整備するときは skill の条件を確認する。** コードから呼べる実行体(CLI・スクリプト)を同梱し、非対話で起動でき、成否を機械的に判定できること。AI向けの手順書だけの skill は、探索では使えても回帰テストにならない(作業20でスキップされ、需要リストに `実行体なし` で戻ってくる)
- あわせて、その skill でできる操作が禁止操作リストのどの行に当たるかを確認しておくと、AIのエスカレーションが減る。印刷指示なら `CLIENT` の行(テスト用キューの限定など)を先に書いておく
- **整備したら、需要リストに整備記録(整備日・skill名)を書いて状態を `整備済` にし、再探索フローを指示する。** 整備記録を書いただけではシナリオは探索し直されない。指示は「EXT-002 を再探索して」程度でよい
- 需要リストの `整備済` は「整備した」という記録であり、動作環境に skill が配備されていることは保証しない。AIが食い違い(整備済なのに skill が見つからない)を報告してきたら、記録された skill名で探して配備する
- 再探索で `確立不可` が続く需要は、skill の説明が不足しているか、skill が対象の操作に合っていない可能性が高い。KB T05・`kb/gotchas/` の記録と合わせて見る
- 整備しないと決めた需要は `見送り` にして理由を残す。放置された `未整備` と区別できる

## 記入用テンプレート(90 / 91 / 92 / 93 / 94 / 95)について

2026-09-23 改訂で 90 / 91 / 92 を更新し、93(外部操作需要リスト)を新設した(`000_overview.md` 改訂履歴10)。同日の改訂で 92 に手順版を加え、94(手順改善台帳)を新設した(改訂履歴11)。語彙の扱いは次のとおり。

- **90(禁止操作リスト)の禁止レベル・適用対象・包括原則**、**91(申し送り台帳)の理由コード・引き継ぎ先・状態**、**92(フロー記録)のフロー種別・フロー状態**、**93(外部操作需要リスト)の状態・不足の区分・代替手段・操作対象**、**94(手順改善台帳)のシグナルの種別・出所・振り分け先・状態、手順箇所の書式、改訂の区分・状態、切り分け結果**は、いずれも `vocab.yaml` に同じものがある
- **`vocab.yaml` が正本である。** テンプレート側の表はその写しであり、食い違ったら `vocab.yaml` を正とする(lint の `vocab_sync`)
- 語彙を増減するときは `vocab.yaml` を先に変更し、テンプレート側を追随させる

### 90 禁止操作リストの記入について

- **完璧な網羅を目指さない。** ブラックリストの漏れは包括原則が拾う。AIが包括原則でエスカレーションしてきた操作のうち、恒久的に禁止すべきものをこの表へ追記していく運用でよい
- **「理由」欄が包括原則の精度を決める。** AIは表の理由欄から「この環境で何が危険とされているか」を学習し、表にない操作のグレーゾーン判断に使う。**空欄にしない**
- 実機の制約(枚数上限等)は運用しながら緩めてよい。逆にシミュレータは、VMスナップショットで復元できる限り原則自由とし、禁止は最小限に留める
- 「同時実行の可否」は操作対象ごとに書く。作業20が、同時実行できない対象を使うテストだけを直列化する根拠になる

### 91 申し送り台帳について

- **件数が多いことは失敗ではない。** ステップ1が正しく粗い網に留まっている証拠である
- `想定手段` が空欄のまま残っている項目は、ステップ2・3の設計時に検討する。**空欄を埋めるためにAIに推測させないこと**(誤った見当が計画を歪める)
- `操作手段なし` の行は、想定手段に需要ID(`EXT-...`)が入る。skill 整備の優先度はこの台帳ではなく93で見る
- `判定不能` は仕様の欠落を示している。有識者ヒアリング→仕様書追記のサイクルに乗せる候補になる
- ステップ2の開始時、`引き継ぎ先: ステップ2` かつ `状態: open` の行を抽出すれば、そのまま単発型項目の生成対象リストになる

### 92 フロー記録について

- 領域指示は「1〜2機能」または「1ユースケース」程度の粒度が扱いやすい。大きい場合はAIがフロー分割を提案してよい
- 台帳の `suspended` が溜まっている場合、領域指示の粒度か環境の問題を疑う
- 再探索フローは種別 `reexplore` として台帳に載る。通常フローと同じく作業10 → 20 を1巡するが、シナリオは新規に作らない
- 台帳の「手順版」列で、どのフローがどの版の手順で作られたかが分かる

### 93 外部操作需要リストについて

- AIが書くのは事実だけで、**優先度と整備記録は人間が書く**。AIに優先度を付けさせない
- 1つの skill で複数の需要を満たせる場合は、該当する全行に同じ整備記録を書く
- 上の「外部操作 skill の整備と再探索フロー」の節も参照

### 94 手順改善台帳について

- シグナル(§1)は実行AIが事実だけを書き、振り分けと改訂(§2)は作業40が行う。**人間が書くのは区分Bの採否と、回帰実行の切り分け記録(§3。CI 導入後)だけ**である
- 申し送り台帳(91)・外部操作需要リスト(93)とは扱う対象が違う。91は「テストとして扱わなかった対象」、93は「必要な外部操作の手段」、94は「手順書そのものの問題」
- 回帰実行の切り分けを将来AIに任せる場合は、導入前に「製品不具合ではない」と判断することの扱いを決める。不具合を `テスト起因` として処理すると、テストの修正で不具合が隠れる経路になりうる
- 上の「§40 手順改善」の節も参照

### 95 要確認事項台帳について

- **Q-001 が open の間も、パイプラインは進められる。** INV-001・002 を「未実装(スキーマ未確認)」として扱えばよい。INV-003〜005 は先行して起草・使用できる
- 回答が出たら、台帳の「回答・反映先」に記入した上で、**必ず該当手順書側も更新する**。台帳だけ更新して手順書が古いままになるのが最悪のパターン(AIは手順書を読んで動く)
- **Q-001(課金スキーマ構造)は、§01 の調査対象にすると解消が早い。** S3(DB定義と蓄積データの調査)で、テーブル定義・実在値・1対Nの関係が観測される。ただし**裁定はAIが行わず**、抽出結果を判断材料として台帳に添付し、人間が結論を記入する
- 本台帳は**成果物のレビュー状況とは別物**である。こちらは「手順の前提となる事実が未確定」を扱い、レビュー状況は「AI出力を人間が見たか」を扱う
