# 98 ゴールデンイメージ自動復元 — 設計の記録

2026-09-26 作成。手順版 `proc-v003` として正本(`skills版/procedure/`)に反映済み。規約の正本は手順書側であり、本書は**なぜこの形にしたか**の記録である。改訂の内容と指示の原文は `procedure/docs/000_overview.md` 改訂履歴 13 を参照。

## 1. 目的

- ゴールデンイメージ(Hyper-V の運用チェックポイント)の復元を人手から外す。手動では手間がかかり、忘れることがある
- **復元するかどうかの判断、復元したかどうかの確認をAIにさせない。** 確認のたびにトークンを使い、判断も揺れるため。AIの仕事は「決まった契機で実行体を1回呼ぶ」ことだけにする

## 2. 前提(2026-09-26 時点)

| 項目 | 内容 |
|---|---|
| 対象 | PMS サーバーVM 1台 |
| チェックポイント | 運用チェックポイント。VM はドメイン非参加 |
| ホスト | 現状は AI 実行環境と同じ PC。将来分離の可能性があるため、リモートにある前提で設計する。全台 Windows・ドメイン非参加・WinRM 使用可 |
| 復元の契機 | 回帰テスト前・作業10の開始前・作業20の開始前。作業後はそのまま(人間が手で確認するため) |
| 利用者 | 当面は個人のみ。複数人運用は考慮しない(将来の課題として 000 §5 に記載) |

## 3. 構成

```
[AI実行環境 / CI]                                             [Hyper-V ホスト]
 Playwright globalSetup (PMS_RESTORE=1) ──┐
   └ 続いて setup project `readiness` ──┐  │
 skill restore-golden-image (作業10/20) ─┼─┴─ restore-golden-image.ps1 ──WinRM──▶ JEA: PmsGoldenRestore
                                         │        │                                └ 停止→チェックポイント適用→起動
                                         │        └ readiness.command を呼ぶ(作業10/20のとき)
                                         ▼
                     tests/readiness/server-ready.setup.ts
                     = ログイン fixture と同じ部品で Web UI にログインできるまで待つ
                       (ファイルがない間は 終了コード4 → 人間がログインを確かめる)
 lint env_restored(Test-EnvRestoreMarker.ps1) ── status.yaml の env_restore を復元記録と突合
```

| 層 | 置き場所 | 役割 |
|---|---|---|
| 復元専用エンドポイント(JEA) | Hyper-V ホスト | 設定で固定した VM を固定したチェックポイントへ戻すことだけを公開する。仮想アカウントの権限は Hyper-V Administrators のみ |
| 外部操作 skill `restore-golden-image`(OP-VM-001) | `.kiro/skills/`・`.github/skills/` | 実行体(PowerShell)で JEA を呼び、設定の起動確認コマンドを呼び、復元記録を残す。**ログイン確認の処理は持たない** |
| 起動確認テスト | `tests/readiness/server-ready.setup.ts` | ログイン fixture と同じシナリオ部品で Web UI にログインできるまで待つ。作業10がログイン fixture を初めて整備したときに作る |
| globalSetup | `tests/global-setup.ts` | `PMS_RESTORE=1` のときだけ復元する(起動確認は setup project `readiness` が担う) |
| lint `env_restored` | skill 同梱 | 呼び忘れ・失敗した復元の使用・流用・人間の確認なしの開始を検出する |

## 4. 主な判断とその理由

| 判断 | 理由 |
|---|---|
| **判断はAIにさせず、契機を3つに固定** | 「復元済みか確認してから復元」より「決まった契機で必ず復元」の方が単純で確実。確認にトークンを使わない |
| **JEA で操作を絞る** | AI が VM の削除や別チェックポイントの適用をする経路を、手順(禁止操作 PROH-011)だけでなく仕組みとして塞ぐ。ホスト分離後も接続先を変えるだけで済む |
| **起動完了 = Web UI へのログイン成功** | ログイン画面の表示や IIS の応答では、IIS の外で動く Java アプリケーションサーバーの起動完了が分からない(人間の指示) |
| **ログイン確認は skill に持たせず、テストコード側に置く** | ログイン操作の知識をログイン fixture のシナリオ部品1か所に集めるため。ログイン画面が変わっても直すのは1か所 |
| **fixture そのものではなく、fixture が使うシナリオ部品を呼ぶ** | fixture は Playwright のテストの中でしか使えず、1回のテストで1回しか実行されないため、「ログインできるまで繰り返す」に使えない |
| **保存済みセッション(storageState)を使わない** | 保存済みセッションを読むだけではログインが行われず、確認にならない |
| **復元の実行体が起動確認コマンドを呼ぶ** | 復元と起動確認を別々にAIへ呼ばせると、起動確認を忘れる余地が戻る。AIは skill を1回呼ぶだけにする |
| **起動確認のための専用設定 `playwright.readiness.config.ts`** | 回帰テストの設定の globalSetup(復元)と globalTeardown(DB 全体の不変条件検査)を、起動確認の単独実行で走らせないため |
| **globalSetup の復元は `PMS_RESTORE=1` のときだけ** | 作業20の「復元せずに3回連続実行」や個別のデバッグ実行で勝手に復元されると、再実行耐性の確認が無意味になる |
| **ログイン fixture がない初期は人間が確認(終了コード4)** | 初回フローの作業10の開始時点ではログイン fixture がない。AIが画面でログインを試して判断すると、未起動によるログイン失敗を製品の挙動と取り違えるおそれがある(人間の選択 (b)) |
| **この停止を「人間の承認が必要な例外」に加えない** | 行為の許可ではなく環境の前提の確認であり、初期に限られる。保護ブロック `HUMAN_APPROVAL` を変えずに、00 ■回帰実行の環境前提 に置いた |
| **復元記録と lint で呼び忘れを検出** | AIに「復元したか」を確かめさせない代わりに、status.yaml の restore_id を復元記録と機械的に突き合わせる |

## 5. 既知の注意と残課題

- **ログイン画面が変わると、起動確認が「サーバー未起動」のようにタイムアウトする。** 製品側の変化が環境の失敗に見えるため、起動確認テストは最後の試行のエラーとスクリーンショットを残す
- **アカウントのロックアウト**: 起動待ちの間ログインが繰り返される。失敗回数でロックされる仕様なら、ロックされないアカウントを使うか試行間隔を延ばす
- ログインでログイン履歴などのレコードが増える可能性がある(テストは自データスコープが前提なので影響しない想定)
- 実機での確認、作業02の観測開始時の復元、複数人での VM の排他は `000_overview.md` §5 に残した
