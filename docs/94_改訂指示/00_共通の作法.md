## この指示書一式の使い方

docs/94 の方針を手順書に反映する改訂を、4つの段に分けて行う。**1つのセッションで行うのは1つの段だけである。** 人間は各セッションで「`docs/94_改訂指示/0N_….md` に従って改訂して」と指示する。

| ファイル | 段 | 手順版(目安) |
|---|---|---|
| `01_共通の土台.md` | 段1 `pms act`・タスクキュー・カード・提出の検査(作業10のフェーズA) | 改訂時の版 + 1(proc-v017 の見込み) |
| `02_スクリプト実行.md` | 段2 `pms run`(B2)・探索カード・記録からの生成 | 段1 の版 + 1 |
| `03_IDE内ループ.md` | 段3 IDE 内のループ(B1・フックなし) | 段2 の版 + 1 |
| `04_フック.md` | 段4(任意)フック | 段3 の版 + 1 |

あなたが行う段のファイルと、この 00 を読む。**ほかの段のファイルは読まない**(その段の関心が混ざるため。必要な情報は各段のファイルに書いてある)。

## 1. 変更の意図(全段に共通)

低価格のモデル(gpt-6-luna など)でも、記録の抜け・抽象化・記載のばらつき・一部だけの実施が起きないようにする。そのために、手順の正しさを「長い会話の中でAIが規則を覚えていること」と「AIが自分で記録すること」に頼らない形に変える。

docs/94 §3 の原則のうち、全段で守るもの:

| # | 原則 |
|---|---|
| P1 | AIは判断だけをする。順序・記録・集計・完了判定はプログラム(`tools/pms/`)が行う |
| P2 | 1枚のカードで1つの判断をする。カードが終われば会話を捨ててよい形にする(状態はすべてファイルに置く) |
| P3 | 規則は、それを使うカードの依頼文に入れる。使わない規則は見せない |
| P4 | AIの出力は、スキーマのある1つの JSON にする |
| P5 | 出力は提出の瞬間に検査し、通らなければ理由を返して差し戻す |
| P6 | AIが書かなくても残る記録を優先する。道具の実行がそのまま記録になる |
| P7 | モデルの既定の振る舞いに逆らう規則は、文章で頼まず検査で止める |

実行形態の方針(2026-10-07 の人間の決定):

> - docs/94 の提案(`pms act`・タスクキュー・カード・提出時の検査・記録からの生成)で手順書を改訂する
> - 実行形態は、スクリプト実行(B2: 進行役 `pms run` がカードごとにセッションを起こす)を主な経路とし、IDE 内のループ(B1)を副経路とする
> - フックは必須にしない。記録の正しさは `pms act`・キュー・`pms submit` で担保する。フックは、段3の計測でやり直しが目立った場合だけ入れる
> - 導入は4段に分け、段ごとに手順版を上げる

改訂履歴(後述)の「人間の決定」には、この引用と、各段のファイルにある段固有の決定を載せる。

## 2. このリポジトリの改訂の作法

直近の手本は `git show 2d5c51c`(proc-v016)と、`procedure/docs/000_overview.md` の26章である。迷ったらそれに倣う。

### 2.1 正本と生成物

- 手順書の正本は `procedure/` である(5層: `00_common.md`・`vocab.yaml`・`pipeline.dot`・`stages.md`・`methods/`。ほかに `templates/`・`router/SKILL.md`・`skills.config.json`)。**同じことを2箇所に書かない**(00 ■文書の5層構成)
- `.github/skills/` と `.kiro/skills/` は生成物である。**直接編集しない。** 正本を直したら `node tools/build-skills/build-skills.mjs` で再生成する
- 統制語彙の値は `vocab.yaml` だけに書く。00・stages では値を列挙せず `vocab.<キー>` で参照する

### 2.2 保護ブロック

`<!-- protected:ID -->`〜`<!-- /protected:ID -->`(vocab.yaml では `# <protected:ID>`)で囲んだ部分は変更しない(00 ■手順改訂の統制)。とくに次の3つは、カードの依頼文に載せるときも**文言を変えずに引用する**。

- `EXPECTED_IMMUTABLE`(期待結果・判定基準を書き換えない)
- `PROHIBITED_OPS`(禁止操作リスト・包括原則・迷ったら実行しない)
- `HUMAN_APPROVAL`(人間の承認が必要な例外)

保護ブロックを変えないと段の指示を満たせない場合は、**作業を止めて人間に確認する。**

### 2.3 版

1. `procedure/vocab.yaml` の `meta.procedure_version` を1つ上げる(改訂を始める時点の版 + 1)
2. `procedure/00_common.md` 冒頭の「改訂: / 版:」の行を、既存の書式に倣って更新する(今回の要約と、前版の要約1行)
3. 完了後、コミットに版と同じ名前の git タグを付ける

1フローは1つの版で実行する(00 ■手順書の版と配備)。**新しい lint 規則は、その版以降で始めたフローにだけ当てる**(作業10の status.yaml の `procedure_version` で判定する。`tools/lint/rules/exploration.mjs` の `setup_steps_recorded` が手本)。

### 2.4 改訂履歴

`procedure/docs/000_overview.md` の、最新の改訂の章の**上**に新しい章を足す。書式は26章に倣う。

```markdown

> - <1章の引用と、段固有の決定>

| # | 修正 | 対象 |
|---|---|---|

### 変更していないもの・後の段で行うもの

```

### 2.5 ツール

- 置き場所は `tools/<名前>/`。**Node.js 18 以上だけで動かす(外部パッケージを使わない)。** 既存の `tools/lint`・`tools/env`・`tools/pre-stage` と同じ
- ファイル先頭のコメントに、使い方・オプション・標準出力の形・終了コード・依存・テストのコマンドを書く(`tools/env/env.mjs` の先頭が手本)
- 終了コードは 0 = 成功 / 1 = 失敗(検査の不合格・操作の失敗)/ 2 = 使い方・設定の誤り、を基本にする。別の値が要るときはコメントに書く
- 機械が読む結果は標準出力に JSON で出す。人間向けの説明は標準エラー出力に出す
- **秘密情報の値を、標準出力・標準エラー出力・記録のファイルに出さない。** 値は `<env:キー>` と書く(00 ■検証環境の情報、lint `env_value_leak`)
- テストは `tools/<名前>/test/*.test.mjs` に置き、`node --test` で動かす。ブラウザや外部の CLI を要するテストは書かない(偽物のコマンド=スタブに差し替える)。実物での確認は、手順を書いて人間に頼む
- 設定ファイルは `config/` に置く。各自の値を含むものは `.sample.json` を git に入れ、実物を `config/.gitignore` に加える(`environments` が手本)

### 2.6 lint

- 規則の一覧の正本は 00 ■lint の表である。ランナーはこの表を読む。新しい規則は表に行を足し、実装したら「実装: `tools/lint/lint.mjs`」と書く(ランナーは「実装:」と実装の一致を起動時に確かめる)
- ERROR の規則の追加は区分B(人間採否)に当たるが、本改訂は人間の明示的な指示によるため追加してよい

### 2.7 利用説明書

`docs/skills版_利用説明書.md` のうち、利用者・管理者の手順が変わる箇所を直す(使い方・導入手順・既知の制約)。

## 3. 完了の確認(全段に共通)

次のすべてを満たしてからコミットする。

| 確認 | コマンド | 期待 |
|---|---|---|
| テスト | `node --test tools/` | 全件成功(件数を報告に書く) |
| skills が正本と一致 | `node tools/build-skills/build-skills.mjs --check` | 終了コード 0 |
| pre-commit と同じ検査 | `node tools/lint/lint.mjs --rule skills_in_sync` | 終了コード 0 |
| lint の表と実装の一致 | `node tools/lint/lint.mjs --list` | エラーなく一覧が出る |
| 差分 | `git status` / `git diff --stat` | 正本・生成した skills・ツール・設定の見本・文書だけが変わっている。作業場所の成果物(`work/` の中身)を変えていない |

## 4. コミット

- 正本と再生成した skills を**同じコミット**に入れる(pre-commit の `skills_in_sync` が通らなければコミットできない)
- メッセージは既存に倣う。1行目は英語の要約と版(例: `Add pms act and setup cards for phase A (proc-v017)`)、本文に変更点を箇条書き、テストの件数、skills を再生成したこと
- コミットのあと、版と同じ名前のタグを付ける。**push はしない**(人間が判断する)

## 5. 止まって人間に確認するとき

次のときは、推測で進めずに作業を止め、状況と選択肢を示して確認する。

- 保護ブロックの変更が必要になった
- 指示書の内容が、現行の手順書の規定と食い違い、どちらを採るかで結果が変わる
- 外部の道具(playwright-cli・Copilot CLI・Kiro CLI)の実際の仕様が、指示書の前提と違う
- 指示書に書かれていない設計上の判断のうち、利用者の操作や成果物の形が変わるもの(内部の実装の判断は自分で決め、`tools/pms/README.md` に書く)

## 6. 人間への完了報告

次の項目で報告する。

1. 上げた版とタグ
2. 変えたこと(改訂履歴の表の要約)
3. 変えていないこと・次の段に回したこと
4. 完了の確認の結果(テストの件数を含む)
5. **人間が次の段へ進む前に確かめること**(各段のファイルの末尾にある。実機での確認の手順を具体的に書く)
6. 指示書と違う判断をした箇所と理由
