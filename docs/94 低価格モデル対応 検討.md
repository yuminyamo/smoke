## 0. 結論

**「AIに正しく読ませる」から「AIが読まなくても外れない」へ移す。** 具体的には、次の3つをAIの仕事から外し、決定的なプログラム(以下「進行役」)に移す。

1. **次に何をするかを決めること**(進行管理)
2. **記録を書くこと**(操作列・ロケータ・時刻・件数・報告書・status.yaml)
3. **終わったかを判断すること**(完了判定)

AIに残すのは、**1回に1つの判断**(この画面でどの要素を操作するか、この結果は期待結果を満たすか、など)だけにする。各判断は、それに必要な規則と入力だけを載せた**タスクカード**で渡し、出力は**スキーマで縛った1つのJSON**で受け取り、受け取った直後に機械検査して、通らなければその場でやり直させる。

要求者の想定(作業を適切な粒度に区切り、必要な分だけのコンテキストを渡し、入出力を具体的にする)は、調査した事例と一致する。ただし事例はもう2点を加えている。

- **記録の義務そのものを無くす**のが最も効く。記録をAIに「忘れずに書かせる」限り、粒度を細かくしても抜けはゼロにならない。操作を実行する道具が記録を自動で残す形にする
- **検査を作業の末尾ではなく、1つの出力ごとに行う**(バックプレッシャー)。現在の lint は作業10の最後にまとめて走るため、抜けが見つかったときには、それを埋めるための情報(画面・ロケータ)がすでにコンテキストから消えている

| # | 提案 | 効く失敗 | 規模 |
|---|---|---|---|
| **A** | 操作と記録の一体化(記録する道具 `pms act`) | 記録抜け・抽象化・時刻の抜け | 小〜中 |
| **B** | 進行役(状態機械)とタスクキュー。AIは「次のカードを取る→実行→提出」を繰り返すだけ | 一部の作業だけ実施・順序の逸脱・指示の忘却 | 中 |

| **E** | 報告書・status.yaml・flow.md のチェック・台帳の件数を、記録から機械生成 | 集計の誤り・報告と実態の食い違い | 小 |

## 1. 要求の整理 — 失敗のしかたと原因

要求にある「安定しない」状態を、現行の手順のどこから生じるかで整理する。

| 失敗のしかた | 例 | 現行の手順での原因 |
|---|---|---|
| 記録が抜ける | setup-log の `steps`・`locator` がない(調査票001) | 記録は「操作の直後にその場で書け」という**自然文の義務**であり、書かなくても作業は先へ進める。気づくのは作業末尾の lint か、作業20 |
| 記録が抽象化される | 「ログイン画面でログインする」としか書かれない | 出力の書式が付録の自然文で示されるだけで、書いた瞬間に検査されない |
| 記載レベルがばらつく | シナリオによって `actions` の細かさが違う | 判断の基準が規則163個の中に散っている。記入例がカードの手元にない |
| 一部の作業だけ実施 | パートCの一部シナリオを探索しないまま報告書を書く | 「全部やったか」をAI自身が DoD(65項目)で自己点検する。自己点検は読み落としに弱い |
| 最初の指示を忘れる | continue・コンパクションの後に脱線する(調査票001の H6) | 1つの作業が1つの長い会話で行われ、起動時に約11.5万字(00 6.2万字・本文 3.2万字・vocab 2万字)を読ませたうえで、snapshot が積み上がる |

数値は `.github/skills/pms-10-explore/` の proc-v016 で数えた(文字数・`stages.md` §10 の箇条書きと番号付きの行・DoD のチェック項目)。

**根本は1点である。手順の正しさが、「長い会話の中でAIが規則を覚えていること」と「AIが自分で記録すること」に依存している。** 粒度を細かくするだけではこの依存は残る。

## 3. 設計の原則

本提案のすべての変更は、次の7原則から導く。手順書に採用する場合は 00 の冒頭に置く。

| # | 原則 | 反例(現行) |
|---|---|---|
| P1 | **AIは判断だけをする。** 順序・記録・集計・完了判定はプログラムが行う | AIが pipeline.dot を読んで次の作業を決める。AIが報告書の件数を数える |
| P2 | **1カード1判断、1カード1コンテキスト。** カードが終われば会話を捨てる | 作業10の全パートを1つの会話で行う |
| P3 | **規則は、それを使うカードの依頼文に入れる。** 使わない規則は見せない | 起動時に 00 と vocab を全文読む |
| P4 | **出力はスキーマ付きの1つのJSON。** 自由記述は、スキーマの中で長さと語彙を縛った欄だけ | YAML を手で書き、付録の自然文で書式を知る |

## 4. 提案

### 提案A — 操作と記録の一体化(記録する道具 `pms act`)

**効く失敗**: 記録抜け・抽象化・ロケータの不安定・時刻の抜け(調査票001の型は構造的に起きなくなる)

探索とセットアップの画面操作を、playwright-cli を直接ではなく、薄い包み `node tools/pms/act.mjs`(以下 `pms act`)を通して行う。`pms act` は1回の操作ごとに次を自動で行い、記録ファイルに追記する。

1. 操作の前後の時刻(`started_at`・`ended_at`)
2. 操作対象の参照(`e15` など)から `generate-locator` でロケータを求め、00 の優先順位で安定かを判定する(一時ID・CSS なら、その場で警告を返す)
3. 操作の種類と入力値(秘密情報は `<env:キー>` に置き換えて記録)
4. 操作後の URL・画面タイトル

```
pms act --flow F-003 --target S-ADMIN-LOGIN --intent "管理者IDを入力" fill e15 "<env:pms.admin.user>"
→ {"ok":true,"seq":3,"locator":"getByLabel('ユーザーID')","locator_class":"stable","started_at":"...","ended_at":"..."}
```

AIが書くのは `--intent`(この操作の目的。1行)だけである。**操作列・ロケータ・時刻は書かない。**

状態の整備やシナリオの探索が終わったら、AIは「成功した最短の操作列」を、記録された連番の範囲で指定するだけにする。

```
pms submit --flow F-003 --card C-0412 --file out/C-0412.json   # 出力の JSON に "seq_range": "3-6"
```

`pms submit` が、検査に合格した提出の連番の範囲から、setup-log の `steps`(または exploration-log の `actions`)を書く。範囲の中に記録のない連番や安定でないロケータがあれば拒否する(提案D)。

- fixture・シナリオ部品のコードも、この記録から生成する(AIが書いたコードと記録が食い違う、という型の失敗がなくなる。調査票001の H5)
- playwright-cli を直接呼んだ操作は記録に残らないため、その連番を含む提出は不合格になる(提案D)。B2 ではセッションの起動時に playwright-cli を使用禁止にする(Copilot CLI `--deny-tool`、Kiro CLI `deniedCommands`)。B1 でフックを使える場合は PreToolUse でも止める(提案F)
- 外部操作 skill の実行体も、同じく `pms ext` で包んで時刻と引数を記録する

確かめること: playwright-cli のブラウザのセッションが、別のプロセス・別の会話から同じものを使えるか(提案Bでカードごとに会話を切るための前提)。使えなければ `pms` 側でブラウザを常駐させる。

### 提案B — 進行役(状態機械)とタスクキュー

**効く失敗**: 一部の作業だけ実施・順序の逸脱・指示の忘却

`pipeline.dot` と各作業の手順を、進行役 `node tools/pms/pms.mjs` が持つ。進行役は flow ごとにタスクキュー(`work/_flows/F-<番号>/queue.json`)を持ち、AIに次の1枚のタスクカードを渡す。

```
pms next  --flow F-003            → 次のカード(Markdown)を標準出力に出す。人間の判断が要る場面なら STOP と理由
pms submit --flow F-003 --card C-0412 --file out.json
                                  → 検査して、合格ならキューを進め記録を書く。不合格なら理由を返す(提案D)
pms status --flow F-003           → 残りのカード数・止まっている理由
```

キューはプログラムが**展開**する。例えば作業10のパートCでは、シナリオ一覧と `requires` から「状態ごとの整備カード」と「シナリオごと・ステップごとの探索カード」を機械的に作る。**AIが「どれをやるか」を選ぶ場面がないので、一部だけ実施するという失敗が起きない。**

AIの側の指示は、どのモデルでも守れる長さにする。入口 skill の本文は次だけになる。

```
1. `pms next --flow <ID>` を実行する
2. STOP なら、出力された文をそのまま利用者に伝えて終わる
3. カードの指示どおりに行い、カードが指定するファイルに出力を書き、`pms submit` を実行する
4. submit が不合格なら、返された理由だけを直して再提出する
5. 1 に戻る
```

**実行形態は2段階で用意する。**

| 形態 | 仕組み | 1カード1コンテキスト | 向く場面 |
|---|---|---|---|
| **B2 スクリプト(主)** | 進行役 `pms run` が、カードごとに `copilot -p ... --agent ... --model ... --no-ask-user --deny-tool ...`(Kiro は Kiro CLI)でセッションを起こし、終わったら捨てる(Ralph ループ型)。提出されていなければ同じカードを出し直し、上限を超えたら人間へ回す | 完全に独立 | 通常の実行・夜間の無人実行。会話の継続確認(`chat.agent.maxRequests`)とコンパクションが原理的に起きない。人手が要らない |
| B1 IDE 内(副) | 入口の custom agent が上のループを回し、各カードは subagent(custom agent。カードの種類ごとにモデルを指定)で実行する | subagent ごとに独立 | カードの作り込み・初めての画面の探索(見ながら止められる)・チャットで進めたい人。途中の人間の判断にその場で答えられる |

カード・検査・記録の道具は共通なので、どちらの形態でも作り直しにはならない。B1 でサブエージェントが提出せずに終わった場合は、次の `pms next` が同じカードを出し直す(入口は結果を信じず必ず `pms next` を呼ぶ)。入口エージェント自身が止まった場合は、利用者が「続けて」と伝えれば `pms next` から再開する。

**B1 が B2 より優れる点**(B2 を主にしても B1 を残す理由):

- 途中の人間の判断(環境情報の不足・要許可操作・ログイン確認など)に、チャットでその場で答えられる。B2 では STOP して人間が答えたあと、`pms run` を実行し直す(正しく止まり再開できる点は同じで、違いは待ち時間と手間)
- AIの動きを見ながら止められる。B2 は終わってからログを読む
- 今の使い方(チャットで「F-003 の続き」)のまま使える。B2 には Copilot CLI(または Kiro CLI)の導入・認証と、組織の設定での許可が要る
- 課金の数え方によっては B1 の方が安い。旧来の premium requests では、利用者が送ったプロンプトだけを数えるため、B1 は1回の依頼で多くのカードを回せるが、B2 はカードごとに1件(× モデルの倍率)を使う。2026-06 以降、多くのプランは AI credits に移っているため、組織の契約を確かめる

なお、現行の入口 skill が担う「依頼の種類の振り分け」「止まったときの伝え方」も、状態と理由コードから進行役が文面を出す(伝え方の表はそのまま文面のテンプレートになる)。

### 提案C — タスクカード

**効く失敗**: 記載レベルのばらつき・規則の読み落とし・指示の忘却

1枚のカードは、**それ単体で完結する**依頼文である。カードの外の資料を読む必要がない(読んでよい資料はパスで明示する)。

```markdown
# カード C-0412 / 種類: setup.build(状態の整備) / F-003

## やること(1つだけ)
状態 S-PRINTER-REGISTERED(プリンターが1台登録済み)を、画面操作で作る。

## 入力
- 状態の定義: 「プリンター一覧に、名前が `PRT-F003-<一意化>` の行が1行ある」
- established check の案: プリンター一覧で上の名前の行が見える
- 参考になる資料(必要なら読む): kb/screens/printer-list.md
- 現在の画面: ログイン済み・ダッシュボード

## 規則(このカードに必要なものだけ)
- [R-LOC-1] 画面操作は必ず `pms act` で行う。playwright-cli を直接使わない
- [R-UNQ-2] 作るデータの名前は `<接頭辞>-F003-<6桁の英数>` とする
- [R-INV-3] 禁止操作リストに当たる操作をしない。迷ったら操作せず `blocked` で提出する
- [R-STP-1] 最後に、成功した最短の操作の連番を `seq_range` に書く

## 出力(この形の JSON を out/C-0412.json に書く)
{
  "result": "built | blocked",
  "seq_range": "3-9",
  "established_check": {"locator": "<pms act が返したロケータ>", "expect": "visible"},
  "blocked_reason": null,
  "notes": "失敗した試行の要点(1〜2文。なければ null)"
}

## 記入例(別の状態の、合格した出力)
{ "result": "built", "seq_range": "12-17",
  "established_check": {"locator": "getByRole('row', { name: 'USR-F001-a8k2zq' })", "expect": "visible"},
  "blocked_reason": null, "notes": "初回は保存ボタンが無効だった。必須欄の部署を選ぶと有効になる" }

## 終わったら
`pms submit --flow F-003 --card C-0412 --file out/C-0412.json` を実行する。
```

カードの原本(テンプレート)は手順書側に、カードの種類ごとに1つ置く。現在の `stages.md` の節と 00 の ■ セクションは、**規則IDの付いた1規則1行**に分解し、カードのテンプレートが規則IDで引用する(build-skills.mjs が今の「参照付録」の行と同じ仕組みで差し込む)。これにより、

- 規則の正本は1か所のまま(現行の「同じことを2箇所に書かない」を守れる)
- どのカードがどの規則を使うかが一覧でき、手順改善シグナルの手順箇所も規則IDで指せる
- 1枚のカードに載る規則は、多くても10前後に収まる

カードの書き方の規約(低価格モデル向け):

- 指示は肯定形・命令形で、1文1動作。条件分岐は表にし、2段以上の入れ子にしない
- 出力の各欄に、許される値(列挙・パターン・文字数の上限)を書く
- 合格した記入例を必ず1つ付ける(ばらつきを最も減らすのは例である)
- 規則は理由を付けず短く書く(理由は手順書の正本と人間向けの補足に残す)

### 提案D — 提出時の即時検査と差し戻し

**効く失敗**: 抽象化・ばらつき・不完全な出力

`pms submit` は次の順で検査し、1つでも落ちたら理由を返して差し戻す。

1. **スキーマ**: JSON Schema(必須欄・列挙・パターン・長さ)
2. **参照の実在**: `seq_range` の連番が記録にある、ロケータが安定、需要ID・禁止IDが台帳に実在する
3. **カード単位の lint**: 現行の lint の規則を、フロー全体ではなくそのカードの出力に適用する(例: `setup_steps_recorded` をこの状態だけに)
4. **形式による異常の検出**(MAKER の red-flagging): あいまい語(「適宜」「など」「必要に応じて」「〜等」)、指定より長すぎる・短すぎる欄、期待結果の文言の変更(保護ブロック)を機械的に検出する

差し戻しの回数に上限を置き(例 3 回)、超えたらカードを `needs_human` にして進行役が止まる。重要な判断(禁止操作に当たるか、期待結果を満たすか)は、別の会話で2回引いて一致しなければ人間へ回す、という多数決も選べる(費用とのかね合いで、カードの種類ごとに設定する)。

作業末尾の lint は残す(フロー横断の整合を見るため)が、主な関所はカードの提出に移る。

### 提案E — 報告書・status.yaml・台帳の件数の機械生成

**効く失敗**: 集計の誤り・報告と実態の食い違い・DoD の自己点検の読み落とし

報告書の数値と一覧、status.yaml の `context_updates`、flow.md のタスクのチェック、台帳の件数は、すべて記録(exploration-log・setup-log・台帳)から決まる。これらは `pms report` が生成する。AIが書くのは、報告書の中の所見の欄(人間に伝えたいこと)だけにする。

DoD の65項目のうち、記録から機械的に判定できる項目は進行役の検査に移し、AIの自己点検から外す。機械的に判定できない項目だけをカードの出力欄(「〜を確かめたか: yes/no と根拠」)にする。

### 提案F —(任意)IDE のフックによる歯止め

**効く失敗**: 途中終了・記録の道具を通さない操作・コンパクション後の脱線を**早めに**止め、やり直しを減らす

**必須にしない。** フックがなくても、記録の正しさは提案A・B・D で担保される(`docs/004_フック処理_図解.html` 7章)。フックが減らすのは、直接呼んだ操作のやり直しと、B1 で入口が止まったときに「続けて」と伝える手間である。B1 で直接呼びによる差し戻しが目立った場合にだけ入れる(§6 段4)。Copilot CLI(B2)も `.github/hooks/*.json` のフックを読むが、B2 では使用禁止の設定(`--deny-tool`)で大半の用が足りる。

| フック | 行うこと |
|---|---|
| PreToolUse | playwright-cli を直接呼ぶ端末コマンドを拒否し、`pms act` を使うよう返す。手順書(`procedure/`)・skills への書き込みを拒否する |
| PostToolUse | `pms act` の結果でロケータが安定でなければ、その場で警告を文脈に足す。毎回、現在のカードIDを1行添える(コンパクションの後でも見失わないため) |
| Stop / SubagentStop | `pms status` を実行し、未提出のカードがある(または lint の ERROR がある)のに止まろうとしたら、継続させて理由を伝える。人間の判断待ち(STOP)は通す |
| PreCompact | 現在のカードIDと、次に実行すべきコマンドを状態ファイルに書く(記録のため。PreCompact はAIに文脈を足せない。§9) |
| SessionStart | `pms next` の結果を文脈に入れる(最初の指示が常に最新の状態から始まる) |

フックは Copilot ではプレビューの機能を含むため、設定はリポジトリの `.github/hooks/` に置く。Kiro はフックでできることが少ない(§9)。フックが動かない環境でも、提案B・D の検査で同じ失敗は止まる(フックは早く止めるための補助)。フックの処理の流れは `docs/004_フック処理_図解.html` に図解した。

### 提案G — 手順の評価用セット

**効く失敗**: 改善したかどうかが分からない

調査票001のような事後調査ではなく、手順の版を上げるたびに計測する。

- **固定の評価用フロー**: 検証環境で、結果が分かっているシナリオ3〜5本(セットアップあり・blocked あり・外部操作ありを含む)
- **指標**: 記録の完全性(必須欄の充足率・安定ロケータ率・時刻の充足率)、カードの初回合格率と差し戻し回数、人間へ回った割合、生成したテストの成功率、費用(トークン)
- **モデルの行列**: 低価格モデル(gpt-6-luna など)と上位モデルで同じフローを流し、差が許容範囲かを見る
- 作業40(手順改善)の判定の「検出力ガード指標」(docs/97)に、この指標を加える

カード単位の設計にすると、評価もカード単位でできる(「setup.build カードの初回合格率が低い」と分かれば、そのテンプレートだけを直せばよい)。

## 8. リスクと対策

| リスク | 対策 |
|---|---|
| カードに切ると、画面をまたいだ文脈(前のステップで何をしたか)が失われ、探索の質が落ちる | 進行役が「前のステップの要約」を記録から機械生成してカードに入れる(AIの要約ではなく記録の抜粋)。探索カードの単位はステップから始め、質が落ちるならシナリオ単位に広げる |
| カードの数が増え、費用と時間が増える | 1カードの入力が小さいため、合計のトークンはむしろ減る見込み(現行は起動時だけで約11.5万字を読み、snapshot が積み上がる)。評価用セット(提案G)で確かめる |
| 進行役(プログラム)の保守が増える | 現行でも lint・build-skills・env・pre-stage の各ツールがある。進行役は pipeline.dot とカードのテンプレートを読む汎用の仕組みにし、手順の内容をコードに書かない |
| Copilot のフック・subagent の仕様がプレビューで変わる | フックは任意とし、正しさは `pms act`・キュー・`pms submit` の検査で担保する。主な経路の B2 は IDE に依存しない |
| Copilot CLI・Kiro CLI のフラグや出力の形が変わる | `pms run` からの呼び出しを設定ファイル(コマンドの雛形)にし、コードに書かない。CLI の版を記録に残す |
| 想定外の画面・状況でカードの範囲に収まらない | どのカードにも出力の選択肢として `cannot_proceed`(理由コード付き)を置き、進行役が人間への確認か差し戻しに回す。AIにカードの外の判断をさせない |

## 9. 実現性の確認(2026-10-07)

§4 提案A の「確かめること」と、§8 の Copilot・Kiro の仕様を確かめた。playwright-cli は macOS で `@playwright/cli 0.1.22`(内部の Playwright は 1.64 の alpha 版)を実際に動かした。フックは公式のドキュメントで確かめた。図解は `docs/004_フック処理_図解.html`。

### playwright-cli

| 確かめたこと | 結果 | 対応 |
|---|---|---|
| セッションを別のプロセス・別の会話から使えるか | **使える。** `-s=<名前> open` で開いたブラウザはデーモンとして常駐する。別のシェル(環境変数なし)・別のディレクトリから `list`・`snapshot`・`fill`・`click` で操作できた | カードごとに会話を切ってよい。セッション名はフローIDにする |
| 安定ロケータを道具で取れるか | **取れる。** `generate-locator e3` → `getByRole('textbox', { name: 'ユーザーID' })`。名前のない要素は `locator('div')` になる | 先頭が `getBy` なら安定、`locator(` なら不安定と判定する。一意かどうかは `run-code` で `count()` が1かを確かめる(確認済み) |
| 操作の結果にロケータが出るか | **条件付き。** 通常の出力には「Ran Playwright code」としてロケータ付きのコードが出るが、`--json` では `fill` の結果が `{}` だった | ロケータは操作の前に `generate-locator` で取る(操作の後は画面が変わり、参照が無効になることがある) |
| 秘密情報 | **対策が要る。** `fill` の通常の出力に、入力した値がそのまま出た(`.playwright-cli/` のファイルには残らない) | `pms act` が `<env:キー>` を自分で値に置き換え、出力の値を伏せてからAIに返す |
| セッションの寿命 | **対策が要る。** ヘッドレスのセッションは1時間操作がないと自動で閉じる | `open --idle-timeout=0`。ログイン状態は `state-save`・`state-load` で戻せる |
| 操作の記録(recording)を別プロセスで使えるか | **使える。** `recording-start`・`click`・`recording-stop` をそれぞれ別のプロセスで実行し、Playwright のコードが得られた | fixture のコードを生成するときの照合に使える |
| 版の安定性 | **注意。** 0.1.x で、1.0 に達していない | 版を固定する。playwright-cli を直接呼ぶのは `pms act` だけにする |

### VS Code + Copilot

| 確かめたこと | 結果 | 対応 |
|---|---|---|
| 提出前の終了の差し止め | **できる。** Stop・SubagentStop で `{"decision":"block","reason":…}`。入力の `stop_hook_active` で差し止め済みかが分かる。差し止めるたびにAIの利用枠を使う | `stop_hook_active` が true なら通す。未提出は `pms status` に残し、次の `pms next` で同じカードを出し直す |
| playwright-cli の直接呼びの拒否 | **できる(1点確認)。** PreToolUse の `permissionDecision: "deny"`。端末ツールの `tool_name` は環境ごとに違う | 受け取った入力を記録するだけのフックを先に置き、実際の名前を確かめる |
| コンパクションの後に指示を戻す | **直接はできない。** PreCompact は共通の出力欄(continue・stopReason・systemMessage)しか持たない | カードごとに会話を切る(提案B)を本命にする。補助として PostToolUse で現在のカードIDを毎回添える |
| カードの種類ごとのモデル | **できる。** custom agent の `model`(候補を順に並べられる)。サブエージェントとして呼ばれても、そのエージェントのモデルで動く | build-skills.mjs でカードの種類ごとに custom agent を生成する |
| 利用の条件 | **確認が要る。** フックはプレビュー機能。`chat.useHooks`(既定で有効)とワークスペースの信頼が必要で、組織の設定で止められている場合がある。エージェントごとのフック(`.agent.md` の `hooks`)もプレビュー | 管理者に組織の設定を確かめる。最初はワークスペース全体のフック(`.github/hooks/`)で始める |

### Kiro

| 確かめたこと | 結果 |
|---|---|
| IDE のフック | Pre Tool Use だけが止められる。ただしコマンドのフックにはツール名と引数が渡らない(kirodotdev/Kiro Issue #7500、2026-04 から未解決)ため、playwright-cli だけを選んで止めることはできない。Agent Stop で処理を続けさせることもできない |
| CLI(v3)のフック | `.kiro/hooks/*.json`。PreToolUse・UserPromptSubmit・PreTaskExec が終了コード 2 で止められ、入力は標準入力の JSON。Stop で処理を続けさせることはできない |

**結論**: Copilot ではフックを補助として使える。Kiro ではフックに頼らず、`pms submit` の検査(記録にない連番の提出は不合格)と、進行役がループを持つ実行形態(B2)で同じ効果を得る。どちらの環境でも、正しさは `pms act` と `pms submit` が担保し、フックの有無で変わるのはやり直しの回数だけである。
