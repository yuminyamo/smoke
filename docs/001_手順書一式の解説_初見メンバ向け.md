## 1. そもそも何をするための手順書か

### 1.1 背景となる課題

- 対象は約15年運用されてきたオンプレミス型 Print Management System(PMS)。コードは1,000万行超で、顧客要求の取り込みにより機能が複雑に絡み合っている
- 新機能追加・OS対応・バグ修正のたびに、**既存機能の手動検証工数が膨大**になる。外部仕様を変えない互換性制約の中で、2次障害と環境変化による不具合の検知を人手に頼っている
- 課金機能は金額のわずかなズレが致命的不具合になるため、検証コストが特に高い
- ドキュメントの充足度が低い(体感値でマニュアル5割・仕様書6割・設計情報2割)ため、「文書を見てテストを書く」ことが成立しにくい

### 1.2 手順書一式がやること

生成AIに、**テスト項目の策定 → 実画面での探索的実行 → 回帰テストコード生成**までを担当させるための「AI向け作業指示」と「人間向けの運用ルール」の一式である。

- 生成された回帰テストは**実行時にAIを使わない決定的な Playwright コード**になる(コスト・再現性・速度のため)
- 人間はレビューとガバナンス(行為の許可・正解の確定)を担う
- **手順書そのものも、実行の経過と結果から改善していく。** AIが手順の迷い・矛盾・逸脱をその場で記録し、作業40(手順改善)が数フローごとに集約して、手順書を差分で改訂する。ただし安全と検出力の根幹はAIが自律的に変えない

### 1.3 3ステップ構成(網の目を段階的に細かくする)

| ステップ | 対象 | 目的 | 網の目 | 状態 |
|---|---|---|---|---|
| **ステップ1** | E2E / シナリオ型のみ | 全機能の基本動作が通ることの保証 | 粗い | **現在の対象** |
| ステップ2 | E2E / 単発型 + シナリオ型のバリエーション | E2Eの充実 | 中 | 未着手 |
| ステップ3 | E2E以外(HTTP層・DB層・メタモルフィック等) | 機能特性に応じた効率的・網羅的な検証 | 細かい | 未着手 |

ステップ1はさらに **単機能シナリオ**(3〜6ステップ、1機能内で完結。現在の生成対象)→ **連結シナリオ**(機能をまたぐ)の順に進む。**手順書一式が現在定めているのはステップ1だけ**である。

### 1.4 フロー反復モデル(実行の単位)

1回の実行は「**1フロー = 人間が指示した対象領域(1〜2機能程度)について、作業10 → 作業20 を1巡**」である。フローを繰り返して回帰テストセットを累積していく。フローを重ねるほど、fixture・部品・KB・カタログが流用できて1フローあたりのコストが下がる。1フローは1つの手順版で実行する。

```
人間: 領域指示(例「印刷実行まわり」)
   │
   ▼
 [手順改善の要否]──(lint / 人間の指示)──▶ 40 手順改善(別セッション・停止しない)──┐
   │                                                                                 │
   ▼ ◀───────────────────────────────────────────────────────────────┘
 [事前作業の要否]──(人間が指示)──▶ 01 知見蓄積 ──┐
   │            └─(未収載の値あり)──▶ 02 非決定値カタログ ─┤
   ▼                                                     ▼
 10 シナリオ生成と探索 ◀─────────────────────────────────┘
   │  ├─ 要許可操作が必要 → [人間: 許可判断] → 10へ戻る        … 停止点②
   │  ├─ 知見不足       → 01 知見蓄積 → 10へ戻る
   │  ├─ 外部操作の skill がない → 外部操作需要リスト(93)に記録し、そのシナリオは blocked(停止しない)
   │  └─ DB不変条件違反  → [人間: 起票して続行 / 中断]
   ▼  (完了報告 + status.yaml を出して停止)                  … 停止点①
 20 回帰テストコード生成 ──(コード化不能が残る)──▶ 10へ差し戻し
   │
   ▼
 フロー完了   ※複数フロー後、人間の指示で 30 状態カタログ案(データ変更前に停止) … 停止点③

 (全作業)手順の迷い・矛盾・逸脱・後段不足 → 手順改善台帳(94)にシグナルを記録 → 次の作業40の材料
 (別の時期)[人間] 需要リストを見て skill を整備 → 再探索フローを指示
            → 10(パートR: blocked だったシナリオを探索し直す)→ 20 → フロー完了
```

正確な定義は `pipeline.dot` にある(`dot -Tsvg pipeline.dot -o pipeline.svg` で描画できる)。

## 2. 手順書を貫く6つの考え方

個々の規約は多いが、根底にある考え方は次の6つに集約できる。4章の各項目はどれかの具体化になっている。

| # | 考え方 | 代表的な具体化 |
|---|---|---|
| 1 | **AIには手順ではなく「到達条件」と「離散状態」を渡す** | シナリオには操作手順を書かない / 各作業の完了条件(DoD) / status.yaml の列挙値で次段を決める |
| 2 | **推測より観測** | 現行の実挙動を正解とする(オラクル原則) / 非決定値は反復観測で強度を決める / 状態カタログは探索記録から起こす |
| 3 | **欠落は捨てずに「管理された欠落」にする** | 申し送り台帳 / 外部操作需要リスト / DISC(不整合)台帳 / 「判明しなかったこと」の報告 / 突合表のスキップ理由 / 要確認事項台帳 |
| 4 | **一度調べたことは二度調べない** | 知見ベース(KB) / 確立済み操作の台帳(KB T05) / 既存資産の流用義務 / 発見ログと再発見率 |
| 5 | **人間は「行為の許可」と「正解の確定」だけを握る** | 非ブロッキングレビュー / 必須の停止点は3つだけ / as-is 凍結の判断はAIにさせない / 禁止操作リストは人間が書く / 外部操作 skill は人間が整備し、優先度も人間が付ける |
| 6 | **手順そのものも実行から学ぶ。ただし検出力と安全の根幹は人間だけが変える** | 手順改善シグナル / 作業40(手順改善)/ 改訂の区分(自律適用・人間採否・不可侵)と保護ブロック / 検出力ガード指標 / 人間の明示的な指示には区分に関わらず従う |

## 4. 手順書ごとの解説

各ファイルについて「一言で」「対処する課題」「解決のアイデア」「実装箇所」の順に示す。実装箇所は `ファイル ■見出し` / `§節 番号.スロット` の形で示す。

### 4.1 `00_common.md` — 全作業に共通の既定

**一言で**: どの作業のAIにも必ず渡す「共通ルールブック」。テーマごとに課題とアイデアが独立しているので、表で示す。

| テーマ | 対処する課題 | 解決のアイデア | 実装箇所 |
|---|---|---|---|
| 文書構成と投入単位 | 同じ規約が複数ファイルに散在し、改訂のたびに波及管理が必要。無関係な作業の指示まで読ませるとAIの関心が混入する(探索中にコード生成の関心が入る等) | 4層に分けて再掲を禁止。**統合は保守の単位、投入は抽出単位**と分ける。再掲を見つけても実行中は直さず、シグナルとして記録する | ■文書の4層構成(規約1〜4)/ ■AIへの渡し方 |
| フロー | 全機能を一度に扱うと膨大で、外部操作の skill も段階的にしか整備されない | 領域指示ごとに10→20を1巡。ステップ1の粒度規則は全フロー共通・不変。**別セッションのAIが flow.md だけで引き継げる**ことを基準にする。種別は通常フローと再探索フローの2つ。1フローは1つの手順版で実行する | ■フロー(実行の単位)の表「種別」「手順版」「スコープ規範」「中断・再開」 |
| 既存資産の流用 | 同じ操作手順の再探索が、AIの処理コストと時間の最大の浪費源 | 着手前の流用確認を義務化。前提状態は既存 fixture の実行が第一選択。部品化の判断は**フローをまたいで数える**。報告で流用/新規を区別し蓄積効果を測る | ■既存資産の流用 1〜5 |
| 再実行耐性とテストデータ | VM復元はスイート開始前の1回だけ。実行中はデータが蓄積し、retry 等で復元なしの再実行も必ず起こる | 作成データを実行ごとに一意化(`AT-<シナリオID>-<実行識別子>`)、アサーションは**自データにスコープ**、前提は毎回 established check で確認 | ■回帰実行の環境前提とテストデータ規約 1〜4 |
| オラクル(正解の定義) | 文書が不完全・不正確で、文書では正解が決まらない | **現行バージョンの実挙動を正解**とする。文書との食い違いは DISC に記録し、どちらが正しいかは人間が判断 | ■オラクル(正解の定義)の原則 / ■不整合レポート(DISC)規約 |
| 判定と検証手段 | 無理な合否判定はハルシネーションの温床。画面だけでは永続化層の破損を見逃す | 判定は4値(`passed`/`failed`/`human-check`/`blocked`)。検証は原則「画面+DB の両方」、DB単独には理由を1文 | ■判定と検証手段 |
| DB不変条件 | シナリオ個別の期待結果だけでは整合性の破壊(1ジョブ2課金等)を見逃す | 全シナリオ共通の事後チェック(INV)。**シナリオ末尾は自データ限定、スイート終端でDB全体**の2段構え。違反は自動リトライせず人間へ | ■DB不変条件 |
| 非決定値 | 実行ごとに変わる値を固定すると即壊れ、全部無視すると金額の誤りを見逃す | 値ごとの検証強度はカタログ(作業02)で決め、**AIが個別に判断しない**。未登録値は推測せず追加候補として報告 | ■非決定値の扱い |
| 非同期待機 | 固定待機は遅いか不安定かのどちらか | 固定待機を全面禁止。「**目的の状態が成立した**」を条件にするポーリング契約。DB側条件を優先。タイムアウトをAIが場当たりに変えない。実測値を残す | ■非同期完了の待機(ポーリング契約) |
| 外部操作 | Web UI 以外の操作(印刷指示・機器パネル・AD等)は、手段が用意されていなければ実行できない。AIが勝手に手段を作ると、検証されない手段が回帰テストに入る。回帰テストは実行時にAIを使わないため、AIだけが使える手段では回帰テストにならない。実機やVM外システムへの誤操作は巻き戻らない | **外部操作は skill を介してのみ**行い、skill は人間が段階的に整備する。skill には**コードから呼べる実行体の同梱**を求める。skill がなければ**外部操作需要リスト**に積み、該当シナリオは `blocked` にして先へ進む。整備後は**再探索フロー**で拾う。**禁止操作リスト+包括原則**(迷ったら実行しない)。確立した操作は **KB T05 に登録してから**使う。「リストは人間が守り、skill は人間が整備し、台帳はAIが育てる」 | ■外部操作(手段は skill に限る / 外部操作 skill の条件 / 禁止操作リスト / 外部操作需要リスト / 操作の資産化) |
| 知見ベース(KB) | 同じ調査の繰り返し。KB全読みはコンテキストを圧迫 | 索引だけ読んで該当ファイルに絞る。新知見はその場で反映。KBには事実だけ(判断はDISCへ)。KBに無く自分で調べた事項は発見ログへ。同一目的の調査は3回まで | ■知見ベース(参照規約/更新規約/発見ログ) |
| レビュー | 人間工数が有限で、承認待ちが全体を律速する | **非ブロッキング**。進捗軸とレビュー軸を分離し、全成果物にレビューヘッダ。後段で不調が出たら前段の未レビュー成果物を原因候補にする(切り分けプロトコル)。AIが「優先レビュー推奨」を申告 | ■非ブロッキングレビュー方針 |
| 人間の承認 | 何でも承認待ちにすると止まる。一方で止めるべき行為は確実に止めたい | 承認が要るのは「行為の許可」2つだけ(要許可操作/作業30のデータ変更)。加えて `failed`/`human-check` を as-is として凍結する判断はAIにさせない。手順改訂の区分Bの採否も停止点ではない | ■人間の承認が必要な例外(2つのみ) |
| プロトタイピング | 完璧な手順を事前に編み出すのは不可能 | 事前の完璧を狙わず、**手順の不備は実行中に直さずシグナルとして記録**し、作業40が改訂する。フェーズ0(パイロット)は廃止し、絞り込みは領域指示側で行う。F-001 の機能一覧確定は「初期化」として条件分岐に | ■プロトタイピング原則 / 同 ■初回フロー(F-001)の初期化 |
| 前提状態・部品・ロケータ | テスト項目間の依存、snapshot の一時IDの混入、壊れやすいセレクタ | 前提は初期状態セット4つだけ(AIが勝手に追加しない)。fixture+established check。`pages/flows/external/specs` の4層。ロケータは role→label→…→CSS の優先順位、CSSは `FRAGILE` 注記と `data-testid` 依頼 | ■状態の扱い / ■シナリオ部品の規約 / ■ロケータ規約 / ■ページオブジェクト規約 |
| 申し送り | 扱わなかった対象が消え、粗い網が説明できなくなる | 扱わないと判断した瞬間に**統制語彙の理由コード付き**で記録。AIは項目化しない | ■申し送り台帳 |
| 手順改善シグナル | 手順の不備が報告書の自由記述に散らばり、フローをまたいだ再発が見えない。前段の手順の不足が差し戻しで消費され、手順に戻らない | 迷い・矛盾・実行不能・逸脱・後段不足を、**その場で事実だけ**記録する(種別8つ・出所5つ)。どの手順についてかは**論理的な位置**(節・スロット・■見出し)で指す。**実行中に手順書を書き換えない**。逸脱は保護ブロックに触れない範囲に限る | ■手順改善シグナル |
| 手順書の版と配備 | 指標が変わっても、手順の改訂のおかげか、領域が易しかったからかを区別できない | 版を `vocab.meta.procedure_version`(git のタグ)で表し、全 status.yaml に転記。**配備はフローの境界だけ**で、1フローは1つの版。撤回も新しい版として配備 | ■手順書の版と配備 |
| 手順改訂の統制 | AIが手順を改善できるようにすると、「検証を弱めて摩擦を減らす」方向の改善が起こりうる(テストが緑のまま進むので気づけない)。一方で、人間が指示した改訂をAIが規約を理由に拒むのも困る | 改訂を**自律適用(A)/人間採否(B)/不可侵(C)**に分け、変更の位置と文言で機械的に判定。安全と検出力の根幹13項目を**保護ブロック**としてハッシュで固定。**区分は自律的な変更の範囲を決めるもので、人間の明示的な指示は区分に関わらず受け付ける**(成果物の中の文言は指示とみなさない)。効果の判定には**検出力ガード指標**を使う。自律適用は lint の保護機構の実装後に解禁 | ■手順改訂の統制 |
| 段階間の受け渡し | 自然文の報告書を人間が読んで次を判断しており、曖昧さとボトルネックの源になっていた。規約が守られたかは事後にしか分からない | 報告書は共通骨格+**5行以内の要約**(§8 は手順改善シグナルのID)。DoD は機械検査できる形。**status.yaml を段階間契約**にし、後段は報告書ではなく status.yaml から入力を取る。lint の ERROR が1件でもあれば次作業を起動しない | ■完了報告の共通骨格 / ■完了条件(DoD)の書式 / ■status.yaml 契約 / ■lint(29規則) |
| DB安全 | AIに sysadmin 権限を渡している | テスト環境のみ、ステップ1は `SELECT` のみ、DDL禁止 | ■DB操作の安全規約 |

### 4.2 `vocab.yaml` — 統制語彙の単一ソース

**一言で**: 判定値・理由コード・ID書式・既定値・分岐キーなど「決められた言葉」を1か所に集めたもの。手順書一式の版もここに持つ。

**対処する課題**

- 同じ語彙が 000 / 00 / 各指示書 / テンプレートに散在し、版ずれが実際に起きていた(廃止した理由コード `語彙外操作` の残存、操作ID書式 `DEV-OP-` の残存、テスト種別の旧称の残存)
- 自由記述が混じると、理由コード別の集計(= ステップ2・3の投資計画)が壊れる
- `pipeline.dot` の分岐条件が参照する値の定義場所が必要

**解決のアイデア**

- **値そのものは vocab、値の使い方の原則は 00** に分ける。値を増減するときは必ず vocab を先に変える
- テンプレート(90/91/92/93/94)の表は vocab の**写し**とし、食い違えば vocab が正(lint `vocab_sync` で検出)
- 語彙に「意味」だけでなく「次の投資」まで持たせ、集計がそのまま計画になるようにする

### 4.3 `pipeline.dot` — 実行順序と分岐の単一ソース

**一言で**: 「どの作業の次に何をするか、どこで止まるか、どこへ差し戻すか」を Graphviz の DOT 形式で書いたグラフ。

**対処する課題**

- 実行順序が 000(2か所)・00・各指示書冒頭に散在し、改訂時の波及管理が必要だった
- 「〜が多ければ〜する」のような自然文の分岐は解釈がぶれる
- 作業20でコード化できない項目が出ても、人間が報告書を読んで気づかないと作業10へ戻らなかった

**解決のアイデア**

- 順序・分岐・停止点・差し戻し先を**このファイルにだけ**書く
- 分岐条件で使える演算子を `=` / `!=` / `&&` の3つに限定する。**判断はノード(AI)の中で行い、辺は status.yaml に出力された列挙値でルーティングするだけ**にする(閾値判定などはAIが離散値にしてから出力する。数えれば決まる `improvement_due` は lint が出す)
- 本線は `10 → 20` の2作業だけ。01・02・30・40 は条件付き起動の枝にする
- 人間の判断点を `wait.human` ノードとして明示する
- `goal_gate` と `retry_target` で差し戻しを構造化する。ただし **DB不変条件の違反は差し戻さず人間判断へ**(自動リトライで揉み消さない)
- モデル割り当てと文脈量(fidelity)も宣言的に書く
- ランナー(実行エンジン)は導入しない。**人間とAIが読む仕様**として機能させる

**実装箇所**

| 箇所 | 見どころ |
|---|---|
| 冒頭コメント | 単一ソースであること、条件式の制約、保護ブロックの目印、描画コマンド |
| `graph [...]` | `goal`(1フローの到達目標)、`default_fidelity = "compact"`、`retry_target`、`model_stylesheet`(`.operate` = UI・外部操作用モデル、`.text` = テキスト処理用モデル、`.improve` = 作業40。実モデル名は未記入のプレースホルダ) |
| `start` ノード | 領域指示(通常フロー)だけでなく、再探索指示(再探索フロー)でも始まる |
| `due` ノードと `imp` ノード | フロー開始時に手順改善の要否を判定し、必要なら作業40を通ってから `pre` へ進む。`imp` は停止しない |
| `pre` ノードと3本の辺 | 事前作業(01/02)の要否をルーティングだけで決める |
| `exp` ノード | `goal_gate = true`, `allow_partial = true`, `retry_target = "exp"` |
| `cod` ノード | `goal_gate = true`, `retry_target = "exp"` |
| `perm` / `chg` / `inv` ノード | 人間の判断点(六角形)。要許可操作の許可、作業30のデータ変更許可、INV違反の判断。**保護ブロック**(HUMAN_APPROVAL / INV_NO_RETRY) |

| 注記1〜8 | goal_gate は訪問したノードしか検査しないので中断は `outcome: fail` で記録する / F-001 の初期化は条件分岐 / 30 は実際には独立起動してよい / ランナー未導入 / **再探索フローの経路** / 作業20で skill の不備が見つかっても差し戻さない理由 / **作業40の位置づけ**(フロー開始時・別セッション・停止しない・人間の指示による改訂はグラフの外でいつでも)/ 保護ブロック |

### 4.4 `stages.md` — 各作業に固有な内容

**一言で**: 旧 01/02/10/20/30 の5つの指示書を統合し、作業40を加えたもの。各作業の「固有部分」だけが書いてある。**AIには該当節だけを抜き出して渡す。**

#### 共通の仕組み(8スロット規約)

**対処する課題**: 旧5指示書では原則の再掲が多く、書き方もばらばらで、「この作業が終わった」の判定が暗黙だった。

**解決のアイデア**: 各作業を同じ8つの見出し(役割 / 起動条件 / 入力 / 固有手順 / 固有の禁止事項 / 出力 / DoD / status.yaml 契約)で書く。該当なしでも見出しを残して「なし」と書く(空欄は仕様の穴)。出力形式は散文で説明せず、**ゴールド例(付録A〜G)**で示す。**節番号とスロット番号は、手順改善シグナルが手順箇所を指すための位置でもある**(`ST/10/4-C` = §10 スロット4 パートC)。全作業の出力に手順改善台帳への記録があり、DoD に「報告書 §8 に SIG-ID(なければ「なし」)を列挙した」がある。

**実装箇所**: ■8スロット規約 / ■渡し方 / 目次(作業とノードIDの対応表)/ 付録A〜G

#### §01 知見蓄積(ノード `kb`・任意)

| 観点 | 内容 |
|---|---|
| 対処する課題 | 作業ごとに同じ調査(この画面はどこか、この列の意味は何か、この処理は何秒かかるか)が繰り返される。人間が調査項目を列挙するのは高コスト。文書が不足している |
| 解決のアイデア | 人間は**調査対象だけ**を指示し、何を調べるかは**後段の作業が必要とするものからAIが逆算**する。文献は転記せず**所在(ポインタ)だけ**記録。DB定義だけでなく**実データを観測**する(文書にしかない「死んだenum値」の発見)。**「分からなかったこと」も成果物**。外部操作の skill がなければ実行を試みず需要リストへ記録する。目標は発見ゼロではなく「同じ発見が二度起きないこと」 |
| 実装箇所 | 1.役割 / 2.起動条件(任意であること)/ 4.S1 の逆算表と逆算例 / S2(ポインタのみ・「文書に記載なし」の明記)/ S3(機械抽出部と注記部の分離、Q-001 への判断材料提供)/ S4(外部操作は skill のみ・なければ需要リストへ、非同期処理は3回実測してタイムアウト根拠を算出)/ カテゴリの拡張機構(KBカテゴリは暫定追加可、**理由コードは不可**という線引き)/ 6.固有セクション3「判明しなかったこと」・6「外部操作需要リストへの記録」/ 8.`knowledge_gap_resolved` |

#### §02 非決定値カタログ抽出(ノード `nd`)

| 観点 | 内容 |
|---|---|
| 対処する課題 | 「実挙動を正解として凍結」する方式では、毎回変わる値(ジョブID・日時等)を固定すると即壊れ、逆に全部検証しないと金額・枚数の誤りを見逃す。取り違えると**テストが緑のまま不具合を通す** |
| 解決のアイデア | **推測ではなく観測で決める**。回帰実行と同じ条件(復元を挟まない)で同じ入力を3回連続実行し、何が変わるかを実測。強度は上位から検討(関係式にできないか→パターン一致にできないか→最後に存在のみ)。業務的に重要な値の揺れは強度を下げる前に報告。観測中に編み出した操作列はKBへ回収。初回作成+以降は増分のみ |

#### §10 シナリオ生成と探索(ノード `exp`・本線⑴)

| 観点 | 内容 |
|---|---|
| 対処する課題 | 文書が不完全で、操作手順を事前に書けない。探索結果が曖昧だと、コード生成時に画面や文書を再解析する羽目になる。AIが範囲を勝手に広げたり、扱わない対象を黙って落としたりする。外部操作の skill がまだないシナリオが、整備後に拾われずに埋もれる |
| 解決のアイデア | **シナリオには操作手順を書かず、検証意図と判定基準だけを書く。手順は探索でAI自身が編み出す**(これが本作業の本質)。生成(パートB)と探索(パートC)を1作業で連続実行。スコープは単機能粒度・正常系・代表1値に固定し、外れる対象は台帳へ。成果物は**作業20が再解析なしでコードを書ける具体性**(成功した最短操作列・安定ロケータ・assertion_hint・実測待機秒・持ち回りデータ)で残す。**変更してよいのは検証手段だけ**で、期待結果・判定基準は変えない(**保護ブロック**)。作業20とは連続実行せず停止する。skill のない外部操作を含むシナリオも**作成して blocked で残し**、需要リストに記録する。skill 整備後は**再探索フロー(パートR)**で同じシナリオを探索し直す |
| 実装箇所 | 1.役割 / 2.起動条件(退出時に停止、フロー種別による手順の切り替え)/ 4.パートA(A1 領域指示を原文転記・手順版を記録、A2 F-001だけ機能一覧確定、A3 資産棚卸し、A4 未経験機構は1本先行してよい)/ **パートR**(再探索フロー: R1 フロー記録、R2 skill と実行体の確認、R3 対象シナリオの特定、旧記録を残して追記)/ パートB(スコープ、妥当性基準「利用者が実際に行う一連の作業か」、記載ルール1〜9。ルール6が外部操作と需要リストへの記録)/ パートC フェーズA(既存fixture優先、セットアップは2回実行、確認できなければ `verified: false`)/ 探索の進め方(**T05 登録の7手順**。手順3で skill と実行体を確認、手順4で実行体だけで完結することを確認)/ 安定ロケータの解決(操作成功直後にその場で)/ 検証と判定 / 記録(手順改善シグナルもその場で)/ 5.固有の禁止事項 / 6.報告書の固有セクション1〜12 / 7.DoD(パートB 8項目・パートC 18項目・パートR 6項目)/ 8.status.yaml(`codeable_items` が作業20の入力、`assertion_gap_items`・`ext_demand_*` 等)/ 付録A(exploration-log のゴールド例。`blocked_by` に需要IDと申し送りID)・B(setup-log)・C(scenarios.md) |

#### §20 回帰テストコード生成(ノード `cod`・本線⑵)

| 観点 | 内容 |
|---|---|
| 対処する課題 | 実行時にAIを使うテストはコスト・再現性・速度で不利。コード生成時にAIが操作を「発明」すると、検証されていない手順が混入する。不具合を回帰テストの正解として凍結してしまう危険。項目が黙って落ちる。flaky(不安定)なテストは回帰テストの信頼を失わせる。前段の記録の不足が差し戻しで消費され、作業10の手順が直らない。CI で落ちたテストがどの手順で作られたか分からない |
| 解決のアイデア | **実行時にAIを使わない決定的コード**を生成(**保護ブロック**)。作業10で実証された操作列を**忠実に**コード化し、不足は推測で埋めず差し戻す。入力は報告書の読解ではなく **status.yaml の `codeable_items`**。開始時に**手順版が作業10と同じか確認**する。**コード生成の前に外部操作 skill の配備と実行体の同梱を確認**し、不備があるシナリオは差し戻さずスキップ(未配備なら配備後に再実行、実行体なしなら改修後に再探索フロー)。**ID突合**(一意性・完全性・ステップ完全性)を必須にし、スキップも理由付きで突合表に残す。VM復元後に実行し、さらに**復元なしで3回連続実行**して flaky を特定。flaky の対処でテスト側の強度を下げない。as-is 判断が済んでいない `failed`/`human-check` はコード化しない。「コード化不能」「逸脱」は**作業10の手順箇所を指す後段シグナル**としても記録する。全テストに**生成元の注釈 `generated-by`**(フローIDと手順版)を付ける |
| 実装箇所 | 1.役割 / 3.入力(コード化対象リストの取り方)/ 4.手順版の確認(開始時)/ 既存回帰テストセットへの統合(IDは全フロー通算で一意、突合表は累積、共通資産変更時は依存テストも実行)/ **外部操作 skill の確認**(3項目と不備の扱い)/ ID突合検証と突合表の例 / 生成コードの実行確認1〜4 / **後段シグナルの記録** / 5.固有の禁止事項 / 7.DoD(26項目)/ 8.status.yaml(`rework_required` が差し戻しの分岐キー、`ext_skill_unavailable` は差し戻しに含めない、`deviations`)/ 付録F(1シナリオ=1 `test()`・各ステップ=`test.step()`・IDタグと `generated-by` 注釈、`両方` は画面とDBの両アサーション、`// DB-ONLY:` コメント、INV の `afterEach` と `globalTeardown`、ラッパは実行体を呼ぶだけ、`@external` タグと操作対象ごとの直列化 `@serial-<対象略号>`、`serial` は最終手段) |

## 5. 手順書作成にあたり参考にした一般的なアプローチ

ここでは、(A) 手順書・検討資料で**明示的に参照しているもの**と、(B) 名前は出ていないが**一般的な手法に対応しているもの**を分けて示す。

### 5.1 (A) 明示的に参照しているもの

#### ① StrongDM Attractor(NLSpec)— 4層構成化の直接の参考

**概要**: AIエージェントによるソフトウェア開発ワークフローを定義する仕様群(https://github.com/strongdm/attractor)。ワークフローを DOT 形式のグラフで書き、各ノード(AIの作業)は `status.json` を出力し、エンジンはそれだけを読んで次のノードへルーティングする。本質は「DOTを使うこと」ではなく、**ワークフローを自然文の手順ではなく〈離散状態+遷移条件+到達すべきゴール〉として書き、AIには手順ではなく到達条件を渡す**ことにある。

検討の結論(`96 Attractor適用検討.md` 0章): 本パイプラインは統制語彙・機械可読なYAML・外部オラクルを既に持ち、同じ方向に7割方到達していた。欠けていたのは「離散値が報告書の自然文の中にあり、次段の起動条件を決める機械可読な状態になっていないこと」だった。

**取り入れたポイント**

| Attractor の要素 | 概要 | 本手順書での取り入れ方 | 箇所 |
|---|---|---|---|
| DOTによるワークフロー定義 | グラフがそのまま仕様(プログラム) | 順序・分岐・停止点の単一ソース。ランナーは作らず「読む仕様」として使う | `pipeline.dot` |
| 意図的に貧弱な条件式 | `=` / `!=` / `&&` のみ。判断はノード、辺は列挙値 | 同じ制約を採用。閾値判定はAIが離散値にしてから出力 | `pipeline.dot` 冒頭 / `00` ■status.yaml 契約 規約2 |
| status.json 契約 | 各ノードが outcome と context_updates を書く | **status.yaml** として導入。report.md は人間用として残し役割を分ける | `00` ■status.yaml 契約 / `stages.md` 各§8 |
| goal_gate / retry_target | 未達のゲートがあれば差し戻し先へ戻る | `exp`・`cod` にゲート、`cod → exp` の差し戻し。**INV違反は差し戻さず人間へ**という例外を追加 | `pipeline.dot` |
| PARTIAL_SUCCESS | 「完了したが積み残しあり」に名前を付ける | `blocked`/`human-check` があれば `partial_success`(粗い網として正常) | `00` ■status.yaml 契約 規約3 / `exp` の `allow_partial` |
| Definition of Done | 仕様が自らの合格条件をチェックリストで持つ | 全作業のスロット7。機械検査できる形で書く | `stages.md` 各§7 / `00` ■DoD の書式 |
| 実行前バリデーション(lint) | ERROR があれば実行を拒否 | 29規則。ERROR 1件で次作業を起動しない。**DoD がそのまま lint の仕様** | `00` ■lint |
| モデルスタイルシート | CSS風セレクタでノードのモデルを一括指定 | `.operate` / `.text` / `.improve` の3クラス | `pipeline.dot` `model_stylesheet` |
| コンテキスト忠実度 | 次段へ持ち越す文脈量を宣言 | `default_fidelity = "compact"` | `pipeline.dot` |
| 多段の既定値と上書き | 各ノードは既定と異なる点だけを書く | `00` = 既定、`stages.md` = 差分 | 4層構成全体 |

**取り入れなかったもの**: ランナー(実行エンジン)の本格実装(将来の任意事項)/ 「コードを人間がレビューしない」原則(課金の致命性・互換性制約・外部依存のクローン基盤がないため。as-is 凍結判断はAIにさせない方針を維持)

#### ② StrongDM Software Factory の技法 — Attractor の背景思想

| 技法 | 概要 | 本手順書での対応 |
|---|---|---|
| Scenario(≠ Test)/ holdout | ユーザーストーリーをコードベースの**外**に置き、コードに合わせて書き換えられないようにする | `scenarios.md` は `work/`、テストは `tests/`。作業10は期待結果の書き換え禁止、作業20は作業10の記録にない操作を足さない |
| Gene Transfusion | 実例(exemplar)を示して動くパターンを移植する | 出力形式を散文ではなく**ゴールド例**(付録A〜G)で示す。シナリオ粒度の基準例も付録Cに埋め込む予定(`000` §5) |
| Pyramid Summaries | 圧縮しても詳細へ展開できる多段要約 | 報告書冒頭の**5行要約**+status.yaml → 必要な節だけ開く。KBの「索引→エントリ→文書ポインタ」 |
| The Filesystem | ファイル・索引をモデルの記憶基盤として使う | `kb/`、`work/_flows/flow.md`、各台帳。DBや重厚なツールを使わない |
| Shift Work | 対話が必要な作業と無人実行できる作業を分ける | 人間の判断が要る点を停止点3つに限定し、それ以外は連続実行 |
| Digital Twin | 外部依存の振る舞いクローンを作る | **未採用**。申し送り台帳の `操作手段なし`・`状態未整備`・`禁止操作` の件数と外部操作需要リストが、機器シミュレータ等への投資順位になるという整理に留めている(ステップ3候補) |
| Satisfaction | 二値ではない確率的な満足度指標 | **未採用**(検討資料で提案のみ) |

#### ③ 自律テスト成熟度モデル(Katalon ASTM ほか)

**概要**: テスト自動化の自律度を自動運転のように Level 0(完全手動)〜 Level 5(完全自律)で段階化したもの。Level 3 は「AIが生成・実行・保守・分析を担い、人間はレビューとガバナンスに回る」、Level 4 は「差分検知から報告までの閉ループ」。

**取り入れたポイント**: 目標を **Level 3 の確立+Level 4 要素の段階的取り込み**に置いた(`説明資料` 1〜2章)。AIがテスト項目策定からコード生成までを担い、人間はガバナンスに専念する分担、回帰実行にはAIを使わない決定的実行、`goal_gate` による差し戻し(人間が再実行するのではなくパイプラインが収束する方向=Level 4 への布石)に反映されている。手順の自己改善(作業40)は、Level 4 の「保守・最適化をAIが閉ループで回す」考え方を、テストコードではなく**テストを作る手順**に適用したものである。ただし安全と検出力の根幹は人間が握る。

#### ④ Intent-Driven Testing(意図駆動テスト)

**概要**: エージェントに操作手順ではなく高レベルの意図を与え、手順は自律的に探索させる研究方向。

**取り入れたポイント**: シナリオには**検証意図と判定基準だけを書き、操作手順は探索でAIが編み出す**(`stages.md` §10 1.役割、パートB 記載ルール2)。

#### ⑤ Human-on-the-Loop(人間は並行して監督する)

**概要**: 各段で人間の承認を待つ Human-in-the-Loop ではなく、人間は並行して監督し、必要な箇所に介入する運用。

**取り入れたポイント**: 非ブロッキングレビュー、進捗軸とレビュー軸の分離、切り分けプロトコル、AIによる優先レビュー推奨の申告、承認は「行為の許可」2つだけ(`00` ■非ブロッキングレビュー方針 / ■人間の承認が必要な例外)。手順改訂の区分Bの採否も、フローを止めない。

#### ⑥ ACE(Agentic Context Engineering)— 手順の自己改善の参考

**概要**: LLMに渡す文脈(プロンプト・手順)を、実行の結果から自己改善していく枠組み(Zhang et al., 2025, arXiv 2510.04618)。実行役(Generator)・振り返り役(Reflector)・統合役(Curator)に役割を分け、文脈を丸ごと書き直すのではなく**局所的な差分**で更新する。丸ごとの書き直しを繰り返すと、蓄積した詳細が失われていく現象(context collapse)を指摘している。

**取り入れたポイント**

| ACE の要素 | 本手順書での取り入れ方 | 箇所 |
|---|---|---|
| 役割の分離(Generator / Reflector / Curator) | 各作業の実行AIがシグナルを記録し、作業40(別セッション)が振り返りと改訂を行い、lint が区分と保護ブロックを検査する | `00` ■手順改善シグナル / `stages.md` §40 / `00` ■lint |
| 差分(delta)による更新 | 1 IMP = 1 手順箇所の差分。全面・節単位の書き直しをしない | `stages.md` §40 S3 |

**取り入れなかったもの・加えたもの**: ACE は正解ラベルや実行結果を材料に文脈を自由に育てるが、本手順書では**検出力を下げる方向の改善を防ぐ仕組み**(保護ブロック・区分・検出力ガード指標・判定基準の事前登録)と、**手順の肥大化を既定で防ぐ仕組み**(削減の先行検討、効果不明の追加は撤回)を加えた。課金の致命性と、テストが緑のまま不具合を通す失敗は気づきにくいという性質のためである。
