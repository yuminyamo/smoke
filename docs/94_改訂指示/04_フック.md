## 0. 始める前に(この段は任意)

**この段は、人間が「行う」と判断したときだけ行う。** 次の2つを人間に確かめ、どちらかが満たされなければ何もせずに終わる(その旨を報告する)。

1. 段3の計測(`pms stats` の実行形態 `b1`)で、記録のない操作による不合格(`seq_missing`)や出し直し、「続けて」と伝える手間が目立ち、人間がフックを入れると決めた
2. 組織の Copilot の設定で、フック(プレビュー機能)が許可されている

## 1. この段でやること(要約)と意図

VS Code + Copilot のチャットで進める B1 のときに、取り決めから外れた動きを**その場で**押し戻すフックを入れる。

- **正しさは変わらない。** 記録の正しさは段1〜3の `pms act`・キュー・`pms submit` が担保している。フックが減らすのは、直接呼んだ操作のやり直しと、入口が止まったときに「続けて」と伝える手間である(`docs/004_フック処理_図解.html` の7-5)
- そのため、**フックが動かない環境でも手順は成り立つ**ように書く。フックに頼る規定(「フックがあるので〜しなくてよい」)を手順書に書かない
- 主な経路の B2(`pms run`)には影響させない。Copilot CLI も `.github/hooks/*.json` を読むため、B2 のセッション(`PMS_RUNNER=b2`)ではフックが何もしないようにする

## 3. 作るもの

### 3.1 最初に: 端末ツールの名前を確かめる

VS Code のドキュメントによると、端末ツールの `tool_name` は環境ごとに違う。まず、受け取った入力の `tool_name` と、コマンドの最初の語だけを記録するフック(監査用)を置く。**コマンドの全文や値は記録しない**(秘密情報が混ざるため)。人間に B1 で1枚のカードを流してもらい、記録から実際の名前を確かめてから 3.2 を書く。

### 3.2 フックのスクリプト(`tools/hooks/`)

| ファイル | イベント | 行うこと |
|---|---|---|
| `guard.mjs` | PreToolUse | 端末で playwright-cli を直接呼ぶ(`npx` 経由を含む)、`tools/env/env.mjs get ... --reveal` を呼ぶ、`procedure/`・生成した skills・エージェントに書き込む、のどれかなら `permissionDecision: "deny"` で拒否し、理由に正しいやり方(例: `pms act click e6 --intent "…"`)を書く |
| `stop-gate.mjs` | Stop・SubagentStop | 入力の `stop_hook_active` が true なら通す(無限ループを避ける)。`pms status --json` で、現在のカードが未提出なら `{"decision":"block","reason":"…"}` で続けさせる。STOP(人間の判断待ち)や done なら通す |
| `after-tool.mjs` | PostToolUse | 現在のカードがあれば、文脈に `now`・`next` を1行足す。`pms act` の結果が `css` や一意でないロケータなら警告を足す |
| `session-start.mjs` | SessionStart・SubagentStart | `pms status` の現在地を最初の文脈に入れる |
| `pre-compact.mjs` | PreCompact | 現在のカードと再開のコマンドを状態ファイルに書く(PreCompact は AI に文脈を足せないため、記録だけ) |

- どのスクリプトも、`PMS_RUNNER=b2` のときは何もせずに通す
- フローが特定できないとき(pms を使っていない会話)は何もせずに通す
- 失敗(例外・`pms` が動かない)のときは通す。**フックの不具合で作業を止めない**
- 秘密情報を出力・記録に出さない

### 3.3 設定ファイル

- `.github/hooks/pms.json` に置く。VS Code は Copilot CLI の形式(`version` を持つ形)も読むとドキュメントにあるため、**1つのファイルで VS Code と Copilot CLI の両方に効く形式**を選ぶ。どちらの形式を選んだかと理由を `tools/hooks/README.md` に書く
- Windows でも動くこと(`node tools/hooks/<名前>.mjs` の形にし、必要なら Windows 用のコマンドの欄を書く)
- エージェントごとのフック(`.agent.md` の `hooks`)はプレビューのため使わない

### 3.4 Kiro

Kiro では行わない。IDE のフックにはツール名と引数が渡らず(kirodotdev/Kiro Issue #7500)、Stop で続けさせることもできないため、段1〜3の仕組みだけで進める。利用説明書の既知の制約に書く。

## 4. 手順書の変更

- `00_common.md` に短い節 **■ フック(任意の補助)** を足す。フックの役割、正しさは pms が担保しフックの有無で変わらないこと、設定の置き場所、止め方(ファイルを外す)、Kiro では使わないこと。フックに頼る規定を書かない
- `stages.md` は変えない(フックはどの作業の手順も変えない)
- 利用説明書の第2部(管理者向け): フックの有効化(`chat.useHooks`、ワークスペースの信頼、組織の設定)、動作の確認のしかた、止め方

### 変えないもの

- 保護ブロック・`pipeline.dot`・`stages.md`
- `pms` の検査・記録・出し直しの規則(フックがあってもなくても同じに動くこと)

## 5. テスト

`tools/hooks/test/` に置く。入力の JSON の見本を標準入力に渡し、出力と終了コードを確かめる。

- `guard.mjs`: 拒否すべき各コマンドで deny と理由。`pms act` や読み取りのコマンドは通す。`PMS_RUNNER=b2` で通す
- `stop-gate.mjs`: 未提出なら block、`stop_hook_active: true` なら通す、STOP・done なら通す、`pms` が失敗したら通す
- `after-tool.mjs`・`session-start.mjs`・`pre-compact.mjs`: 出力の形と、秘密情報が出ないこと

## 6. 人間が確かめること(完了報告に書く)

1. VS Code で `.github/hooks/pms.json` が読み込まれていることの確かめ方
2. B1 で1フローのパートCを進め、`pms stats` の `b1` の `seq_missing` と出し直しの回数が、段3の計測より減ったか
3. B2(`pms run`)の動きと費用が、フックを入れる前と変わらないこと
