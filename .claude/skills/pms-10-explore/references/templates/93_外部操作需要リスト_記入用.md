# 外部操作需要リスト(記入用テンプレート)

配置先: `work/_common/external-op-demand.md`
記入者: **生成AI**(需要の記録・要求元の追記・確立結果の反映) / **人間**(優先度・整備記録・見送りの判断)

---

## この台帳の役割

外部操作(Web UI 以外の手段で行う操作。`vocab.external_op`)は、**外部操作 skill を介してのみ**行う。skill の整備はコストがかかるため段階的に行い、特に初期は必要な skill が揃っていないことが多い。

この台帳は、**回帰テストを作る過程で必要と分かった外部操作を累積し、人間が優先度を付けて skill を整備できるようにする**ためのものである。

- **外部操作1つにつき1行。** 1つの外部操作が複数のシナリオを止めるため、優先度の判断材料は操作単位で集める(シナリオ単位の欠落は申し送り台帳 `91` が受け持つ)
- **需要の記録と skill の整備を切り離す。** AIは必要と分かった瞬間に記録するだけで、整備を待たずに作業を続ける。人間は任意の時期にこの台帳を見て、まとめて整備する
- **どの skill があるかの一覧ではない。** skill の正本は skills の機構である。ここに書く skill名は、動作環境に skill がない場合に探して配備するための参考情報である

## ライフサイクル

```
 [AI] 需要の発生 ────────────▶ 未整備 ──[人間] skill を整備し整備記録を記入──▶ 整備済
      (作業10パートB・C / 01 / 02)   ▲                                           │
       同じ操作なら要求元を追記       │                         [人間] 再探索フローを指示
                                     │                                           ▼
                                     └──── 確立できず(区分を更新)──── [AI] 再探索(§10 パートR)
                                                                                 │ 確立できた
                                                                                 ▼
                                      [人間] 整備しないと判断 ──▶ 見送り          確立済(KB T05 の操作IDを記入)
```

| 段階 | 誰が・いつ | この台帳への記録 | 他の記録 |
|---|---|---|---|
| 需要の発生 | AI。使える skill がないと判明したとき | 行を追加(状態 `未整備`)、または既存行の要求元に追記 | 申し送り台帳に `操作手段なし`(想定手段に需要ID)。当該ステップ以降は `blocked` |
| skill の整備 | 人間。任意の時期に | 整備記録(整備日・skill名)を記入し、状態を `整備済` にする | — |
| 再探索 | AI。人間が再探索フローを指示したとき | 確立できたら `確立済` にして操作IDを記入。確立できなければ `未整備` に戻し、不足の区分を更新 | KB T05 に登録。解消した申し送り行を `done` に |
| 見送り | 人間 | 状態を `見送り` にし、備考に理由を書く | — |

## 統制語彙(`vocab.yaml` の写し。食い違ったら vocab を正とする)

### 状態(`vocab.ext_demand_status`)

| 状態 | 意味 |
|---|---|
| `未整備` | 回帰テストに使える skill がない(理由は不足の区分) |
| `整備済` | 人間が skill を整備・改修し、整備記録を記入した。操作は未確立(再探索待ち)。使えるかどうかは使用時に skills の機構で確認する |
| `確立済` | AI が skill を使って操作を確立し、KB T05 に登録した(操作IDを記入) |
| `見送り` | 人間が整備しないと判断した |

### 不足の区分(`vocab.ext_gap`)— 状態が `未整備` の行に書く

| 区分 | 意味 | 次の一手 |
|---|---|---|
| `skillなし` | skills の機構で該当する skill が見つからない | skill の新規整備 |
| `実行体なし` | skill はあるが、コードから呼べる実行体を同梱していない(回帰テストにできない) | skill への実行体の追加 |
| `確立不可` | 条件を満たす skill はあるが、調査上限まで試しても操作を確立できない | skill の説明・KBの補強、または skill の改修 |

### 代替手段(`vocab.ext_alternative`)

`なし` / `あり` / `不明`。Web UI や DB の確認で、その外部操作を使わずに同じ検証意図を満たせる見込みがあるか。`あり` の場合は備考に内容を1文で書く。

### 操作対象(`vocab.external_op.target`)

`実機` / `シミュレータ` / `CLIENT` / `AD` / `SMTP` / `PMS-OS`。型番や識別子が決まっていれば `実機:<型番>` のように書く。

## AIの記入ルール

1. **その場で記録する。** 使える skill がないと判明したら、作業を止めずにその場で記録する(作業10パートB・パートC、作業01、作業02)
2. **重複させない。** 追記の前に、同じ外部操作(業務語)と操作対象の行がないかを確認する。あれば新しい行を作らず、要求元に追記する(lint `ext_demand_unique`)
3. **事実だけを書く。優先度は付けない。** 優先度の判断材料になる事実(要求元・代替手段・禁止操作との関係)を正確に書くことがAIの責任である
4. **`整備済` は出来事の記録として扱う。** 使えるかどうかは使用時に skills の機構で確認する。整備記録と食い違ったら(整備済なのに skill が見つからない、実行体がない等)、報告書に書く
5. **skill を作成・改変しない。** 整備は人間が行う
6. 申し送り台帳の `操作手段なし` の行は、想定手段欄にこの台帳の需要IDを書く(lint `ext_demand_linked`)

## ◆ 人間向け補足

- **優先度は人間が付ける。** 目安は次のとおり(どれを重く見るかは状況次第でよい)
  - 要求元の件数が多い(止めているシナリオが多い)
  - 要求元に課金など影響の大きい機能が含まれる
  - 代替手段が `なし`
  - 操作対象がシミュレータ(VMで巻き戻るため整備・運用の負担が小さい)か、実機か
- **skill を整備するときは、外部操作 skill の条件を満たすこと。** コードから呼べる実行体(CLI・スクリプト)を同梱し、非対話で起動でき、成否を機械的に判定できること(`00_common.md` ■外部操作 skill の条件)。条件を満たさない skill は、AIが使えても回帰テストにならない
- 整備したら、この台帳の整備記録を書いて状態を `整備済` にし、**再探索フローを指示する**(例: 「EXT-002 を再探索して」)。整備記録を書いただけではシナリオは探索し直されない
- 1つの skill で複数の需要を満たせる場合は、該当する全行に同じ整備記録を書けばよい
- 整備しないと決めた需要は `見送り` にし、理由を備考に残す。放置された `未整備` と区別できる
- `確立不可` が続く需要は、skill の説明が不足しているか、skill 自体が対象の操作に合っていない可能性がある。KB T05・`kb/gotchas/` の記録と合わせて見る
