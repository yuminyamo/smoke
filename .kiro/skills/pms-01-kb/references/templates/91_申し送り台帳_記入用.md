# 申し送り台帳(記入用テンプレート)

配置先: `work/_common/handoff-register.md`
記入者: **生成AI**(項目生成時・探索時にその場で追記) / 人間(レビュー時に引き継ぎ先を調整)

---

## この台帳の役割

ステップ1で**意図的に扱わなかった対象**を記録し、ステップ2・3へ引き継ぐ。

- 判断した瞬間が記録コストの最も低いタイミングである。後から洗い直すと同じ分析をやり直すことになる
- **「扱わなかった」を「管理された欠落」に変えるための台帳**である。これがあることで、ステップ1の粗い網が説明可能になる
- 理由コード別に集計すると、**ステップ2・3の計画がそのまま出てくる**

**AIは気づきを項目化してはならない。この台帳に記録するだけにとどめる。**

---

## 理由コードの統制語彙

| コード | 意味 | 既定の引き継ぎ先 |
|---|---|---|
| `同一経路` | 構造的に同じ処理経路を値違いで通るだけのため代表1件に畳んだ | ステップ2 |
| `異常系` | 異常系・境界値・入力検証・権限外のため基本動作の範囲外 | ステップ2 |
| `基本操作外` | 基本操作に該当しないため対象外 | ステップ2 |
| `初期状態外` | 初期状態セット外の前提状態を要する(**実操作では作成可能**) | 連結シナリオ |
| `状態未整備` | **実操作で作れない**前提状態を要する | ステップ3 |
| `操作手段なし` | 必要な外部操作に使える skill がない、または skill があっても操作を確立できない(旧 `語彙外操作`)。**外部操作需要リストの需要IDを必ず参照する** | 要人間判断 |
| `禁止操作` | 禁止操作リストの `禁止` / `要許可` に該当する、または包括原則でエスカレーションした | 要人間判断 |
| `E2E非効率` | E2Eで確認できるが手段として非効率(組み合わせ爆発等) | ステップ3 |
| `判定不能` | 期待結果を確定できない | 要人間判断 |

**`操作手段なし` と `禁止操作` の判別基準**: 手段がないのか、手段はあるが実行してはならないのか。前者の投資先は外部操作 skill の整備(外部操作需要リスト `93` で優先度を判断)、後者は人間の許可判断または代替手段の設計であり、次の一手が異なる。

**`操作手段なし` の内訳**: 理由コードは増やさず、外部操作需要リストの「不足の区分」(`skillなし` / `実行体なし` / `確立不可`)で区別する。skill がないのか、skill はあるのに使いこなせないのかで、次の一手(skill の整備か、skill・KBの補強か)が異なるためである。

**`初期状態外` と `状態未整備` の判別基準**: その前提状態を、現在のUI操作(+確立済みで禁止操作リストに抵触しない外部操作)だけで作れるか。作れるなら `初期状態外`(連結シナリオによるシナリオ連鎖またはステップ2のfixture整備で解決)、作れないなら `状態未整備`(ステップ3のデータセットアップ基盤が必要)。この区別が投資判断の集計を正確にする。

## 台帳

**レビュー扱い**: 本台帳はAIが追記し、人間のレビューを待たずに後段(ステップ2・3の計画立案)が参照してよい(00の非ブロッキングレビュー方針)。人間が内容を確認した行は `状態` を `open` のまま `review` 列で `reviewed` と記録する(列がなければ備考に記載)。

|---|---|---|---|---|---|---|---|
| HO-XXX-001 |  |  |  |  |  |  | open |

### 各列の記入要領

| 列 | 記入内容 |
|---|---|
| ID | `HO-<機能コード>-<3桁連番>`。機能横断のものは `HO-COM-<連番>` |
| 対象 | 何を扱わなかったか。1文で具体的に(「異常系全般」のような粗い記述は不可) |
| 理由コード | 上表の統制語彙から選択。自由記述禁止 |
| 引き継ぎ先 | `連結シナリオ` / `ステップ2` / `ステップ3` / `要人間判断` |
| 想定手段 | 検証手段の見当。**分からなければ空欄でよい**(空欄を埋めるために推測しない)。ただし理由コードが `操作手段なし` の行は、**外部操作需要リストの需要ID(`EXT-<3桁>`)を必ず書く** |
| 発生元 | 記録のきっかけになったフローID・作業・項目ID(例: `F-002 / 作業10 / SC-PRT-01-S1`) |
| 起票日 | 記録した日 |
| 状態 | `open` / `planned`(ステップ2・3で計画済) / `done`(処理済。`操作手段なし` の行は再探索フローで解消したとき) / `dropped`(不要と判断) |

## ◆ 人間向け補足

- **件数が多いことは失敗ではない。** ステップ1が正しく粗い網に留まっている証拠である。レビューで「項目が足りない」と感じたら、まずこの台帳に入っているかを確認すること。入っていれば設計通りである。
- **理由コード別の集計が、ステップ2・3の計画そのものになる。** どの理由が多いかで次の投資先が決まる。
  - `同一経路` が多い → 組み合わせテストの手法整備が効く
  - `初期状態外` が多い → 連結シナリオへの早期着手とfixture整備が効く
  - `状態未整備` が多い → データセットアップ基盤(DB投入)への投資が効く
  - `操作手段なし` が多い → 外部操作 skill の整備が課題。**どの skill から整備するかは、この台帳ではなく外部操作需要リスト(`93`)で操作単位に判断する**(1つの外部操作が複数の行を生んでいるため)
  - `禁止操作` が多い → 禁止操作リストの制約が厳しすぎるか、シミュレータでの代替環境の整備が必要
  - `E2E非効率` が多い → HTTP層・DB層への降下を検討する段階
- `想定手段` が空欄のまま残っている項目は、ステップ2・3の設計時に検討する。空欄を埋めるためにAIに推測させないこと(誤った見当が計画を歪める)。
- `判定不能` は仕様の欠落を示している。有識者ヒアリング→仕様書追記のサイクルに乗せる候補になる。
- ステップ2の開始時、`引き継ぎ先: ステップ2` かつ `状態: open` の行を抽出すれば、それがそのまま単発型項目の生成対象リストになる。
