配置先: `work/_common/state-demand.md`
記入者: **生成AI**(需要の記録・要求元の追記・整備結果の反映) / **人間**(採否・判断日・状態ID と定義の修正)

## この台帳の役割

ステップ1のシナリオの前提状態(`requires`)には、**初期状態セット**の状態だけを使う。初期状態セットは、`vocab.initial_state_set` の基本の状態と、**この台帳で人間が採用した状態**を合わせたものである(`00_common.md` ■状態(前提条件)の扱い)。

単機能粒度では、ある機能の結果(例: ジョブログの収集)を前提にする別の機能(例: ジョブログの表示・検索)のシナリオは、その結果が前提状態として使えなければ書けない。この台帳は、**回帰テストを作る過程で必要と分かった前提状態を累積し、人間が採用した状態を以後のフローで使えるようにする**ためのものである。

- **状態1つにつき1行。** 1つの状態が複数のシナリオ候補を止めるため、採否の判断材料は状態単位で集める(シナリオ単位の欠落は申し送り台帳 `91` が受け持つ)
- **需要の記録と採否を切り離す。** AIは必要と分かった瞬間に提案するだけで、採否を待たずに作業を続ける。人間は任意の時期にこの台帳を見て、まとめて採否を決める。**採否はフローの停止点ではない**
- **状態カタログ(作業30)ではない。** 状態カタログはステップ2の語彙を網羅的に作るもの、この台帳はステップ1で具体的に需要の出た状態を1つずつ足すものである。作業30はこの台帳を入力として読む

## 統制語彙(`vocab.yaml` の写し。食い違ったら vocab を正とする)

### 状態(`vocab.state_demand_status`)

| 状態 | 意味 |
|---|---|
| `提案` | AI が、初期状態セットにない前提状態の需要を記録し、状態として追加することを提案した(人間の採否待ち。フローは止めない) |
| `採用` | 人間が採用した。以後のフローで requires に使える(初期状態セットに含まれる)。fixture は未整備 |
| `整備済` | AI が実操作で fixture と established check を整備した(fixture の所在を記入)。初期状態セットに含まれる |
| `不採用` | 人間が採用しないと判断した(理由を備考に書く)。要求元の申し送りは元の理由コードのまま残る |

### 分類(`vocab.state_category`)

`AUTH` / `DATA` / `ENTITY` / `CONFIG` / `ENV`。意味は `stages.md` §30 の分類の表と同じ。

## AIの記入ルール

1. **その場で記録する。** シナリオ候補の前提状態が初期状態セットにないと分かったら、申し送り台帳に `初期状態外` で記録し、提案の条件を満たせば作業を止めずにこの台帳にも記録する(作業10パートB)
2. **提案の条件**(すべてを満たすものだけを提案する):
   1. 実操作で作れる見込みがある(`状態未整備` に当たるものは提案しない)
   2. 要求元に、具体的なシナリオ候補の申し送りIDがある(先回りして提案しない)
   3. パラメータの差を状態にしない(代表1値で足りる状態にする)
   4. 組み合わせ状態を作らない(既存の状態を `requires` に並べて表せるものは提案しない)
   5. 検証したい事柄そのもの、画面上の一時的な表示状態、他のテスト項目の実行結果を状態にしない
3. **重複させない。** 追記の前に、同じ意味の状態が基本の状態(`vocab.initial_state_set`)とこの台帳(状態を問わない)にないかを確認する。あれば新しい行を作らず、要求元に追記する(lint `requires_in_state_set` は需要IDの重複を検査する)
4. **事実と案だけを書く。採否と優先度は書かない。** 行の状態を `採用` / `不採用` にしない。採否を待って止まらない
5. **採用されていない状態を `requires` に書かない**(lint `requires_in_state_set`)
6. 申し送り台帳の `初期状態外` の行で提案・追記した場合は、想定手段欄にこの台帳の需要IDを書く

## ◆ 人間向け補足

- **採否は人間が決める。** 目安は次のとおり(どれを重く見るかは状況次第でよい)
  - 要求元の件数が多い(止めているシナリオ候補が多い)。1件だけの需要は、連結シナリオで扱う方が安いこともある
  - 構築の見込みが既存の部品・確立済みの外部操作で足りる(足りない外部操作がある状態は、採用しても `blocked` になりやすい)
  - fixture の実行時間。回帰テストはゴールデンイメージの復元を一括実行の前に1回しか行わないため、fixture はテスト項目ごとに実行される。外部操作を伴う重い状態は、採用するほど回帰テストセットの実行時間が延びる
  - 値違い・組み合わせになっていないか(AIの提案の条件をすり抜けたもの)
- **採用したら、その状態を使うフローを指示する。** 例: 「SD-001 の状態を使うシナリオを作って」。採用しただけでは、対象機能のフローが次に回るまでシナリオは作られない
- 採用のときに状態ID・定義を直してよい。**採用後は状態IDを変えない**
- 採用しないと決めた需要は `不採用` にし、理由を備考に残す。放置された `提案` と区別できる。あとで要求元が増えたら採否を見直してよい
- `vocab.initial_state_set` の基本の状態を変えたいときは、従来どおり語彙の改訂として行う(手順版を上げ、skills を再生成する)。この台帳の採用は手順書の改訂ではないため、版を上げる必要はない
