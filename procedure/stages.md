## ■ 8スロット規約

各作業の節は、必ず以下の8スロットをこの順で持つ。**該当なしの場合も見出しを残し「なし」と書く。** 空欄は仕様の穴として扱う。

| # | スロット | 内容 |
|---|---|---|
| 1 | 役割 | この作業のAIが何者か。1〜3文 |
| 2 | 起動条件 | `pipeline.dot` のノードIDと、この節に入る条件 |
| 3 | 入力 | 成果物IDの一覧のみ。レビューヘッダの確認義務は00の既定なので書かない |

| 6 | 出力 | 成果物ID+スキーマ参照+ゴールド例参照+報告書の固有セクション |

節番号とスロット番号は、手順改善シグナルが手順箇所を指すための位置(`vocab.procedure_location` の `ST`)でもある。**番号を付け替えない。**

# §01 知見蓄積

ノードID: `kb` / クラス: `.operate,.text`
参照付録: E / 参照テンプレート: 91, 93, 94

## 1. 役割

あなたは対象システムの調査者である。人間が指示した**調査対象**について、**自動回帰テスト作成の各作業が何を必要とするかを逆算し**、有用と推測される情報を調査してKBに記録する。人間は調査項目を列挙しない。**何を調べるべきかの推測はあなたの仕事である。**

達成すべきは「発見活動をゼロにすること」ではない。**同じ発見が二度起きないこと**である。

## 4. 固有手順

### S1: 調査範囲の逆算(最重要)

**各作業が何を必要とするかを逆算し、調査項目を自分で立てる。** 以下を出発点とする(これに限らず、有用と判断した項目は追加してよい)。

| 後段の作業 | その作業が必要とする知見 | KBカテゴリ |
|---|---|---|
| **02 非決定値カタログ** | 値が画面のどこに出るか、DBのどの列に入るか、操作の反復に必要な操作列、環境の癖 | T01 / T03 / T09 |
| **10 シナリオ生成(パートB)** | 業務用語と画面表記とDB名称の対応、画面の所在と到達経路、ロール別の可視性、外部操作の可否(確立済みか、使える skill があるか)、根拠にできる文書の章番号 | T08 / T01 / T07 / T05 / T11 |
| **10 探索的実行(パートC)** | 画面の到達方法・主要要素と安定ロケータ、操作起因の遷移、**確立済み操作の台帳(再探索の回避)**、外部操作の前提と挙動、非同期の完了判定条件と実測時間、既知の落とし穴 | T01 / T02 / T05 / T06 / T10 |

**S1の出力として、調査項目の一覧と、それぞれがどの後段作業のために必要かを1文で示す。** この一覧を報告書の冒頭に置く。

### S2: 文献調査(ポインタの記録)

- 対象に関する記述の**所在**を特定する
- **本文を転記・要約しない。** 記録するのは「何が、どの文書の、どこに書かれているか」(例: `ジョブステータスの一覧と遷移: PMS仕様書 v12.3 / 5.2章`)
- 記述が見つからなかった項目は**「文書に記載なし」として明示的に記録する**(後段が探し直さないため。**「見つからなかった」ことも知見である**)
- 文書間で記述が矛盾している場合は、両方のポインタと矛盾の要点を記録し、DISC候補として報告する

### S3: DB定義と蓄積データの調査

- `INFORMATION_SCHEMA`(TABLES / COLUMNS / KEY_COLUMN_USAGE / REFERENTIAL_CONSTRAINTS)から、対象に関係するテーブルの定義・PK/FK・NULL可否・型を機械抽出する
- **実際に蓄積されているデータを観測する**(`SELECT` のみ。`node tools/pms/pms.mjs db -- "<SELECT 文>"` で行う。00 ■DB への接続 [R-DB-2])。列の意味は定義だけでは分からないことが多い
  - 例: ステータス列に実在する値の一覧、金額列が予測系か実績系か、日時列が更新のたびに変わるか
  - 実在値の一覧は仕様書の記載と突き合わせる。**文書にあるが実データに存在しない値**(死んだenum値)、**実データにあるが文書にない値**はどちらも重要な知見
- 機械抽出部と注記部を明確に分離し、**機械抽出部を手で編集しない**(再抽出で上書きされる前提)
- 課金スキーマ(`95` Q-001)に関係する調査を行った場合、結果を判断材料として95に参照リンクする。**裁定はしない**

### S4: 実操作による調査

**Web画面操作**(主たる手段):

- 調査を始める前に `node tools/env/env.mjs require` で環境情報を確かめる。調査に要る値(外部操作の対象機器の接続先など)が足りなければ `--keys` に加え、まとめて人間に聞いて保存する(00 ■検証環境の情報)。KB には値ではなくキーを書く
- **前提の基本操作は既存の fixture・シナリオ部品を実行して作る**(00の資産流用規約)。自分で操作を編み出すのは、調査対象そのものの操作と、資産が存在しない前提操作に限る
- 対象に関係する画面へ到達し、URL・画面タイトル・主要要素・安定ロケータ・遷移経路を記録する
- ロール別の可視性差(管理者/一般ユーザー)を確認する
- **テスト環境に対しては書き込み操作を行ってよい**(データを作らないと観測できない知見が多いため)。実施した変更は報告書の「環境への影響」に記録する

**外部操作**(必要な場合): 印刷指示、機器パネル操作等。00の ■外部操作 に従い、skill を介してのみ行う。

- KB T05 に確立済みの操作があればそれを使う。なければ skills の機構で使える skill(実行体を同梱したもの)を確認し、あれば使い方を確立して T05 に登録する
- **使える skill がなければ、調査対象そのものの操作であっても実行を試みず、外部操作需要リストに記録する**(要求元は `作業01:<調査対象>`)。その操作に依存する調査項目は「判明しなかったこと」として報告する
- 非同期処理を伴う操作は、**同一操作を3回実行して所要時間を実測し**、タイムアウト根拠(実測値の3倍程度)を算出して T06 に記録する

**観測の記録原則**: 「何をしたら何が起きたか」を、再現できる粒度で書く。曖昧な要約(「正常に動作した」等)を残さない。

### S5: KBへの反映

- 付録Eのカテゴリ別フォーマットに従って書き込む
- 全エントリに00のレビューヘッダと、付録Eの共通メタデータ(出所コード・確度・観測日)を付ける
- `kb/00_索引.md` を更新する
- ファイルは `vocab.default.kb_file_lines` 行以内を目安に分割する

### カテゴリの拡張機構

カテゴリ(T01〜T11)は統制語彙だが、**AIによる暫定追加を認める。** 追加してよい条件(いずれか):

1. 既存カテゴリに割り当てられない発見ログエントリが累計3件以上になった
2. `gotchas/` 内に同種とみなせるエントリが2件以上再発した
3. ステップ2・3への移行で新たな知見需要が生じた

手続き: レジストリ(`kb/01_知見対象レジストリ.md`)に `unreviewed` の行として追記し、テンプレートを作成し、索引を更新する。**追加理由(どの条件を満たしたか、該当する発見ログのエントリ)を必ず書く。根拠のない追加は禁止。**

**申し送り台帳の理由コードには、この暫定追加を適用しない。** 理由コード別の集計がそのままステップ2・3の投資計画になる統制語彙であり、AIが勝手に語彙を増やすと集計の意味が壊れるため。KBのカテゴリは集計対象ではなく格納場所の分類なので暫定追加を許容する、という線引きである。

一定期間(目安: バージョン更新2回分)参照実績のないカテゴリは、廃止・統合の候補として報告する。廃止時はファイルを削除せず `kb/_archived/` へ移す。

## 5. 固有の禁止事項

- **人間の指示なく本作業を開始しない**
- マニュアル・仕様書の本文をKBに転記・要約しない(ポインタのみ)
- **「分からなかったこと」を報告せずに済ませない**
- KBに判断・推測を事実として書かない(推測と明示するか、DISCへ回す)
- 指示された対象から無制限に調査範囲を広げない(広げた場合は範囲と理由を報告する)
- 網羅的な事前ドキュメント整備を目指さない。**KBの完成はパイプライン開始の前提条件ではない**

# §02 非決定値カタログ抽出

ノードID: `nd` / クラス: `.operate`
参照付録: D, E / 参照テンプレート: 91, 93, 94

## 1. 役割

あなたは観測者である。**同一環境で同じ操作を複数回実行し、UI・DBに現れる値のうち何が変わり何が変わらないかを実測して**、値ごとの検証強度を決めたカタログを作る。**推測ではなく観測で決めることが本作業の要点である。**

実挙動を正解として凍結する方式では、実行のたびに変わる値をそのまま固定すると回帰テストは初回実行の直後から壊れ始める。一方で変わりうる値をすべて「検証しない」にすると、金額や枚数のような**変わってはいけない値まで見逃す**。ここを取り違えると、テストが緑のまま不具合を通す。

## 2. 起動条件

| 項目 | 内容 |
|---|---|
| ノード | `nd` |
| 進入元 | `pre` または `kb`(`context.nd_needed=yes`) |
| モード | **初期作成**(カタログが存在しない。初回フロー前)/ **増分実施**(対象領域にカタログ未収載の操作・値が見込まれる場合のみ) |
| 退出先 | `exp` |

増分実施の主な入力は、作業10の報告書「非決定値カタログへの追記候補」である。

## 3. 入力

| 成果物ID | 所在 |
|---|---|
| `nd-catalog` | `work/_common/nondeterministic-catalog.md`(増分実施時) |
| `prohibited-ops` | `work/_common/prohibited-operations.md` |

## 4. 固有手順

### 工程1: 観測対象操作の選定

- **初期作成時**: ステップ1のシナリオで使われる見込みの操作を列挙する。最低限、以下のカテゴリから各1つ以上を含める
  - ログイン / マスタ登録(ユーザー、デバイス等) / 設定変更 / ジョブ実行(外部操作を伴うもの) / 一覧・レポートの表示 / 検索・絞り込み
- **増分実施時**: 当該フローの対象領域で使われる見込みの操作のうち、**カタログ未収載のもの**だけを対象にする。既収載の値は再観測しない
- 外部操作を伴う観測対象で、KB T05 に確立済みの操作も使える skill もない場合は、観測を試みない。外部操作需要リストに記録し(要求元は `作業02:<観測対象の操作>`)、カタログの「未観測・未分類」に理由付きで載せる

**網羅は不要。** 各カテゴリの代表1操作で、そのカテゴリに現れる値の種類はおおむね押さえられる。

### 工程2: 反復観測

**観測条件は回帰テストの実行条件に合わせる**(00の環境前提)。ゴールデンイメージ復元は回帰テストセットの実行開始前に1回だけ行われ、テスト項目間では復元されない。したがって**操作の反復ごとに環境を復元してはならない。** 復元直後にしか成立しない値を「毎回同一=完全一致」と誤判定し、回帰実行中の2回目以降でテストが壊れるためである。

**画面操作は `pms pwcli` を通して playwright-cli で行う**(`node tools/pms/pms.mjs pwcli -- <playwright-cli の引数>`)。本作業は進行役 pms のカードを使わないので、`pms act` は使えない(R-PMS-1〜5 はカードの規則であり、本作業には当てはまらない。00 ■進行役と記録の道具)。ログインのパスワードなど環境情報の値は `<env:キー>` のまま渡す(例 `pwcli -- fill <ref> <env:pms.password>`。00 R-ENV-2)。値は `pms pwcli` が入力し、出力からも伏せるので、値を取り出したり fill を避けたりしなくてよい。ログインを観測対象として反復する場合も同じである。外部操作は skill を介して行う(00 ■外部操作)。

操作ごとに:

1. **観測開始時に1回だけクリーンな状態に戻す**
2. 操作を実行し、UI(スナップショットとスクリーンショット)とDB(変化したテーブルの行内容。`SELECT` のみ。`pms db` で行う。00 [R-DB-2])を記録する
3. **2 を復元を挟まず `vocab.default.observation_runs` 回連続で繰り返す。** 判断がつかない値があれば、その値についてのみ追加実行する
   - 蓄積の影響(件数・連番・集計値)を切り分けたい値に限り、復元を挟んだ追加観測を行ってよい。その場合「復元直後の値」と「連続実行時の値」を分けて記録する
4. 突き合わせて判定する
   - 毎回同一 → `完全一致` の候補
   - 毎回異なる → 工程3で強度を決める
   - 一部の回のみ異なる → **要注意**。条件依存の可能性があるため notes に記録し、追加観測する

観測の注意:

- **同じ入力を与えること。** 入力値が違えば出力が違うのは当然であり、非決定性の観測にならない
- 他のテストや人間の操作が同時に走っているとノイズが乗る。可能なら排他的に実施し、できない場合はその旨を記録する
- 反復を**日をまたがずに**行う。日付依存の値を「毎回同じ」と誤判定するのを防ぐため。日付依存の疑いがある値は notes に書いて人間に確認を求める

### 工程3: 強度の割り当て

毎回異なる値について、`vocab.strength.order` の順(上位から)に検討する。

1. **`関係式` にできないか。** 他の観測値との間に、実行によらず成り立つ関係があるか(例: 作成日時 > ログイン日時、明細合計 = 総額、ジョブIDが直前の採番より大きい)。**関係式が書ける値を `存在のみ` に落としてはならない**
2. **`パターン一致` にできないか。** 書式が定まっているなら正規表現を書く(例: `^JOB-\d{8}$`)。書式の崩れが不具合を示すため `存在のみ` より強い
3. 上記いずれも該当しない場合のみ `存在のみ` とする

**業務的に重要な値(金額、枚数、ユーザー名、権限、設定値)が「毎回異なる」と観測された場合は、強度を下げる前に必ず報告すること。** 本来一致すべき値が一致していないのであれば、それは不具合の可能性がある。

### 工程4: 副産物のKBへの反映

本作業では観測のために操作手順を自力で編み出すことになる。これは作業10と同種の探索であり、**成功した操作列を捨てると作業10で同じ探索をやり直すことになる。** 00のKB更新規約に従い、その場で反映する。

- 操作に成功した画面ごとに、操作列と安定ロケータを `kb/screens/` へ
- 非同期完了を待った箇所は、待機条件と実測所要時間を `kb/async/` へ
- 値がDBのどの列に入るかを `kb/db/` へ
- 素直に操作できなかった要素の攻略法を `kb/gotchas/` へ

### 増分実施の規約

- カタログは累積資産である。**既存のID・強度は変更せず追記する。** 既存の強度に疑義がある場合は変更せず、見直し提案として報告する(回帰テストの検出力に直結するため人間が判断する)
- 増分分の観測条件は初回と同じ

**DB への接続を確かめる**(`node tools/pms/pms.mjs db --check`。00 ■DB への接続)。パートCのカードが DB を確かめる前に、接続・ログイン・接続先を1回確かめておく(探索を終えてからカードが接続できずに止まらないようにするため)。出力の `target`(サーバ名・DB名・ログイン名)を flow.md のメモ欄に残す。終了コード1のときは出力の `reason` で分ける: `env_missing` は足りない環境情報の確認(00 ■検証環境の情報)と同じく人間にまとめて聞き、`set` で保存して `--check` をやり直す。`connect_failed`・`target_mismatch` は**作業を始めない。** flow.md のメモ欄に「DB 接続不可」と `error` を書いて止まり、利用者に伝える(ログインの方式 `db.auth`・アカウント・証明書の扱いを人間が直したら、`--check` からやり直す。復元はやり直さない)。

**開始前シナリオのあと、禁止操作リストの記入状態と版を照合スクリプトで取得する**(`node tools/checks/prohibited-ops.mjs`。出力の JSON の `state` と `digest`)。flow.md のメモ欄に残し、status.yaml の `prohibited_ops` に転記する。記入状態が `unfilled` / `absent` のときは禁止操作なしとして扱う(00 ■外部操作 禁止操作リストが未記入・存在しないとき)。**リストが未記入・存在しないことを理由に、シナリオやステップを `blocked` にしない。** 再開時は取り直さず、メモ欄の値を使う。

### パートA: フロー開始と資産棚卸し

**A1 フロー記録の整備** — `work/_flows/F-<連番>/flow.md` を作成し(テンプレート92)、**領域指示を原文のまま転記**し、開始時の手順版(`vocab.meta.procedure_version`)とシナリオ策定方式(入口 skill から渡された `scenario_source`。渡されなければ `vocab.default.scenario_source`)を記録する。フロー台帳に行を追加する。領域指示がステップ1の規範と矛盾する場合は、進めずに人間へ確認する(00のスコープ規範)。

**A1b 方式の前提条件の確認** — 方式ファイルを開き、スロット1の前提条件を、方式ファイルが定める方法で確かめる(前提条件が「なし」なら何もしない)。満たさなければシナリオを作らず、flow.md のメモ欄に「方式の前提条件を満たさない」と、確かめた内容を書いて止まる(status.yaml は出力しない。00 ■シナリオ策定方式)。

**A2 対象機能の特定**

- **`context.flow_seq=first`(初回フロー F-001)のときだけ**: 方式ファイルのスロット1が定める確定元(`manual_usecase` ではマニュアルの目次構造)から**機能一覧と機能コードを確定する**(章・節など確定元の単位=機能の単位。「この機能が全く動かなかったら出荷不能か」がYesのものを対象とし、迷ったものは未確認事項へ)。**機能コードはディレクトリ名・項目IDになるため後から変えない**
- それ以外: 既存の機能一覧から領域指示に該当する機能を選ぶ。一覧にない機能が必要なら追加採番する
- 領域指示が複数機能にまたがる場合、成果物は機能ごとの `work/<feature_code>/` に置き、flow.md からリンクする
- 領域指示が状態需要リストの需要ID(`SD-...`。例: 「SD-001 の状態を使うシナリオを作って」)を指す場合は、その行の要求元の申し送りの機能を対象機能とする。行の状態が `採用` / `整備済` でなければ、進めずに人間へ確認する

**A3 資産棚卸し(流用計画)** — 00の資産流用規約に従い、対象領域に関係する既存資産を列挙し、流用計画を flow.md のメモに残す。**前提状態・共通操作は既存実装の実行が第一選択であり、再探索しない。**

**A4 未経験機構の扱い** — そのフローに未経験の機構(初めての種類の外部操作、初めての検証手段等)が含まれる場合、**1本だけ先に通してから展開する進め方を選んでよい。停止は不要。** その判断をしたことを報告書に記す。

### パートR: 再探索の対象特定(再探索フローのみ)

`context.flow_kind=reexplore` のとき、パートA・Bの代わりに行う。人間が外部操作 skill を整備したあと、需要ID(状態 `整備済`)を指定して指示する。需要IDの指定がなければ、状態 `整備済` の全行を対象とし、その旨を flow.md に記す。

**R1 フロー記録の整備** — flow.md を作成し(テンプレート92の再探索フロー用タスク)、**指示を原文のまま転記**し、対象の需要IDと開始時の手順版を記録する。フロー台帳に種別 `reexplore` で行を追加する。

**R2 skill の確認** — 対象の需要IDごとに、整備記録の skill名を手がかりに skills の機構で skill を確認し、**コードから呼べる実行体が同梱されていること**を確認する。見つからない・実行体がない場合はその需要を対象から外し、需要リストの状態を `未整備`(不足の区分 `skillなし` / `実行体なし`)に戻して報告する(整備記録は消さない)。skill の操作対象に要る環境情報(機器の接続先など)を洗い出し、`require --keys` で確かめ、足りなければまとめて人間に聞く(00 ■検証環境の情報)。

**R3 対象シナリオの特定** — 需要リストの要求元から対象シナリオを特定する。要求元が HO-ID なら申し送り台帳の発生元を辿り、`操作手段なし` で `blocked` になったシナリオを特定する。要求元が `作業20:<シナリオID>` なら、そのシナリオを対象にする。要求元が作業01・02のもの(シナリオを伴わないもの)は対象外とし、報告書に列挙する(その操作を使う次の通常フローで扱われる)。

**R4 資産棚卸し** — A3 と同じ。

**シナリオは作り直さない。** 既存の scenarios.md をそのまま使い、**期待結果・判定基準を変更しない**。例外として、操作を確立したあと、scenarios.md の「使用する外部操作」の需要IDの横に、確立した操作IDを追記してよい。

パートCでは、対象シナリオを**最初のステップから**探索し直す(ステップは前の結果を引き継ぐため)。探索記録は、当該シナリオの記録に新しい `flow_id` と `reexplore_of: <旧フローID>` を付けて追記し、**旧記録(blocked)は削除しない**。

- 操作を確立できたら: KB T05 に登録し、需要リストを `確立済`(操作IDを記入)に、解消した申し送り行を `done` にする
- 確立できなかったら: 需要リストを `未整備` に戻し、不足の区分を更新する(`実行体なし` / `確立不可`)。シナリオは `blocked` のまま、申し送り行は `open` のままとする

### パートP: 禁止操作の再判定(`context.prohibition_recheck=yes` のときのみ)

作業20の開始前の照合で、`禁止操作` で `blocked` にしたステップがあるのに禁止操作リストが変わっていたときに行う(00 ■外部操作 禁止操作リストの版と blocked の再判定)。パートA・Bの代わりに行う。**フローIDは変えず、同じフローの中で行う。**

**P1 対象の特定** — 前回の作業10の status.yaml の `blocked_by_prohibition` にあるステップと、それを含むシナリオを対象とする。flow.md のメモ欄に、再判定を始めたことと照合の結果(旧版・新版)を書く。申し送り台帳の `禁止操作` の行のうち、シナリオのステップを持たないもの(パートBでシナリオに書かなかった操作)は対象外とし、報告書に列挙する(その操作を使う次の通常フローで扱われる)。

**P2 判定し直し** — 対象のステップの操作を、工程0で取得した現在の禁止操作リストで判定し直す。

- 実行できる(`禁止` / `要許可` に該当しない。`条件付き許可` は制約の範囲内)→ パートCで、そのシナリオを**最初のステップから**探索し直す(ステップは前の結果を引き継ぐため)
- まだ `禁止` に該当する → `blocked` のまま。探索し直さない
- `要許可` または包括原則に該当する → 00 ■外部操作 の規約どおり記録してエスカレーションする

**P3 記録** — 探索し直したシナリオは、当該シナリオの記録に `recheck_of: <前回の prohibited_ops.digest>` を付けて追記し、**前回の記録(blocked)は削除しない**。解消した申し送りの `禁止操作` の行を `done` にする。

**シナリオは作り直さない。** 既存の scenarios.md をそのまま使い、期待結果・判定基準を変更しない。探索し直さなかった(前回 `passed` などの)シナリオの記録はそのまま使う。

### パートB: シナリオ項目生成

**方式ファイルと共通契約** — シナリオ候補の抽出(入力資料・抽出手順・根拠の書き方・代表値と範囲外の扱い)は、flow.md の `scenario_source` が指す方式ファイルのスロット1〜4に従う。以下のスコープ・妥当性基準と選定指針・記載ルール・既存テストスクリプトの扱いは、**どの方式にも適用される共通契約である。方式ファイルは共通契約を緩めない。**

- 方式ファイルのスロット5(方式固有の禁止事項)とスロット6(方式固有のDoD)は、本節の禁止事項・DoD に加えて守る
- 方式ファイルと共通契約が食い違うと思われたら共通契約に従い、手順改善シグナルを記録する(手順箇所は `MT/<方式ID>/<スロット>`)
- 本フローで作成したシナリオには、付録Cの「策定方式」の行に方式IDとフローIDを書く

**スコープ**(00のステップ1規則。全フロー共通・不変):

- **シナリオ型のみ。正常系のみ。各パラメータは代表1値**
- **単機能粒度**: 3〜6ステップ、1機能内で完結。終端は1機能の基本操作完了時点(例: 印刷実行と結果確認まで。課金結果確認は課金機能側の別シナリオ)。機能をまたぐ連鎖は連結シナリオの対象
- 1機能につきシナリオ数は `vocab.default.scenarios_per_feature`
- 扱わない対象は捨てず、判断した瞬間に**申し送り台帳へ記録する**。「重要そうだから入れる」で範囲を広げない

**妥当性基準と選定指針**:

- 妥当性は**「利用者が実際に行う一連の作業に対応しているか」**で判定する。機能単位で機械的に切ったシナリオ(開くだけ・遷移するだけ)は不可
- 構造的に異なる処理経路を優先する(例: プリント/スキャン/コピーは別経路、A4/A3は同一経路→代表1件に畳んで台帳へ)。ただし**重複排除は目的ではない**。共通操作列は実装時に部品化されるため、定義段階の重複は気にしない

**記載ルール**:

1. 1ステップ = 1検証意図
2. **操作手順を書かない**(パートCで編み出す)。書くのは検証意図と判定基準
3. 全ステップに根拠。書き方は方式ファイルのスロット3に従う。どの方式でも、文書に記載があれば文書名+章番号を先に書き、文書にもスロット3の資料にも記載がなければ `推測(仕様未記載)` / `画面観察` とする
4. 期待結果は業務的な意味で書く(画面文言そのものを判定基準にしない。文言自体が仕様の場合のみ `[厳密一致]` を付記)
5. 検証手段を必ず付与。原則 `両方`。`DB` 単独は理由を1文併記
6. 外部操作は **KB T05 に登録済みの操作ID**で指定する。未登録の外部操作が必要な場合は、skills の機構で使える skill(コードから呼べる実行体を同梱したもの)があるかを確認する
   - **ある**: 操作名を業務語で書き(例: 「機器パネルから印刷実行」)、パートCで使い方を確立して登録する
   - **ない**: シナリオは作成し、当該ステップに操作名を業務語+需要IDで書く(例: 「機器パネルからスキャン投入(EXT-002)」)。**その場で**申し送り台帳に `操作手段なし` で記録し(想定手段に需要ID)、その HO-ID を要求元として外部操作需要リストに記録する(同じ外部操作と操作対象の行があれば要求元の追記のみ)。当該ステップ以降はパートCで `blocked` とする。シナリオを残すのは、skill 整備後の再探索フローで同じシナリオを探索し直すためである
   - **禁止操作リストで `禁止` / `要許可` に該当する操作をシナリオに書かない**
7. ID書式は `vocab.id_format`。**過去フローの採番と重複させない**(既存 scenarios.md を確認)
8. `requires` は初期状態セット(`vocab.initial_state_set` と、状態需要リストで `採用` / `整備済` の状態。パートBの開始時に読んだもの)のIDのみ、シナリオ単位で1回。他の前提が要るシナリオは作らず、申し送り台帳へ `初期状態外`(実操作で作れないものは `状態未整備`)で記録する。`初期状態外` のうち 00 ■状態(前提条件)の扱い の提案の条件を満たすものは、**その場で**状態需要リストに提案し(同じ状態の行があれば要求元の追記のみ)、申し送りの想定手段に需要IDを書く。**状態需要リストの行を `採用` にしない・提案の採否を待って止まらない**
9. 判断に迷った点・仕様の矛盾は報告書の「未確認・要確認事項」へ。確信のない断定をしない

**既存テストスクリプトの扱い**(人間が指定した、または KB T11 に所在があるもの。どの方式でも適用する。方式 `legacy_script` ではスクリプトが主たる入力になり、抽出のしかたは方式ファイルに従う):

- マニュアル・仕様書と並ぶ**シナリオ策定の参考情報**として読んでよい。利用者が実際に行う一連の作業、確認している観点、代表値の選び方を知る手がかりにする
- **参考情報であり、正解の根拠でも操作手順の正本でもない**(00 ■オラクルの原則 の仕様書・マニュアルと同じ扱い)。期待結果はスクリプトの記載を写さず業務的な意味で書き(記載ルール4)、スクリプトの操作手順を scenarios.md に書き写さない(記載ルール2)。パートCでは、スクリプトの操作手順は仮説の材料の1つとし、実画面で確かめる
- スクリプトの記載(操作・期待結果)と実挙動が食い違ったら、実挙動を正として続け、食い違いを DISC(種別 `実画面≠既存テスト`)に記録する。スクリプトが古いのか製品の不具合なのかをAIは判断しない
- スクリプトに含まれるステップ1の範囲外の確認(異常系・値のバリエーション・機能をまたぐ確認など)はシナリオに入れず、申し送り台帳に記録する。**スクリプトがあることを理由に、スコープ(単機能粒度・正常系・代表1値)を広げない**
- スクリプトの所在は KB T11(文書ポインタ集)に登録する(内容は転記しない)
- スクリプトに書かれた接続先・アカウント・パスワードの値は使わず、環境情報のキーで扱う(値が要るときは人間に確かめる。00 ■検証環境の情報)

**採用された状態による申し送りの見直し**: 対象機能の申し送りの行(理由コード `初期状態外`・状態 `open`)のうち、想定手段の需要IDが状態需要リストで `採用` / `整備済` になったものは、シナリオ候補として見直す(スコープ・妥当性基準・1機能あたりのシナリオ数は他の候補と同じ)。シナリオにしたら、申し送りの行を `done` にし、備考にシナリオIDを書く。シナリオにしなかったものは `open` のままにし、理由を報告書の固有セクション11に書く。

**単発型候補**: 生成・探索中の気づきは、**項目化せず**申し送り台帳へ記録するだけにとどめる。

**環境情報の洗い出し**: scenarios.md(付録C)を確定出力したら、パートCの前に、シナリオの実行に要る環境情報(基本キー以外。外部操作の対象機器の接続先・アカウント、連携システムの接続先など)を洗い出す。KB T05 のエントリにある「使う環境情報のキー」と、既存のキー(`node tools/env/env.mjs list`)を先に確かめ、同じものに別のキーを作らない。`node tools/env/env.mjs require --keys <キー>:<種類>,...` で確かめ、足りなければ**まとめて1回で**人間に聞いて保存する(00 ■検証環境の情報)。揃ってから flow.md の該当タスクをチェックし、パートCへ進む。

### パートC: 探索的実行

パートCは、進行役 `pms`(00 ■進行役と記録の道具)が出すカードで行う。**主な実行形態は B2 である(既定)**: 進行役 `pms run` が、カードを1枚ずつ新しいAIのセッション(Copilot CLI・Kiro CLI)で行わせ、提出が合格したかをキューの記録で確かめて次へ進む。**副経路として B1 を選んでよい**: 利用者が IDE のチャットのエージェントを `pms-runner` に切り替え、`pms-runner` がカードを1枚ずつサブエージェント(カードの種類のエージェント)に行わせる。**どちらでも、どのカードを行うか・記録・集計・完了の判定は pms が行い、AIはカードの判断だけを行う。** カード・提出の検査・記録(setup-log・探索記録・台帳)・報告書と status.yaml は、B1 と B2 で同じである。

**作業10の流れ(proc-v018 以降)**

1. 工程0・パートA・パートB(再探索フローはパートR、禁止操作の再判定はパートP)は、この skill(チャットの作業10)が行う
2. 終わったら、工程0〜パートB(R・P)の結果を `work/_flows/F-<番号>/stage10-context.json` に書く(書式は `procedure/schemas/stage10-context.json`。環境ID・`env_restore`・`pre_stage`・`prohibited_ops` は道具の出力とメモ欄から、台帳の需要ID・操作ID・SIG-ID はパートA・B・R・Pで書いたものを写す。推測しない)。`pms report` が status.yaml の最上位の項目とこれらのキーに使う
3. `node tools/pms/pms.mjs queue build --flow <フローID> --phase all` を実行する(再探索フロー・パートPは `--scenarios <シナリオID,...>` で対象を渡す)。フェーズAとパートCのカードがキューに入る
4. flow.md のメモ欄に「pms run 待ち」と書き、利用者に進め方(既定は端末で `node tools/pms/pms.mjs run --flow <フローID>`。チャットで進めるならエージェント `pms-runner`)を伝えて止まる(伝え方は入口 skill)。status.yaml は出力しない
5. `pms run`(B1 では `pms-runner`)が、フェーズA → パートCの探索 → 報告の所見の順にカードを行わせる。人間の判断が要るカード(STOP)があれば、理由を出して止まる。`pms run` は、終わったら報告書と status.yaml を記録から作り(`pms report`)、完了前の lint を実行する。`pms-runner` はカードだけを行い、報告書と lint は入口 skill が次の「続き」で行う(`pms status` の `report_pending`)

**B1 を選んでよい場面**(proc-v019 以降): カードのテンプレートを作り込むとき・初めての画面を探索するとき(AIの動きを見ながら止められる)、途中の人間の判断(環境情報の不足・要許可操作など)にチャットでその場で答えたいとき、Copilot CLI・Kiro CLI を使えない人・環境。どれでもなければ B2 にする。B1 の正しさはフックに頼らず、`pms act`・キュー・`pms submit` で保つ(00 ■進行役と記録の道具 の「フックを使わずに正しさを保つ仕組み」)。

**IDE でサブエージェントを使えない場合の代わり**: `pms run` を実行できず、IDE でもサブエージェント(`pms-runner`)を使えない場合(組織の設定で止められている等)だけ、この skill が同じ会話の中で、`pms next` のカードを順に行ってよい(下のフェーズAの2〜4と同じやり方。`next` が `done` を返したら `node tools/pms/pms.mjs report --flow <フローID>` を実行し、完了前の lint へ進む)。カードごとに会話を捨てられないので、会話が長くなる。

**フェーズA: 初期状態の準備**

フェーズAのカードは、どの状態を整備するかも pms が決め、setup-log・台帳への記録も pms が書く。AIはカードの判断だけを行う。

1. キューは上の3で作る(フェーズAだけを先に作るときは `--phase A`)。pms が、対象シナリオ(このフローで作ったシナリオ。再探索フロー・パートPでは `--scenarios`)の `requires` の状態IDを重複排除して列挙し、状態ごとにカードを作る
2. (IDE でサブエージェントを使えない場合の代わりのとき)`node tools/pms/pms.mjs next --flow <フローID>` を実行し、出力の `body`(カード)の指示どおりに行う。カードが指定するファイルに出力の JSON を書き、カードの「終わったら」のコマンド(`pms submit`)を実行する。不合格なら、返された理由だけを直して再提出する。**`next` が `done` を返すまで2を繰り返す**
3. `next` が `STOP` を返したら、出力の `message` を利用者に伝えて指示を待つ。利用者が続けてよいと答えたら、`pms next` から続ける(STOP のカードは人間の確認待ちとして残り、報告書の固有セクション1に載る)
4. 中断・会話の要約のあとは、`node tools/pms/pms.mjs status --flow <フローID>` で現在のカードを確かめ、`pms next` から続ける(提出していないカードは、`next` が同じカードを出し直す)

**pms がカードにする規則**(AIは選ばない):

- **`requires` の整備は、そのシナリオが途中で `blocked` になる見込みでも省略しない**(pms は全部の状態をカードにする)。`blocked` はステップ単位の判定であり、前提状態の整備はその対象ではない。整備しておけば、blocked が解けたとき(パートP・再探索フロー)と作業20で、前提状態の作り方を探し直さずに済む
- 過去のフローで整備・確認済み(`verified: true`)の fixture がある状態は `setup.reuse`(既存 fixture を実行して確かめるだけ)。成立しなければ、pms が作り直しの `setup.build` と `setup.code` を出す(既存の fixture・部品を同じ名前のまま作り直す)。過去の記録に操作列か安定ロケータがないときも、記録を取り直すために `setup.build` を出す
- それ以外の状態は `setup.build`(画面操作で作る)。合格したら、pms が `setup.code`(部品と fixture のコード)を出す
- 初期状態セットにない `requires` は、カードにせず、pms が setup-log に `classification: blocked`(理由 `初期状態外`)と申し送り台帳の行を書く。AIは何もしない(当該シナリオはパートCで `blocked` とする)。`S-CLEAN-ENV`(ゴールデンイメージの復元の直後)は工程0の復元そのものなので、pms が `provided` として記録する
- 状態需要リストで `採用` の状態も、基本の状態と同じくカードで整備する。整備・確認できたら pms が行を `整備済` にし fixture の所在を書く。整備できなければ `採用` のまま、setup-log は `classification: blocked`

**カードの規則**(カードの依頼文に差し込まれる。00 ■進行役と記録の道具):

- **[R-SETB-1]** 状態は、文書(KB・マニュアル)から操作手順の仮説を立て、実画面で探索して作る。文書と実画面が食い違ったら実画面を優先して続ける。試行錯誤してよい。成功した最短の操作列だけを、`pms act` の記録の連番で `seqs` に示す(失敗した試行は `notes` に要点だけ書く)
- **[R-SETB-2]** 状態の成立は、established check(状態成立の機械的確認。例: ログイン済 → ヘッダーにログアウトリンクが表示される)を `pms act assert` で確かめて示す。確かめられない状態を `built` にしない
- **[R-SETB-3]** 状態需要リストの行の「established check の案」と「構築の見込み」は仮説の材料であり、実画面で確かめる
- **[R-SETB-4]** 作れない状態は `blocked` で提出する。理由は `vocab.reason_code` から選ぶ(実操作で作れないなら `状態未整備`、必要な外部操作に使える skill がないなら `操作手段なし`、禁止操作リスト・包括原則に当たるなら `禁止操作`。判別は `vocab.discrimination`)。`禁止操作` は禁止IDか包括原則の番号を、`操作手段なし` は外部操作需要リストに書く項目を添える
- **[R-SETC-1]** 合格した操作列を、シナリオ部品(`tests/flows/`)として実装し、それを呼ぶ fixture を `tests/fixtures/` に実装する。**established check を fixture に必ず実装する**
- **[R-SETC-2]** 実装したセットアップは2回実行して確かめる(2回目が残留データで失敗するなら、後始末を足すか専用データにする)。2回とも成功しなければ、pms が `verified: false` と記録する(作業20の最初の確認対象になる)
- **[R-SETC-3]** ログイン状態(`S-ADMIN-LOGIN` / `S-USER-LOGIN`)の fixture を本フローで初めて整備した場合は、起動確認テスト `tests/readiness/server-ready.setup.ts` も作る(00 ■回帰実行の環境前提 / 起動完了の判定)。整備したログインのシナリオ部品を呼び、fixture の established check と同じ条件で成功を判定する。既にあれば作らない
- **[R-SETC-4]** 作り直し(既存の fixture で状態が成立しなかった、または記録を取り直した)のときは、既存の fixture・部品を**同じ名前のまま**直す(ほかのテストがその名前で使っているため)
- **[R-SETR-1]** 既存の fixture は1回実行し、established check が通るかを確かめるだけにする(再整備・再探索しない)。通らなければ直さずに `broken` で提出する(作り直しは pms が別のカードで出す)

### 完了前の lint(全パート共通)

報告書と status.yaml を出力したあと、**完了報告(停止)の前に** `node tools/lint/lint.mjs --flow <フローID> --stage 10 --skip skills_in_sync` を実行する(00 ■lint 実行の契機)。

**`pms run` は、報告書と status.yaml を作ったあと(`pms report`)にこの lint を自分で実行する。** チャットの `pms-runner` で進めたときは、入口 skill が次の「続き」で `pms report` と lint を実行する(結果の扱いは `pms run` と同じ)。 ERROR がなければ終わり(終了コード 0)、ERROR が残れば「lint 止まり」として止まる(STOP。終了コード 3)。**pms run は lint の指摘を直すカードを作らない。** 指摘は、入口 skill が次の「続き」で、下の「lint の指摘による差し戻し」の経路でこの skill に渡す。この skill が直したら、`node tools/pms/pms.mjs report --flow <フローID>` で報告書と status.yaml を作り直してから lint を再実行する(proc-v018 以降のフローでは、報告書の数値と status.yaml を手で書き換えない)。

- **ERROR があれば、指摘された成果物を直して再実行する。** ERROR が0件になるまで繰り返す
- 直すのは、記録の漏れ・誤り(例: `blocked_by` の参照、blocked の手前のステップの記録、status.yaml のキー)と、足りない整備(例: setup-log にない `requires` の状態)である。整備が要るものは、フェーズAと探索の規約どおりに画面・外部操作で整備する
- **指摘を消すために、記録を削る・判定や期待結果を変える・blocked を外すことをしない**
- 直せない ERROR が残る場合は、その指摘と理由を報告書 §6 に書き、手順改善シグナル(種別 `検査不能` または `実行不能`)を記録し、DoD の該当項目を未チェックのまま `outcome: partial_success` とする(proc-v018 以降のフローでは `pms report --flow <フローID> --dod-unmet "<指摘と理由>"` で作り直す。§6 と outcome は pms が書く)
- 「未実行」の規則(PowerShell がなく `env_restored` を実行できない等)は ERROR ではない
- 直したら、報告書の該当箇所と status.yaml を出し直してから lint を再実行する(proc-v018 以降のフローは `pms report` で作り直す)

**lint の指摘による差し戻し**(`context.lint_error=yes`。作業20の開始前の lint で ERROR が出た)で起動したときは、工程0のあと、パートA・B・R・Pを行わず、入口 skill から渡された指摘を上の規約どおりに直し、この lint を実行する。報告書は直した箇所を更新し、本作業の §8 と固有セクション1に修正の内容を書く。status.yaml は出し直す(`env_restore` は今回の復元)。

### H1: 問い合わせ skill の確認

skills の機構で、問い合わせ skill(00 ■健全性シグナルと問い合わせ)を確認する。

- 見つかった → H2 へ進む(`context.inquiry_skill=found`)

続けて、ログ収集 skill を確認する(問い合わせ skill が見つかったときだけ)。

### H3: 問い合わせ(シナリオごと。初回を含めて `vocab.default.inquiry_limit` 回まで)

**初回の入力**

| 項目 | 書くこと |
|---|---|

| 本来得たい結果 | scenarios.md の期待結果を**そのまま**書く(言い換えない) |

1. 前回までの回答の要点(回ごとに1〜3行)
2. **前回の回答に対して追加で行った操作と、その結果**(新たに観測した状態値・メッセージ・DB の行を含む)。追加で行った操作のあいだのログを、同じ規約で集め直して添付する

- 実行体が失敗した(回答が得られなかった)呼び出しも1回と数え、記録を残す

### H4: 回答の扱い

**回答は情報源であり、正解の根拠ではない**(00 ■オラクルの原則と同じ扱い)。回答を理由に期待結果・判定基準を変えない。回答の内容を `vocab.inquiry_answer_kind` で区分し、問い合わせの記録に書く。

回答が原因の根拠としてログIDを挙げたら、そのIDが添付したログのログIDの一覧に出現するかを確かめ、問い合わせの記録に「確認済み」/「一覧にない」を書く。一覧にないIDは KB に記録しない。

| 区分 | 扱い |
|---|---|
| 操作の変更 | 回答が示す操作を試す(下記)。解消しなければ、試した操作と結果を付けて次の問い合わせへ |
| 環境の変更 | **禁止操作リストに従って試す**(下記「環境の変更を試すとき」)。禁止されている、または許可が得られなかったときは、提案として報告書の固有セクション3に書き、`unresolved` とする(操作の変更で解決できる見込みがあれば、その旨を付けて次の問い合わせへ進んでよい) |
| 情報の追加依頼 | 読み取りだけで集め(H2 と同じ手段)、次の問い合わせに含める |
| 製品不具合の見立て | AIは正否を判断しない。DISC に記録し(00 ■不整合レポート規約)、`unresolved` とする |
| 原因不明 | 次の問い合わせへ(上限まで) |

**操作の変更を試すとき**

- 対象シナリオを**最初のステップから**探索し直す(ステップは前の結果を引き継ぐため)。§10 パートCの規約(探索の進め方・安定ロケータの解決・検証と判定・DB不変条件・記録)に従う。**期待結果・判定基準は変えない**
- 試すのは回答が示した操作に限る(ロケータの解決など、実行に要る最小限の調整を除く)。回答から外れた独自の試行錯誤に広げず、うまくいかなければ次の問い合わせで聞く
- 新たな外部操作は §10 パートCの手順(KB T05 への登録・禁止操作リストの照合)に従う。使える skill がない、または `禁止` に当たる操作は実行せず、外部操作需要リスト・申し送り台帳に §10 と同じく記録し、そのシナリオを `unresolved` とする。`要許可` / 包括原則に当たる操作は、下の「禁止操作リストの扱い」に従う

**環境の変更を試すとき**

環境の変更とは、シナリオのステップの外で、PMS・機器・接続システムの設定や登録内容を変えることである(`vocab.inquiry_answer_kind`)。

- 手段は、PMS の Web UI(playwright-cli)か、外部操作 skill に限る(00 ■外部操作。skill がない変更は §10 と同じく外部操作需要リストと申し送り台帳に記録し、`unresolved` とする)。外部操作は KB T05 に登録してから使う
- **実行の前に禁止操作リストで判定する**(下の「禁止操作リストの扱い」)。変更する対象が復元範囲(ゴールデンイメージの復元で戻る対象。`node tools/pre-stage/run-scenarios.mjs --restore-scope` の出力で確かめる。00 ■回帰実行の環境前提)の外なら、表に行がなければ包括原則4に当たる。復元範囲の中なら包括原則4には当たらない(包括原則1〜3と表の行は別に判断する)
- 変更の前後の値と戻し方を、実行の直前に flow.md のメモ欄と問い合わせの記録に書く(戻し方が分からない変更は実行しない)
- 変更のあと、対象シナリオを**最初のステップから**探索し直し、健全性シグナルが消えるかを確かめる(§10 パートCの規約に従う。期待結果・判定基準は変えない)
- **環境の変更は回帰テストで再現されない**(復元範囲の中の変更は、次の作業の工程0のゴールデンイメージの復元で消える)。そのため、環境の変更で健全性シグナルが消えたシナリオは `env_changed` とし、**探索記録を追記せず、コード化の対象にしない。** 変更の内容・前後の値・戻し方を報告書の固有セクション3に書き、環境の前提(ゴールデンイメージ。VM のチェックポイント、または開始前シナリオ)に取り込むかの判断を人間に求める。原因と、変更で解消した事実は KB T09 に反映する
- 変更は元に戻さなくてよい(復元範囲の中は次の作業の開始時に戻る)。**復元範囲の外の変更(許可を得て行ったもの)は、残っている変更として報告書の固有セクション3に明記する**

**禁止操作リストの扱い**(操作の変更・環境の変更に共通。00 ■外部操作 禁止操作リスト)

| 判定 | 扱い |
|---|---|
| `禁止` | 実行しない。申し送り台帳に `禁止操作` で記録し、そのシナリオを `unresolved` とする |
| `要許可` / 包括原則 | 実行しない。申し送り台帳に記録し、`context.escalation=permission_required` を出力して**止まる**(`pipeline.dot` の `perm`)。許可されたら許可の範囲で実行し、申し送りに回されたらそのシナリオを `unresolved` とする。他のシナリオは、止まる前に進められるところまで進めてよい |
| `条件付き許可`(範囲内)/ 該当なし | 実行してよい |

### H5: 解消の判定と記録

**解消** — 操作の変更で探索し直した記録のどのステップにも健全性シグナルが出ず、全ステップが判定されたとき(`resolved`)。

- exploration-log の当該シナリオの記録に、同じ `flow_id` と `health_fix`(付録A)を付けて**追記する。** 作業10の記録は削除しない
- 判定が `passed` なら status.yaml の `codeable_items` に入れる(作業20の入力)。`failed` / `human-check` なら通常どおり証跡・DISC を付けて記録する(健全性シグナルとは別の問題として扱う)
- 原因と解消の方法を KB に事実として反映する(T10 落とし穴、環境の事実は T09。00 ■知見ベース 更新規約)。例: 「複合機に認証設定があると、登録外のユーザー名で送った印刷ジョブは認証エラーになる。登録済みのユーザー名で送ると完了する」
- 回答が挙げ、ログIDの一覧で確認済みのログIDごとに、事象・原因・対処を KB T12(付録E)に記録する(出所 `OBS`、原因の確度 `中`、問い合わせの記録へのリンク、観測したビルド番号)。同じログIDのファイルがあれば、事象の行を追記する
- 操作列を変えたことで fixture・シナリオ部品・ページオブジェクトを変えた場合は、setup-log と既存資産の規約(00 ■既存資産の流用)に従って反映する

**環境の変更で解消**(`env_changed`) — 上の「環境の変更を試すとき」のとおり、探索記録を追記しない。作業10の記録(健全性シグナル付きの `human-check`)を残す。確認済みのログIDは、`resolved` と同じく KB T12 に記録する(対処の欄に環境の変更の内容を書く)。

**未解消**(`unresolved` / `no_skill`) — 探索記録を**追記しない。** 作業10の記録(健全性シグナル付きの `human-check`)をそのまま残す。報告書の固有セクション4に、as-is の判断に回す前に環境の是正を検討すべきことを書く(**健全性シグナルが出た状態を as-is として凍結すると、誤った環境・操作を回帰テストの正解として固定するおそれがある**)。優先レビュー推奨リストに載せる。

### 完了前の lint

報告書と status.yaml を出力したあと、**完了報告(停止)の前に** `node tools/lint/lint.mjs --flow <フローID> --stage 15 --skip skills_in_sync` を実行する(00 ■lint 実行の契機)。作業10の成果物に追記した探索記録も、この lint で検査される。

- **ERROR があれば、指摘された成果物を直して再実行する。** ERROR が0件になるまで繰り返す
- 直すのは、記録の漏れ・誤り(例: `health_fix`、status.yaml のキー)と、足りない整備である
- **指摘を消すために、記録を削る・判定や期待結果を変える・健全性シグナルの記録を消すことをしない**
- 直せない ERROR が残る場合は、その指摘と理由を報告書 §6 に書き、手順改善シグナル(種別 `検査不能` または `実行不能`)を記録し、DoD の該当項目を未チェックのまま `outcome: partial_success` とする
- 直したら、報告書の該当箇所と status.yaml を出し直してから lint を再実行する

**lint の指摘による差し戻し**(`context.lint_error=yes`。作業20の前の関所の lint で ERROR が出た)で起動したときは、H0 のあと、入口 skill から渡された指摘を上の規約どおりに直し、この lint を実行する。問い合わせはしない。報告書は直した箇所を更新し、§8 に修正の内容を書き、status.yaml を出し直す。

### 既存回帰テストセットへの統合

本作業の出力は、過去フローで蓄積された回帰テストセットへの**追加**である。

- 既存の `tests/` 配下を再利用し、同等の実装を新規に作らない(00の資産流用規約)
- シナリオID・タグは**全フロー通算で一意**にする
- 突合表は**累積更新**する(既存行を保持して追記し、各行にフローIDを記録する)。再探索フロー・パートPで探索し直したシナリオは既存行を更新し、備考に旧判定と旧フローID(パートPは前回の判定)を残す
- 作業15で解消したシナリオは、`health_fix` の付いた最新の記録をコード化する。突合表の備考に「健全性の是正で解消(作業15)」と書く。作業15で解消しなかったシナリオは `human-check` のため、as-is 判断待ちとして扱う
- 既存の共通資産を変更した場合、**それに依存する既存テストを実行確認の対象に加える**。影響範囲は報告書に記載する

**as-is判断が未了の項目を、AIが独自に「現状挙動が正解」としてコード化してはならない。** `failed` / `human-check` の項目は突合表に理由付きで残し、人間の判断がついた後の再実行で拾う。誤った挙動を回帰テストの基準として凍結すると、以後その不具合が「仕様」として保護されてしまうためである。

### 外部操作 skill の確認(コード生成の前に行う)

コード化対象のシナリオが使う全 `operation_id` について、**コード生成の前に**次を確認する(00 ■外部操作 skill の条件)。探索時と実行環境が異なる場合や、探索後に skill が変わった場合に、コード化してから失敗するのを防ぐためである。

1. KB T05 に記録された skill名で、skills の機構に skill があること
2. その skill に、コードから呼べる実行体が同梱され、KB T05 に記録された呼び出し方で起動できること。確認は**副作用のない方法**(ヘルプ表示・バージョン表示等)に限る。副作用のない確認手段がなければ実行体の存在確認にとどめ、起動できるかは後段の実行確認で判断する
3. `tests/external/` のラッパが、その実行体を呼んでいること

満たさないシナリオはコード化しない。**`rework_required` にはしない**(作業10をやり直しても解消しないため)。

| 不備 | 扱い |
|---|---|
| skill が動作環境に配備されていない | 突合表に理由付きのスキップとして残し、報告書に skill名を挙げる。配備は人間が行い、配備後に作業20を再実行すれば拾われる |

2. **完全性**: コード化対象リストの全IDがコードに存在すること。逆に、対象リストに無いIDのタグがコードに存在しないこと(勝手な追加の検出)

### 生成コードの実行確認

1. **工程0の復元のあとの環境で**、当該フローで生成したテスト(+変更した共通資産に依存する既存テスト)を実行し、結果を記録する。**環境変数 `PMS_RESTORE` を付けずに実行する**(付けると実行のたびに復元される)。累積スイート全体の実行は本作業の必須要件としない(指示があれば `PMS_RESTORE=1` で実行する)
   - **工程0の復元のあとの環境を、テストコード(fixture・シナリオ部品・テスト本体)以外の手段で変えない。** playwright-cli での画面の手操作、DB への書き込み、外部操作 skill の手動実行で、データを作ったり設定を変えたりしない。テストが前提とするデータがテストコードのどこでも作られていないこと(セットアップの欠落)を、この実行で見つけるためである
   - **工程0の復元のあとの最初の実行の結果を `clean_run` として status.yaml に記録する**(修正後の再実行の結果と区別する)
2. 期待は「作業10で `passed` だったシナリオのテストは green になる」こと。red の場合は切り分ける
   - コード側の不備(ロケータ・待機・データ分離) → 修正して再実行
   - **前提状態の欠落**(テストが前提とするデータ・設定を、テストコードのどこも作っていない。探索時の環境に残っていたデータに依存していた等) → **コード化不能・要差し戻し。** テスト本体や手作業で前提を作って green にしない(セットアップを新規に発明しない)。`clean_run.red_setup_missing` に記録する
   - 作業10の記録との乖離(画面が変わった等) → 修正せず報告書に記載(差し戻し候補)
3. **同一テストを、環境を復元せずに最低3回連続実行し、flaky なテストを特定する**(`PMS_RESTORE` を付けない。skill `restore-golden-image` も使わない)
   - **復元しないと通らないテストは、再実行耐性の欠陥として報告する**(一意化漏れ・全体件数アサーションが典型原因)
   - flaky の原因が非決定値の強度設定にある場合、**テスト側で強度を勝手に下げず、カタログへの見直し提案として報告する**
   - 待機不足が原因の場合、タイムアウト値の変更を提案し、根拠(実測値)とともに報告する
4. **実行時間を計測して報告する。** 外部操作を含むテスト / 含まないテストに分けて計測する

### 後段シグナルの記録

「コード化不能・要差し戻し」と「逸脱一覧」の各行は、差し戻しや逸脱コメントとは別に、**作業10の手順箇所を指す手順改善シグナル**(種別 `後段不足`、出所 `後段`)として記録する(00 ■手順改善シグナル)。例: `assertion_hint` にDB検証の対象列がなかった → `ST/10/付録A`。前提状態の欠落 → `ST/10/4-C`。差し戻しでその場は直っても、同じ不足が次のフローで繰り返されないようにするためである。

### 完了前の lint

報告書と status.yaml を出力したあと、**完了報告(フロー完了)の前に** `node tools/lint/lint.mjs --flow <フローID> --stage 20 --skip skills_in_sync` を実行する(00 ■lint 実行の契機)。

- **ERROR があれば、指摘された成果物を直して再実行する。** ERROR が0件になるまで繰り返す
- 直すのは、記録の漏れ・誤り(例: status.yaml のキー、突合表のコード化の記録)と、生成コード・fixture の不足である。fixture の不足は、作業10の成果物にあるセットアップをコード化して直す。**セットアップを新規に発明しない**(作業10の記録にないものは「コード化不能・要差し戻し」にして `rework_required=yes` とする)
- **指摘を消すために、突合表の行を消す・コード化の記録を事実と違えて書く・判定を変えることをしない**
- 直せない ERROR が残る場合は、その指摘と理由を報告書 §6 に書き、手順改善シグナル(種別 `検査不能` または `実行不能`)を記録し、DoD の該当項目を未チェックのまま `outcome: partial_success` とする
- 「未実行」の規則は ERROR ではない
- 直したら、報告書の該当箇所と status.yaml を出し直してから lint を再実行する

**lint の指摘による差し戻し**(`context.lint_error=yes`。フロー完了の前の lint で ERROR が出た)で起動したときは、工程0のあと、入口 skill から渡された指摘を上の規約どおりに直す。生成コード・fixture を直した場合は、生成コードの実行確認(`clean_run` を含む)をやり直す。報告書は直した箇所を更新し、§8 に修正の内容を書き、status.yaml を出し直して(`env_restore` は今回の復元)、この lint を実行する。

# §30 状態カタログ案生成

ノードID: `cat` / クラス: `.text`
参照付録: G, E, A, B / 参照テンプレート: 94, 96

## 1. 役割

あなたはPMSのテスト設計者である。**完了済み全フローの累積探索記録を主入力とし**、実観測された状態を一次情報としてカタログ化する。仕様書・ソースからの列挙は補完的な二次情報である。

**あなたが作るのは案であり正本ではない。** 断定できないことは断定せず、確度を明示する。

このカタログの主な用途は**ステップ2(単発型の項目生成)の語彙を提供すること**である。

**責務境界**: 本作業は「どんな状態が必要か」を定義するだけである。**テスト項目を書いてはならない。フィクスチャを実装してはならない**(実装はステップ2の探索作業の担当)。

**状態カタログとKBの役割分担**: 状態カタログは「シナリオの前提状態を指す統制語彙」、KBは「対象システムに関する事実の記録」である。**同じ内容を両方に書かない。** 状態の成立方法・確認方法の詳細な観測記録はKBに置き、カタログは状態ID・定義・成立条件・established check という語彙としての最小限を持つ。

## 4. 固有手順

### 状態とは何か

「状態」とは、**テスト開始前に成立していなければならない前提**であり、フィクスチャが作るものである。以下は状態ではない。

- 操作手順(「ログイン画面でIDを入力する」) → フィクスチャの実装内容。状態は「ログイン済」
- テスト項目の実行結果(「TC-XXXを実行した後」) → 項目間依存は禁止
- 検証したい事柄そのもの(「集計値が一致している」) → それは期待結果
- 画面上の一時的な表示状態(「モーダルが開いている」) → 通常はテスト本体の操作範囲

**例外**: UI途中状態でも、到達までの操作が長く、複数項目がその地点から検証を始めるなら状態として登録してよい。判断基準は「複数のテスト項目が同じ前提を共有するか」。

### 分類

抽出漏れを防ぐため、`vocab.state_category` の**5分類すべてについて候補を探す**。

| 分類 | 内容 | 典型例 |
|---|---|---|
| AUTH | 認証・権限状態 | 管理者ログイン済、未ログイン、セッション期限切れ |
| DATA | データ存在状態 | 印刷実績あり/なし、ユーザー登録済 |
| ENTITY | エンティティのライフサイクル状態 | ジョブ: 待機中/処理中/完了/エラー |
| CONFIG | 設定・ポリシー状態 | 印刷ポリシーON/OFF、上限枚数設定済 |
| ENV | 環境・外部連携状態 | プリンタ接続済/未接続、ライセンス期限切れ |

### フェーズ1: 探索記録からの抽出(一次情報)

探索記録を機械的に読み、以下を状態候補として起こす。

1. **`requires_setup` に現れた状態** → 既にカタログ化されている。`established_check` と操作列を setup-log から転記する
2. **各ステップの `verified_by` / `observed`** → 「操作の結果として成立した状態」が読み取れる(例: 「ジョブが完了状態になった」→ `S-JOB-COMPLETED`)
3. **`carried_data`** → 持ち回られたデータは、後続ステップにとっての前提状態を示している
4. **`blocked` になったステップの理由** → 作れなかった状態が明示されている
5. **申し送り台帳の `初期状態外`・`状態未整備`** → 需要が確定している未整備状態。前者は `未整備`、後者は `未整備(実操作不可)` に対応する見込み
6. **状態需要リストの行** → ステップ1で追加された状態。`整備済` は setup-log・fixture から転記して `整備済`、`採用` は `未整備`。**状態IDは状態需要リストのものをそのまま使う**(requires・fixture から参照されているため)。`不採用` は人間の判断の記録として catalog-log.yaml に残す

**探索記録から起こした状態には、成立確認方法と構築の骨子が既に実績として存在する。推測で書き直さず、記録から転記すること。**

### フェーズ2: 文書・ソースからの補完(二次情報)

フェーズ1で拾えなかった状態を、5分類ごとに補完する。

- **AUTH**: ロール定義を列挙し、ロールごとに1状態。「未ログイン」「セッション切れ」も検討
- **DATA**: 主要エンティティごとに「存在する/存在しない」を検討。**データ量の差(0件・大量)は需要が出るまで登録しない**
- **ENTITY**: ステータス enum を列挙し、**画面上の挙動が分岐する状態だけ**を候補にする
- **CONFIG**: 設定項目のうち、**他機能の挙動を変えるもの**だけを候補にする
- **ENV**: 外部依存の接続有無。テスト環境で制御可能かを併記

**この段階で追加した状態の確度は `文書のみ` または `推測` である。**

**フェーズ2の完了時点で停止して報告し、人間の許可を得る。** 停止時の報告内容:

- 候補一覧と、画面確認が必要なもの(確度 `文書のみ`/`推測`)
- 画面確認のうち**データを変更する操作**(登録・削除・設定変更)の一覧
- 確認に必要なテストアカウント・テストデータ

**許可が得られない間はフェーズ2までの成果物を出力して作業を終える**(後段はその成果物を参照してよい)。

### フェーズ3: 実画面による確認(許可後に実施)

1. **読み取り専用の確認を先に行う**(ステータス表示、権限による出し分け、空一覧の表示など)
2. データ変更を伴う確認は許可された範囲でのみ行う。実施した変更は記録し、可能なら元に戻す
3. 各状態について確定させる: **成立確認方法**(00のロケータ規約に従う。**snapshot の一時IDを記録してはならない**)/ **構築の骨子**(要旨のみ。詳細な操作列はステップ2の担当)/ **実操作で作れるか** / **解除方法**
4. 情報源間で整合しない点は DISC に記録する

**このフェーズでフィクスチャのコードを書いてはならない。**

実画面操作の安全規則: 読み取り専用操作は自由に行ってよい。登録・更新・削除・設定変更は許可された範囲のみ。設定変更は変更前の値を必ず記録し、確認後に戻す(戻せなかった場合は報告)。削除操作は自分が作ったデータに限定する。

### フェーズ4: 正規化・統合

1. 同じ意味の候補を統合し、命名規則(`vocab.id_format.state`)に揃える
2. **排他関係**を明記する(例: `S-PRINT-LOG-EXISTS` と `S-PRINT-LOG-EMPTY`)
3. **前提関係**を明記する。ただし依存は浅く保つ。3段以上の依存が出たら粒度が細かすぎる合図
4. **整備状況**を判定する(`vocab.provisioning`)。`tests/fixtures/` を確認し、既にあるものは `整備済`
5. 「検証担当項目」は、ステップ1のシナリオで当該状態を作る機能を検証しているものがあればそのID。なければ `<機能コード>-未採番`。機能検証が不要なデータ状態は `不要(データ状態のみ)`

**粒度の原則**(カタログ肥大化を防ぐ最重要ルール):

1. **需要のない状態は登録しない。** 「ありうる」ではなく「複数の項目が使う」が基準。**申し送り台帳に対応する記録があるものは需要が確定している**ため優先的に登録する
2. **パラメータで表せる差は状態にしない。** 「実績3件」「実績100件」は別状態ではなくデータ量パラメータ
3. **組み合わせ状態は作らない。** 「管理者ログイン済かつデバイス登録済」は2状態を `requires` に並べれば表現できる
4. **画面挙動が分岐しない ENTITY 状態は落とす**
5. 落とした候補は `catalog-log.yaml` に**不採用理由付きで残す**

### 増分更新の規約(2回目以降)

- 既存の状態ID・定義は変更せず追記する。訂正が必要な場合は旧記述を残して訂正理由と日付を書く
- 前回処理済みのフローIDを `catalog-log.yaml` の `processed_flows` に記録し、次回は**未処理フローの探索記録だけを読む**

### 不明点の扱い

- 情報源間で矛盾する場合は**実画面を優先**し、矛盾は DISC に記録する
- 実画面でも確認できない場合は確度 `確認不能` で登録し、`open-questions.md` に理由を書く

## 1. 役割

あなたは手順書の保守者である。フローの実行で記録された手順改善シグナル、各作業の status.yaml と成果物、人間の指摘を材料に、手順書に小さな差分の改訂を加え、その効果を判定する。

### S1 集計

### S2 振り分け

- 未処理シグナルを全件 `vocab.signal_route` に振り分ける。**手順に来るのは一部である**
- 手順以外の行き先は、該当台帳へ回付した事実だけを記録する(回付先の内容は書き換えない)
- 1件だけのシグナルで、後段・人間・回帰実行の裏付けもないものは `様子見` にする

### S3 改訂案

手順行きのシグナルを手順箇所ごとにまとめ、改訂案(IMP)を起こす(ID書式は `vocab.id_format.improvement`)。

- **削減・統合で解消できないかを先に検討する**
- **差分で書く。1 IMP = 1 手順箇所。** 手順書の全面・節単位の書き直しをしない
- 個別の画面・機能に固有の内容をルールにしない(KB へ回付する)
- 起票時に、**期待する変化・判定期間(対象の手順箇所が実行される回数)・撤回条件**を登録する。起票後に変更しない
- 撤回した手順箇所は、撤回後に新しいシグナルが出るまで再提案しない

### S4 区分判定

変更の位置と文言で区分を判定する(00 ■手順改訂の統制)。複数に当たる場合、迷った場合は上位の区分にする。

### S5 適用

- 区分A(自律適用の解禁後)と、人間が `採用` にした改訂を試行版として適用し、状態を `試行中` にする。**1回の作業40で試行を開始するのは `vocab.default.max_trials_per_run` 件まで、同一の手順箇所で同時に試行するのは `vocab.default.max_trials_per_location` 件まで。** 超える分は `提案` のまま待たせる
- 区分Bと、自律適用の解禁前の区分Aは、状態を `承認待ち` にして台帳に積む
- 区分Cは、状態を `報告のみ` にして報告書に載せる
- 適用後に lint を実行し、ERROR があれば適用を取り消す
- `vocab.meta.procedure_version` を上げ、git にコミットしてタグを付ける。000 改訂履歴に、IMP ごとに1行(IMP-ID・手順箇所・変更の要旨・理由・版)を追記する。配備は次のフローの開始時に行う

### S6 判定

判定期限に達した `試行中` の改訂を判定する。

- **主判定は、対象シグナルの再発の有無**(同じ手順箇所に同じ種別のシグナルが出なくなったか)とする。フローの数が少なく対象領域も毎回違うため、集計指標の差より頑健である。効率指標は副次的に見る
- **ガード異常が出た改訂**: 作業40が自律適用したものは撤回する(効率指標の改善と相殺しない)。人間が採用・指示したものは `撤回推奨` にして報告する(撤回するかは人間が決める)
- **効果が確認できない改訂**: 追加は撤回、削減は定着とする(手順の肥大化を既定で防ぐため)。人間が採用・指示したものは撤回せず `撤回推奨` とする
- 対象の手順箇所が判定期間内に実行されなかった場合は、`vocab.default.max_trial_extensions` 回まで延長する。それでも実行されなければ、上の既定で決める
- 撤回も新しい版として適用する(00 ■手順書の版と配備)
- (任意)作業20に関わる改訂は、過去フローの探索記録を入力に作業20を再実行する**リプレイ評価**で判定してよい。作業10に関わる改訂はリプレイで比較できない(KBが育っているため)ので、以後のフローでの試行で判定する

### 人間の明示的な指示による改訂

S1〜S6 とは独立に、いつでも受け付ける(00 ■手順改訂の統制 人間の明示的な指示の扱い)。

- 箇所と内容が特定された指示には、**区分に関わらず従う。** 懸念があれば具体的に1回伝えてよいが、人間が指示を維持したら改訂する。曖昧なら箇所と内容を確認する
- 改訂表に状態 `指示適用` で記録し、000 改訂履歴に**指示の原文を転記する**。保護ブロックを変えた場合は基準ハッシュを更新する
- lint を実行し、版を上げ、コミットしてタグを付ける。配備はフローの境界で行う

## 5. 固有の禁止事項

- 人間の明示的な指示なしに、保護ブロックを変更しない
- 区分Bの改訂案(および解禁前の区分A)を、人間の採用または明示的な指示なしに適用しない
- **区分や保護ブロックであることを理由に、人間の明示的な指示を拒否しない**

- 実行中のフローがある間に手順書を配備しない

- `actions[].locator` は**安定ロケータ(またはページオブジェクト/部品のメソッド参照)のみ**。snapshot の一時IDを書かない
- `assertion_hint` は**必ず書く**(`blocked` のステップを除く)。決定的に検証できる形で、**自シナリオのデータにスコープして**書く(環境全体の件数を基準にしない)。判定不能なら「決定的な検証手段が見つからない」と正直に書く
- `wait` は非同期待機を行ったステップに必ず書く
- `nondeterministic` は非決定値を扱ったステップに書く。未登録の値は `catalog_id: 未登録` とする
- `carried_data` はシナリオ単位で1箇所にまとめる(各ステップには書かない)
- **`blocked` のシナリオでも `requires_setup` を書き、blocked のステップより前のステップを判定付きで記録する**(lint `requires_covered` / `blocked_recorded`)
- `blocked` の最初のステップの `blocked_by` には、理由・参照・`resume_from` を書く。`操作手段なし` は需要IDと申し送りID(lint `ext_demand_linked`)、`禁止操作` は禁止ID(または包括原則の番号)と申し送りIDを書く。後続のステップは `{ reason: 前ステップが blocked }` でよい
- 再探索フローの記録は、当該シナリオの記録に新しい `flow_id` と `reexplore_of: <旧フローID>` を付けて追記する。パートPの記録は `recheck_of: <前回の prohibited_ops.digest>` を付けて追記する。いずれも旧記録は削除しない
- 健全性シグナルが出たステップには `health_signal`(種類 `kind` は `vocab.health_signal_kind`、要点 `detail`、観測した時刻 `observed_at`)を書き、判定を `passed` にしない(lint `health_recorded`)
- 探索したステップには `started_at`・`ended_at`(`vocab.timestamp_format`。AI実行マシンの時計)を書く。ステップの最初の操作の直前と、判定に使った観測の直後の時刻とする(待機を含む)。`blocked` で実行しなかったステップには書かない。作業15がサーバーのログを集める時間範囲に使う(00 ■健全性シグナルと問い合わせ ログの添付)。健全性シグナルのあるステップの `started_at` と `observed_at` は lint `health_recorded` が検査する(proc-v014 以降のフロー)
- **proc-v018 以降のフローでは、探索記録は進行役 pms が書く**(§10 パートC)。`explore.step` のカードの提出が合格したときに、`actions`・`started_at`・`ended_at`(そのカードの `pms act` の記録の最初と最後の時刻)・`verified_by.screen`(assert の記録)・`evidence`(`pms act screenshot` が `evidence/<ステップID>_<連番>.png` に保存したもの)・`act`(カードと連番)を記録から作り、判定・`verified_by.db`・`assertion_hint`・`observed`・`nondeterministic`・`wait`・`health_signal`・`blocked_by`・`carried_data` をカードの出力から写す。検証手段を変えた理由は `verification_note` に、`DB` 単独の理由は `verification` に `DB(理由: …)` の形で書く。シナリオの判定・`requires_setup`・`invariants`・`discrepancies`・`manual_gap` も pms が書く。`act` の連番と `actions` が記録と一致することを lint `explore_act_linked` が検査する(作業15の `health_fix` の記録を除く)
- 作業15で解消した記録は、同じ `flow_id` と `health_fix`(問い合わせの回数・原因・変えた操作・問い合わせの記録のパス・確認済みのログID)を付けて追記する。作業10の記録は削除しない。`health_fix` の付いた記録のどのステップにも `health_signal` があってはならない

## T12 ログID知見 — `kb/log-ids/`(1ログID1ファイル)

**ログIDは、PMS がログメッセージの種別ごとに割り当てた固定のIDである**(回帰テストの作成で採番するIDではない)。ログIDを主キーにし、そのログIDが出たときに観測した事象・原因・対処を蓄積する。同じログIDでも原因は1つとは限らないため、事象ごとに行を分ける。`kb/log-ids/00_ログID索引.md` に、ログID・メッセージの要旨・事象の件数・最終観測日の一覧を維持する。ファイル名はログIDとし、共通メタデータの `id` は接頭辞 `LID` + 連番とする。

マニュアル・仕様書に原因・対処の記載があっても、それは代表的な一例にとどまる。記載の所在は T11 にポインタとして置き、ここには転記しない。ここに書くのは観測した事象である。

| # | 事象 | 原因 | 対処 | 確度 | 出所 | 観測日 | ビルド | 記録 |
|---|---|---|---|---|---|---|---|---|
| 1 | 印刷ジョブは一覧に出るが状態が Error(AUTH-401) | 複合機に認証設定が残っており、登録外のユーザー名のジョブが拒否された | 登録済みのテスト用ユーザー名で印刷する(操作の変更) | 中 | OBS | 2026-09-03 | <ビルド番号> | work/PRT/health/inquiries/SC-PRT-05-1.md |

- 記録するのは、作業15で解消したとき(`resolved` / `env_changed`)に、問い合わせの回答が原因の根拠として挙げ、添付したログのログIDの一覧で確認したログIDだけである(§15 H5)

# 付録F: Playwright コード規約

作業20が参照する。他作業には渡さない。

## 構造とID突合

- **1シナリオ = 1 `test()`、各ステップ = `test.step()`**
- 全テストにシナリオIDを tag として付与する。これがIDとコードの突合キーである
- **全テストに生成元の注釈 `generated-by`(生成したフローIDと手順版)を付ける。** 回帰実行の失敗を切り分ける人(将来はAI)が、生成したフローと手順版へ遡れるようにするため(00 ■手順改善シグナル)。再探索フローや作業20の再実行で作り直したテストは、注釈を更新する

```typescript
test('印刷ジョブの投入と実行結果の確認 [SC-PRT-01]',
  {
    tag: ['@SC-PRT-01', '@PRT', '@external', '@serial-DEV'],
    annotation: { type: 'generated-by', description: 'F-002 / proc-v001' },
  },
  async ({ page, userLogin }) => {
    await test.step('S1: 印刷ジョブの投入 [SC-PRT-01-S1]', async () => { ... });
  });
```

- **1つのシナリオIDは、コード全体でちょうど1つの test にのみ付与する。** 1つの test に複数のシナリオIDを相乗りさせることも禁止
- ステップIDは `test.step()` のタイトルに `[SC-PRT-01-S1]` の形式で含める
- テストタイトルはシナリオ名を使い、末尾に `[シナリオID]` を付ける

> Playwright の tag・annotation 機能(test の詳細オブジェクト)は v1.42 以降。バージョンが古い場合はタイトル内 `[SC-...]` を grep する運用に切り替え、一意性検証は同様に行う。生成元はテスト本体の先頭に `// generated-by: F-002 / proc-v001` のコメントで残す。

## 前提状態(requires)の実装

- `requires` の各状態は、**作業10フェーズAで整備されたセットアップで充足する。作業20でセットアップを新規に発明しない**
- テスト本文の中でログイン操作等を毎回行わない(その操作自体が検証対象であるステップを除く)
- セットアップが未整備の状態を要するシナリオは、コード化せず「コード化不能・要差し戻し」として報告する
- `setup-log` で `verified: false` のセットアップは、実行確認で最初に単体実行し established check が通ることを確認してからテスト生成に使う
- **セットアップから他のテスト項目を呼んではならない**
- ログイン系状態は storageState を用いた setup project で実装してよい

## アサーション

- `assertion_hint` に基づき、web-first assertion で実装する。値を取り出してからの同期比較よりロケータベースの expect を優先する(自動リトライを効かせるため)
- **`verification` が `両方` のステップでは、画面アサーションとDBアサーションの両方を実装する。片方を省略しない**
- **`verification` が `DB` 単独のステップでは、コメントで理由を残す**

```typescript
// DB-ONLY: 内部処理の完了状態は画面に露出しないため
await expect.poll(() => queryJobStatus(jobId)).toBe('Completed');
```

- 値の比較強度は**非決定値カタログに従う**(実装方針は `vocab.strength` の `impl`)。カタログの強度を無視して完全一致を書いてはならないし、安定させたいという理由で強度を勝手に下げてもならない
- 期待結果の業務的意味を検証する。UI文言への厳密一致は `[厳密一致]` 指定のステップのみ

## 非同期待機

- **固定待機は禁止。** 00のポーリング契約に従い `tests/helpers/waitFor.ts` の `waitUntil()` を使う
- タイムアウト値は**作業10の `wait.measured_seconds` をもとに設定する**(実測値の3倍程度)。根拠をコメントで残す

```typescript
// 実測 42秒 (SC-PRT-01-S3)。余裕を見て 180秒
await waitUntil(() => jobIsCompleted(jobId), { timeout: 180_000 });
```

- 作業10の記録にない待機を追加する必要が生じた場合、逸脱としてコメントと報告書の両方に記録する
- 待機条件・タイムアウト値は、作業10の記録と `kb/async/`(T06)の双方を確認する。**両者が食い違う場合は作業10の実測を優先し、KBを訂正する**

## DB不変条件

00の2段構え設計に従って実装する。

```typescript
// シナリオ末尾: 自シナリオのデータにスコープした検査
test.afterEach(async ({}, testInfo) => {
  await waitForBillingQuiescence(ctx.jobIds);          // 非同期書き込みの完了を待つ
  await assertInvariantsScoped(ctx, ['INV-001', 'INV-002', 'INV-003', 'INV-004', 'INV-005']);

// globalTeardown: スイート終端でDB全体を1回検査

```

- **グローバルなDBスキャンを `afterEach` に書いてはならない**
- 実装は `tests/helpers/invariants.ts` に集約し、シナリオごとに書き分けない
- 不変条件の違反は、シナリオ本体のアサーションとは**区別可能な形で失敗させる**(失敗メッセージに `INVARIANT` を含める等)

## 環境情報

- **接続先・アカウント・パスワードなどの環境情報をコードに直接書かない。** `tests/helpers/env.ts` の `envValue('<キー>')` で読む(00 ■検証環境の情報。lint `env_value_leak` / `env_value_hardcoded`)。探索記録の `<env:キー>` は `envValue('<キー>')` に置き換える
- `envValue` は `tools/env/env.mjs get` を呼ぶだけにする(環境の選び方・各自の設定による上書きを1か所で決めるため)。使う環境は環境変数 `PMS_ENV` で切り替える(未指定なら設定の既定)。値がないときは例外で失敗させる(黙って空文字で進めない)
- `playwright.config.ts` の `baseURL` も `envValue('pms.url')` から取る
- DB への接続(`tests/helpers/invariants.ts` など)は、サーバ名・DB名を `envValue('db.server')` / `envValue('db.name')` から取り、サーバ証明書の検証は環境情報の `db.trust_server_certificate` に従う(00 ■DB への接続 [R-DB-1])。`true` または未登録なら `trustServerCertificate: true`、`false` なら検証する
- DB へのログインは環境情報の `db.auth` に従う(00 ■DB への接続)。`sql` なら `envValue('db.user')` / `envValue('db.password')` で SQL Server 認証、`windows` または未登録なら実行するアカウントの Windows 認証(Node の `mssql` では `msnodesqlv8` ドライバの `trustedConnection: true`)。**`db.trust_server_certificate` と `db.auth` は未登録を既定値(`vocab.env_optional_keys`)で補い**、`envValue` の例外で失敗させない

```typescript
// tests/helpers/env.ts — 検証環境の情報を読む(00 ■検証環境の情報)。値は config/environments*.json にあり、コードには書かない
import { execFileSync } from 'node:child_process';

const cache = new Map<string, string>();
export function envValue(key: string): string {
  if (!cache.has(key)) {
    // 値がなければ env.mjs が終了コード1で終わり、execFileSync が例外を投げる(テストは失敗する)
    const out = execFileSync(process.execPath, ['tools/env/env.mjs', 'get', key, '--reveal'], { encoding: 'utf8' });
    cache.set(key, out.replace(/\r?\n$/, ''));
  }
  return cache.get(key)!;
}
```

## 外部操作

- `tests/external/` のラッパ経由で呼ぶ。KB T05 の操作IDと1対1に対応させる
- 実行体に渡す機器のホスト・IP・アカウントは、KB T05 の「使う環境情報のキー」を `envValue` で読んで渡す(ラッパに値を書かない)
- **ラッパは skill 同梱の実行体を、KB T05 に記録された呼び出し方で呼ぶだけにする。** テスト実行時に skill の説明文を読んだり、AIに判断させたりしない。実行体の成否(終了コード等)はラッパの中で確認し、失敗時はテストを失敗させる
- **KB T05 に未登録の操作をコードに書かない**(作業10への差し戻し候補として報告する)
- **禁止操作リストの `禁止` / `要許可` に該当する操作をコードに書かない。** `条件付き許可` の操作は制約値を満たすことをコード上で確認できる形にし、制約の根拠を該当行IDとともにコメントに残す
- **外部操作を含むテストには `@external` タグを付ける**(含まないテストと分離し、実行時間を分けて計測するため)
- **直列化は操作対象ごとに決める。** 禁止操作リストの「同時実行の可否」が不可の操作対象を使うテストには `@serial-<対象略号>`(操作IDの対象略号。例 `@serial-DEV`)を付け、そのタグの Playwright project を `workers: 1` にする。同時実行できる操作対象(例: テスト用OU内のAD操作)まで直列化しない。操作対象の共有に起因する直列化は構成であり、後述の `serial` 最終手段ルールの対象外

## ロケータとページオブジェクト

- ロケータは原則ページオブジェクト経由で参照する。不足があれば追加してよいが、**追加分は作業10の探索記録(`actions[].locator`)に根拠があるものに限る**
- 2つ以上のテストが同じ操作列を使う場合、シナリオ部品経由で呼ぶ。テスト内で操作列を複製しない
- FRAGILE(CSS暫定)ロケータをそのまま使う場合、`// FRAGILE:` コメントを引き継ぐ

## 並列実行・再実行耐性とデータ分離

- **ゴールデンイメージ復元は回帰テストセットの実行開始前に1回のみ。** 環境がクリーンであることに依存したアサーション(全体件数等)を書いてはならない
- **テストが前提とするデータ・設定は、すべてテストコード(fixture・シナリオ部品・テスト本体)が作る。** ゴールデンイメージにないもの(探索時に作られて環境に残っていたデータ、手作業で作ったデータ)に依存しない。依存していると、復元のあとの回帰実行で失敗する
- 復元は `tests/global-setup.ts` が環境変数 `PMS_RESTORE=1` のときだけ行う。**globalSetup を書き換えて復元を既定にしない。テスト本体・fixture・`afterAll` から復元を呼ばない**
- 起動確認テスト(`tests/readiness/`)は setup project `readiness` とし、**全 project の `dependencies` に `readiness` を入れる**。ほかの project の対象から `tests/readiness/` を外す
- 各テストは**復元なしの再実行に耐えること**。作成データは一意化し、アサーションは自テストのデータにスコープする
- シナリオ間の並列実行を前提に書く
- 共有データ(設定・ポリシー等、一意化で分離できないもの)を変更するシナリオには専用のテストデータを割り当てる。割り当てられない場合はコード化せず報告書に記載する
- `test.describe.configure({ mode: 'serial' })` は最終手段とし、使う場合は理由を注記する

**整備状況について**: フィクスチャは**整備済みか否か**で扱いが決まり、実現手段では区別しない。ここでは**「実操作で作れるかどうか」だけを判定する**。API/DB投入でも作れるが未整備なだけのものは単に `未整備` とする。`未整備(実操作不可)` は過去日付の実績、0件状態、大量データ等に限る。**この判定に時間をかけないこと。**
