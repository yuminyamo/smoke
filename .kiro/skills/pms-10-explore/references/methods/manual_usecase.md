# 方式: manual_usecase

方式名: マニュアル起点の基本ユースケース / 既定の方式(`vocab.default.scenario_source`)

本ファイルはシナリオ策定方式の1つである(00 ■シナリオ策定方式)。`stages.md` §10 パートBの共通契約(スコープ・妥当性基準・記載ルール・既存テストスクリプトの扱い)は全方式に適用され、本ファイルはそれを緩めない。本ファイルが定めるのは、シナリオ候補をどこから、どう抽出するかだけである。

## 1. 入力資料

| 資料 | 所在 | 扱い |
|---|---|---|
| 利用者マニュアル・仕様書 | 領域指示、または KB T11(文書ポインタ集) | 主たる入力。対象機能の章・節を読む |
| 既存テストスクリプト | 人間が指定したもの、または KB T11 に所在があるもの | 参考情報(§10 パートB「既存テストスクリプトの扱い」) |
| 実画面 | 検証環境 | 文書に記載がない操作の確かめ(根拠 `画面観察`) |

- **前提条件**: なし
- **機能一覧の確定元**(初回フローの A2): マニュアルの目次構造(章・節 = 機能の単位)

## 2. 候補の抽出手順

1. 対象機能のマニュアルの章・節を読み、利用者がその機能で行う一連の作業(基本ユースケース)を候補として列挙する。章・節の見出しと、手順の記載が手がかりになる。仕様書は、マニュアルにない処理経路や完了条件を補う
2. 既存テストスクリプトの所在が示されていれば、確認している観点と代表値の手がかりとして読む(共通契約の「既存テストスクリプトの扱い」に従う)
3. 候補を共通契約の妥当性基準と選定指針で選ぶ。「この機能が全く動かなかったら出荷不能か」に当たる基本動作を残し、1機能あたり `vocab.default.scenarios_per_feature` 本に絞る。落とした候補は申し送り台帳に記録する
4. 残した候補を、検証意図ごとのステップ(3〜6)に分け、ステップごとに根拠の章番号を特定する
5. マニュアルに記載がないが利用者の作業として必要なステップは、`推測(仕様未記載)` または `画面観察` を根拠にする。手順の記載がないこと自体は、パートCでドキュメントギャップ情報として記録する

## 3. 根拠の書き方

- 文書名+章番号(例: `利用者マニュアル4-2`・`PMS仕様書 v12.3 5.2章`)
- 既存テストスクリプトを参考にしたステップ: `既存テスト:<スクリプト名>#<該当箇所>`(文書に記載があれば文書を先に書く)
- 文書に記載がない: `推測(仕様未記載)` / `画面観察`

## 4. 代表値と範囲外の扱い

- パラメータの代表値は、マニュアルの記載例または画面の既定値から1つ選ぶ
- 同一経路のバリエーション(用紙サイズ違い等)は代表1件に畳み、残りを申し送り台帳(`同一経路`)へ記録する
- その他の範囲外(異常系・初期状態外など)は共通契約どおり申し送り台帳へ記録する

## 5. 方式固有の禁止事項

なし

## 6. 方式固有のDoD

- [ ] 全シナリオで、少なくとも1つのステップの根拠が文書名+章番号である(対象機能にマニュアル・仕様書の記載がない場合は、その旨を報告書 §6 に書いた)

## 7. 方式固有のKB・DISC

- KB: 根拠にした文書の所在が KB T11 になければ登録する(内容は転記しない)
- DISC: 文書と実画面の食い違いは種別 `実画面≠マニュアル` / `実画面≠仕様書` / `仕様書≠マニュアル` / `三者不一致`(00 ■不整合レポート)
