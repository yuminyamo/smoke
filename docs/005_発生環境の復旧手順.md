# 発生環境の復旧手順(手順の改訂を取り込んで続きを行う)

作業の途中で止まり、原因が手順書か道具(`tools/`)にあったため、このリポジトリで手順を改訂した。その改訂を、**止まった環境(発生環境)に取り込み、同じフローを止まったところから続ける**ための手順である。

- 読む人: 発生環境で作業を進めているメンバー(と、その管理者)
- 1〜6章はどの改訂でも同じ手順である。改訂ごとに要る作業(設定の追加・確かめ方)は7章に改訂ごとに書く
- 改訂の内容と理由は `procedure/docs/000_overview.md` の改訂履歴(手順版ごとの章)にある

---

## 1. 全体の流れ

| # | すること | 章 |
|---|---|---|
| 1 | 止まった状態を控える(まだ何も直さない) | 2 |
| 2 | 改訂(新しい手順版のタグ)を取り込む | 3 |
| 3 | 各自のファイル(git に入っていない設定)を改訂に合わせる | 4 |
| 4 | 改訂ごとの作業を行い、直ったことを確かめる | 7 |
| 5 | 版を途中で上げたことを flow.md に記録する | 5 |
| 6 | 止まったところから再開する | 6 |

---

## 2. 止まった状態を控える

取り込む前に、いまの状態を控える。あとで「何が直って、何が残っているか」を比べるためである。

```
node tools/pms/pms.mjs status --flow F-xxx
```

- 出力のうち、「人間の確認待ち」の行(カードID・種類・理由)を控える
- `work/_flows/F-xxx/flow.md` のメモ欄の最後の数行を控える(チャットの作業で止まった場合は、ここに止まった理由がある)
- **`work/` の記録(queue.json・setup-log・探索記録・台帳)を手で直したり消したりしない。** 続きはこの記録から始まる

---

## 3. 改訂を取り込む

```
git status                         (作業ツリーに手で変えたものがないかを見る)
git pull
git fetch --tags
```

- `git status` に `procedure/`・`tools/`・`.github/`・`.kiro/` の変更が出ていたら、取り込む前に管理者に相談する(これらは手で変えないファイルである)。`work/` の変更は、フローの記録なのでそのままでよい
- `git pull` で衝突したら、それ以上進めずに管理者に相談する

取り込めたら、版と skills を確かめる。

```
grep procedure_version: procedure/vocab.yaml       (改訂の手順版。例 proc-v024)
node tools/build-skills/build-skills.mjs --check   ("skills_in_sync: OK" と、同じ手順版が出る)
```

skills とエージェント(`.github/`・`.kiro/`)は改訂のコミットに含まれているので、再生成は要らない。

---

## 4. 各自のファイルを改訂に合わせる

次のファイルは各自のもので git に入っていないため、`git pull` では変わらない。改訂で見本が変わったときは、自分で合わせる。

| ファイル | 見本 | 合わせ方 |
|---|---|---|
| `config/pms.json` | `config/pms.sample.json` | 下のコマンドで差を見る。**使用禁止のパターン(`runner.<名前>.deny`)は足りないものを必ず足す。** 見本にあって自分の設定にないキーは、既定値で動くので、値を変えたいときだけ足す |
| `config/environments.local.json` などの環境情報 | `config/environments.sample.json` | 直接編集しない。改訂で加わったキーを `node tools/env/env.mjs set` で保存する(7章に書く) |

`config/pms.json` と見本の差を見るコマンド(何も出なければ差はない):

```
node -e "const r=(f)=>JSON.parse(require('fs').readFileSync(f,'utf8'));const s=r('config/pms.sample.json'),p=r('config/pms.json');for(const k of Object.keys(s))if(!k.startsWith('_')&&!(k in p))console.log('設定にないキー(既定値で動く):',k);for(const n of Object.keys(s.runner??{})){if(n.startsWith('_')||!p.runner?.[n])continue;for(const d of s.runner[n].deny??[])if(!(p.runner[n].deny??[]).includes(d))console.log('足りない使用禁止:',n,d)}"
```

最後に、環境情報が揃っているかを確かめる。

```
node tools/env/env.mjs require
```

## 5. 版を途中で上げたことを記録する

手順書の配備は、本来フローの境界でだけ行う(00 ■手順書の版と配備)。止まったフローを直して続けるためにフローの途中で版を上げるのは、**人間の判断による例外**である。flow.md のメモ欄に次の形で1行書く。

```
手順版を proc-v0XX から proc-v0YY に上げて続行(理由: <止まった内容>。判断: <判断した人>。<日付>)
```

- 報告書と status.yaml の `procedure_version` は、フローを始めたときの版のままになる(pms がキューに記録した版を書く)
- 作業20は、flow.md の版と現在の版の食い違いを報告書に書き、手順改善シグナルとして記録する。メモ欄にこの行があれば、それは想定どおりの食い違いである

---

## 6. 止まったところから再開する

止まり方によって再開のしかたが違う。2章で控えた状態で選ぶ。

| 止まり方 | 再開のしかた |
|---|---|
| `pms run` の STOP(カードが人間の確認待ち。`pms status` に「人間の確認待ち」がある) | 改訂で直ったカードを、1枚ずつ戻してから続ける(下のコマンド)。同じシナリオの後続のステップのカードも一緒に戻る |
| チャットの作業で止まった(flow.md のメモ欄に「環境情報待ち」「開始前シナリオ失敗」「DB 接続不可」などがある) | チャットで `/pms-regression F-xxx の続き` と伝え、直した内容(誰が何をしたか)を添える。入口の skill がメモ欄から再開点を決める |

`pms run` の STOP から再開する:

```
node tools/pms/pms.mjs reopen --flow F-xxx --card C-xxxx   (直ったカードごと)
node tools/pms/pms.mjs run --flow F-xxx
```

チャットで進めている(`pms-runner`)ときは、`reopen` のあとに `pms-runner` へ「続けて」と伝える。

- 戻したカードは、次に出るときに**新しい版のテンプレートで作り直される**(カードのファイルは出すたびに作る)。古いカードを手で直す必要はない
- 改訂と関係のない理由で止まったカードは戻さなくてよい。`pms run` を実行すれば、そのカードは人間の確認待ちのまま残りのカードが進み、報告書に載る
- **環境を復元し直さない。** 再開では復元しない(工程0をやり直すよう 7章に書いてある場合を除く)
- 再開してもまた同じ理由で止まったら、それ以上は進めず、`pms status --flow F-xxx` の出力と、止まったカードの出力(`work/_flows/F-xxx/out/C-xxxx.json`)を添えて改訂した人に伝える

## 7. 改訂ごとの作業

新しい改訂でこの手順を使うときは、この章に節を足す(新しい版を上にする)。節には、きっかけ・発生環境でしてほしいこと・確かめ方・戻すカードを書く。

### proc-v025 — `pms db` のパスワードの渡し方(2026-10-09)

**きっかけ**: proc-v024 を取り込んだあと、SQL Server 認証で `node tools/pms/pms.mjs db --check` が `"ok": false` になった。`pms db` がパスワードを環境変数で渡していたが、同時に付けていた sqlcmd の `-X` が環境変数の読み込みを止めていた。proc-v025 では標準入力で渡す。改訂の詳細は `procedure/docs/000_overview.md` 35章。

**1. 取り込む**: 3章のとおり取り込む。`config/pms.json` と環境情報は proc-v024 から変わらない(4章のコマンドで差がないことだけ確かめる)。保存した `db.auth`・`db.user`・`db.password` はそのまま使う。

**2. DB に接続できることを確かめる**: `node tools/pms/pms.mjs db --check` が `"ok": true` になり、`target` に検証環境のサーバ名・DB名・ログイン名が出ればよい。`"ok": false` のときは、下の proc-v024 の手順4の表で `reason` ごとに分ける。

**3. 続き**: proc-v024 の手順の途中だったときは、proc-v024 の手順5(戻すカード)から続ける。5章の flow.md の記録は、proc-v024 の行に続けて「proc-v025 に上げて続行」を1行足す。

### proc-v024 — DB の確認を `pms db` に集約(2026-10-08)

**きっかけ**: `pms run --flow F-001` が `explore.close` のカードで STOP した(理由「DB不変条件の検査に必要な認証確認とSELECTを実行できなかった」)。カードの AI が DB の接続先を調べようとして `env.mjs get` を実行し、`pms run` の使用禁止に当たった。改訂の詳細は `procedure/docs/000_overview.md` 34章。

**1. `config/pms.json` を直す**(4章のコマンドで差を確かめる)

- `runner.copilot.deny` に `"shell(sqlcmd)", "shell(sqlcmd:*)"` を足す
- sqlcmd を `sqlcmd` という名前で呼べないときは、`"db_cli": ["<sqlcmd のパス>"]` を足す

**2. sqlcmd を用意する**

DB の確認(`pms db`)が sqlcmd を呼ぶ。ODBC 版か Go 版(`go-sqlcmd`)を入れ、端末から `sqlcmd -?` で起動できることを確かめる。

**3. DB のログインの方式を決めて保存する**

検証環境の SQL Server は混合モードなので、Windows 認証と SQL Server 認証のどちらも使える。何も保存しなければ、AI を動かすアカウントの Windows 認証になる。

SQL Server 認証にするとき(読み取りだけの権限のアカウントを勧める):

```
node tools/env/env.mjs set db.auth sql
node tools/env/env.mjs set db.user <ログイン名>
node tools/env/env.mjs set db.password -          (値を標準入力から。各自の environments.local.json に入る)
```

**4. DB に接続できることを確かめる**

```
node tools/pms/pms.mjs db --check
```

`"ok": true` になり、`target` に検証環境のサーバ名・DB名・ログイン名が出ればよい。`"ok": false` のときは、出力の `reason` で分ける。

| `reason` | 意味 | すること |
|---|---|---|
| `env_missing` | 環境情報が足りない | `error` に書かれたキーを `env.mjs set` で保存する |
| `connect_failed` | 接続・ログインに失敗した | `error` を見て、ログインの方式・アカウント・DB 側の権限を直す。証明書のエラーなら `db.trust_server_certificate` を確かめる(00 ■DB への接続 [R-DB-1]) |
| `target_mismatch` | 接続した DB が `db.name` と違う | `db.server`・`db.name` が検証環境のものかを確かめる |

**この改訂で初めて実物の sqlcmd を使う。** sqlcmd が `-X`・`-C`・タブ区切り(`-s`)などのオプションを受け付けないというエラーが出たら、出力をそのまま改訂した人に伝える(`tools/pms/README.md` 2.7 の「実物の sqlcmd で確かめていないこと」)。

**5. 戻すカード**

STOP した `explore.close` のカード(F-001 で「DB不変条件の検査に必要な認証確認とSELECTを実行できなかった」と出たもの)。6章のとおり `reopen` してから `pms run` を実行する。DB の確認のあるほかのカード(`explore.step`・`explore.session_close`)が同じ理由で止まっていれば、それも戻す。
