全体構想と、今の skills の位置付け

構想のねらいは、機能追加・不具合修正・OSや連携ソフトのバージョンアップのたびに発生するE2Eテストの工数を減らし、不具合を早く見つけ、社内の品質点検の基盤にすることです。AIがテスト項目の策定・探索的実行・回帰テストコード生成を担い、人はレビューとガバナンスに回る形(自律テスト成熟度モデルの Level 3)を目指しています。

全機能・全観点を一度に自動化せず、3つのステップで網の目を細かくしていきます。今の skills が作るのは、そのうちステップ1の「単機能シナリオ」です。

  • ステップ1の範囲は固定です。シナリオ型・正常系のみ・各パラメータは代表1値・1機能内で完結(3〜6ステップ)。依頼に「異常系も」とあっても範囲は広げず、AIは確認のために止まります。
  • 扱わないものは捨てません。異常系・値違い・機能をまたぐ連鎖・実操作で作れない前提状態・手段(skill)のない外部操作などは、9語の理由コード付きで申し送り台帳に記録されます。理由コード別の件数が、そのままステップ2・3で何に投資すべきかを示します。
  • 正解は「今の製品の実際の動き」です。マニュアル・仕様書は手順を考えるための材料で、実挙動と食い違えば実挙動で進め、食い違いを不整合レポート(DISC)に残します。作った回帰テストは「基準バージョンから挙動が変わっていないこと」を機械的に確かめるものになります。

1つの作業 skill の中身

作業ごとの skill には「その作業に必要なものだけ」が入っています。作業10を行うAIに作業20のコード規約を読ませない、というように関心を分けるためです。

├── VERSION             procedure_version: proc-v011

KB の索引(kb/00_索引.md)と flow.md は作業場所のデータなので同梱されず、skill の起動時に読み込まれます。

入力情報

入力は「人が用意するもの」と「過去のフローの蓄積から読むもの」に分かれます。人が毎回用意するのは依頼文だけで、それ以外は一度用意すれば以後のフローで使い回されます。

人が用意するもの

  • 依頼文: 対象領域(1〜2機能)と、シナリオを何から作るかの手がかり。flow.md に原文のまま転記されます
  • 文献: 利用者マニュアル・仕様書・既存のテストスクリプト(所在を依頼文に書くか、KB の文書ポインタ T11 に登録)
  • 検証環境: Hyper-V 上の PMS サーバ VM とそのゴールデンイメージ(config/golden-restore.json)
  • 環境情報: PMS の URL・アカウント・DB・複合機の IP など。共有分は config/environments.json、パスワードは各自の environments.local.json。足りなければAIがまとめて聞き、保存して次から聞きません
  • 禁止操作リスト: work/_common/prohibited-operations.md。AIが実行してはならない操作。未記入でも始められます(包括原則だけが働く)
  • 外部操作 skill(印刷指示・機器操作など)と問い合わせ skill: 人が段階的に整備。なければAIは記録だけ残して先へ進みます。作り方は→ 補足
  • 開始前シナリオの設定(任意): config/pre-stage-scenarios.json。VM の復元では戻らない機器設定などを作業前に戻す

蓄積から読むもの

  • KB の索引 kb/00_索引.md: 開始時はこれだけを読み、必要なファイルだけを開きます(全読み禁止)
  • 既存のテスト部品 tests/: 前提状態は既存 fixture の実行が第一選択。同じ操作を探索し直さない
  • 過去フローの記録: scenarios.md・探索記録・セットアップ記録(確立済みの操作列・ロケータ・待機の実測値)
  • 非決定値カタログと各台帳(申し送り・外部操作需要・DISC)
  • 前の作業の status.yaml: 後段の作業は報告書を読み解かず、ここから入力を機械的に取ります(例: 作業20のコード化対象は作業10の codeable_items)

シナリオ策定方式(シナリオを何から作るか)

入口 skill が依頼文の書き方から方式を1つ選び、最初に1行で伝えます。方式で変わるのは「シナリオ候補をどの資料からどう拾うか」だけで、成果物の置き場所・書式・それ以降の作業は同じです。1フローの途中で方式は変えません。方式を増やす手順は → 補足

方式依頼の言い方の例主な入力前提条件シナリオの根拠の書き方
manual_usecase
既定		「印刷実行機能の回帰テストを作って」マニュアル・仕様書なし利用者マニュアル4-2
legacy_script「既存の手順書 X をもとに作って」既存テストスクリプトスクリプトの所在が分かる既存テスト:印刷_回帰テスト手順書.xlsx#印刷!No.3

どの方式でも、文書にもスクリプトにも記載がないステップの根拠は 推測(仕様未記載) または 画面観察 と明記され、レビューで見分けられます。既存スクリプトの操作手順や期待結果は書き写さず、実画面で確かめます。

作業の流れ

使う人から見た流れ

1フローは2〜3回のチャットに分かれます。作業10と作業20の間では必ず止まり、作業20は新しいチャットで行うことを勧めています(探索の経緯を持ち込まず、記録だけからコードを作るため)。

チャット 1
/pms-regression 印刷実行機能の回帰テストを作って
方式を伝え、フロー番号 F-003 を採番。必要なら作業01・02を先に行い、作業10でシナリオ作成と画面での確認
停止:「新しいチャットで『F-003 の続き』と伝えてください」
チャット 2(必要なときだけ)
/pms-regression F-003 の続き
ジョブがエラーなど、動いたが正常に終わっていない操作があったときだけ作業15。問い合わせて操作をやり直す
停止:「解消 1件、解消せず 1件。次はコード生成です」
チャット 3
/pms-regression F-003 の続き
関所(禁止操作リストの照合と lint)を通り、作業20で回帰テストを生成・実行確認
完了:「回帰テストを 4件追加しました。フローは完了です」

パイプライン全体

実行順序・分岐・停止点はすべて pipeline.dot に定義されています。各作業は終わると status.yaml に結果を列挙値で書き、入口 skill がその値を辺の条件に当てはめて次の作業を決めます。

関所(作業15・20の前)

prohibited-ops.mjs --compare で、作業10のあとに禁止操作リストが書き換えられていないかを照合します(変わっていれば作業10のパートPで保留ステップを判定し直す)。続けて lint.mjs --stage 10 で記録が決まりを満たすかを検査し、ERROR があれば作業10へ差し戻します。

判断は終了コードだけで

照合と lint の結果は、スクリプトの終了コード(0 / 1 / 2 / 3)だけで決まります。AIが「関係のない変更だ」「軽微だ」と判断して省くことはできません。差し戻しは同じ関所で1回までで、それでも直らなければ人に伝えて止まります。

工程0(作業10・20の開始時)

最初の操作の前に、VM をゴールデンイメージへ復元してログインできるまで待ち、設定があれば開始前シナリオで機器なども戻します。作業15・途中再開・作業の終了時には復元しません(作ったデータと記録が食い違うため)。

作業ごとの中身

作業10 シナリオ生成と探索

  1. 環境情報の確認 — env.mjs require。足りなければまとめて聞く
  2. 工程0 — 環境を復元 → 開始前シナリオ → 禁止操作リストの版(digest)を取得
  3. パートA — flow.md を作り依頼文を原文で転記。方式の前提を確認。初回(F-001)だけ機能一覧と機能コードを確定。既存資産を棚卸し
  4. パートB — シナリオを作る。操作手順は書かず、検証意図・判定基準・根拠・検証手段・前提状態だけを書く。範囲外は申し送り台帳へ
  5. パートC — 前提状態を fixture で整備(established check 付き)→ playwright-cli で操作手順を自分で編み出す → 成功直後に安定ロケータを解決 → 画面とDBで判定 → 健全性シグナルとDB不変条件を確認。前提状態の仕組みは→ 補足
  6. 記録と完了 — 報告書と status.yaml を出し、lint で ERROR 0件を確かめて停止

作業20 回帰テストコード生成

  1. 開始前の検査 — 禁止操作リストの照合と、作業10(・15)の記録の lint。どちらも0のときだけ始める
  2. 工程0 — 環境情報の確認 → 環境を復元 → 開始前シナリオ
  3. コード化の前の確認 — 前提状態ごとに fixture があるか、使う外部操作 skill に実行体があるか
  4. コード生成 — 探索記録の操作列とアサーションのヒントを忠実にコード化。1シナリオ=1 test()、1ステップ=1 test.step()
  5. ID突合 — シナリオIDがコード全体でちょうど1回、対象の全IDと全ステップがあるかを機械的に確かめ、突合表を更新
  6. 実行確認 — 復元直後の1回目を clean_run として記録 → 復元せず3回連続で実行して flaky を特定 → 実行時間を計測
  7. 記録と完了 — 報告書と status.yaml → lint → フロー完了(記録不足なら作業10へ差し戻し)

作業15 健全性の是正

期待結果は満たしたが自分のジョブがエラーになっている、といったシナリオについて、読み取りだけで自己診断 → 問い合わせ skill に再現手順と解決してほしいことを渡す(1シナリオ3回まで)→ 回答の操作で最初のステップからやり直します。環境の変更で直ったものは回帰テストで再現できないためコード化せず、人に判断を任せます。 → 補足

作業01 知見蓄積

調査対象を指示されると、後段の各作業が何を必要とするかを逆算して調査項目を自分で立てます。文献は本文を写さず「どの文書のどこに書いてあるか」だけを記録し、DB定義と実データ、実画面も調べて KB に書きます。

作業02 非決定値カタログ

同じ入力で同じ操作を、環境を戻さず3回続けて実行し、毎回変わる値を見つけます。変わる値は「関係式 → パターン一致 → 存在のみ」の順に強い検証を検討し、金額・枚数などが揺れたら強度を下げる前に報告します。 → 補足

成果物の蓄積の仕組み

1フローで全機能を網羅しようとはせず、フローを繰り返して回帰テストセットを育てます。回帰テストは毎回増えていく一方で、前提状態の fixture・シナリオ部品・KB・非決定値カタログは次のフローで流用されるため、フローを重ねるほど新しく作る量が減り、1フローあたりのコストが下がっていきます。

蓄積を成り立たせる決まり

追記が原則

scenarios.md・突合表・非決定値カタログ・台帳は既存の行を変えずに追記します。KB を訂正するときも旧記述を消さず、取り消し理由と日付を残します。

IDは全体で一意

シナリオIDとテストのタグは全フロー通算で一意にし、作業20が機械的に突合します。機能コードは初回フローで確定し、ディレクトリ名になるため後から変えません。

流用が第一選択

前提状態は既存 fixture の実行、外部操作は KB T05 の確立済み操作を使います。同じ操作列が2つ以上のシナリオに出たら部品にします(フローをまたいで数える)。

KB は索引から

開始時は kb/00_索引.md だけを読み、必要なファイルだけ開きます。新しく分かったことはその場で KB に反映し、KB を見ずに調べ直したことは発見ログで見えるようにします。

黙って落とさない

扱わない対象は申し送り台帳へ、コード化しなかったシナリオは突合表へ理由付きで残します。blocked になったシナリオも、前提状態の整備と途中までの記録を残します(後で解けたときに探し直さないため)。

引き継ぎは記録だけで

作業の間の受け渡しは status.yaml と flow.md で行います。別のセッション・別の担当者のAIでも、記録だけを読めば続きから進められます。

止まったシナリオが、あとで回帰テストになる経路

外部操作(印刷指示・機器パネル操作など)の skill は段階的にしか整備できません。skill がない操作は、その場で需要として積み上げておき、整備されたら再探索フローで同じシナリオに戻ります。需要の発生(AI)と skill の整備(人)は切り離されています。

手順そのものも実行から良くなる

KB が「対象システムについての事実」を蓄積する仕組みだとすれば、手順改善は「テストの作り方」を蓄積する仕組みです。実行中のAIは手順書を書き換えず、気づきをシグナルとして記録するだけにとどめます。

人が判断する場面

人のレビューは後段の作業を止めるゲートにはしていません(非ブロッキング)。止まるのは、行為の許可や環境の前提など、人でなければ決められない場面だけです。止まったときは、AIが「何が起きたか・誰が何をすれば進むか」を1〜3行で伝えます。判断した人と内容を添えて「F-xxx の続き」と伝えると、flow.md に記録されて再開します。

非決定値カタログとは

回帰テストは「前回と同じ結果になるか」を比べます。ところが画面やDBには、ジョブID・作成日時のように実行するたびに変わる値が混ざっています。非決定値カタログは、値ごとに「どこまで厳密に比べるか(検証強度)」を決めた一覧です。強度は推測ではなく、同じ入力で同じ操作を3回繰り返した観測で決めます。作業02が work/_common/nondeterministic-catalog.md に作り、作業10の判定と作業20のコードはこれに従います。

強度(強い順)意味値の例テストコードでの書き方
完全一致毎回同じ値になる同じ入力で印刷したときの課金明細の金額(3回とも 120 円)toBe(120) / toHaveText('120')
関係式値は変わるが、他の値との関係は常に成り立つ明細の総和 = 表示合計 / テスト開始時刻 ≤ 作成日時関連する値を取って関係を検証する
パターン一致値は変わるが、書式は決まっているジョブID JOB-00001042 → ^JOB-\d{8}$toHaveText(/^JOB-\d{8}$/)
存在のみ内容は問わず、あることだけ確かめるDBの自動採番(IDENTITY)列toBeVisible() / NOT NULL の確認

強度は上から順に検討し、関係式やパターンが書ける値を「存在のみ」に落とすことはできません。金額・枚数・ユーザー名・権限・設定値のような業務的に重要な値が揺れたら、強度を下げる前に報告します(本来一致すべき値が一致しないのは、不具合の可能性があるため)。

カタログがある場合

  • 変わる値は書式や関係で、変わらない値は完全一致で比べるので、毎回安定して通りながら金額・枚数の誤りは検出できる
  • 強度の判断が根拠(観測値)付きで1か所にまとまり、テストごとにAIが判断しない
  • テストが不安定でもテスト側では緩めず、カタログ見直しの提案として人に上がる。誰がなぜ緩めたかが残る

カタログがない場合

  • 初回の値をそのまま完全一致で固めると、2回目の実行からジョブIDや日時の違いで失敗する(flaky)
  • 逆に揺れそうな値を全部「存在のみ」にすると、金額が0円になってもテストは通る。緑のまま不具合を見逃す
  • 強度がテストごと・担当AIごとにばらつき、緩めた理由が残らない

観測は回帰実行と同じ条件で行います。環境を戻さずに3回続けて実行し、日をまたがず、同じ入力を与えます。毎回環境を戻すと、戻した直後にしか成り立たない値(件数・連番)を「毎回同じ」と誤って判定し、回帰実行の2回目以降で壊れるためです。

DB不変条件違反とは

DB不変条件は、どのシナリオを実行したあとでも常に成り立つべきデータの条件です。シナリオごとの期待結果とは別に、すべてのシナリオのあとで機械的に検査します。不変条件違反とは、この条件が崩れたことを指し、製品の不具合の可能性があります。

ID条件状態
INV-001完了したジョブ1件に対し、課金レコードがちょうど1件対応する課金スキーマ確認待ちで未実装
INV-002課金明細の合計額が請求総額と一致する課金スキーマ確認待ちで未実装
INV-003参照先を失った孤児レコードが存在しない使える
INV-004金額・枚数に負の値が存在しない使える
INV-005主要テーブルの必須列に想定外の NULL が存在しない使える

不変条件の検査がある場合

  • どのシナリオも同時に整合性テストになる。印刷のシナリオが、二重課金や負の金額といった別の箇所の破損も拾う(カバレッジが掛け算で増える)
  • 画面は「受付完了」で期待結果を満たしていても、裏で孤児レコードができていれば検出できる
  • 違反は自動でやり直さず人の判断へ回るので、たまたま通った再実行で不具合が揉み消されない

不変条件の検査がない場合

  • 各シナリオの期待結果に書いた点しか見ないため、画面に出ないデータの破損は回帰テストを素通りする
  • 探索のやり直しで違反が出なくなれば「直った」扱いになり、不具合が記録に残らないおそれがある

違反が見つかると、作業10・15は status.yaml に invariant_violation: found を出して止まります。管理者は「不具合として起票して続行」(フローは残りの作業へ進む)か「中断」を選びます。検査は SELECT だけで書き、tests/helpers/invariants.ts に集約し、失敗メッセージに INVARIANT を含めてシナリオ本体の失敗と区別します。誤った条件は全シナリオに偽の失敗を撒くため、不変条件のSQLは優先レビューの対象です。

健全性の是正とは

期待結果は満たしているのに、操作や環境が正しくないために本来の正常な結果になっていないことがあります。たとえば、印刷ジョブは発行でき一覧で検索もできるが、複合機に残っていた認証設定のためにジョブが「認証エラー」になっている場合です。この兆候を健全性シグナルと呼び、作業10はそのステップを passed にせず human-check として記録します。作業15(健全性の是正)は、そうしたシナリオについて原因を調べ、正常な結果が得られる操作を編み出し直します。

健全性シグナルは自分のテストのデータ・操作に関するものだけを数えます(他のデータのエラーは数えません)。種類は4つです: 自データの異常状態(ジョブがエラー・保留など)/ エラー表示 / 外部操作の異常終了・警告 / 関連システム(機器の表示・ログ)のエラー。

  1. 自己診断 — 記録と証跡、自データに絞った DB の SELECT、KB の落とし穴(T10)・環境(T09)を読み取りだけで確かめる。KB に解消の方法があれば、問い合わせずに試してよい
  2. 問い合わせ — 問い合わせ skill(別の問い合わせ対応エージェント)に、再現手順・本来得たい結果(期待結果をそのまま)・解決してほしいことを渡す。1シナリオにつき3回まで。入力と回答の全文を health/inquiries/ に保存する
  3. 回答の扱い — 回答は情報源であって正解の根拠ではない。「操作の変更」なら最初のステップから探索し直し、「環境の変更」なら禁止操作リストに照らしてから試す。「製品不具合の見立て」は DISC に記録する
  4. 結果の記録 — 下の表の4つの結果のどれかにして、作業20へ進む(解消しないことを理由に止まらない)
結果意味回帰テストへの扱い
resolved操作を変えて、シグナルが出ない操作を編み出せた探索記録を追記し、作業20でコード化する。原因と直し方は KB に残す
env_changed環境(PMS・機器の設定)を変えたらシグナルが消えたコード化しない。環境の変更は回帰テストで再現されないため、ゴールデンイメージや開始前シナリオに取り込むかを人が判断する
unresolved3回問い合わせても解消しない、または製品の修正が要りそうhuman-check のまま残す。as-is 判断の前に環境の是正を検討するよう報告する
no_skill問い合わせ skill がない記録だけ残して作業20へ進む

健全性の是正がある場合

  • エラーになったジョブのような誤った状態を、正解として回帰テストに固めることを防げる
  • 原因と直し方が KB に残り、次のフローで同じ環境の癖につまずかない
  • 環境側の問題は「環境の前提に取り込むか」という具体的な判断材料として人に上がる

健全性の是正がない場合

  • エラーのまま操作列がコード化され、後で環境が直された時点で回帰テストが偽の失敗を出す
  • 人の as-is 判断に「本当は環境や操作の問題」の項目が混ざり、誤った挙動を正解として凍結するおそれがある
  • 同じ環境の問題に毎フローでつまずき、そのたびに調べ直す

作業15は環境を復元せず、作業10が残した環境をそのまま使います。止まるのは、環境の変更に許可が必要なとき(要許可操作・包括原則)だけです。期待結果・判定基準・シナリオは変えません。

Web UI 以外の操作が必要なとき(外部操作 skill の作り方)

複合機のパネル操作、クライアントPCからの印刷指示、ジョブログの収集、AD やメールサーバの操作など、Web UI 以外の操作(外部操作)は、人が整備する外部操作 skill を介してだけ行います。AIは skill を作ったり変えたりせず、skill の使い方を確立して台帳(KB T05)に登録するところまでを担います。回帰テストは実行時にAIを使わないため、skill にはテストコードから直接呼べる実行体(CLI・スクリプト)が必要です。

拡張の手順

  1. 需要を見る — work/_common/external-op-demand.md の状態「未整備」の行を見て、整備する操作を選ぶ。1つの外部操作につき1行で、どのシナリオを止めているか・Web UI や DB による代替手段の有無が書いてある
  2. 禁止操作リストを決める — その操作の対象(実機・シミュレータ・CLIENT・AD・SMTP・PMS-OS)について、禁止 / 要許可 / 条件付き許可と、同時実行できるかを prohibited-operations.md に書く。行がないと包括原則で判断され、ゴールデンイメージで戻らない対象の変更は許可待ちで止まる
  3. skill を作る — .kiro/skills/<skill名>/ に SKILL.md と scripts/ の実行体を置く。Copilot でも使うなら .github/skills/ にも同じものを置く。生成スクリプトは skills.config.json にある skill しか作り直さないので、外部操作 skill は消されない
  4. 単体で確かめる — 実行体を手で起動し、終了コードと出力が下の約束どおりかを確かめる
  5. 整備記録を書く — 需要リストの行に整備日と skill名を書き、状態を「整備済」にする
  6. 再探索を頼む — /pms-regression EXT-002 を再探索して(需要IDを省くと「整備済」の全行が対象)
  7. ここからはAIが行う — 実行体の確認 → 使い方の確立(引数・前提・完了判定・所要時間の実測)→ KB T05 に操作ID(例 OP-DEV-005)で登録 → tests/external/ にラッパを実装 → 止まっていたシナリオを最初のステップから探索し直し → 作業20でコード化

項目約束理由

Web UI に加えて DB でも判定する理由

期待結果は画面での確認を主とし、できる限り DB でも裏付けます(検証手段「両方」)。1つの操作で、画面の層とデータを保存する層の両方を確かめられ、追加のコストが小さいためです。画面に出ない内部処理の完了状態などは DB だけで判定し、その場合は理由を1文添えます。

起きている問題画面だけで確認画面+DB で確認
画面は「受付完了」だが、ジョブの行が保存されていない(または2件保存された)見逃す検出できる
画面の金額は正しいが、DB の課金明細の金額が誤っている見逃す検出できる
一覧の表示が更新されるタイミングがまちまち待ちが不安定になり flakyDB の状態を待機条件にすると安定する
内部処理の完了状態が画面に出ない判定できないDB だけで判定できる(理由を併記)
画面の文言やレイアウトが変わった期待結果を業務的な意味で書いているので影響は小さいDB 側の確認は影響を受けない

DB での判定がある場合

  • 画面と保存されたデータの食い違い(表示だけ正しい)を検出できる
  • 非同期処理の完了を DB の状態で待てるので、待機が安定する
  • DB だけで判定した箇所に理由が残り、ステップ3で検証手段を見直すときの入口になる

画面だけの場合

  • 保存されたデータの誤り(二重登録・金額の誤り)は画面に出るまで見えない
  • 画面の更新タイミングに左右されて、テストが不安定になりやすい
  • 画面に出ない処理は「判定できない」として検証から抜けていく

DB の操作は SELECT だけで、自分のテストが作ったデータに WHERE で絞ります(環境全体の件数では判定しない)。DB の列の意味は KB の T03 に蓄積されます。DB での確認は画面の確認の代わりではなく、利用者に見える画面での確認が主です。

シナリオ策定方式の拡張方法

シナリオを作る材料を増やしたいときは、方式を1つ追加します。方式が担うのは「シナリオ候補をどの資料からどう拾うか」だけなので、作業10のパートC以降・作業15・20・成果物の書式は変える必要がありません。ここでは例として、不具合の改修票から、直した機能の基本動作のシナリオを作る方式(仮の名前 bugfix_ticket)を足す場合を示します。

  1. 語彙に加える — procedure/vocab.yaml の scenario_source に bugfix_ticket と説明を1行足す
  2. 方式ファイルを書く — procedure/methods/bugfix_ticket.md を、下の7つの見出しで、この順に書く(番号は付け替えない)
  3. 入口に手がかりを足す — procedure/router/SKILL.md の「シナリオ策定方式を決める」表に、依頼文の手がかり(例:「改修票 〇〇 から」)を加える。前提条件があれば、入口で確かめる内容も書く
  4. 版を上げて記録する — vocab.yaml の meta.procedure_version を1つ上げ、procedure/docs/000_overview.md の改訂履歴に記録する
  5. 生成して検査する — node tools/build-skills/build-skills.mjs のあと --check。語彙と方式ファイルの過不足や見出しの順が違えば、エラーになり何も書き出さない
  6. コミットして配る — 正本と生成物を同じコミットにし、版と同じ名前のタグを付ける。メンバーへの配布は、実行中のフローが終わってから

fixture・セットアップ記録・established check の関係

シナリオは、前提状態を requires に状態IDで書くだけで、作り方は書きません。前提状態の作り方の記録がセットアップ記録、作り方のコードがシナリオ部品と fixture、できたことの確かめ方が established check です。

名前何か誰が作るかどこにあるか
状態ID(requires)シナリオが必要とする前提の名前。ステップ1では初期状態セットの4つ(S-ADMIN-LOGIN・S-USER-LOGIN・S-DEVICE-REGISTERED・S-CLEAN-ENV)だけを使う語彙は人が決める。シナリオは参照するだけvocab.yaml / scenarios.md
セットアップ記録状態ごとの操作列・確認条件・コードの所在・2回実行で確かめたか(verified)作業10(フェーズA)work/<機能コード>/exploration/setup-log.yaml
シナリオ部品操作列そのもの。アサーションは書かない作業10tests/flows/
fixture部品を呼び、established check で成立を確かめてから、テストに前提を渡す作業10tests/fixtures/
established check状態が成立したことの機械的な確認。例: ナビゲーションにログアウトのリンクが表示される作業10が記録し、fixture に実装するsetup-log と fixture の両方
 
// tests/fixtures/auth.ts(例)
export const test = base.extend<{ userLogin: void }>({
  userLogin: async ({ page }, use) => {
    await loginAsUser(page);                          // シナリオ部品 = setup-log の steps
    await expect(page.getByRole('navigation')
      .getByRole('link', { name: 'ログアウト' })).toBeVisible();  // established check
    await use();
  },
});
  • なぜ established check が要るか。テストが落ちたとき、「前提が作れなかった」のか「検証対象の機能が壊れた」のかを区別するためです。確認なしのセットアップでは、失敗の切り分けができません。また、環境がきれいなことを暗黙の前提にせず、毎回成立を確かめます
  • 既存の fixture があれば流用します。実行して established check が通ることを確かめるだけで、操作を探し直しません
  • 2回実行して確かめます。2回目が残留データで失敗するなら、後始末をするか専用のデータにします。確かめられなければ verified: false と書き、作業20が最初に確認します
  • blocked のシナリオでも前提状態は整備して記録します。blocked が解けたときに作り方を探し直さないためです
  • 作業20はセットアップを新しく作りません。fixture のない前提を要するシナリオは「コード化不能」として作業10へ差し戻します
  • 起動確認テストはログイン fixture と同じ部品・同じ確認条件を使います。ログイン画面が変わっても、直す場所は1か所で済みます
