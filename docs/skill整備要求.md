# skill 整備要求

回帰テスト作成の手順(`procedure/`)が使うことを前提に、今後人間が整備する skill への要求をまとめる。skill を整備・改修するときは、この文書を要求事項として参照する。

- 初版: 2026-10-03(手順版 proc-v014 時点)
- 経緯: `docs/95 ログ・ファイル参照skill 検討.md`
- 手順書の正本が優先する。この文書と手順書が食い違ったら、手順書(`procedure/00_common.md` ほか)を正とし、この文書を直す

| ID | skill | 主な利用者 | 状態 | 優先 |
|---|---|---|---|---|
| SK-INQ | 問い合わせ skill(拡張) | 作業15、健全性チェックの問い合わせ(人間) | 既存 skill の拡張。ログの受け取りと根拠のログIDの回答 | 1 |
| SK-LOG | ログ収集 skill | 作業15、健全性チェックの問い合わせ(人間) | 新規 | 1 |
| SK-CLOCK | 時刻合わせ skill | 開始前シナリオ(作業10・20の工程0) | 新規 | 2 |
| SK-FILE | ファイル参照 skill | 作業10(探索)、回帰テスト(テストコード) | 新規。実現手段は別スレッドで検討 | 3 |

SK-INQ と SK-LOG は組み合わせて初めて効果が出るため、同時に整備する。SK-CLOCK がなくても SK-LOG は使える(時刻のずれは前後10秒の幅で吸収する)。

## 0. 全 skill に共通の要求

手順書の外部操作 skill の条件(00 ■外部操作)と、検証環境の情報の規約(00 ■検証環境の情報)から来る要求である。

| # | 要求 | 理由・根拠 |
|---|---|---|
| C-1 | **コードから非対話で呼べる実行体(CLI・スクリプト)を同梱する。** 本体は CLI とし、skill の説明(SKILL.md)は CLI の使い方を示す薄い入口にする | 回帰テスト・開始前シナリオ・別プロセスから同じものを呼ぶため。AIの対話的な介入が要る手順は回帰テストで再現できない(`vocab.external_op.skill_requirement`) |
| C-2 | **成否は終了コードで機械的に判定できる。** 0 = 成功、1 = 操作の失敗、2 = 使い方・設定の誤り(このリポジトリのツールと同じ割り当て) | 開始前シナリオの実行体・ラッパは終了コードだけで判断する |
| C-3 | **結果は標準出力に JSON 1つで返す。** 人間向けのメッセージは標準エラーに出す | 開始前シナリオの記録(`output`)と、作業の記録にそのまま残すため |
| C-4 | **接続先・アカウントを引数か環境変数で受け取り、skill の中に値を書かない。** 呼び出し側は `tools/env/env.mjs` のキー(`<env:キー>`)で値を渡す | 検証環境ごとに値が変わる。KB・ラッパには値ではなくキーを書く規約 |
| C-5 | **秘密情報(パスワード・接続文字列・トークン)を標準出力・標準エラー・出力ファイルに出さない** | 出力は成果物・問い合わせの入力に残る(lint `env_value_leak`) |
| C-6 | **操作の対象は、呼び出し側が渡した対象(テスト環境)に限る。** 渡されていない対象に作用しない | 包括原則3(`vocab.test_environment`)。テスト環境の対象を経由して外に作用する操作をしない |
| C-7 | 時刻を扱う入出力は ISO 8601(秒まで、時差付き。例 `2026-10-03T13:50:12+09:00`)とする | `vocab.timestamp_format`。探索記録の時刻と突き合わせるため |
| C-8 | `--help` で引数・出力・終了コードを表示できる | AIが使い方を確立し、KB T05 に登録するため(操作の資産化) |
| C-9 | skill名と実行体の場所を、人間が外部操作需要リスト・KB T05 に書ける形で決める(skill名は参考情報。正本は skills の機構) | 00 ■外部操作 操作の資産化 |

AIは skill を作成・改変しない(保護ブロック `EXT_SKILL_ONLY`)。整備・改修・配備は人間が行う。

## SK-INQ 問い合わせ skill(拡張)

### 目的

健全性シグナル(期待結果は満たしたが、自データのジョブがエラーになっているなど)の原因と、正常な結果を得る方法を、別の問い合わせ対応エージェントに調べてもらう。今回の拡張で、**サーバーのログを受け取り、原因の根拠になったログIDを返す**ようにする。

### 呼び出し元

- 作業15(健全性の是正)の H3(`procedure/stages.md` §15)
- 健全性チェックでアラートが上がったときの人間・別の仕組みからの問い合わせ(回帰テストの手順の外。同じ CLI を使う)

### 入力

| 入力 | 必須 | 内容 |
|---|---|---|
| 再現手順 | 必須 | 環境(環境ID・ビルド番号・関係する機器)、前提状態、操作列、観測した結果。秘密情報は含まれない(`<env:キー>` で書かれる) |
| 本来得たい結果 | 必須 | 期待結果(言い換えない) |
| 解決してほしいこと | 必須 | 「原因の根拠になったログIDを示してほしい」「調査のために環境を変更しないでほしい」を含む |
| ログ一式の所在 | 任意 | SK-LOG が出力したディレクトリ。ないときは「添付なし」 |
| 前回までの経緯 | 任意 | 2回目以降の問い合わせ。前回の回答の要点と、追加で行った操作と結果 |

入力はファイル(Markdown か JSON)で渡せること。コマンドライン引数の長さに依存しない。

### 出力

標準出力の JSON に、少なくとも次を含める(全文の回答はテキストのまま `answer` に入れてよい)。

| 項目 | 内容 |
|---|---|
| `answer` | 回答の全文(テキスト) |
| `kind` | 回答の区分の見立て(`vocab.inquiry_answer_kind`: 操作の変更 / 環境の変更 / 情報の追加依頼 / 製品不具合の見立て / 原因不明) |
| `cause` | 原因の要点(1〜3文) |
| `log_ids` | 原因の根拠になったログIDの配列(ログを添付しなかった・根拠がログにないときは空) |
| `actions` | 試すべき操作、または環境の変更(内容・手段・戻し方) |

### 要求

| # | 要求 |
|---|---|
| INQ-1 | 調査のために環境を変更しない(読み取りだけで調べる)。環境の変更が必要な場合は、内容・手段・戻し方を回答として返す |
| INQ-2 | `log_ids` には、添付されたログに実際に出現したログIDだけを挙げる(作業15は、挙げられたIDがログIDの一覧に出現するかを確かめ、出現しないIDは KB に記録しない) |
| INQ-3 | ログの解析は問い合わせ側のプロセスで完結させる。回帰テストを作るAIのコンテキストにログの本文を戻さない(回答にログの本文を長く引用しない) |
| INQ-4 | 呼び出しが失敗したとき(回答が得られない)は終了コード 1 を返す。作業15はそれも1回と数える |
| INQ-5 | 秘密情報を含むログの行を回答に引用しない |

### 受け入れの確認

- ログを添付した問い合わせで、`log_ids` に添付ログのIDが入り、添付ログにないIDが入らない
- ログを添付しない問い合わせでも従来どおり動く
- 同じ入力ファイルで、作業15の skill 経由と、人間がコマンドで実行した場合の両方が動く

## SK-LOG ログ収集 skill

### 目的

指定した時間範囲の PMS サーバーのログを、**既存の製品のログ収集ツール**で集める。秘密情報・個人情報は製品のツールのマスク機能でマスクする。回帰テストを作るAIはログの本文を読まず、集めたログ一式を SK-INQ に渡すだけにする。AIが読むのは**ログIDと件数の一覧**だけである。

**ログID**は、PMS がログメッセージの種別ごとにあらかじめ割り当てた固定のIDである(同じ種別のメッセージは毎回同じID)。

### 呼び出し元

- 作業15(健全性の是正)の H2・H3。手順上は**外部操作 skill**として扱い、AIが使い方を確立して KB T05 に登録してから使う
- 健全性チェックの問い合わせの前に、人間・別の仕組みがログを集めるとき

### 入力

| 入力 | 必須 | 内容 |
|---|---|---|
| 接続先 | 必須 | PMS サーバー(環境情報のキーで値を渡す) |
| 開始時刻・終了時刻 | 必須 | ISO 8601(時差付き)。呼び出し側が前後の幅(`vocab.default.log_window_margin_sec`、既定10秒)を足した範囲を渡す |
| 出力先ディレクトリ | 必須 | ログ一式を置く場所(作業15は `work/<feature_code>/health/inquiries/<シナリオID>-<回>-logs/`) |
| モード | 任意 | `collect`(集めて一覧も返す。既定)/ `ids`(すでに集めた出力先から、ログIDと件数の一覧だけを返す) |
| 対象のログの種類 | 任意 | 製品のツールが対象を選べるなら指定できる。既定は製品のツールの既定 |

### 出力

標準出力の JSON:

| 項目 | 内容 |
|---|---|
| `bundle` | ログ一式を置いたディレクトリ |
| `window` | 実際に集めた範囲(`from`・`to`。サーバーの時刻) |
| `masked` | マスクを適用したか(true でなければ失敗として扱う) |
| `log_ids` | 範囲内に出現したログIDと件数の配列(例 `[{ "id": "PMS-E-2041", "count": 3, "level": "ERROR" }]`)。**メッセージ本文を含めない** |
| `files` | 集めたファイルの名前・サイズの一覧 |
| `server_time_offset_sec` | 取れるなら、呼び出し元とサーバーの時刻のずれ(参考) |

### 要求

| # | 要求 |
|---|---|
| LOG-1 | **読み取り専用。** サーバーの設定・ログのローテーション・ログレベルを変えない |
| LOG-2 | **マスクを必ず適用する。** マスクできないときは集めずに失敗する(終了コード 1) |
| LOG-3 | ログ一式は**VM の外**(呼び出し元の作業場所)に保存する。ゴールデンイメージの復元でサーバー上のログは消えるため |
| LOG-4 | 時間範囲はサーバーのログの時刻で切り出す。時差の扱い(UTC / ローカル)を明示する |
| LOG-5 | ログIDの一覧は、ログの書式からログIDを機械的に抜き出して数える。ログIDを持たない行は件数だけを `"id": null` として返してよい |
| LOG-6 | 出力の大きさに上限を設け、超えたら一覧の `truncated: true` で知らせる(集めること自体は続けてよい) |
| LOG-7 | ログの解析(原因の推定)はしない。解析は SK-INQ の役割 |

### 実現方式(2026-10-04 実装。proc-v015)

リモートコマンドの整備方針(`docs/003_リモートコマンド整備方針.html`)に従う。

| 項目 | 実装 |
|---|---|
| 経路 | PowerShell リモート処理 + JEA。PMS サーバーVMのエンドポイント `PmsRemote` のロール `ServerRead` の関数 `Invoke-PmsLogCollect -From -To` が、VM の中でツールを実行する。PowerShell Direct は使わない |
| 呼び出し | skill `collect-server-logs` の実行体 → CLI 本体 `tools/remote/pms-remote.ps1 logs-collect` / `logs-ids`。テストコード・人間も同じ CLI を呼ぶ |
| 固定するもの | ツールのパス・引数・VM 内の出力先・マスクの指定(空なら必ず失敗)・正常終了とみなす終了コード(既定 0)・上限時間(300 秒)・上限サイズ(200MB)を、リモート側の設定 `remote/targets/pms-vm/config.psd1` の `LogCollect` で固定する。クライアントが渡せるのは時間範囲(ISO 8601 時差付き)だけ |
| 受け渡し | 集めた一式を zip の成果物にし、CLI が 4MB ずつ受け取って `-OutDir` に展開する(LOG-3)。ログIDの集計(LOG-5・LOG-6)は CLI 側で行い、ログの書式は `config/remote-targets.json` の `logCollect` に置く |
| 配置 | PMS VM は復元のたびに CLI が窓口を配置し直す(ゴールデンイメージには一度きりの前提だけを入れる)。導入手順は `remote/README.md` |

### 範囲外

- 任意のファイル・ディレクトリの参照(SK-FILE の範囲。それも定義済みの種別に限る)
- 回帰テストの判定に使うこと(ステップ1ではログを判定に使わない)

### 受け入れの確認

- 健全性シグナルを起こした時間範囲で集め、`log_ids` にその事象のログIDが出る
- 出力(`log_ids`・ファイル)に、テスト用アカウントのパスワードなどの秘密の値が含まれない
- 範囲外の時刻のログが含まれない(範囲の前後の端で確かめる)

## SK-CLOCK 時刻合わせ skill

### 目的

ゴールデンイメージの復元のあと、作業の最初の操作の前に、検証環境の時刻を**共通の時刻源1つ**に合わせる。操作の記録(AI実行マシンの時計)とサーバー・機器のログの時刻を揃え、SK-LOG で正しい時間範囲のログを集められるようにする。VM のチェックポイントから戻した直後は、VM の時計がチェックポイントを作った時刻のままのことがある。

複合機や関連サーバーは共有であり、NTP を安定して設定しておくことが難しいため、毎回合わせる。

### 呼び出し元

- 開始前シナリオの**外部操作のエントリ**(`config/pre-stage-scenarios.json` の `op`・`run`)。`hooks.work10` と `hooks.work20` の両方の先頭に、時刻を合わせる対象を `restores` に書いて置く(00 ■回帰実行の環境前提 時刻合わせ。設定例は `config/pre-stage-scenarios.sample.json`。操作IDは KB T05 に登録したもの。例 `OP-ENV-001`)

### 入力

| 入力 | 必須 | 内容 |
|---|---|---|
| 時刻源 | 必須 | 合わせる先(社内の NTP サーバー・ドメインコントローラーなど)。環境情報のキーで渡す |
| 対象 | 必須 | 合わせる対象の一覧(PMSサーバ VM・複合機・関連サーバー)。環境情報に登録されたテスト環境の対象だけ |
| 閾値 | 任意 | 合わせたあとに許すずれ(秒)。既定は skill 側の設定 |

### 出力

標準出力の JSON(開始前シナリオの記録の `output` に残る):

| 項目 | 内容 |
|---|---|
| `source` | 使った時刻源 |
| `targets` | 対象ごとの `before_sec`(合わせる前のずれ)・`after_sec`(合わせたあとのずれ)・`changed`(変更したか)・`method` |
| `runner_offset_sec` | AI実行マシンと時刻源のずれ(AI実行マシンの時計は変えなくてよい。測って返す) |

### 要求

| # | 要求 |
|---|---|
| CLK-1 | **合わせる先は共通の時刻源1つ。** AI実行マシンの時計を基準にしない(共有の機器を、複数の実行が別々の時計に合わせ合うのを防ぐ) |
| CLK-2 | ずれが閾値以下の対象は変更しない(共有の機器への書き込みを最小限にする) |
| CLK-3 | 合わせたあとも閾値を超えるずれが残ったら失敗する(終了コード 1)。開始前シナリオの復元エントリは `on_failure: stop` なので、作業は始まらない |
| CLK-4 | 何度実行しても同じ結果になる(冪等) |
| CLK-5 | 時刻以外の設定を変えない。対象の再起動を伴う方法を使わない(包括原則2: 復旧に人手・長時間を要する操作) |
| CLK-6 | 対象は呼び出し側が渡したテスト環境の対象だけ(C-6) |

### 受け入れの確認

- VM をチェックポイントから戻した直後に実行し、VM のずれが閾値以下になる
- 2回続けて実行し、2回目は `changed: false` になる
- 時刻源に接続できないときに終了コード 1 を返し、開始前シナリオが `failed` になる

## SK-FILE ファイル参照 skill

**実現手段は別スレッドで検討する。** ここには、このスレッドの検討で決まった要求と、実現手段の検討に持ち込む論点を書く。手順書はまだ変更していない。

### 目的

結果の確認に必要な、特定のフォルダに出力されるファイルを参照する。例: ジョブログ収集機能の、保存期間を過ぎたジョブログを DB から CSV にエクスポートする機能の検証では、エクスポートされた CSV を見る必要がある。

### 呼び出し元

- 作業10(探索): ファイルの内容を見て、判定のしかた(`assertion_hint`)を確立する
- 回帰テスト(テストコード): `tests/external/` のラッパから CLI を呼び、判定に使う

### 入力

| 入力 | 必須 | 内容 |
|---|---|---|
| 種別 | 必須 | skill にあらかじめ定義した種別(例 `joblog-export-csv`)。種別ごとに、置き場所・ファイル名の規則・形式を skill 側に人間が定義する |
| 作成時間帯 | 必須 | 開始・終了(ISO 8601、時差付き。サーバーの時刻) |
| 絞り込みのキー | 任意 | ファイルの中で自データの行を選ぶ条件(例 列 `JobId` = 一意化した値) |
| 返し方 | 任意 | `meta`(一覧だけ)/ `rows`(絞り込んだ行)/ `copy`(ファイルを呼び出し側の場所に複写) |

### 出力

標準出力の JSON: 該当したファイルの一覧(名前・作成時刻・サイズ・行数・ヘッダ)、`rows` のときは絞り込んだ行。該当なしは成功(終了コード 0)で空の一覧を返す(「まだ出ていない」と「失敗」を区別するため)。

### 要求

| # | 要求 |
|---|---|
| FILE-1 | **任意のパスを読まない。** 定義済みの種別の置き場所だけを読む。新しい種別は人間が skill に定義する(足りない種別は外部操作需要リストに記録される) |
| FILE-2 | **読み取り専用。** ファイルを移動・削除・変更しない |
| FILE-3 | **回帰テストの実行時にテストコードから CLI で呼べる**(C-1 は必須。「設定に応じて」ではない) |
| FILE-4 | **「今あるものを1回返す」だけにし、skill の中で待たない。** エクスポートは非同期で出てくるため、待つのはテスト側の `waitUntil`(00 ■非同期完了の待機)に任せる。待機のタイムアウトを AI が場当たりに変えられないようにするため |
| FILE-5 | **時間範囲は候補の絞り込みに使い、判定は自データの行で行えるようにする。** 同じ時間範囲に別のテスト・再実行のエクスポートが混ざり、保存期間切れのエクスポートには他のデータの行も含まれる(00 ■回帰実行の環境前提 テストデータ規約 2: アサーションの自データスコープ) |
| FILE-6 | 作成時間帯はサーバーの時刻で解釈する。呼び出し元との時刻のずれを返せるなら返す |
| FILE-7 | 返す行数・大きさに上限を設ける(探索中のAIのコンテキストに、ファイル全体を入れない) |
| FILE-8 | 秘密情報・個人情報を含む列は、種別の定義でマスクできるようにする |

### 実現手段の検討に持ち込む論点(手順書側)

- 検証手段の語彙(`vocab.verification`)に「ファイル」を加えるか、「DB」に準ずる扱いとするか。原則 `両方`(画面+DB)との関係
- 作業02(非決定値カタログ)の観測対象に、ファイルの中身(出力時刻・ファイル名の連番など)を加える
