# 改訂指示 02 — 段2 スクリプト実行(B2)と探索のカード

- 作成: 2026-10-07 / 前提: 段1(`01_共通の土台.md`)が反映済み / この段で上げる版: 段1 の版 + 1
- 先に `docs/94_改訂指示/00_共通の作法.md` を読むこと

## 0. この段でやること(要約)

1. **`pms run`** を作る。キューのカードを1枚ずつ、**新しいAIのセッション**(Copilot CLI、または Kiro CLI)で行わせ、終わったら提出されたかを確かめて次へ進む。提出されていなければ同じカードをやり直させ、上限を超えたら人間に回す
2. 作業10の**パートC(探索的実行)をカード**にする。`explore.step`(シナリオの1ステップを探索して判定する)・`explore.close`(シナリオの終わりの処理)・`explore.session_close`(探索セッションの終わりの処理)
3. 作業10の**報告書の数値と status.yaml を、記録から生成**する(`pms report`)。AI は所見の欄だけをカード `report.findings` で書く
4. **`pms stats`** で、カードの合格率・差し戻しの回数と区分を出す
5. 作業10のフェーズA・パートC・報告書は `pms run` で行うように手順書を改訂する。工程0・パートA・パートBは、これまでどおりチャットの作業10の skill が行う

## 1. 変更の意図

**主な実行形態を B2 にする**(2026-10-07 の人間の決定)。B2 では、ループ(次のカードを取る・やらせる・終わったかを確かめる)をプログラムが持ち、AI はループの1回分だけを行う。

- AI が途中で終わっても、ループは止まらない(同じカードをやり直させる)。**終わったかどうかを決めるのは、AI の「できました」ではなくキューの提出の記録である**
- カードごとに会話を捨てるので、会話の継続確認(`chat.agent.maxRequests`)とコンパクションが原理的に起きない(調査票001の H6 の型を構造で防ぐ)
- セッションを起こすときに playwright-cli を使用禁止にできる。記録を通らない操作をそもそも実行できない

**探索をカードにする理由**: 段1で setup-log は道具が書くようになったが、探索の記録(exploration-log の `actions`・時刻・判定)はまだ AI が長い会話の中で書いている。探索はステップごとに「何を操作したか(記録)」と「期待結果を満たしたか(判断)」に分けられる。前者を `pms act` に、後者をカードに分ける。

**記録から生成する理由**(docs/94 提案E): 報告書の件数や status.yaml の値は記録から決まる。AI に数えさせると、集計の誤りと、報告と実態の食い違いが起きる。

## 3. 作るもの

### 3.1 `pms run`

```
pms run --flow F-003 [--phase A|C|all] [--runner copilot|kiro] [--max-cards N] [--dry-run]
```

1. `pms next` と同じ規則で次のカードを取る。`done` なら 3.4 の報告書の生成と完了前の lint へ。STOP なら理由を表示して終了コード 3 で終わる
2. カードの種類に応じた**エージェントとモデル**で、新しいセッションを起こす(3.2)。カードの本文は標準入力かファイルのパスで渡す(コマンドラインの長さに頼らない。Windows の上限があるため)
3. セッションが終わったら、キューでそのカードが合格したかを確かめる。合格 → 1へ。未提出・不合格のまま終わった → 同じカードをやり直させる(段1の出し直しの規則と上限回数を使う)
4. 1枚ごとに、セッションの出力(Copilot CLI は `--output-format json` の JSONL)を `work/_flows/F-<番号>/runs/<カードID>-<回>.jsonl` に保存する。秘密情報が出ていないかを保存前に確かめ、出ていたら伏せる
5. 1枚ごとの上限時間を設け、超えたらセッションを止めて「未提出」として扱う
6. 環境変数 `PMS_RUNNER=b2` を付けてセッションを起こす(提出の記録に実行形態を残し、段3・段4の計測に使う)

**終了コード**: 0 = すべてのカードと報告書・lint が終わった / 3 = STOP(人間の判断待ち。理由は標準出力の JSON)/ 1 = 実行の失敗(CLI が起動しない等)/ 2 = 使い方・設定の誤り。

### 3.2 セッションの起こし方(設定で持つ)

呼び出しは `config/pms.json` の雛形で持ち、**コードに CLI のフラグを書かない**(CLI の仕様が変わっても設定だけで直せるように)。Copilot CLI の雛形の例:

```json
{
  "runner": {
    "copilot": {
      "command": ["copilot", "-p", "{prompt}", "--agent", "{agent}", "--model", "{model}",
                  "--no-ask-user", "--output-format", "json",
                  "--deny-tool", "shell(playwright-cli:*)",
                  "--deny-tool", "shell(npx:*)"],
      "timeoutSec": 900
    }
  },
  "cardTypes": {
    "setup.build":  { "agent": "pms-card-setup-build",  "model": ["gpt-6-luna"] },
    "explore.step": { "agent": "pms-card-explore-step", "model": ["gpt-6-luna"] }
  }
}
```

- **使用禁止にするもの**: playwright-cli の直接の呼び出し(`npx` 経由を含む)、`tools/env/env.mjs get ... --reveal`(秘密情報の値を AI が取り出せないように)、手順書と skills への書き込み。実際に指定できる形は、Copilot CLI の `--deny-tool`・`--available-tools`・`--allow-tool` のリファレンスで確かめる
- **Kiro CLI**: 非対話の実行のコマンドとフラグ、エージェントの設定(`toolsSettings.shell.deniedCommands` など)を公式ドキュメントで確かめて雛形を作る。確かめられなければ Copilot だけを実装し、Kiro の雛形は空にして報告する
- **エージェントの定義**: カードの種類ごとのエージェント(Copilot は `.github/agents/pms-card-<種類>.agent.md`、Kiro CLI はその形式)を、`build-skills.mjs` が正本から生成する。正本は `procedure/cards/agents.yaml` などに置き(種類・説明・モデルの候補・使ってよい道具)、**エージェントの本文はどの種類も同じ短い指示にする**: 「`pms next` が出したカードを読み、その指示どおりに行い、`pms submit` で提出する。提出が不合格なら理由だけを直して再提出する。カードの外の作業をしない」。`skills_in_sync` の検査対象に生成したエージェントを含める

### 3.3 探索のカード

| 種類 | 単位 | AI がすること | pms がすること |
|---|---|---|---|
| `explore.step` | シナリオの1ステップ(付録C の Step ID) | ステップの目的に沿って `pms act` で操作し、期待結果を満たすかを判定する | 入力の用意、記録からの `actions`・`started_at`・`ended_at` の作成、exploration-log への追記、台帳への記録 |
| `explore.close` | シナリオ1つ | DB 不変条件の検査(00 ■DB不変条件)、確立した操作の反映先(部品・KB)の決定と反映 | シナリオの判定(ステップの判定からの規則)、記録 |
| `explore.session_close` | フロー1つ | 探索セッションの終わりの全体検査 | 記録、`invariant_violation` の判定 |

**`explore.step` の入力**(pms が埋める): シナリオの目的・合格条件、そのステップの行(確認内容・期待結果・検証手段・根拠)、**前のステップまでの記録の抜粋**(操作の要約と判定。AI の要約ではなく記録から機械的に作る)、持ち回るデータの現在の値、KB の該当ページのパス、現在の画面。

**`explore.step` の規則**(規則IDで原本から差し込む): 実画面を優先し食い違いは DISC、禁止操作(`PROHIBITED_OPS` はブロックごと引用)、期待結果を変えない(`EXPECTED_IMMUTABLE` はブロックごと引用)、検証手段の扱い、健全性シグナル、非決定値、非同期待機、blocked にするときに残すもの、外部操作の確立の手順。

**`explore.step` の出力**(スキーマで縛る):

| 欄 | 内容 |
|---|---|
| `verdict` | `vocab.verdict` |
| `seqs` | このステップの操作の連番(成功した最短の列) |
| `verification` | 画面: `assert` の連番 / DB: 実行した SELECT と結果の要点 |
| `observed` | 観測した事実(文字数の範囲を決める) |
| `assertion_hint` | 作業20への機械的な検証方法の提案(必須) |
| `carried_data` | 持ち回るデータの更新 |
| `nondeterministic` | 非決定値(カタログID か、未登録なら追加候補) |
| `wait` | 非同期待機をしたときの条件と実測 |
| `health_signal` | 健全性シグナル(`observed_at` は操作の時刻の範囲内) |
| `blocked_by` | `blocked` のときの理由・参照・再開するステップ |
| `discrepancies` | 文書と実画面の食い違い(DISC の案。ID は pms が採番) |
| `handoffs` | 申し送り(理由コード・内容) |
| `procedure_signals` | 手順改善シグナル(種別・手順箇所・内容) |
| `evidence` | 証跡(`pms act screenshot` の連番) |

**検査**(段1の区分に足す): `seq_missing`・`unstable_locator`・`red_flag` に加えて、`expected_changed`(出力に期待結果・判定基準を書き換える欄が混ざっていない。入力の期待結果の文言が出力の判定理由で改変されていない)、`verdict_evidence`(`failed`・`human-check` に証跡がある)、`health_time`(`observed_at` が操作の時刻の範囲内)、`blocked_refs`(blocked の参照が台帳に実在する。理由コードが `vocab.reason_code`)。

**合格したら**: exploration-log に付録A の形で追記する。DISC・申し送り・手順改善シグナルは、pms が台帳に行を足す(ID を採番する)。段1で作った台帳への書き込みの部品を使い、DISC と手順改善シグナルの台帳を足す。台帳の表の形は templates の書式に合わせる。

### 3.4 `pms report` と完了前の lint

- 全カードが終わったら、`pms report` が作業10の報告書(00 ■完了報告の共通骨格と §10 の固有セクション)の**数値・一覧の部分**と、status.yaml(§10 の 8章の `context_updates`)を記録から作る
- 所見の欄(人間に伝えたいこと)は、カード `report.findings` で AI が書く。検査は `red_flag` と文字数
- 続けて `node tools/lint/lint.mjs --flow <フローID> --stage 10 --skip skills_in_sync` を実行する。ERROR が残ったら STOP(「lint 止まり」)にする。**この段では、lint の指摘を直すカードは作らない**(現行の「lint の指摘による差し戻し」の経路で、チャットの作業10が直す)

### 3.5 `pms stats`

```
pms stats --flow F-003 [--json]
pms stats --since 2026-10-01 [--json]
```

カードの種類ごと・実行形態(`PMS_RUNNER`。未設定は `b1`)ごとに: カードの枚数、初回合格率、平均の提出回数、不合格の区分ごとの件数(とくに `seq_missing`)、出し直しの回数、STOP の件数。setup-log と exploration-log の必須欄の充足率。

## 4. 手順書の変更

### 4.1 `stages.md` §10

- **パートCの探索的実行**を、「`pms run --flow <ID> --phase all` を実行する。カードは `explore.step`・`explore.close`・`explore.session_close`・`report.findings`」に置き換える。探索の規則の中身は、カードのテンプレートに規則IDで差し込む形に移し、§10 の本文には**キューの作り方(どの単位でカードにするか)と、pms が書くもの・AI が書くものの分担**を書く
- **作業10の流れ**: 工程0・パートA・パートB(・パートR・パートP)はチャットの skill が行い、終わったら `pms queue build --phase all` を実行し、flow.md のメモ欄に「pms run 待ち」と書いて止まる。利用者が端末で `pms run` を実行する
- **CLI が使えない環境の代わり**: `pms run` を実行できない場合は、チャットの作業10が段1と同じく、同じ会話の中で `pms next` のカードを順に行ってよい(段3で IDE 内のループに置き換える)
- **完了前の lint**: `pms run` が行うことを書く
- **5〜8章**: DoD を「pms が検査するもの」と「カードの出力欄で確かめるもの」に分ける。status.yaml は `pms report` が作ることを書く(キーと値の契約は変えない)

### 4.2 入口 skill(`procedure/router/SKILL.md`)

- 「続きの判定」に行を足す: flow.md のメモ欄に「pms run 待ち」があり、キューにカードが残っている → **止まる**。利用者に端末で `pms run` を実行するよう伝える。キューが終わり lint も通っている → 作業10は完了として、これまでどおり作業15・20の前の関所へ
- 「止まったときの伝え方」に文面を足す(例:「F-003 のシナリオができました。続きの画面での確認は自動で行います。端末で `node tools/pms/pms.mjs run --flow F-003` を実行してください。終わったら『F-003 の続き』と伝えてください。」)
- `pms run` が STOP で止まったときの伝え方: STOP の理由は `pms` の出力の文面をそのまま伝える。人間の判断が要る場面(要許可操作・DB不変条件の違反など)は、既存の「管理者の判断を受けて進める」に合流させる

### 4.3 `00_common.md`・`vocab.yaml`

- ■進行役と記録の道具(pms): `pms run`・セッションの起こし方・使用禁止にするもの・`pms stats` を足す。実行形態 B2 を主とし B1 を副とする方針(`00_共通の作法.md` 1章の決定)を書く
- ■lint: 探索の記録と act-log の対応を見る規則(例 `explore_act_linked`: exploration-log の各ステップの `actions` に対応する記録がある)を、この版以降のフローに当てて実装する
- vocab: カードの種類・不合格の区分・実行形態(`b1` / `b2`)・STOP の理由を足す

### 4.4 変えないもの

- 保護ブロックの文言(カードには引用するだけ)・`pipeline.dot` の構造と停止点
- 作業10の工程0・パートA・パートB・パートR・パートP、作業15・20・30
- 報告書の骨格と status.yaml の契約(作り手が pms に変わるだけ)

## 5. テスト

- `pms run`: AI の CLI を偽物に差し替えて、(a) 提出して終わる (b) 提出せずに終わる → 出し直し (c) 上限を超える → STOP (d) 時間切れ (e) CLI が起動しない、の各場合の動きと終了コード。セッションの出力の保存と、秘密情報の伏せ
- 探索のカード: 合格の例で exploration-log が付録A の形になり、既存の lint(`verdict_enum`・`reason_code_enum`・`blocked_recorded`・`no_temp_locator`・`health_recorded` など)を通ること。不合格の例が各区分で返ること
- `pms report`: 見本の記録から、報告書の数値と status.yaml が期待どおりになり、`status_yaml_valid` を通ること
- `pms stats`: 見本の submit-log からの集計
- 生成したエージェントの定義が正本と一致すること(`skills_in_sync`)
