## この表の役割

生成AIが**実行してはならない操作**を列挙するブラックリストである。対象は**外部操作**(Web UI 操作以外の手段で行う操作。`vocab.external_op`)全般であり、機器(実機・シミュレータ)に限らず、印刷指示を出す端末(クライアントPC・プリンタドライバ)や、**PMSが連携するすべてのシステム**(Active Directory、メールサーバ、PMSサーバOS等)を含む。

旧方式(許可された操作のみ実行可)から、次の方式に転換する。

- 外部操作は**外部操作 skill を介してのみ**行う。skill は人間が整備する。AIは、skill の使い方(引数・前提条件・完了判定)を**自律的に確立してよい**。使い方の情報源は skills・KB(T05)・プロンプト指示・自身の調査とする
- ただし、**この表に禁止として列挙された操作は、skill があっても実行しない**。禁止レベルが `要許可` の操作は、人間の明示許可を得るまで実行しない
- 禁止・要許可の操作が必要になった場合、AIは実行を試みず、申し送り台帳に記録してエスカレーションする

### 包括原則(表にない操作へのセーフティネット)

ブラックリストは網羅できない。**表に載っていなくても**、次のいずれかに該当する可能性がある操作は、実行前に申し送り台帳へ記録してエスカレーションする。

1. **物理資源を消費する操作の大量実行**(紙・トナー・ステープル等)
2. **復旧に人手または長時間を要するおそれのある操作**(電源・ファームウェア・恒久設定の変更等)
3. **テスト環境の外に影響が及ぶおそれのある操作**(外部宛メール送信、テスト用OUの外の AD オブジェクトの変更、環境情報に登録されていないプリンタへの印刷指示、外部宛先へのスキャン送信・FAX送信等)

   **テスト環境**とは、人間がテストに使うよう指定した対象であり、検証環境の情報(`config/environments.json`・`config/environments.local.json`)に接続先が登録された機器・サーバー(複合機・プリンタ・AD・メールサーバ・連携システム等)を指す(`vocab.test_environment`)。対象の一部だけがテスト用のとき(AD のテスト用OUなど)は、その範囲を環境情報の説明欄に書く。**テスト環境の中の対象への変更は、この原則に当たらない**(原則1・2・4と禁止操作表の行は別に判断する)。

   ただし、**テスト環境の対象を使って、さらにその外に作用する操作は、この原則に当たる。** 例えば、メールサーバがテスト環境として与えられていても、外部宛のメール送信はテスト環境の外に影響を与えるおそれがあるため実行しない。
4. **ゴールデンイメージの復元で戻らない対象への状態変更**(復元範囲の外。ゴールデンイメージの復元は、VM の復元と開始前シナリオの復元エントリを合わせたもの。復元範囲は `node tools/pre-stage/run-scenarios.mjs --restore-scope` で確かめる。`00_common.md` ■回帰実行の環境前提)

判断の目安: **迷ったら実行しない**。復元範囲(VM の復元で戻る PMSサーバ・DB・VM上のシミュレータと、開始前シナリオの復元エントリが戻す対象)は自由度を高く、復元範囲の外の対象(戻す手段のない実機・連携システム)は保守的に扱う。

## 禁止レベルの統制語彙

| レベル | 意味 |
|---|---|
| `禁止` | いかなる場合も実行しない |
| `要許可` | 人間の明示許可(シナリオ単位)があれば実行可 |
| `条件付き許可` | 「制約/許可条件」欄の範囲内であれば自律実行可。範囲を超える場合は `要許可` として扱う |

## 適用対象の表記

実機とシミュレータで禁止内容が異なるため、適用対象は次の表記で区別する。

| 表記例 | 意味 |
|---|---|
| `実機:ALL` | すべての実機(複合機・プリンタ) |
| `実機:<型番>` | 特定型番の実機のみ |
| `シミュレータ:ALL` | すべての機器シミュレータ |
| `シミュレータ:<識別子>` | 特定のシミュレータのみ |
| `CLIENT` | 印刷指示を出す端末(クライアントPC・プリンタドライバ) |
| `AD` | Active Directory |
| `SMTP` | メールサーバ |
| `PMS-OS` | PMSサーバのOS・IIS・サービス |
| `VM` | 検証環境の仮想マシンと Hyper-V ホスト(ゴールデンイメージの復元) |
| `ALL` | 上記すべて |

同じ操作でも実機とシミュレータで扱いが異なる場合は、**行を分けて**記載する(下の記入例 PROH-001/002 を参照)。

## ◆ 記入にあたっての補足

- **完璧な網羅を目指さない。** ブラックリストの漏れは包括原則(セーフティネット)が拾う。AIが包括原則でエスカレーションしてきた操作のうち、恒久的に禁止すべきものをこの表へ追記していく運用でよい
- **「理由」欄が包括原則の精度を決める。** AIは表の理由欄から「この環境で何が危険とされているか」を学習し、表にない操作のグレーゾーン判断に使う。空欄にしない
- 実機の制約(枚数上限等)は運用しながら緩めてよい。逆にシミュレータは、VMスナップショットで復元できる限り原則自由とし、禁止は最小限に留める
- **この表は「してはならない操作」を定めるものであり、「できる操作」を定めるものではない。** どの外部操作ができるかは skill の整備状況で決まる。skill 整備の計画は外部操作需要リスト(`93`)が担う(旧語彙表の「候補(未確定)」欄は廃止した)
- skill を整備するときは、その skill でできる操作がこの表のどの行に当たるかを確認しておくと、AIのエスカレーションが減る
- **表を書き換えると、ファイルの版(ダイジェスト)が変わる。** 作業10で「禁止操作」のため blocked にしたステップがあるフローは、次に作業20へ進む前に照合で変更が検出され、作業10がそのステップを判定し直す(`00_common.md` ■外部操作 禁止操作リストの版と blocked の再判定)。書き換えたことをAIに伝える必要はない
